## A measured cause of "single-threaded for hours on an idle box"

The baseline run at `a17fcb33c` (16 workers, default `--dist load`) reached 88%
in about 1 h 50 m, then stalled. Over a 10 s sample, **2 of 15 live workers
used CPU and 13 sat in futex waits**. 9,450 items had not run, and at about 12
tests/min it would have hit its 3 h deadline with them unrun. It was stopped
with TERM (cleanup complete). Its 71,957 finished ids (821 failing) are the
partial baseline.

Mechanism, read from installed `xdist` 3.8.0 (`scheduler/load.py:195–207`):
after the initial batch, a node running low receives `len(pending)//nodes//2`
**contiguous** collection-order items. When the pending pool reaches the
continuation-proof files (e.g. `test_web_reserve_reviewed_contracts.py`, about
0.9 worker-minutes per test), one worker takes hundreds of them, and the
scheduler never moves queued work to idle nodes. CI avoids this with
duration-balanced shards (`scripts/ci_test_shards.py`); local runs have no such
protection. One worker also died mid-test in a process-death test
(`test_dag_recovery_partial_terminal.py`, "node down: Not properly terminated"),
and with `--max-worker-restart=0` its queue went back to the other nodes.

xdist ships `--dist worksteal` for exactly this case: idle workers take queued
tests from busy ones. The tip run uses it, and the sampler will show whether all
workers stay busy through the tail. If they do, I'll propose making it the
`addopts` default (it would also apply inside each CI shard). This is *a*
measured cause, not necessarily the only one; agents choosing `-n 0` from stale
policy is a separate mechanism.

**Local runs will mirror CI's partition (John, 05:40: "some of our tests are
just very big tests and we run them as separate processes").** Worksteal only
partly helps: it allows one steal request at a time, and a worker answers only
between tests (`worksteal.py:223–250`). So the tip run's tail still drops to
about 9 of 19 busy workers on multi-minute proofs. CI instead runs:

- the `ordinary` partition as **8 independent shard processes** at `-n 2`,
  assigned by a hash of the node id (`scripts/ci_test_shards.py`), which
  scatters each slow file across shards;
- the **3 long-run proof cases** (`LONG_RUN_CASES`, `ci_test_shards.py:30`),
  each as its own serial process (`landscape-long-run.yml`).

From the next full run on, local runs use the same layout, through
`full-suite-gate.sh --pytest-args` (one gate run per shard and per proof
case). Found while reading it: the proof jobs allow 7,200–14,400 s, but the
three proof tests carry no `pytest.mark.timeout`, so the 600 s per-test limit
still applies inside them. No-escape took 637 s in CI. Their own budget is
derived once they pass (open item).

### 2. Retained enum values passed to unclosed callers (326 rows, about 50 files)

Since enum members can be mutated, the analysis is right to require that every
caller receiving a retained enum value be proven not to mutate it. Two honest ways
to close it:

- **(i) Closure per consumer.** Review each receiving caller and add it to the
  analysis's closed consumer set. No production change; the scope is about 50
  files, each needing review.
- **(ii) Fix at the producer (recommended).** Make the retained enum classes
  genuinely immutable in production: a shared enum base that refuses member
  attribute writes once the class is built. A runtime test would verify every
  retained class (as for `datetime.datetime`), and one fact would then close the
  category. This is a small production change across several enum classes. It
  matches the trust-tier rule of fixing at the producer, but it is a production
  behaviour change, so it is your decision. I haven't sized the exact class
  count yet; that needs a diagnostic pass.

### 3. Enum and record immutability: ruled 2026-11-01 ~05:25

John: "lets not go stupid about immutability, if the language doesn't support
it that's just how it is."

The standard is **language-level immutability**: enum members, frozen
dataclasses, frozen pydantic models, tuples, frozensets and str count as
immutable. Bypasses the language allows (`object.__setattr__`, `vars()`
writes, rewriting `_value_`) are not treated as a hole to close. Consequences:

- **Enum rows (387 + 103 enum-rooted supplier rows):** a reviewed fact admits
  retained enum members, and frozen record classes that hold them, as
  immutable values. No producer seal, no reflective-write gate, and no change
  to the enum classes. It replaces options (i), (ii) and (ii′) and stays
  scheduled at the end.
- **D1:** `frozen=True` on `ComposerOperationError` (the language mechanism its
  siblings already use). No extra freezing of its `body` dict.
- **D2:** shadowing a method by an instance attribute is ordinary Python. It is
  fixed only if `__slots__ = ()` is plainly the clearer class design; it is not
  a defect class to chase.
- Future facts use this standard. The `datetime.datetime` test that also
  checks `object.__setattr__` stays as it is (already landed, and it passes).

Measured background (kept for the record): enum members always have an
instance `__dict__`, so a sealed `__setattr__` refuses plain `setattr` only.
`object.__setattr__` and `vars()` still write (`enum_seal_probe.py`, 3.12 and
3.13).
