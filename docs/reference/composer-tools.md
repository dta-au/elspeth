# Composer Tool Reference

Reference for the composer-facing tools and export surfaces available to the
LLM pipeline composer. Composer uses a tool-use loop where the LLM translates
natural-language pipeline descriptions into valid ELSPETH pipeline
configurations.

## How Tools Work

The composer operates as a **tool-use loop**: the LLM receives the user's message plus the current pipeline state, calls tools to build or modify the pipeline, reviews validation results after each tool call, and continues until the pipeline is valid — then responds with a summary.

Tools fall into two categories:

| Category | Behaviour | Budget |
|----------|-----------|--------|
| **Discovery** | Read-only. Return plugin catalogs, schemas, or grammar references. Cacheable per-composition. | `ELSPETH_WEB__COMPOSER_MAX_DISCOVERY_TURNS` discovery-only turns (required setting; no built-in default) |
| **Mutation** | Modify the `CompositionState`. Return updated state + validation. | `ELSPETH_WEB__COMPOSER_MAX_COMPOSITION_TURNS` turns with at least one mutation (required setting; no built-in default) |

Every mutation tool returns a `ToolResult` containing the full validation state, so the LLM can detect and fix errors immediately.

## Tool Wire Contract

A tool's argument contract has six separately checked surfaces. **SHIPPED** is
the argument schema in the live tool registry; **MODEL** is the owned handler's
argument admission before budget, provider, blob, or state effects; **READ** is
the handler's consumption of the original admitted input; **ADMITTED** is the
audit/redaction projection; **TAUGHT** is the argument guidance the planner
receives; and **FRONTEND** is the user-facing projection where one exists.
Adding or changing a tool argument requires checking each affected surface.

These checks have different reach. Root-name agreement between SHIPPED and
ADMITTED does not prove nested value redaction. A READ check establishes input
extraction, while behavior tests must establish how the value affects state or
provider calls. TAUGHT checks pin exact argument names in their own tool
context; they do not judge the quality of the guidance. The live scorecard is
generated by `scripts/cicd/composer_wire_census.py --scorecard`; focused checks
live under `tests/unit/scripts/`, `tests/unit/web/composer/`, and the frontend
tests. Tool responses have their own owned shape and redaction checks; an
argument check does not certify a response.

## Discovery Tools

### `get_pipeline_state`

Read the current graph, or set `since_start=true` to receive net field changes
from the graph at the start of this turn. Changes use component identities as
keys and report component ordering separately. `since_start` cannot be combined
with `component` and requires a turn-start baseline.

An oversized whole-graph read returns a structural `view` without option values
or descriptions; large `since_start` reads retain exact values in `view="changes"`.
Supply
`field_path` as a JSON pointer to select an exact value. A page contains
`content`, `encoding`, `offset_chars`, `total_chars`, `next_offset_chars`, and
`sha256`; pass `next_offset_chars` as the next offset and `sha256` as
`expected_sha256`. A continuation with a missing or mismatched hash is refused.
Each response discloses at most 32,768 bytes. A structural view or partial page
does not claim complete graph coverage.
For a node, use `/input` or `/options/system_prompt`; for an output, use
`/options/<key>`. Full diagnostic reads include `inspection`; the
`set_pipeline_arguments` authoring document does not. Call `preview_pipeline`
to inspect validation when state inspection diagnostics exceed the budget.

### `list_sources`

List available source plugins with their full catalog summaries.

**Parameters:** None

**Returns:** Array of full `PluginSummary` entries — `name`, `description`, `config_fields` (name, type, required, description, default per option), usage guidance, `composer_hints`, and `secret_requirements` — plus a `prohibited` array naming any source banned from the web authoring surface, with its closed reason. `get_plugin_schema` is needed only for enum values, nested option shapes, or the raw JSON schema.

**When to use:** At the start of composition to discover what source types are available, or when the user asks what data formats are supported.

---

### `list_transforms`

List available transform plugins as a selection index.

**Parameters:** None

**Returns:** `available`, one entry per transform carrying only `name`, `description`, `capability_tags`, `web_config_authority` and `policy_capabilities` (`capability`, `control_role`, `blocks_positive_detection`); a `prohibited` array naming any transform banned from the web authoring surface, with its closed reason; and `details_tool` (`"get_plugin_schema"`). No configuration is listed: call `get_plugin_schema` for a chosen plugin's options and `get_plugin_assistance` for its guidance.

**When to use:** When exploring what processing steps are available — field mapping, LLM classification, content safety, RAG retrieval, etc.

---

### `list_sinks`

List available sink plugins with their full catalog summaries.

**Parameters:** None

**Returns:** Array of full `PluginSummary` entries — `name`, `description`, `config_fields` (name, type, required, description, default per option), usage guidance, `composer_hints`, and `secret_requirements` — plus a `prohibited` array naming any sink banned from the web authoring surface, with its closed reason. `get_plugin_schema` is needed only for enum values, nested option shapes, or the raw JSON schema.

**When to use:** When the user describes where output should go — CSV files, databases, vector stores, cloud storage.

### `get_plugin_schema`

Get the full configuration schema for a specific plugin.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `plugin_type` | string | **Yes** | `"source"`, `"transform"`, or `"sink"` |
| `name` | string | **Yes** | Plugin name (e.g. `"csv"`, `"llm"`, `"database"`) |

**Returns:** Full JSON Schema for the plugin's `options` configuration — field names, types, defaults, enums, and descriptions — plus `usage_when_not_to_use`, the plugin's own stated prohibition (null when it states none). The discovery digest points an omitted transform prohibition here.

**When to use:** Before configuring any plugin. The schema is the source of truth for what options a plugin accepts. Do not guess option names — always check the schema first.

### `preview_pipeline`

Preview the current pipeline configuration — validation status, source summary, and node/output overview without executing.

**Parameters:** None

**Returns:** The authoring check rides on the envelope's `validation` and the
runtime check on its top-level `runtime_preflight`; `data` carries only the
preview stage's own facts:
- `preview_is_valid` — true only when the authoring check, the runtime check, and the source proof all pass (false when no runtime check ran)
- `preview_errors` — entries the preview stage itself produces (`runtime_preflight_not_run` when no runtime check was wired); authoring errors stay on `validation.errors`
- `edge_contracts` for declared producer/consumer field contracts
- `proof_diagnostics` — the source proof against the bound blob; a `blocking` entry forces `preview_is_valid` false
- `structural_preview` when a tolerant structural check ran
- source, node, and output summary data (`sources`, `nodes`, `outputs`, `node_count`, `output_count`)

One entry per producer/consumer pair that was checked, and a pair is checked
only where the consumer requires fields — through `required_fields`, through a
fixed/flexible schema's declared fields, or, for a sink, through an option
naming the field it writes from.
Each entry reports:
- `from` / `to` (`to` is `output:<sink name>` for a sink)
- `producer_guarantees`
- `consumer_requires`
- `missing_fields` — the `consumer_requires` names the producer does not guarantee
- `satisfied`

**When to use:** After making a series of changes, to confirm the pipeline is set up correctly before responding to the user or calling `generate_yaml`.

**Important:** `edge_contracts: []` is not positive contract evidence. It means no field contract was checked. Also treat skipped contract-check warnings as unresolved rather than satisfied.

### `explain_validation_error`

Get a human-readable explanation of a validation error with suggested fixes.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `error_text` | string | **Yes** | The exact validation error message to explain |

**Returns:** Explanation of what the error means and how to fix it.

**When to use:** When a mutation tool or export surface returns validation errors that aren't immediately clear. Pass the exact error text from the validation result.

**Contract-aware behaviour:** Schema contract violations are recognised explicitly. For node contract failures, the guidance directs you to `preview_pipeline` plus `patch_source_options` / `patch_node_options`. For sink contract failures, it can also direct you to `patch_output_options`.

## Export Surface

### `generate_yaml`

Export the current composition state as deterministic pipeline YAML.

**Parameters:** None

**Returns:** YAML text for the current composition state.

**Validation backstop:** The LLM-facing export surfaces re-run validation before emitting YAML.
- The MCP `generate_yaml` session tool returns failure if the current composition state is invalid.
- The MCP `generate_yaml` session tool also enforces generated-file controls such as explicit `collision_policy` on CSV/JSON sinks, so loaded older session state cannot bypass the mutation-tool checks.
- The HTTP `GET /api/sessions/{id}/state/yaml` endpoint returns `409` for invalid state.

**Important:** This is an export step, not the primary validator. Use `preview_pipeline` first to inspect validation results and `edge_contracts`. The underlying serializer remains a pure serializer and is not universally validation-aware at every internal call site.

## Mutation Tools

### `set_source`

Set or replace the pipeline source.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `plugin` | string | **Yes** | Source plugin name (e.g. `"csv"`, `"json"`, `"text"`) |
| `on_success` | string | **Yes** | Connection name for downstream nodes (e.g. `"source_out"`) |
| `options` | object | **Yes** | Plugin-specific configuration (check schema first) |
| `on_validation_failure` | string | For new sources | Explicit `"discard"` or an eligible named route. Omission preserves the same existing source's choice; null/empty is invalid. |

**Behaviour:** Replaces the current source entirely. A pipeline must have exactly one source.

**Connection model:** The `on_success` value becomes the connection name that downstream nodes reference in their `input` field. Choose a descriptive name like `"raw_data"` or `"source_out"`.

---

### `upsert_node`

Add or update a pipeline node — transforms, gates, aggregations, coalesces,
row unions, queues, or collectors.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `id` | string | **Yes** | Unique node identifier (e.g. `"classifier"`, `"quality_gate"`) |
| `node_type` | string | **Yes** | `transform`, `gate`, `aggregation`, `coalesce`, `row_union`, `queue`, or `collector` |
| `input` | string | **Yes** | Input connection name (must match an upstream `on_success`) |
| `plugin` | string | No | Plugin name. Required for transforms, aggregations, and collectors. Null for gates, coalesces, row unions, and queues. |
| `on_success` | string | No | Output connection name. Required for transforms, row unions, and collectors. Null for gates and queues. |
| `on_error` | string | For new transforms/aggregations | Explicit `"discard"` or an eligible named route. An update may omit it to preserve the same node kind's choice. New gates omit it for fail-fast; gate updates preserve an omitted prior choice and clear to fail-fast with null. Collectors reject this field because failures are whole-group verdicts. |
| `options` | object | No | Plugin-specific configuration |
| `condition` | string | No | Gate expression (gates only) |
| `routes` | object | No | Gate route mapping to a sink name, downstream connection name, `"fork"`, or virtual `"discard"` target, e.g. `{"true": "sink_name", "false": "discard"}` (gates only) |
| `fork_to` | array | No | Fork destination connection names (fork gates only) |
| `branches` | array or object | No | Ordered branch inputs for coalesces and row unions (min 2). List form is shorthand for an identity mapping; object form maps each branch name to its input connection. |
| `policy` | string | No | Coalesce policy: `"require_all"`, `"quorum"`, `"best_effort"`, `"first"` |
| `merge` | string | No | Coalesce merge strategy: `"union"`, `"nested"`, `"select"` |
| `timeout_seconds` | number | No | Optional finite positive structural-barrier timeout for `coalesce` or `row_union`; this is a top-level node field, not `trigger.timeout_seconds`. |
| `scope_name` | string | No | Scope identifier for the EXPAND group this collector closes (collectors only) |
| `scope_opener` | string | No | Node id of the multi-row transform that opens the collector's EXPAND group (collectors only) |
| `scope_policy` | string | No | Group arrival policy, `"require_all"` or `"best_effort"` (collectors only) — **required for collectors**, there is no default |

**Behaviour:** If a node with the given `id` already exists, it is replaced. The `id` must be unique across all node types.

**Node type specifics:**

| Type | Required fields | Key behaviour |
|------|----------------|---------------|
| `transform` | `plugin`, `on_success` | Processes rows, emits to `on_success` |
| `gate` | `condition`, `routes` | Evaluates condition, routes by result; optional `on_error` handles row-scoped evaluation failures |
| `aggregation` | `plugin` | Batches rows until trigger fires |
| `coalesce` | `branches`, `policy` | Waits according to `policy`, then merges correlated branch payloads according to `merge` |
| `row_union` | `branches`, `on_success` | A plugin-free, fixed `require_all` N-to-N barrier that releases every original row unchanged in declared branch order |
| `queue` | `id == input` | Declares a shared pass-through connection for multiple producers; omit plugin and routing fields, and use only an optional `options.description` |
| `collector` | `plugin`, `on_success`, `scope_name`, `scope_opener`, `scope_policy` | Closes a declared EXPAND scope with a batch-aware plugin. `scope_opener` names the multi-row transform that opens the group and `scope_policy` decides whether a lost member fails it. A collector flushes on end of group only and accepts neither `trigger` nor `on_error`; plugin failure is a structural whole-group verdict. |

For `row_union`, branch order is significant. Mapping keys must match the
upstream gate's `fork_to` names and mapping values name the connection published
by each branch's final transform. `input` must equal the first branch connection
(it is a serialization placeholder), and `on_success` must name a downstream
processing connection, never a sink. A row union does not accept `policy`,
`merge`, `options`, or routing fields.

**Structural fan-in choices.** Composer represents all three:

- A `queue` is a pass-through coordination point for multiple producers feeding
  one shared connection. It does not wait for correlated fork branches or merge
  their payloads. Set the queue's `id` and `input` to that connection name; see
  [Queue Settings](configuration.md#queue-settings).
- A `row_union` reconverges correlated fork branches N-to-N: it waits for every
  branch in the group, then releases all original rows to downstream processing.
- A `coalesce` reconverges correlated fork branches N-to-1: its `policy` controls
  which arrivals are sufficient and its `merge` strategy combines them into one
  payload. See [Coalesce Settings](configuration.md#coalesce-settings).

### `upsert_edge`

Add or update a connection between nodes.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `id` | string | **Yes** | Unique edge identifier (e.g. `"source_to_gate"`) |
| `from_node` | string | **Yes** | Source node ID, or `"source"` for the pipeline source |
| `to_node` | string | **Yes** | Destination node ID or sink name |
| `edge_type` | string | **Yes** | `"on_success"`, `"on_error"`, `"route_true"`, `"route_false"`, or `"fork"` |
| `label` | string | No | Display label (used as route key for gate edges) |

**Behaviour:** Edges define the data flow through the pipeline. Every node must be connected — orphan nodes cause validation errors.

**Edge types:**

| Type | Meaning |
|------|---------|
| `on_success` | Normal data flow from one node to the next |
| `on_error` | Error-sink edge for transform/aggregation processing failures. Gate expression-evaluation failures use the gate node's `on_error` field; Composer rejects an `on_error` edge from a gate. |
| `route_true` | Gate route when condition evaluates to `True` |
| `route_false` | Gate route when condition evaluates to `False` |
| `fork` | Gate fork to parallel paths |

### `patch_source_options`

Apply a shallow merge-patch to the current source options.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `patch` | object | **Yes** | Keys in the patch overwrite existing keys. Keys set to `null` are deleted. Missing keys are unchanged. |

**When to use:** To modify specific source options without replacing the entire source. More surgical than `set_source`.

---

### `patch_node_options`

Apply a shallow merge-patch to a node's options.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `node_id` | string | **Yes** | ID of the node to patch |
| `patch` | object | **Yes** | Merge-patch (same semantics as `patch_source_options`). The merge is shallow: a nested value such as `queries` is replaced whole, so send every query; a `queries` value that omits an existing query is refused (`queries_patch_omits_existing`), and `queries: null` removes every query. |

**Replacing an LLM prompt with new text.** A patch that carries `prompt_template` as text together with `prompt_template_parts: null` replaces the node's whole prompt, whatever was there. A structured prompt's `prompt_template_parts` and every vague-term review of the old text (pending or accepted) are removed, the result names them in `superseded_review_ids`, and the new text gets its own pending `llm_prompt_template` review card; nothing approved for the old prompt approves the new one. Other reviews on the node (model choice, pipeline decisions) are kept. Leave `interpretation_requirements` out of the patch; sent as `null` it is refused. Text exactly equal to the node's existing prompt (the stored text, or the text `get_pipeline_state` returns for it; the same characters, whitespace and line endings included) never changes the prompt's structure or reviews, with or without the `prompt_template_parts` key and in all three tools; the result names each such node in `prompt_unchanged_node_ids`, and never also in `superseded_review_ids`. `upsert_node` and `set_pipeline` accept the explicit pair in a node's `options`, and refuse a changed `prompt_template` on a structured prompt without `prompt_template_parts: null` (`prompt_template_parts_required`), because a whole node re-sent with stale text must not flatten a reviewed prompt. A file marker is never accepted this way: bind a file with `wire_blob_inline_ref`.

### `set_pipeline`

Atomically replace the entire pipeline in one call.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `source` | object | **Yes** | `{plugin, options, on_success, on_validation_failure}`; full replacement requires an explicit nonempty failure choice. |
| `nodes` | array | **Yes** | Array of `transform`, `gate`, `aggregation`, `coalesce`, `row_union`, `queue`, or `collector` node specs: `[{id, input, plugin?, node_type, options?, on_success?, on_error?, condition?, routes?, fork_to?, branches?, policy?, merge?, timeout_seconds?, scope_name?, scope_opener?, scope_policy?}]` |
| `edges` | array | **Yes** | Array of edge specs: `[{id, from_node, to_node, edge_type}]` |
| `outputs` | array | **Yes** | Array of output specs with required explicit `on_write_failure`: `[{name, plugin, options, on_write_failure}]`. |
| `metadata` | object | No | `{name?, description?}` |

**When to use:** When the user describes a complete pipeline and you can construct the whole thing at once. More efficient than sequential `set_source` + `upsert_node` + `upsert_edge` + `set_output` calls. Also useful for major restructuring where most components change.

Generated `csv` and `json` outputs must include `options.collision_policy`; the web composer and MCP composer controls reject missing policy choices before export.

### `get_blob_content`

Read a ready blob's decoded text for inspection, with bounded continuation.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `blob_id` | string | **Yes** | Blob ID to read |
| `offset_chars` | integer | No | Nonnegative start offset in original Unicode code points; defaults to `0` |
| `expected_content_hash` | string or null | After offset `0` | Lowercase 64-hex SHA-256 of the original bytes. Omit or use null at offset `0` for no expected-identity constraint; every non-null hash is checked, including at offset `0` |

**Returns:** `content`, verified original-byte `content_hash`, full `size_bytes`
and `total_chars`, half-open `[start_char, end_char)` range, `truncated`, and
`next_offset_chars`, plus blob identity and recorded origin metadata. Each page
preserves original Unicode code points. The complete serialized JSON tool
response, including metadata and escaping, is bounded to 4,096 UTF-8 bytes.
A successful page carries no `validation` block, so the saved pipeline's
findings never reduce how much content a page holds.

Continue with `offset_chars` set to the returned `next_offset_chars` and
`expected_content_hash` set to the returned `content_hash`. A changed content
identity is refused. `truncated`
means `end_char < total_chars`; `next_offset_chars` is null at the end. A prefix
does not establish whole-file inspection, and `size_bytes` describes the full
blob rather than this page. Whole-file inspection needs enough configured
discovery turns to read every page.

| Parameter | Type | Required | Description |

| `plugin` | string | No | Source plugin override. Inferred from MIME type if omitted. |

### `wire_blob_inline_ref`

Wire a ready blob into a plugin option as audited inline content.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `field_path` | string | **Yes** | Canonical target path such as `source.options.<field>`, `node:<node_id>.options.<field>` for a transform, aggregation, or collector, or `output:<name>.options.<field>`. An existing list item is addressed by its 0-based position, such as `node:<node_id>.options.queries.0.template`; a position never creates an item or a mapping key |
| `blob_id` | string | **Yes** | Ready inline-text blob ID to wire; for prompts, upload or create plain text (.txt or .md) |
| `encoding` | string | No | One of `utf-8`, `utf-8-sig`, `utf-16`, or `latin-1`; defaults to `utf-8` |

**When to use:** When a long-form config field, such as an LLM prompt template or SQL query, should be supplied from a session blob without exposing the bytes to the composer LLM. The tool pins `sha256` from blob metadata. A user-created or agent-authored UTF-8 text file may bind to `llm` `prompt_template`, `system_prompt`, or one `queries.<name>.template` / `queries.<index>.template` scalar. Binding opens a mandatory card with the full file text. The user approves it before validation or Run admits the file. A content change or re-point opens a new card and requires another approval. The server checks current file bytes again at run admission and records their hash in Landscape.
Binary MIME, `model`, whole `queries` and malformed markers are refused. `wire_blob_inline_ref` onto `prompt_template` replaces the whole prompt, including a structured one: its `prompt_template_parts` and every vague-term review of the old text (pending or accepted) are removed, and the file gets its own review card, which supersedes them. To keep a structured prompt, edit its text parts in place with `change_substring` or `patch_node_options`, preserving `interpretation_ref` entries. To replace it with new text rather than a file, see `patch_node_options`. A file marker written straight onto a structured prompt by `patch_node_options`, `upsert_node`, `set_pipeline` or imported YAML is refused (`prompt_template_parts_required`) and the refusal points at `wire_blob_inline_ref`. Substring editing inside a file is not supported in this release.
YAML import (`POST /api/sessions/{id}/state/yaml`) imports nothing when a prompt file's review card cannot be prepared. `malformed_inline_blob_content` (400, the validation code, here raised before anything is saved) names the option fields whose `blob_ref` mapping is not a complete file marker: at most five field paths, each shown whole with characters outside letters, digits and `_ . : -` shown as `?`, then the exact count of the rest (import again after fixing those to see the next); values are never echoed. `import_prompt_file_unverified` (409) means a referenced prompt file is missing, not ready, or differs from the `sha256` in the YAML; it names the file-backed prompt fields of the first step that could not be verified: remove the reference and import again, then attach the file in the session, or bind it by id in `inline_blob_bindings`. A source bound by `source_blob_ids` stores `path` and `blob_ref` without `mode`; that is a source binding, not a file marker.
The session owner can edit a bound prompt file in the graph node inspector; Save records that the user saved these bytes for this step, carries the approval of the step's other prompt files, and does not raise a separate card. The save refuses files also used outside a prompt (`prompt_file_mixed_use`), files bound to more than one prompt (`prompt_file_shared_binding`, so a save never approves a prompt the user is not looking at), and prompts that read the file with an encoding other than UTF-8 (`prompt_file_encoding_unsupported`). A node may use several prompt files; each is edited and saved on its own, and the save re-records the approval of the node's other prompt files with their unchanged bytes. Every prompt file on the node must already be approved (`prompt_file_stale` otherwise). If a pending card covers other prompt content on the node, the user must approve the card first: `prompt_file_review_pending_inline` for inline prompt text, `prompt_file_review_pending` for another prompt file; `prompt_file_binding_changed` asks the user to reload after a re-point.

### `report_composer_bug`

Record a suspected mismatch between the composer's guidance (the skill or a tool description) and what a tool call actually did.

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `summary` | string | **Yes** | One-line summary, 1–240 characters |
| `expected_behavior` | string | **Yes** | What the skill or tool description says should happen, 1–4,000 characters |
| `observed_behavior` | string | **Yes** | What the tool call actually did, with any error described in the model's own words, 1–4,000 characters |
| `guidance_reference` | string | No | The skill section or tool description being contradicted, 1–1,000 characters |
| `related_tool` | string | No | Name of the composer tool involved: a lowercase letter, then lowercase letters, digits or `_`; at most 100 characters |

**Returns:** `blob_id`, `filename` and `status` (always `suspected_unverified`). The report prose is not echoed in the result.

**Where the text is kept:** the prose fields are redacted only from the assistant message's tool-call record, which keeps a length placeholder for each. As for every tool, the full arguments are also kept in the tool message's visible tool event (`received_arguments`) and in the audit message, and the visible event feeds the advisor transcript. The report file holds the text as well.

**Behaviour:** Saves one JSON file (`application/json`, named `composer-bug-report-<uuid>.json`) in the session's files, created by the assistant with the usual composer provenance. The file holds `report_type` `suspected_composer_bug`, `status` `suspected_unverified`, the time of the report, the observations as supplied, and the context that produced them: session, state id and version, user message, composer model, version and provider, skill hash and tool-arguments hash. The pipeline state is returned unchanged; nothing is repaired or verified. Blank, over-length, mistyped or extra fields are refused. The field limits count characters; the saved file, written as UTF-8 JSON, is limited to 16,384 bytes, so long text in several fields can reach the file limit before the field limits (ordinary ASCII at every field limit takes about 10 KB, and one behaviour field at its limit fits in two- or three-byte text but not in four-byte text such as emoji). A refused report writes nothing. A session keeps at most 20 reports; past that the call fails with a message telling the model to stop reporting and continue the task, and nothing is written. The session file quota applies. Credential-shaped text in any argument ends the whole turn (the composer request is refused, as for every tool call), so the model is told to describe error messages in its own words and never paste tokens, keys, passwords or connection strings. Like other changes, a successful report in a tool batch blocks a later `inspect_prompt_targets` in the same batch, so the description asks for reports after reads. Like `create_blob`, it runs immediately when the session requires approval for changes, because it only adds a file; `update_blob` and `delete_blob` still need approval.

**When to use:** Once per distinct mismatch, then continue the user's task.

## Tool Result Format

Every tool returns a `ToolResult`. The model receives it serialized verbatim;
the audit row receives the redaction manifest's projection of the same object.
The key vocabulary is one registry (`src/elspeth/web/composer/tool_result_envelope.py`)
that the producer, the redaction manifest, and the planner's closed discovery
twin all derive from, and this section is pinned to it by
`tests/unit/web/composer/test_tool_result_envelope_gate.py`.

```json
{
  "success": true,
  "validation": {
    "is_valid": true,
    "errors": [],
    "warnings": [
      {"component": "source", "message": "Source schema mode is 'observed' — consider 'fixed'", "severity": "low"}
    ],
    "suggestions": [],
    "semantic_contracts": [],
    "graph_repair_suggestions": []
  },
  "affected_nodes": ["classifier", "quality_gate"],
  "version": 3,
  "applied_component": {"nodes": [{"id": "classifier", "node_type": "transform", "plugin": "llm_classifier", "input": "source"}]},
  "validation_delta": {"new_errors": [], "resolved_errors": [], "new_warnings": [], "resolved_warnings": []}
}
```

Always present:

| Field | Description |
|-------|-------------|
| `success` | Whether the tool call succeeded |
| `validation` | Whole-document validation after this change: `is_valid`, `errors` / `warnings` / `suggestions` (entries with `component`, `message`, `severity`, `error_code` when the entry has one, `rejected_component` when the rejection is about one component (`source` / `source:<name>` / `node:<id>` / `output:<name>`) and absent when it is about the whole candidate, and, when the code carries facts, a `contract`, `row_union_schema`, or `coalesce_union_type` block), `semantic_contracts` (one check per producer, consumer and required field), `graph_repair_suggestions` (the facts of a duplicate consumer: the connection and the steps reading it; no repair is proposed). Absent on a successful `get_blob_content` or `read_attachment`. |
| `affected_nodes` | Component ids the call touched |
| `version` | Pipeline state version (increments on each mutation) |

Present only when set:

| Field | When | Description |
|-------|------|-------------|
| `data` | most tools | The tool-specific payload; each tool's description names its keys. A failure carries `error`, and `error_code` when the failure has a closed code; a credential-wiring failure adds `credential_fields`, `components`, and `repair`; a proposal under approval custody carries `status: "APPROVAL_REQUIRED"` with `proposal_id`; a prevalidation rejection carries `status: "PREVALIDATION_REJECTED"` with `applied: false` |
| `runtime_preflight` | `preview_pipeline` | Runtime readiness check: `is_valid`, `checks`, `readiness`, `errors`, `warnings`, `semantic_contracts` |
| `validation_delta` | successful mutations | `new_errors`, `resolved_errors`, `new_warnings`, `resolved_warnings` relative to the state before the call |
| `post_call_hints` | successful mutations whose plugin returns them | Plugin-authored next steps |
| `plugin_schemas` | failed option-shape mutations | `"<kind>/<plugin>"` → the plugin's schema (`json_schema`, `knob_schema`, `composer_hints`, `secret_requirements`, …) |
| `validation_guidance` | failed mutations | `codes`: each `error_code` → `explanation` and `suggested_fix`; `explain_tool` when a code had no catalogue entry |
| `applied_component` | successful incremental mutations | The stored `source` / `sources` / `nodes` / `outputs` / `edges` the call touched — the authoritative post-change state, so no confirming read is needed |

`set_pipeline` results additionally carry `pipeline_content_hash_schema` and
`pipeline_content_hash`, attached after dispatch for recovery.

**Validation drives the loop.** After each mutation, check `validation.errors`
and `validation_delta`. If there are errors, fix them before responding to the
user. The LLM should not present a pipeline as complete until `preview_pipeline`
returns `preview_is_valid: true` — the authoring check passing is necessary but
not sufficient, because that verdict also folds in the runtime check and the
source proof.

## Expression Syntax Quick Reference

Gate conditions use a restricted expression language validated by `ExpressionParser`.

### Allowed

| Construct | Example |
|-----------|---------|
| Field access | `row['field']`, `row.get('field')` |
| Built-in functions | `len()`, `abs()` |
| Comparisons | `==`, `!=`, `<`, `<=`, `>`, `>=` |
| Boolean operators | `and`, `or`, `not` |
| Arithmetic | `+`, `-`, `*`, `/`, `%` |
| Membership | `in`, `not in` |
| Literals | `True`, `False`, `None`, numbers, strings |
| Ternary | `x if condition else y` |

### Forbidden

| Construct | Reason |
|-----------|--------|
| Type coercion (`int()`, `str()`, `float()`, `bool()`) | Not needed — source schema guarantees type safety |
| `row.get('field', default)` | Default values fabricate data the source never provided |
| Imports, lambdas, comprehensions | Security |
| Attribute access (except `row.get()`) | Security |
| F-strings | Security |

### Examples

```python
row['amount'] > 1000
row['status'] == 'approved'
row['category'] in ('A', 'B', 'C')
row.get('optional_field') is not None
row['score'] > 0.5 and row['status'] != 'rejected'
len(row['name']) > 0
```
