## A. Multiple explicit-approval edits share one base

### Root cause and candidate comparison

**Verified:** `run_tool_batch` starts with `state = acc.state` and copies `current_state_id` from context. Ordinary explicit-approval preview calls execute against that `state`. Publication records `current_state_id` as the proposal base. The staging branch then returns an unchanged-state result and `continue`s without assigning the preview state to `state`. Consequently the second staged mutation does **not** see the first staged mutation. More precisely, it sees the current working state at that point, which can include earlier immediate effects, but never the cumulative effect of earlier staged proposals. `src/elspeth/web/composer/tool_batch.py:1010-1021`, `:1742-1751`, `:2153-2181`, `:2246-2258`, `:2291-2309`, `:2330-2382`.

**Verified:** accepting an ordinary proposal reads the persisted head and refuses a mismatched non-null base with `proposal_base_state_changed` before running the tool. The underlying mutation transaction independently checks both expected head and proposal base, then inserts a successor checkpoint. This is why a successful state-changing accept invalidates its same-base siblings; it is not just frontend stale marking. Blob-only acceptance is a distinct path that can bind the existing state, so “only one can ever be accepted” should be scoped to the reported composition-changing proposals. `src/elspeth/web/sessions/routes/composer/proposals.py:410-449`, `:523-549`, `:771-780`; `src/elspeth/web/sessions/mutation_capabilities.py:433-480`.

**Verified:** the stale-base route raises before any proposal rejection. The inspected proposal router exposes list, events, accept and individual reject, and its stale message asks for a rebase without implementing one in that router. The frontend marks the named proposal stale and refreshes lifecycle state; that does not retire the pending database row. This explains persistence of stale cards, but is not an independent measurement of the reported eleven cards or a repository-wide proof about every conceivable API. `src/elspeth/web/sessions/routes/composer/proposals.py:285-318`, `:437-449`, `:813-823`; `src/elspeth/web/frontend/src/stores/sessionStore.ts:299-325`.

**Verified:** ordinary mutation admission rejects `success=False` or unchanged content, not every invalid resulting graph. The earlier `validation.is_valid` condition controls required-control finalization; it is not a general staging gate. At accept, a changed-version result reaches `_state_data_from_composer_state`; that helper computes and stores invalidity rather than refusing all invalid graphs. Acceptance then publishes that state. Thus the code permits an invalid intermediate edit to become canonical, independently of whether the following repairing proposal can be accepted. The exact sink and tool sequence in the probe cannot be identified without its arguments. `src/elspeth/web/composer/tool_batch.py:2182-2223`; `src/elspeth/web/sessions/routes/composer/proposals.py:578-609`, `:643-656`, `:750-780`; `src/elspeth/web/sessions/routes/_helpers.py:2856-2881`, `:2932-2965`.

**Verified:** `APPROVAL_REQUIRED` has `success=True`, `updated_state=state`, no affected nodes, and the prior/current validation. Its message already says “pending human approval and has not been applied,” but does not say explicitly that the envelope validation is about the unchanged state. A green envelope therefore does not certify the candidate or the combined proposed changes. The observed model's precise wording is probe evidence, not something source reading can reproduce. `src/elspeth/web/composer/tool_batch.py:2330-2355`.

**Verified, older/candidate:** candidate already previews each incremental mutation against `state`, stores the same base, and returns the same unchanged-state successful envelope. Candidate's accept route already has the base mismatch refusal and the changed-state acceptance path. This central defect was not introduced by the remediation range. `candidate:src/elspeth/web/composer/tool_batch.py:2056-2113`, `:2133-2145`, `:2178-2235`; `candidate:src/elspeth/web/sessions/routes/composer/proposals.py:407-419`, `:551-562`, `:657-686`. Current-line blame also points to pre-range commits for the envelope and base guard; this establishes older lineage, not an exhaustive first-introduction analysis.

**Verified remediation delta:** `ef14c2fc1` makes failed/no-op previews and argument errors stop before staging; candidate previously swallowed preview `ToolArgumentError` and still staged the call. A later call referring to an object present only in an earlier proposal can therefore now be refused immediately. That is a correct individual admission result against an inadequate shared-base model, not evidence that the earlier candidate had cumulative evaluation. Compare `candidate:src/elspeth/web/composer/tool_batch.py:2114-2121` with `src/elspeth/web/composer/tool_batch.py:2209-2226` and the inspected `ef14c2fc1` diff.

**Verified worsening:** the same commit removed candidate's whole-batch preflight cap and moved enforcement to admitted publication. An eleven-change batch previously failed before publication; it can now leave ten pending proposals before the eleventh throws. The counter also resets per provider batch, so the cap is not a session-wide pending limit. This is a concrete worsening of partial publication/accumulation; it does not prove which route produced the probe's eleven cards. `candidate:src/elspeth/web/composer/tool_batch.py:1038-1057`; `src/elspeth/web/composer/tool_batch.py:1134`, `:2232-2239`; `tests/unit/web/composer/test_proposal_cap_turn_counts.py:39-45`, `:62-84`; `tests/integration/web/composer/test_freeform_proposal_prevalidation.py:1637-1684`.

### Options and recommendation

All four options below are **inferred/design**, grounded in the staging and acceptance owners above.

| Option | Assessment |
|---|---|
| 1. One cumulative proposal | **Long-term recommendation.** Apply the provider's ordered commands to an isolated candidate, retain the original committed base, validate the cumulative result, and publish/accept one proposal atomically. Preserve each contributing call's provenance. Server execution of those explicit commands must not fill gaps with invented nodes or routes. Blob allocation/effects, custody and audit ownership make this substantially more than replacing the loop's `state` variable. Existing separate custody/publication paths are at `tool_batch.py:1958-2007`, `:2106-2146`, `:2246-2313`. |
| 2. Chained proposals | Each proposal needs an explicit dependency and reviewed resulting-state identity; merely guessing future state IDs is insufficient. Accept-in-order still exposes invalid intermediate graphs. Atomic accept-all could solve that but needs a batch transaction and lifecycle/UI semantics, approaching option 1 with more pending objects. Existing acceptance owns one proposal and one optional successor: `sessions/service.py:4866-4904`, `sessions/mutation_capabilities.py:389-398`, `:433-480`. |
| 3. One staged mutation | **Today-sized containment.** Enforce one outstanding approval proposal across provider rounds and compose requests, not just one per batch. For a batch of dependent edits, refuse the mutation batch before effects and ask the LLM for one atomic `set_pipeline`. If a proposal already exists, return its identity and tell the model to await acceptance/rejection. A normal tool refusal lets the model explain the action; a convergence exception after publishing a prefix does not. Existing reusable seams: `tool_batch.py:383-405`, `:1212-1255`, `:1742-1751`. |
| 4. Rebase on accept | Not a small correct fix. Apparent disjoint node IDs do not prove independence: connections, sinks, reviews, required controls and blob references can interact. Re-execution against a changed base can change what the user reviewed. Keep the base guard unless an explicit independence/review contract is designed; never implement this by removing the CAS. Existing revalidation and reconciliation seams: `proposals.py:437-449`, `:523-609`; `tools/transforms.py:1416-1447`. |

**Inferred/design, exact today work:** in `run_tool_batch`, reuse pending-proposal discovery from `_preflight_session_tool_call_ids` or an explicit pending query, reject multiple approval-required mutations before publishing any of them, and refuse another staged mutation while a pending proposal exists. Preserve immediate `create_blob` and approval-required destructive blob behavior. Separately reject an invalid ordinary incremental preview with its candidate findings and request a complete provider-authored replacement. Existing canonical `SetPipelineCandidate.acceptable` and its review handling remain authoritative for `set_pipeline`; do not replace them with a blanket ban on interpretation handoff. `src/elspeth/web/composer/tool_batch.py:383-405`, `:1212-1255`, `:1742-1751`, `:2209-2226`; `src/elspeth/web/composer/tools/sessions.py:589-598`.

**Inferred/design, size and completeness:** the pending guard and clear refusal can plausibly fit below ~80 production lines. That containment alone does **not** fully fix A. A complete change also needs ordinary accept-time invalid-graph refusal for already-staged proposals, truthful validation scope, and an explicit way to retire existing stale proposals. Do not call that complete package an ≤80-line quick win. Keep existing proposals/evidence; no silent deletion, implicit rebase or unconditional batch rejection of stored records. The existing no-op/refusal terminalization helper can support an explicit invalid-accept policy, but it must not confuse canonical pending-review settlement with invalid topology. `src/elspeth/web/sessions/routes/composer/proposals.py:84-112`, `:353-408`, `:611-641`, `:750-780`.

Prefer an explicit validation-subject/applied-status contract in the eventual atomic design, and carry candidate validation only when it was actually computed, clearly separate from applied-state validation and runtime preflight. Do not manufacture a failing validation of a valid saved state just to discourage the model. Adding keys requires updating the owned payload and its teaching/census gates; the existing exact key set is pinned. `src/elspeth/web/composer/tool_batch.py:253-273`, `:2330-2355`; `tests/unit/web/composer/test_tool_result_envelope_gate.py:3806-3865`.

## B. Opted-out interpretation review writes state behind the loop

**Verified caller chain:** `_handle_request_interpretation_review` invokes the event-creation callback, then returns the original `state` and validation when the event is `AUTO_INTERPRETED_OPT_OUT`. The callback is injected by the session-tool dispatcher. Repository `create_or_reconcile_pending` returns only `.event`, discarding the internal result's `produced_state`; its pipeline-candidate sibling retains the full result. `src/elspeth/web/composer/tools/sessions.py:3381-3421`; `src/elspeth/web/composer/session_tool.py:419-445`; `src/elspeth/web/coordination/repository.py:1071-1083`; `src/elspeth/web/sessions/service.py:5132-5138`.

**Verified reason for the write:** opt-out is automatic resolution, not “ignore the requirement.” The pending-interpretation planner resolves the relevant vague term, prompt, source, contract, pipeline decision or model choice, validates the patched state, and requests an `interpretation_resolve` successor. The repository requires that successor for OPTED_OUT, writes the next version, and internally returns the produced record. Deleting this write would lose the accepted interpretation/artifact bindings. `src/elspeth/web/sessions/pending_interpretation.py:2024-2031`, `:2050-2153`; `src/elspeth/web/coordination/repository.py:1272-1298`, `:1368-1415`.

**Verified stale-head mechanism:** the batch supplies the old `current_state_id` to the handler and later adopts only its returned state. `_SessionAwareDispatchOutcome` cannot carry a produced head. The loop's checkpoint callback still supplies its captured head; `persist_compose_turn` compares it with the newest state and raises before inserting the assistant message. The independently committed interpretation state therefore survives the failed compose checkpoint. `src/elspeth/web/composer/tool_batch.py:2886-2901`, `:2952-2955`; `src/elspeth/web/composer/session_tool.py:71-96`; `src/elspeth/web/composer/service.py:2552`, `:2826-2838`; `src/elspeth/web/composer/turn_audit.py:495-521`; `src/elspeth/web/sessions/service.py:2100-2124`.

**Measurement limit:** the inspected successful opt-out append accounts for one successor per call. Three calls alone account for three increments, not the six increments from v3 to v9. Other mutations/checkpoints in the live trace are needed to explain the remainder; this report does not invent them. `src/elspeth/web/coordination/repository.py:1368-1397`.

**Verified attribution — older/candidate:** candidate returns the same original state, discards the same produced-state result, appends the successor, and uses the same stale-head guard and checkpoint caller. The remediation does not introduce this ownership mismatch. `candidate:src/elspeth/web/composer/tools/sessions.py:3371-3384`; `candidate:src/elspeth/web/coordination/repository.py:1070-1075`, `:1358-1396`; `candidate:src/elspeth/web/sessions/service.py:2100-2113`; `candidate:src/elspeth/web/composer/service.py:2826-2838`. Local candidate-to-HEAD comparison of `pending_interpretation.py` and `session_tool.py` was unchanged; the relevant handler semantics remain those cited above.

**Inferred/design option assessment:**

1. **Do not write:** incorrect for the existing opt-out contract. It would leave the requirement unresolved while reporting automatic interpretation. The write is semantically necessary at the current ownership seam. `pending_interpretation.py:2050-2153`; `repository.py:1272-1298`.
2. **Advance expected head:** recommended direction, but carry the exact produced record and updated state, not merely a freshly queried UUID. Expose `PendingInterpretationCreationResult` through repository/service, session handler, `_SessionAwareDispatchOutcome` and `_DispatchOutcome`. Advance the working state and owned persisted head before the next tool. Distinguish an already-persisted interpretation successor from an ordinary in-memory mutation awaiting checkpoint. `repository.py:1071-1083`; `session_tool.py:71-96`; `tool_batch.py:2886-2955`.
3. **Do not advertise the tool:** at most guidance, not a correctness fix. Existing requirement resolution and already-issued calls still need correct semantics, including preference changes. The current session-tool dispatcher explicitly does not filter its advertised set. `src/elspeth/web/composer/session_tool.py:182-189`; `src/elspeth/web/sessions/pending_interpretation.py:2024-2153`.

**Inferred/design, smallest correct scope:** this is **not an honest ≤80-line fix**. Returning the produced state without changing checkpoint ownership also fails: `turn_audit` emits a new checkpoint payload whenever `post_version > pre_version`, and session persistence inserts that payload again. Mixed ordinary-mutation/review batches require explicit sequencing so unpersisted edits are neither overwritten by the service's persisted snapshot nor inserted after a later resolution as stale content. The concrete change belongs in `_RepositoryInterpretationMutations.create_or_reconcile_pending`, the corresponding `SessionService`/protocol return contract, `_handle_request_interpretation_review`, session/batch outcome carriers, and `_persist_turn_audit`/`persist_compose_turn` binding of already-produced states. Preserve the original checkpoint CAS. `src/elspeth/web/coordination/repository.py:1071-1083`; `src/elspeth/web/composer/turn_audit.py:409-417`; `src/elspeth/web/sessions/service.py:2140-2165`; handler/caller citations above.

**Inferred/design, PostgreSQL implications:** no schema change is inherently necessary, but this changes persistence ownership and must be tested under real transaction/fence contention. Keep the locked live-head read, session-operation authorization and next-version append. An exact own-write receipt may advance expected head; “read the newest row and trust it” must not adopt a foreign or stale-fence write. Test failure/cancellation between resolution and chat checkpoint as well as normal success. `src/elspeth/web/coordination/repository.py:1111-1118`, `:1368-1415`; `src/elspeth/web/sessions/service.py:2100-2113`.

**Proposed tests, not run:** three distinct opted-out review sites in one real compose batch must each resolve once, leave the returned state equal to persisted state, and persist the assistant reply without a duplicate checkpoint. Add mutation→review, review→mutation and multiple-review order cases; enabled-review calls must retain their pending-event semantics. Add a serial PostgreSQL test proving a foreign writer or expired fence is refused while an exact own-write successor is accepted. The existing opt-out unit test checks the suppression payload/event/draft but does not drive the final compose checkpoint; it cannot establish this property. Extend `tests/unit/web/composer/test_request_interpretation_review_tool.py:1530-1577` and add loop/persistence coverage; `tests/testcontainer/web/test_review_authority_postgres.py:1-95` supplies an existing contention-test pattern, not coverage of this defect.

## C. Freeform diff has no baseline dependency

**Verified:** `execute_tool` expects `baseline: CompositionState | None`, defaulting to `None`. Both freeform call sites omit it. `_execute_diff_pipeline` reads `context.baseline`, returns `diff_baseline_unavailable` if absent, otherwise validates that baseline and passes it to `diff_states`. It does not query historical versions. The preview call at line 2154 is inside mutation approval admission, so the normal freeform discovery refusal is specifically the general dispatch at line 3137; supplying both sites is dependency consistency, not evidence that diff normally traverses both. `src/elspeth/web/composer/tools/_dispatch.py:800-813`; `src/elspeth/web/composer/tool_batch.py:1742-1747`, `:2153-2181`, `:3136-3166`; `src/elspeth/web/composer/tools/generation.py:4669-4689`.

**Verified:** related validation-help text translates missing baseline into “the session was created without a loaded baseline state” and “Do not retry ... in this session.” This is stronger than the handler establishes. It can encourage the mistaken no-history explanation, but source alone does not establish which wording the model used in a particular probe. `src/elspeth/web/composer/tools/generation.py:458-463`.

**Verified other surfaces:** planner discovery supplies `baseline=current_state` and dispatches against that same current state, making that comparison uninformative. MCP owns an actual baseline snapshot, initialized/assigned at session creation/load seams; a separate assignment before success checking is the checklist's MCP issue. These are distinct owners, not a historical-versions service implicitly available to freeform. `src/elspeth/web/composer/pipeline_planner.py:3462`, `:4927-4935`; `src/elspeth/composer_mcp/server.py:722-732`, `:878`, `:922-925`.

**Verified attribution — older/candidate:** both omissions and the missing-baseline refusal already exist on candidate. `candidate:src/elspeth/web/composer/tool_batch.py:2059-2087`, `:3008-3038`; `candidate:src/elspeth/web/composer/tools/generation.py:4659-4670`. The checklist explicitly leaves freeform baseline 02.04, MCP success-only baseline 02.05, planner self-diff 02.06 and decision D8 unchecked. This remediation range did not claim to implement those source dependencies. `docs/architecture/composer-remediation/CHECKLIST.md:51-55`, `:661`.

**Inferred/design, baseline choice:** use the state at the start of the **user's compose request**, held fixed across all provider rounds in that request. It is ordinarily the accepted head at entry. Do not reset it at each provider tool batch: that hides edits made in earlier rounds. Do not choose the previous `/state/versions` row by default: that measures a different historical interval, possibly including changes predating this request. A history comparison needs an explicit historical-version selection contract. In explicit approval, diff should honestly show no applied changes while a proposal is pending; comparing proposed edits requires a separate proposal view. The current description already permits request-start semantics, and the loop already captures initial state in `TurnEvidence`. `src/elspeth/web/composer/tools/generation.py:4692-4706`; `src/elspeth/web/composer/service.py:2410-2421`; `src/elspeth/web/composer/turn_effects.py:360-366`; A's unchanged-state staging at `tool_batch.py:2330-2355`.

**Inferred/design, smallest wiring change:** bind `diff_baseline = state` once in `ComposerServiceImpl._compose_loop`, thread it through `_dispatch_tool_batch` into a `ToolBatchContext` baseline field, and pass it to the two `execute_tool` sites. Alternatively reuse the existing `turn_evidence.effects.initial_state` if made a required invariant for those paths, rather than falling back silently to each batch's changing `state`. Keep direct/unit callers explicit. Change the missing-baseline help to “This surface supplied no comparison baseline; this does not establish whether saved revisions exist.” Estimated well below ~80 production lines. `src/elspeth/web/composer/service.py:2410-2421`; `src/elspeth/web/composer/tool_batch.py:895-918`, `:2153-2181`, `:3136-3166`; `src/elspeth/web/composer/tools/generation.py:458-463`.

**Proposed tests and risks, not run:** use the actual service dispatch with scripted provider responses: diff at request start returns zero; mutation then diff in one batch; mutation then diff in a later provider round retains the original baseline; a second compose request resets the baseline; explicit-approval staging does not appear as an applied diff. Retain the missing-baseline direct-dispatch case. Existing test bodies: `tests/unit/web/composer/test_service.py:1402-1450`; `tests/unit/web/composer/test_agent_tooling.py:741-782`. Keep diff uncacheable (`src/elspeth/web/composer/tools/generation.py:4706`); do not add a cache-key change. This fix needs no persistence write or PostgreSQL behavior change. Do not silently bundle MCP baseline lifecycle or planner D8 decisions into the freeform wiring change.

## D. Splice requires visual edges despite logical connections

**Verified:** the empty visual-edge representation is admitted: the planner exemplar has `edges: []`, and `set_pipeline` copies supplied validated edges rather than deriving a full visual graph. This supports the reported planner-built shape, but does not prove all planner-built states always have empty edges. `src/elspeth/web/composer/planner_authoring_aids.py:2489-2502`; `src/elspeth/web/composer/tools/sessions.py:1960-1970`, `:1997-2003`.

**Verified root cause:** `_splice_topology_error` already checks that the predecessor's `on_success` equals the successor's `input`, checks supported source/transform types and branch/error restrictions, and checks other consumers and sink termination. It nevertheless requires exactly one matching visual edge. `_execute_splice_transform` then unconditionally retrieves that edge, derives a visual ID, and splits it. Replay independently requires two visual edges and their order. Removing only the first refusal would crash at `next()` or break idempotency. `src/elspeth/web/composer/tools/transforms.py:1130-1175`, `:1191-1228`, `:1340-1367`, `:1385-1396`.

**Verified attribution — older/candidate:** the candidate has the same logical/visual prerequisite. Local function history attributes the original visual-edge requirement to older commit `4b9910dfd` (“splice transforms atomically”), not the remediation range. `candidate:src/elspeth/web/composer/tools/transforms.py:1143-1162`; current equivalent `src/elspeth/web/composer/tools/transforms.py:1156-1175`.

**Inferred/design, recommendation:** fix the tool rather than merely stop offering it. The direct logical connection is recoverable from provider-authored names at this point; it need not be invented. For the bounded quick fix, when the **entire** edge tuple is empty, retain all scalar/type/branch/multiple-consumer checks, allow the logical splice, and preserve `edges=()`. Do not generate arbitrary mirror-edge identities. For nonempty edges, keep existing explicit-edge consistency and collision requirements. This matches the existing mirror reconciliation policy, which deliberately does not invent absent mirrors. `src/elspeth/web/composer/tools/transforms.py:1034-1078`, `:1130-1175`.

**Inferred/design, exact changes:** update `_splice_topology_error` for both first application and replay; branch visual-edge retrieval/ID derivation/splitting inside `_execute_splice_transform`; omit nonexistent `replaced_edge_id`/`new_edge_id` in the implicit-path response and explain the conditional response fields in the splice declaration. Keep node insertion immediately before successor, deterministic connection allocation, full profile validation, required review reconciliation, and one-version advancement. Existing replay already omits those visual IDs. Estimated 40–70 production lines, not a measured patch. `src/elspeth/web/composer/tools/transforms.py:1191-1228`, `:1321-1330`, `:1347-1396`, `:1405-1448`, `:2250-2256`.
