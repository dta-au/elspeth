## Ranked failures (worst for an ordinary user first)

### 1. explicit_approve follow-ups: one-tool-per-proposal batches cannot be accepted together; leaves broken or half-applied pipelines (REPRODUCED, s2, 4 turns)
- Repro (s2): trust mode `explicit_approve`; turn 2 "Change the threshold to 500 instead of 300." The model issued `upsert_node` + `set_output` x2 in one batch. Each returned `APPROVAL_REQUIRED` and became three separate pending proposals with the SAME `base_state_id` (v2). Accepting the first succeeded (-> v3); the other two returned `409 proposal_base_state_changed: "The session state changed after this proposal was created. Ask ELSPETH to rebase the proposal."` and stayed `pending` forever.
- Turn 3 "Drop the low-value sink": four proposals (`upsert_node` gate false->discard, `set_output`, `remove_output`, `set_metadata`). Only the first accepted (the gate rewire); `remove_output` 409'd. Result: state v4 INVALID: `Graph validation failed: 1 unreachable node(s) detected: sink_low_value_cfcf0122aa48 (sink)`. The user is left with a broken pipeline unless they accept in exactly the right order, and only the first can ever be accepted per turn.
- Turn 4 "validation is failing, finish removing it": the model burned 3 calls, retried `remove_output`, then escalated to a full `set_pipeline`, producing 5 more proposals (4 stale + 1 `set_pipeline` that 409'd `pipeline proposal base changed`). The state only became valid when the first accepted proposal happened to be `remove_output`. Accumulated pending-but-unacceptable proposals: 11 across the session (I rejected 5 manually via `/proposals/{id}/reject`, all 200).
- Misleading success: every `APPROVAL_REQUIRED` result carried `success: true` and a `validation` block computed on the UNCHANGED saved state (`"is_valid": true`, version N). The model reported "All three changes passed validation with no errors" / "All four passed validation". That validation says nothing about the proposed change, and the model could not know the batch would be un-acceptable.
- Model reasoning in turn 4 (tap call 90) shows it confused: "I didn't make any tool calls in my prior turns apparently ... So the actual state is version 4", and later "my mutations are being queued as proposals awaiting approval rather than applied".
- Root cause (**verified**): `src/elspeth/web/sessions/routes/composer/proposals.py:437-451`: accept requires `current_record.id == proposal.base_state_id`; every proposal staged in one batch shares the pre-batch base (tool_batch.py around line 2350 stages each tool call as an independent proposal). There is no rebase route anywhere (`grep -ni rebase` finds only that message text), although the 409 tells the user to "ask ELSPETH to rebase".
- Skill contribution (**verified**): `src/elspeth/web/composer/skills/pipeline_composer.md:462-465` says on `APPROVAL_REQUIRED` "tell the user it awaits approval and stop", but the skill also teaches the model to author multi-tool edits (e.g. the table at line 172-178 recommends narrow tools per edit), which in this mode produce non-composable proposals.
- Smallest fix: in explicit_approve mode, either (a) chain proposals in a batch (`base_state_id` of tool N = result of tool N-1) and accept the chain atomically, or (b) coalesce a batch's mutations into ONE proposal (a single `set_pipeline`-like draft with one draft_hash), and (c) make the `APPROVAL_REQUIRED` envelope not carry a green `validation` of the unchanged state (or label it `validation_of: "saved_state"`).
- First-turn variant (API surprise): even in `auto_commit`, three of five first turns (s1, s2, s4: those with invented-source or LLM review obligations) left a `set_pipeline` proposal `pending`; `accept` then requires `{"draft_hash": <pipeline_metadata.draft_hash>}` (empty body returns `422 "Canonical pipeline proposal acceptance requires draft_hash."`). The assistant text said "ELSPETH will commit it atomically" for s3/s5 (committed directly, no proposal) but "staged it for your review ... It has interpretation review cards to resolve" for s1/s2 even when no review cards existed afterwards (s1: 0 pending reviews; s2: 1).

### 2. Opted-out session: a follow-up turn that calls `request_interpretation_review` loses the whole turn with HTTP 409 `stale_compose_state` (REPRODUCED, s4 turn 2)
- Repro: s4 `POST /interpretations/opt_out` (200), then first turn "Use an LLM to flag the urgent ones ..." (OK, v3). Turn 2: "Also have the LLM give each ticket a priority of high, medium or low, and add a separate yes/no column for tickets that need escalating to a manager. Use your own judgement for what counts as escalation-worthy."
- Model did `patch_node_options` + `patch_node_options` + `patch_output_options` (all succeeded, v4-v6), then (tap call 117) called `request_interpretation_review` x3 (`vague_term`: priority, escalation-worthy, urgent) exactly as the skill requires ("When `interpretation_review_disabled=true`, still call the tool", `skills/pipeline_composer.md:1225-1226`).
- Terminal: operation `failed`, `{"http_status":409,"error_type":"stale_compose_state","detail":"The session changed while the compose turn was running."}`. No assistant reply, no tool rows persisted for the turn (messages-turn2.json ends at the provider-call audit), the model never saw the three review results. State had advanced v3 -> v9 (and later v10): three extra state versions (v7, v8, v9) were written one per review call, plus the three edits. At the failure moment the head was INVALID (`interpretation_review_pending` for `llm_prompt_template:flag_urgent`); a later turn found it valid (v10).
- The edits survived (turn 3 "did my last change go through?" confirmed priority/escalation columns present), so the damage is: user sees a raw 409, no explanation, and the half-finished model state.
- Root cause (**inferred, mechanism partly verified**): the opt-out branch returns `interpretation_review_suppressed_by_opt_out` (`src/elspeth/web/composer/tools/sessions.py:3411-3424`) but the persistence path used for auto-interpretation (`create_pending_interpretation_event(..., proposed_state=...)`, `src/elspeth/web/sessions/service.py:5002-5017`) writes a composition state per call; the end-of-turn `persist_compose_turn` then refuses because the head moved: `src/elspeth/web/sessions/service.py:2100-2113` raises `StaleComposeStateError`, mapped to 409 at `src/elspeth/web/app.py:1897-1907`. Evidence for "one state per call": 3 review calls -> exactly 3 new versions (7, 8, 9) immediately before the failure.
- Smallest fix: the loop's expected-head tracker must advance when the opt-out branch writes a state (or the opt-out branch must not write a state version); add a test with 3 opted-out `request_interpretation_review` calls in one batch.

### 3. `diff_pipeline` always refuses on the freeform surface (REPRODUCED, s1 turns 5 and 6)
- Repro: s1 turn 6 "Please run the diff tool and show me what your last edit changed." Tool call `diff_pipeline {"_elspeth_no_arguments":true}`; result: `{"success": false, ... "message": "No baseline available. Load or create a session first.", "error_code": "diff_baseline_unavailable"}`.
- Turn 5 ("show me exactly what changed compared to the first version") the model did not even try the tool; its reasoning (tap call 72): "diff_pipeline compares current with the baseline supplied by surface — which is the request-start state, not the first version", then answered from conversation memory with an explicit caveat, i.e. the tool description ("which may be the request-start state") trained it that the tool cannot do what was asked. In turn 6 the model's final text told the user "this session stores no snapshot of an earlier revision ... a true revision-to-revision diff isn't available", which is false: `GET /state/versions` returned all 7+ versions.
- Root cause (**verified**): the handler needs `context.baseline` (`src/elspeth/web/composer/tools/generation.py:4652-4675`) but neither `execute_tool` call in the freeform loop passes `baseline=` (`src/elspeth/web/composer/tool_batch.py:2154` and `:3137`; `grep -n baseline tool_batch.py` returns nothing). Only the planner/commit paths (`pipeline_planner.py:3462`, `pipeline_commit.py:517,593`) pass `baseline=current_state`.
- Also misleading: the error-pattern table tells the model "the session was created without a loaded baseline state ... Do not retry diff_pipeline in this session" (`generation.py:459-463`), which makes the model give up permanently after one product defect.
- Smallest fix: pass `baseline=<turn-start CompositionState>` (the loop already has `turn_start_state_id`/version in its system context message) at both `execute_tool` sites; fix the description to say "versus the state at the start of this request".

### 4. `splice_transform` refuses on every planner-built pipeline ("insert a step") (REPRODUCED, s3 turn 4)
- Repro: s3 turn 4 "Add an age_group column ... senior if age is over 60": model (correctly following the skill table) called `splice_transform {"predecessor_id":"source","successor_id":"keep_name_city","node":{...value_transform...}}`. Result: `success:false, error_code: "splice_topology_unsupported", message: "Splice path must have exactly one direct visual on_success edge."`.
- The committed state of the planner-built pipeline has `edges: []` (verified via `GET /state`: `edges == []`; s1, s2, s3 all show `edges: []` in their YAML/state), because the planner authors topology through `input`/`on_success` connection names only.
- Recovery cost: the model fell back to two `upsert_node` + `patch_output_options` in one parallel batch (intermediate `transform_on_success_dangling` and `duplicate_connection_consumer` errors, then valid). Final state valid; 1 wasted call and a user-visible detour. The skill row `src/elspeth/web/composer/skills/pipeline_composer.md:176` ("one-transform insertion ... `splice_transform`") and the tool description (`src/elspeth/web/composer/tools/transforms.py:2248-2255`: "Requires exactly one direct visual on_success edge") never mention that a planner-built graph has none.
- Root cause (**verified**): `src/elspeth/web/composer/tools/transforms.py:1160-1168` requires `len(matching) == 1` over `state.edges`.
- Smallest fix: derive the direct edge from `predecessor.on_success == successor.input` when `state.edges` is empty (the code already checks that equality at line 1155), or materialise edges when committing a planner proposal.

### 5. `get_blob_content` mislabels an over-size file as a credential finding; the model then tells the user their file contains a credential (REPRODUCED, s5 turn 2)
- Repro: uploaded a 602,023-byte benign CSV (`widget-N`, qty, price; no secrets). Turn 1 asked for a pipeline AND "tell me what the first 3 lines of my file contain": the planner turn ignored the second half and finished with the canned "I prepared and validated the requested pipeline" (turn ended without doing what was asked). Turn 2 "what are the first 3 lines of sales.csv?": `get_blob_content {"blob_id":...,"offset_chars":0}` -> `{"success": false, "errors":[{"message":"This control content appears to contain a credential. Store the value through the secret service and use a secret reference.","error_code":"credential_material_rejected"}]}`. Then `read_attachment` -> the CORRECT message: "The attachment is 602023 bytes, exceeding the current 262144-byte whole-input credential inspection limit".
- Final reply to the user: "the file's content tripped the credential guard ('content appears to contain a credential') ... I cannot disclose any of the data rows". That is a false accusation about the user's data, caused by the tool's wrong error. The model also spent 5 tool calls and 130 s.
- Root cause (**inferred for the oversize->refusal link, mapping verified**): `_credential_safe_blob_discovery_result` (`src/elspeth/web/composer/tools/blobs.py:122-137`) maps every `CredentialMaterialRefused` to the credential message; `get_blob_content` calls it on the whole decoded payload (`blobs.py:2198`), and `require_no_credential_material` has a default `max_string_bytes=262_144` (`src/elspeth/web/credential_guard.py:76`), which matches the 262144 limit `read_attachment` reports. `read_attachment` has its own size pre-check with the right text.
- Smallest fix: in `get_blob_content`, check size against the inspection limit first and return the same size-limit message as `read_attachment`; better, page-inspect so a big file can be read at all (the description at `blobs.py:2317` already promises neither reader can disclose it).

### 6. Advisor (completion review) unavailable: the model's real, correct reply is replaced by boilerplate; turn takes 250 s (REPRODUCED once, s3 turn 3; also long tail elsewhere)
- Repro: s3 turn 3 (swap source to nested-JSON data). Tool work finished in ~10 s and the model wrote a good final answer (tap call 106, preview table etc.). The operation then took 249.7 s total and the user-visible assistant text became: "[ELSPETH-SYSTEM] Completion advisory review could not be obtained: the advisor model was unavailable. Composer completion is withheld. Retry the request ..." (the correct reply is withheld). `server.log`: `composer.advisor_checkpoint_pass ... verdict: unavailable, provider_attempts: 2` at 23:17:38 and again `pass_index 2` at 23:19:38, i.e. ~2 min per pass, then `composer.advisor_terminal_publication reason: unavailable`.
- Same slowness without the failure: advisor passes with `provider_attempts: 2` (s2 turns 3 and 4: 107.7 s and 148.8 s; s5 turn 2: 129.6 s) versus 20-45 s for turns where the advisor needed 1 attempt.
- Not a tool defect and probably DeepSeek-endpoint flakiness (advisor requests that time out are not in the tap), but for an ordinary user the effect is: edit applied, answer thrown away, 4 minutes. Suspected cause is the advisor call timeout/retry budget; **inferred**, not read.
- Smallest fix: when the advisor is unavailable and preflight is green (`preflight_shape: "green"` in the log), publish the model's own reply with the "review unavailable" banner appended rather than replacing it; and cap per-pass advisor wait well below 2 minutes.

- s1 turn 4 and s3 turn 4: parallel multi-tool batches (`upsert_node` + `set_output`) produce a transient INVALID result for the first call; the model then waits for the later result. Works but looks like a failure in the tool rows.
- Model preference: across the edit turns the model reached for `upsert_node` (whole node) and `set_output` (whole sink) far more often than the narrow patch tools (`patch_output_options` and `patch_node_options` appeared only in s3 turn 4, s4 turn 2 and s2-s1 reasoning; count taken by eye from the tap, not a registry query), even where its own reasoning said "this is an option-only edit ... use patch_node_options" , then calling `set_output`/`upsert_node` anyway (calls 64 and 77). Not an error, but the rewrite-everything tools re-emit sibling fields and re-emit sibling fields.
- Stale pipeline description: renaming the output file (s1) never updated `metadata.description` ("write the result to out.csv"); the model noticed ("still says out.csv") in three consecutive turns and offered rather than fixed it.
- `preview_pipeline` does not preview data. The user asked "preview what the output will look like" (s3 turn 2): the tool returns structure/contracts only; the model composed a sample table from the source JSON in its own reasoning and presented it under "Preview result". Accurate in these cases (trivial field selection) but not tool-produced.

## API-flow notes
- Preference enum is `explicit_approve|auto_commit` (not `approval`); `PATCH /composer/preferences` requires both `trust_mode` and `density_default`.
- `POST /state/revert` requires an `operation_id` UUID in the body (not exercised).
- Accept of a canonical pipeline proposal needs `draft_hash` from `pipeline_metadata`; omitted -> 422.
- No endpoint to rebase or bulk-supersede stale proposals; stale ones must be rejected one by one (`/reject` works, `reason` optional); stale pending proposals do not block new compose turns but pile up in `GET /proposals`.
- A compose operation still running (long advisor wait) makes a second `POST /messages` return `409 composer_operation_active` (correct); the operation poll protocol (`/operations/{id}`) worked every time.
- The `state/yaml` export says "NOT runnable as exported" (custody-redacted) so it cannot serve as a user-facing "what does my pipeline look like" artefact.
