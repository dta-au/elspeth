# Continuation workers and container grace periods (0.8.10)

> Design requirements for units U-37 (C4a worker yield/resume/restart), U-38
> (C5 production policy) and U-39 (C4b recovery gate) on the two priority
> deployment targets, AWS ECS and Azure Container Apps.

All repository facts were measured on `release/0.8.10-assembly` at `d39ff6660`
on 2026-10-24. Platform limits are quoted from vendor documentation fetched the
same day.

The two targets differ in kind. On ECS, "another replica recovers the segment"
means **the replacement task** of the same single-task service, after the old
task is gone. With zero overlap there is never a live peer. On ACA production
there are 2–4 live peers, so recovery can be a true peer takeover while the
dying replica is still within its grace period.

## 2. Measured worker facts

**Two leases, both 30 s.**

- **Queue claim.** It is renewed while the job waits for the session lock,
  before any provider work, every `claim_lease_seconds / 3`. The lock wait is
  polled at `min(0.25, lease/3)` (`sessions/composer_async_worker.py:473–488`).
  `composer_async_claim_lease_seconds` defaults to **30**, range 5–600
  (`web/config.py:402`). On stop or drain in this phase, the claim is
  **released** (`release_claim`, `:479–481`). That path is already a clean
  hand-back.
- **Running operation lease.** It is a `SessionOperationLease` with
  `session_operation_lease_seconds`. That defaults to **30** in the
  `SessionService` constructor (`sessions/service.py:757`), and no production
  caller overrides it: the only assignment is `service.py:789`. Renewal runs
  every `min(lease/3, 30 s)` (`coordination/lifecycle.py:110, 210–214`),
  i.e. **10 s**.

**Shutdown today.**

- `ComposerAsyncWorker.stop()` sets `_stopping` and cancels every job and the
  claim loop with `COMPOSER_SHUTDOWN`. It then waits at most
  `composer_async_drain_seconds`, default **10 s**, greater than 0 and at most
  120 (`config.py:405`).
  Jobs still unfinished keep their custody. A peer's reaper settles them only
  once the COMPOSE lease has lapsed (`composer_async_worker.py:414–427`).
- Turn code checks `_stopping or _instance_draining` before and during a turn,
  and raises or cancels with `COMPOSER_SHUTDOWN` (`:811–812`, `:954–956`).
- Neither ECS nor ACA sets any `COMPOSER_ASYNC_*` or lease setting. A search of
  both deploy directories for `COMPOSER_ASYNC|LEASE_SECONDS|DRAIN` returned
  nothing, so production runs on these defaults.

**When `stop()` actually runs.**

- The worker is stopped only in the FastAPI lifespan `finally`, after
  `web_instance_membership.begin_drain` (`web/app.py:1214, 1220`).
- `elspeth web` starts uvicorn without `timeout_graceful_shutdown`
  (`cli.py:5292–5300`), and the installed uvicorn (0.46.0) defaults it to
  `None`. On SIGTERM, uvicorn closes its listeners, then runs
  `asyncio.wait_for(_wait_tasks_to_complete(), timeout=None)`. That waits,
  **without bound**, until every open connection and task has finished. Only
  then does it send the lifespan shutdown (`uvicorn/server.py:271–301`).
- A Composer progress stream (`BoundedComposerStreamResponse`) may stay open for
  `STREAM_LIFETIME_SECONDS = 120.0` (`web/composer_stream.py`). The module has
  no reference to draining.
- So with one subscriber attached, `stop()` can start up to 120 s after SIGTERM.
  That is later than both the 30 s ECS default and the 60 s ACA setting.
- Until then, `instance_draining` is unset, so the worker keeps claiming new
  queued operations on a process that is about to be killed.

This is the binding constraint. The checkpoint itself is small next to it.

## 3. Requirements

Let `G` be the platform grace period (ECS: `stopTimeout`; ACA:
`terminationGracePeriodSeconds`). The shutdown budget after SIGTERM is:

```text
t_signal→drain  (≈0 once R1 holds)
+ H   bounded HTTP drain (uvicorn timeout_graceful_shutdown / stream hook)
+ D   composer worker drain (composer_async_drain_seconds, default 10)
+ Y   per-segment yield transaction(s) inside D
+ S   membership stop and process exit
+ M   safety margin
≤ G
```

### R1 — Shutdown begins promptly (U-37)

1. **Draining is set at SIGTERM, not in the lifespan `finally`.**
   `instance_draining` must be set before uvicorn starts its connection wait,
   for example by wrapping uvicorn's exit handler or by running uvicorn through
   `Config`/`Server` with an owned signal hook. From that moment the composer
   worker makes **no new claims** (`_loop` and `_claim_once` already respect
   `_instance_draining`).
2. **The HTTP drain is bounded below `G`.** Use either uvicorn's
   `timeout_graceful_shutdown = H`, or a draining hook in
   `BoundedComposerStreamResponse` that ends each stream with a terminal
   "reconnect elsewhere" frame. Prefer both. Streams currently live up to
   120 s, which exceeds both platforms. The gateway sidecar already runs with
   `--timeout-graceful-shutdown 30` (`ecs.tf:113`), so the setting has
   precedent in our own task.
3. Only then do the checkpoint and the lease release (R2) run.

### R2 — Yield a durable checkpoint and release the lease inside `D` (U-37)

For every v2 segment the replica owns when draining starts:

- **At a committed cut** (no prepared or dispatched effect): one transaction
  per segment writes a handoff checkpoint (`append_complete_snapshot(…,
  handoff=True)`) and marks the attempt `outcome="yielded"`. It sets the
  segment to `state="yielded"`, clears its claim and sets
  `next_eligible_at = now`. It releases the session-operation fence, so that a
  peer or the replacement task can claim immediately instead of waiting for
  lease expiry. It uses the same compare-and-swap predicates as
  `recover_composer_segment` (generation, claim token, checkpoint id and cursor).
- **With a provider or business effect in flight:** do not write a partial
  yield. Cancel the provider call; its cost is spent and its result is
  discarded. Then either settle the operation explicitly (R5) or leave the
  segment for recovery (R4/R5). Never leave it `running` with no owner path.
- **Queued and pre-start claims** keep today's behaviour: `release_claim` on
  drain (`composer_async_worker.py:479–481`).

The yield must not depend on the segment's timing policy. A SIGTERM one second
into a 300 s segment yields just as well as one at the cooperative point.

### R3 — Values that fit (U-37 config, deploy files)

With R1 in place: `H = 5 s`, `D = 10 s` (today's default), `Y` measured by
U-37 (expected sub-second on PostgreSQL, but **not yet measured**), `S ≈ 1 s`,
`M = 5 s`. That sums to about 21 s plus `Y`, which fits the ECS 30 s default
with about 9 s to spare and ACA's 60 s comfortably. **Without R1 no value of
`G` up to the platform maximums is safe.** A 120 s stream plus `D` already
exceeds the Fargate maximum of 120 s.

**Evaluation of the caps (maintainer rule: is the cap itself too
burdensome?).**

- **ECS.** 30 s is a platform default, not a choice we made. Set it
  explicitly to **60 s** on the web container:
  - it makes the budget a reviewed setting rather than an inherited default;
  - it matches ACA, so one shutdown budget serves both targets;
  - it leaves room to raise `D` to 30 s if U-37's measured `Y` needs it.

  Cost: the service deploys with zero overlap, so a longer `stopTimeout` adds
  downtime **only when shutdown hangs**. A healthy process exits as soon as its
  drain finishes. Worst-case extra downtime per deploy is 30 s, on top of the
  replacement's start (health-check grace 150 s), and of the ALB's 30 s
  deregistration delay if ECS serialises it before the stop. That ordering is
  AWS behaviour this note has not measured. Going to the 120 s maximum buys nothing: no grace up to the
  maximum can absorb an in-flight 120 s provider call (fixture
  `physical = 120`) plus drain. That case is R5's job, not the grace period's.
- **ACA.** Keep **60 s**. Raising it is unproven: there is no documented
  maximum. It would also lengthen scale-in and single-revision turnover. The
  old revision's replicas linger up to `G` during a revision change, holding
  database connections and membership rows against the shared connection
  budget. 60 s already covers the R3 budget twice over.

**Proposed diff, not applied** (`deploy/aws-ecs/terraform/modules/scenario/ecs.tf`, web container):

```diff
   candidate_web_container = {
     name       = local.web_container_name
     image      = terraform_data.candidate_image_provenance.output
     essential  = true
+    # Shutdown budget: bounded HTTP drain + composer drain + yield + margin.
+    # Fargate default is 30 s and maximum 120 s; matches ACA's 60 s.
+    stopTimeout = 60
     entryPoint = ["/bin/sh", "-ceu", local.ecs_identity_wrapper, "--"]
```

Apply the same line to `rollback_web` if it is kept in step. No ACA diff.

### R4 — Recover a killed replica's segment without duplicates (U-39)

After SIGKILL (or a missed grace), a segment at a committed cut is recovered:
- on PostgreSQL, only after **both** the fence lease and the owner's
  `web_instances` membership lease have expired, using the database clock;
- by exactly one recoverer;
- with exactly one new generation, one `recovered` event and one checkpoint;
- with no re-dispatch of a provider or business effect.

The recoverer differs by platform:
- on **ACA** it is a live peer, typically within the 30 s lease plus one
  10 s renewal period;
- on **ECS** it is the **replacement task**, after its start and readiness
  (health grace 150 s). With one task, recovery latency is the restart time,
  not the lease.

A production caller is required: a reaper or claim path that invokes recovery
and then `claim_segment` and `start_composer_segment`. None exists on any tree
today.

### R5 — No session is left wedged (U-39)

A v2 parent that is still `queued`/`running` blocks every non-owning fence
acquire for its session. The block is `SessionOperationConflictError` at
`coordination/repository.py:4950–4960` on the v152 prototype (`897dabeb8`).
Recovery refuses prepared or dispatched cuts by design
(`continuation_next_action.py`, "cannot retry a prepared or unknown business
effect"). So an operation killed mid provider call is never recovered **and**
never settled, and Composer is dead for that session.

U-39 must therefore settle such a parent, after the same expiry and membership
proof as R4, into a terminal state that records the effect as unknown. That
frees the fence, so a new Compose can start. This matters most on ECS: a
deploy SIGTERMs the only task, and in-flight provider calls there are routine.

### R6 — Production segment policy (U-38)

The fixture (`tests/helpers/continuation_policy.py`: nominal 300, watermark 120,
quantum 180, reserve 25; provider action physical 120, total 136) is a test
value, not a container design.

- Segment duration is `max(nominal, action.total + reserve + watermark)`, so
  every segment is ≥ 300 s, 5–10× either grace period. A SIGTERM almost always
  lands mid-segment. That is why R2 is signal-driven and does not wait for a
  cooperative point.
- **`reserve 25` is not justified by any measurement.** It is settlement
  headroom for one action. The settle is a database transaction, so 25 s is
  generous rather than tight. Set it from U-37's measured `Y` (p99 × a stated
  factor), not from the grace period.
- **`quantum 180` and `nominal 300` need no change for grace purposes.** With
  R2 in place, grace does not constrain them. Their real constraints are
  provider timeouts and fairness, which U-45 measures. If R2 were cooperative
  only, `quantum` would have to be ≤ `G − M`. That is a reason to keep R2
  signal-driven, not to shrink the quantum.
- **`physical 120`** (the provider action bound) exceeds every grace period. No
  grace setting can cover it, so in-flight provider calls at SIGTERM go
  through R2's cancel branch and R5.
- The production policy must come from settings (`from_settings`) and be
  persisted per operation with a versioned payload. That is already U-38's
  scope. Both targets inject settings by environment.

### R7 — Membership identity (U-39, minor)

On PostgreSQL, takeover requires the dead owner's membership row to be
expired. A restarted replica that reuses a pinned `WebSettings.instance_id`
re-registers a fresh lease under the dead owner's id, and that blocks peer
takeover. Either refuse a pinned `instance_id` when replicas > 1, or have
recovery treat a re-registration with a newer process start as proof that the
old owner is dead.

These must be real-process tests: a subprocess running `elspeth web` against

themselves "deterministic expiry is not process death". Each case states its
platform shape.

## 5. What the v152 prototype already covers

Source: a read-only analysis of `897dabeb8` against the target and the WIP
overlay (`255f1cff3`), with the load-bearing citations re-checked by hand.

- **C4a (U-37): not covered.** Nothing writes a yield. All 17
  `append_complete_snapshot` call sites pass `handoff=False`. A YIELD timing
  decision raises `AuditIntegrityError` (`continuation_title_provider.py`,
  `continuation_composition_initialization.py`). There is no v2 worker driver:
  `composer_async_worker.py` is identical between the overlay and the
  prototype, and `claim_next` and `list_expired_running` handle
  `lifecycle_version == 1` only. The vocabulary exists (segment state and
  attempt outcome `yielded`, the `yielded` event tag, a claim predicate that
  accepts `interrupted`), so R2 builds on it.
- **C4b (U-39): partly covered, as a library transition only.**
  `recover_composer_segment` (`coordination/repository.py:5014–5194` at
  `897dabeb8`, +182 lines) is correct for the cuts it admits:
  - it is serialised by a PostgreSQL session advisory transaction lock and
    `FOR UPDATE` on the fence and on the owner's membership row;
  - it requires the fence lease to have expired by the database clock **and**,
    on PostgreSQL, the owner's membership lease;
  - it compare-and-swaps three rows (attempt `interrupted`, segment generation
    +1, parent ownership generation +1) and appends one `recovered` event and
    checkpoint by compare-and-swap on (checkpoint id, cursor);
  - it leaves the fence for the next `start_composer_segment` to advance
    (epoch +1, new token), which fences out the old owner.

  The gaps:
  - it refuses prepared or dispatched cuts (R5 wedge);
  - **no production code calls it**, nor `claim_segment` or
    `start_composer_segment`;
  - v2 admission is unreachable in production because no
    `continuation_policy` is passed (`app.py`), so the authority refuses v2.
- **Tests.** There are 8 deterministic tests: 3 in
  `test_continuation_p4_recovery_start.py` and 5 in
  `test_continuation_p4_recovery_boundaries.py`, both re-exported under
  `tests/testcontainer/web/*_postgres.py`. They include an in-process
  two-caller race. None is a real process kill, a SIGTERM, or a
  worker-driven recovery.
- **Schema.** All of it depends on epoch-79 tables and columns, and on the
  prototype's `sessions/continuation.py` and its successor-action modules. It
  cannot be lifted alone: at `recover_composer_segment` the overlay and the
  prototype differ only by this function, but the prototype is a sibling of the
  overlay, not a superset.
