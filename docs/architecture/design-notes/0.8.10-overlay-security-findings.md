# 0.8.10 Continuation overlay — security findings and fix specifications

Defensive review of ELSPETH's own code. The source is a Codex Daybreak Blue
static review of the Continuation overlay (`git diff
release/0.8.10-assembly...codex/0.8.10-continuation-overlay -- src`), which
reviewed overlay `b2cb4d977` against target `78adcdd1d`: 161 files,
+34,901/−4,723. That review's verdict was CHANGES REQUESTED, with one Medium and
one Low. Both findings were **verified here against the overlay source at
`b2cb4d977`**. Every `file:line` below was read at that commit.

The fixes land **after** the overlay, as fix-on-fail. This note specifies them
and does not change overlay code. Each fix is test-first: the regression must
fail on the overlay as it stands, and a mutation control must turn it red
again after the fix.

## F-1 (Medium) — authority-revoked graph results replay as successful Advisor evidence

**Owner:** U-29 (mutation authority). **Blocks the release: yes.** It corrupts
durable review evidence, and later Advisors reason from that evidence. The fix
must land before the single 0.8.10 merge.

### Verified mechanism (`b2cb4d977`)

1. **Capture.** `composer/turn_audit.py:419–436` (`visible_event_for`) builds
   `VisibleToolEvent.capture(…, selected_result=selected, display_result=…)`.
   `selected` comes from `turn_evidence.transcript.current_tool_strings(...)`,
   which is the tool result the model received in that turn: the graph
   mutation's success.
2. **Revocation.** `turn_audit.py:215–246` (`_revoked_graph_rows`) runs when
   P4 publication finds automatic mutation authority revoked. It builds a
   `_failure_result(…, error_code="auto_mutation_revoked")` display, sets
   `content=display` and `composition_state_payload=None`, and calls
   `row.visible_event.with_display_result(display)`.
3. **The gap.** `composer/visible_tool_event.py:228–233` (`with_display_result`)
   replaces **only** `display_result_hash`. `payload_json` keeps
   `"selected_result"` (the pre-revocation success), and `payload_hash` stays
   bound to that payload. The persisted event is internally consistent: its
   hashes match. It is semantically contradictory: the display says refused,
   the payload says this success was the selected result.
4. **Propagation.** History reconstruction in
   `composer/advisor_transcript.py:380–405` validates the recorded link against
   the refusal display (`validate_recorded_link(display_result=row.content)`,
   which passes), then **overwrites the event content**:
   `if payload["selected_result"] is not None: event["content"] =
   payload["selected_result"]` (`:401–403`).
5. **Reaches a model.** `composer/advisor_context.py:281–291` inserts that
   transcript (`transcript.provider_json`) into the next Advisor's prompt.

**Effect.** After P4 records `auto_mutation_revoked`, a later Advisor sees the
graph mutation as having succeeded, and reasons about a graph that was
explicitly refused. The primary tool row correctly holds the refusal and no
graph state is written (`sessions/service.py:2156–2169, 2205–2246`, per the
review). So this is **not** an unauthorised database write. It is
contradictory durable evidence that is fed back into model guidance.

**Nuance for the fix.** `selected_result` is probably the historically true
string the model saw before revocation. Keeping a record of that is not itself
wrong; presenting it as the event's outcome is. The fix must keep the
candidate, if at all, only as labelled diagnostic evidence, never as the
visible result.

### Fix

1. **`visible_tool_event.py`:** add a dedicated transition,
   `VisibleToolEvent.with_authority_revocation(display_result: str)`, used
   only by `_revoked_graph_rows`. It returns an event whose:
   - `display_result_hash` is that of the refusal display;
   - `payload_json` has `"selected_result": null`, plus an explicit
     availability marker such as `"availability_gaps": [...,
     "authority_revoked_after_selection"]`. If the rejected candidate must be
     retained, it goes under a distinct key that reconstruction never treats
     as content, for example `"revoked_candidate_hash"`, a hash rather than
     the body;
   - `payload_hash` is **recomputed** over the new payload.

   `with_display_result` keeps its current narrow meaning, and should refuse
   to be applied when the payload carries a selected result that differs from
   the new display.
2. **`turn_audit.py:242–244`:** call `with_authority_revocation(display)`
   instead of `with_display_result(display)`.
3. **`advisor_transcript.py:401–403`:** defence in depth. Before substituting
   `selected_result`, refuse (`AuditIntegrityError`) any envelope whose
   availability marks the selection superseded but still carries a
   `selected_result`. When the marker is present, keep `row.content` (the
   refusal) as the event content.

## F-2 (Low) — continuation attachment admission reads the entire file before enforcing its size limit

**Owner:** U-32 (attachment admission). **Blocks the release: no.** It is
authenticated, same-session, and bounded by the existing upload limit
(100 MiB) and per-session storage limit (500 MiB) (`web/config.py:549–550`).
It is a resource-amplification defect; fix it in 0.8.10 if U-32 has capacity,
otherwise in the next patch.

### Verified mechanism (`b2cb4d977`)

1. **Caller.** `composer/continuation_attachment_read.py:103–116` builds
   `AttachmentInspectionPolicy(READ_ATTACHMENT_MAX_UTF8_BYTES, …)` and calls
   the discovery tool with it. `READ_ATTACHMENT_MAX_UTF8_BYTES`
   (`composer/redaction.py:3424`) is
   `min(JSON_MAX_TOTAL_UTF8_BYTES, DEFAULT_CREDENTIAL_TRAVERSAL_POLICY.max_string_bytes)`,
   and `max_string_bytes = 262_144` (`contracts/credential_material.py:132`).
2. **Whole-file read under the lock.** `composer/tools/blobs.py:1973–1987`:
   inside `_locked_blob_row_for_read`, `data = Path(row.storage_path).read_bytes()`
   reads the **entire** file. `_verify_blob_content_integrity(record, data)`
   then hashes all of it.
3. **The size check comes last.** `inspect_attachment_original`
   (`composer/attachment_admission.py:70–81`) hashes `raw` **again**
   (`:76–78`), and only then checks `len(raw) > policy.max_bytes` (`:79`) and
   refuses.
4. **The size was known in advance.** The locked row carries `size_bytes`
   (`_blob_record_to_tool_dict`, `blobs.py:1917–1924`).

**Effect.** Each oversized continuation read allocates up to 100 MiB and
hashes it twice, under the blob row lock, for a refusal that the recorded size
already determined. Concurrent authenticated sessions can turn this into
avoidable worker memory and I/O pressure. The whole-file primitive predates
the overlay; the overlay adds this new consumer.

### Fix (only in the `attachment_inspection_policy is not None` path; other callers unchanged)

1. Inside the locked read, before materialising the file: if
   `record["size_bytes"] > policy.max_bytes`, raise the **same**
   `AttachmentInspectionRefused` message that `attachment_admission.py:80–82`
   produces, without reading the file. Record the observation exactly as
   today.
2. Otherwise read at most `policy.max_bytes + 1` bytes (an `open` +
   `read(n)`; do not use `read_bytes`).
   - If more than `max_bytes` arrive, or the length differs from `size_bytes`,
     raise `AuditIntegrityError`: the row and the disk disagree, so this is an
     integrity failure, not a size refusal.
   - Then run the existing `_verify_blob_content_integrity` on the bounded
     bytes, which is the complete file in this branch.
3. Leave the existing `len(raw) > max_bytes` check in `inspect_attachment_original`
   as a backstop.

## Not findings

The review traced, and found no diff-introduced bypass in: tenant and session
authorisation, leases and fencing, replay and idempotency, continuation secret
retention, SQL and log sinks, PromptShield provenance, and the two composer
invariants.

An independent pre-read
(`.claude/lanes/release-0.8.10/overlay-prereview/prereview-notes.md`, a lane
note) agrees on session isolation. An AST scan, with positive, negative and
blind-spot controls, found 113 statements on the seven new tables. All are
session-scoped except `claim_segment`'s id-only queue hint
(`coordination/composer_operation_authority.py:1242`), which is re-selected
under `locked_session_transaction(hint.session_id)` before any write. That is
benign by design.

The same pre-read lists eight snapshot-writing modules that call no
credential guard locally. These are leads, not findings: their content may be
admitted upstream, and the Daybreak review found no credential-retention
bypass. They are worth a provenance trace if U-44b reworks those phases.
