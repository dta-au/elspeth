## 0. Vocabulary

The four control words in the unit brief name different owners. They are
not four user buttons.

| Word | Meaning in this design | Who initiates | Owner |
|---|---|---|---|
| **continue** | The same logical request moves to its next segment. Two sources: the model's closed `checkpoint_and_continue` control tool (U-40), and host-only safe rollover at a segment deadline or SIGTERM (runtime). | Model or host. Never the user: the original plan's C8 exit forbids a new Continue/confirmation workflow, and this note keeps that. | U-40 (tool), runtime (rollover) |
| **stop** | The user's durable request to end the logical request. One action, one durable marker (`cancel_requested_at`), one terminal outcome (`failed` + `request_cancelled`). | The authenticated owner, from the top-level Stop button. | U-40 authority semantics, U-41 route, U-42 button |
| **cancel** | The HTTP verb and route that carry *stop*: `POST /api/sessions/{sid}/operations/{oid}/cancel`. "Stop" is the user-facing word; "cancel" is the wire word. There is no second, weaker cancel. | — | U-41 |
| **resume** | Never a user verb. Two internal meanings: the runtime claims a successor or recovers a lapsed segment (runtime), and the client reattaches its observer after reload, network loss or a replica change (U-41/U-42). A stopped request is terminal and is never resumed; the user sends again or uses the existing "Retry interrupted request" recompose. | Worker or browser | runtime, U-41, U-42 |

*Revert* (`POST /api/sessions/{sid}/state/revert`) stays a separate action.
§2.4 defines how it composes with a live v2 request.

### 1e. What this means for the design

1. The v1 async-operation protocol is complete and is the base. V2 is a
   schema and an authority with no route, no setting, no worker and no
   client. The protocol units build the route and client layers. They do
   not rework admission, hashing or replay.
2. Three server defects must be fixed before any v2 row can exist outside a
   test: the v1-only projection (S10), the v1-only cancel (S11) and the
   v1-only settlement (S13). S11 and S13 belong to the runtime units. S10
   belongs to U-41.
3. Resume across replicas needs no new storage. The parent row's
   `status_revision` is SQL-authoritative and already monotonic where it is
   written. It must be written on every parent transition (S15), which §2.6
   requires of the runtime.

## 2. C6 — continuation control (U-40)

### 2.1 Scope and invariants

U-40 owns two things. The first is the model-facing continuation control:
the `checkpoint_and_continue` tool and the v2 Advisor follow-through that
decides whether a request keeps going. The second is the semantics of human
Stop: what it means, when it settles and what it records. U-41 carries Stop
over HTTP and U-42 renders it. The runtime units execute yields, successors
and recovery.

Four invariants hold for every C6 change. A test pins each one (§5).

- **I-1. The provider authors every continuation.** The host never derives
  the next action, a graph argument or a "resume prompt" server-side. A
  successor segment replays the retained frame stack and calls the provider
  through the normal compose path. A `primary_turn` prescribed action carries
  model-authored text. A `read_tool` action names a currently permitted
  read-only tool with model-authored JSON arguments. Graph and mutation
  arguments always go through normal primary authoring and tool admission
  (AGENTS.md:333–345). No path sets `provider="server"` (A9 count stays 1).
- **I-2. No tutorial branch.** The tool, palettes, Stop and every refusal are
  the same for tutorial and freeform sessions. 0 occurrences of a tutorial
  predicate in any file U-40 touches; §5 adds the grep as a case.
- **I-3. Human Stop bypasses model adjudication.** Stop never waits for, asks
  or is vetoed by the Advisor or the provider.
- **I-4. Progress is evidence, not prose.** Notes passed to
  `checkpoint_and_continue`, renamed labels, timers and scheduling receipts
  never certify progress. This is the original plan's frontier rule, kept
  unchanged. Its implementation is `continuation_progress.py` (§1 K3).

### 2.2 Continue: the `checkpoint_and_continue` tool

| Property | Design |
|---|---|
| Palette | Only the v2 compose palettes carry it. The v1 palette never does (a v1 job has no segment to yield). `provider_gateway.py:composer_loop_tool_definitions` (`:394`) gains a lifecycle parameter. Recovery-only and continuation-only palettes stay distinct, as the original plan requires. |
| Arguments | Closed schema: `{"notes": string}` optional, 1..500 UTF-8 bytes, strict extra-field refusal. Registered through the existing strict dialect owner, not the synchronous tool registry. |
| Batch rule | It must be the only tool call in its batch. A mixed batch is refused before any mutation with `error_code="CONTINUATION_CALL_NOT_ALONE"`, modelled on `TERMINAL_CALL_NOT_ALONE` (`error_codes.py:35`). The new code is registered in `_EMITTED_VALIDATION_ERROR_CODES` (pinned by `tests/unit/web/composer/test_error_code_redaction.py`). |
| Duplicate | A second call in the same segment returns the same tool result and schedules nothing new. |
| Effect | Asks the runtime to yield the current segment at its next boundary. The runtime's closed `ContinuationYieldReason` is `quantum`, `watermark`, `action_fit`, `slice_limit` or `shutdown` (runtime design §2.1); this design asks it to add `model_request` (§2.7 R9). The tool itself writes nothing; the runtime's yield transaction owns the checkpoint and successor. |
| Tool result | Confirms that a checkpoint was requested and that the current step ends at its next boundary. It does not say a successor is queued, because the yield commits after the tool returns, and it never says one ran. No wake time. Text is a constant registered with the other tool-result strings. |
| Refusals | `CONTINUATION_UNAVAILABLE` when the operation is v1, when Stop is pending, or when the runtime refuses to mint a successor (for example `rollover_reason` budget exhausted per the U-38 policy). | Host rollover | The runtime yields without the tool for its own reasons (`quantum`, `watermark`, `action_fit`, `slice_limit`, `shutdown`). That needs no model call and no tool result. |

The v2 Advisor follow-through keeps the original plan's design unchanged
(`c095251c1` plan § "Progress, stop scope and human controls"): the closed
`ContinuationAdvisorDecision` (`advisor_output.py:322–344`) with `CONTINUE`,
`CONTINUE_WITH_LIMITATION` or `STOP_CONFIRMED`, `subset` or `whole_request`
scope, and the frontier and receipt rules in `continuation_progress.py`. U-40
wires them into the turn path. A model `STOP_CONFIRMED` is a model verdict
that leads to a normal completed or failed settlement. It is not a human Stop
and never writes `cancel_requested_at`.

### 2.3 Stop: state machine

**The durable marker** is `composer_async_operations.cancel_requested_at`,
written once, in database time, under `locked_session_transaction`. Every
replica reads the same marker. The local `signal_local_cancel`
(`operations.py:290`) stays as a latency hint only.

**Parent states** as the protocol sees them (status / phase, from the v2
CHECK bundle):

| State | status / phase | Running segment? |
|---|---|---|
| `Q` | `queued` / `queued` | no (segment 1 `queued`, possibly claimed and not started) |
| `X` | `running` / `executing` | yes (`running`) |
| `CQ` | `running` / `continuation_queued` | no (predecessor `yielded`, successor `queued`) |
| `RW` | `running` / `retry_waiting` | no (segment `queued` with `next_eligible_at` in the future, or `interrupted` after a runtime handover) |
| `RC` | `running` / `reconciling` | no live owner (segment `interrupted`; any replica may **claim** it, `composer_operation_authority.py:130–131`) |
| `DONE` | `completed` / `settled` | — |
| `FAIL` | `failed` / `settled` | — |

This table is design, not a record of current writes. It combines what the
overlay writes with the runtime design's handover transition (runtime §2.1).
The runtime owns the final status and phase mapping.

**Transitions driven by Stop:**

| # | From | Event | To | Transaction | HTTP reply |
|---|---|---|---|---|---|
| ST-1 | `Q`, `CQ`, `RW`, `RC` (current segment `queued` or `interrupted`) | Stop | same state with the marker set; then `FAIL` (`request_cancelled`) when the next claimer settles it | Set the marker, advance `status_revision`, and make the current queued or interrupted segment eligible now (§2.7 A2). The next worker that claims and starts the segment settles it through the owner terminal path, which keeps one settlement owner (runtime design §2.7). **Latency:** one scan interval for an unclaimed segment. If a claimant holds an unexpired claim and has not started, settlement waits for that claimant's start, or, if it dies first, for its claim to expire (claim lease default 30 s, `config.py:403`). Eligibility cannot override a live claim (`composer_operation_authority.py:186–187`). | 202, live snapshot, `cancel_requested=true` |
| ST-2 | `X` | Stop | `X` with the marker set | Set the marker and `status_revision += 1`. The owner settles at its next boundary (ST-4). | 202, live snapshot, `cancel_requested=true` |
| ST-3 | — | — | — | Merged into ST-1. An interrupted segment is claimed, not recovered again: recovery accepts only a `running` segment (`coordination/repository.py:5067`). | — |
| ST-4 | `X` + marker | owner reaches a boundary: claim, resume, action admission, pre-dispatch, effect commit, yield, final completion (`sessions/continuation.py:188` refuses new work) | `FAIL` (`request_cancelled`, `settled_by="owner_terminal"`) | Owner terminal transaction. | ST-6 | `DONE`, `FAIL` | Stop | unchanged | Read only. A completed request is never cancelled after the fact. | 200, terminal snapshot |
| ST-7 | `X` | Stop and the final completion race | `DONE` or `FAIL` | Session transaction order decides. If completion commits first, the parent is `DONE` and the later Stop is ST-6. **What Stop does to work in flight.** Stop admits no new work after the
marker, with one exception: owed P4 retention of an effect issued before
Stop (§1 S12). A provider call already inside the SDK is the runtime's to
handle. The runtime design's v2 watcher reacts to Stop as v1 does (runtime
§3.3), and v1 cancels the owner task (`composer_async_worker.py:943–945`),
so the call is abandoned and its effect stays `dispatched` for the
runtime's physical-accounting reconciliation (runtime §3.4). §7 Q2 asks
whether to keep that or wait for the call. The protocol is the same either
way. Stop does not undo effects already committed: graph revisions saved
before the stop stay saved. The failure outcome already reports them through
`saved_revisions` (`types/composerOperations.ts:19–24`), and U-42's copy says
so (§4.2).

**Stop latency.** The acknowledgement is immediate (one session-locked
write). Settlement takes until the owner's next boundary (ST-4) or the next
claim (ST-1). U-42 shows "Stopping" until the terminal arrives.

**Stop that cannot be persisted.** If the marker write fails, nothing is
recorded and the route answers 503 through the existing application database
error mapping (no new code; U-18 F1 owns the `database_unavailable` label).
The client keeps its Stop intent in custody (`requestComposerStop`, already
persisted in `sessionStorage`) and retries the cancel with backoff until it
gets a 200 or 202 (§4.3).

### 2.4 Revert while a request is live

The landing code already refuses every other session operation while a v2
parent is active: `_advance_exclusive_fence_on_connection` raises
`SessionOperationConflictError` for any kind but the owning compose
(`coordination/repository.py:4950–4961`). This holds between segments, when
the session fence itself is released. Revert is therefore refused while a
request is live, for both lifecycles.

This design keeps that refusal. To revert, the user stops the request and
then reverts. The original plan instead had Revert admission cancel the
logical request inside the same exclusion domain. That needs one transaction
spanning the composer authority and the revert receipt authority, and a
"stopped, then revert failed" report. §7 Q1 asks whether to build it. The
refusal must reach the user at the top level (§4.2).

### 2.5 Authority checks and refusal codes

Every control route keeps today's order: `require_pipeline_user`, then
`_verify_session_ownership` (non-disclosing 404 `Session not found`), then
the row's `actor_user_id` must equal the caller (non-disclosing 404
`Operation not found`), all with `Cache-Control: no-store`. The authority
re-checks owner, provider type and archive state inside the locked

operation's actor may stop it, and an administrator cannot stop another
user's request through this route.

The three new HTTP error types are route refusals raised before any mutation.
They are not terminal failure categories, so they do **not** join
`ComposerOperationPublicFailureType` or `COMPOSER_OPERATION_PUBLIC_FAILURE_TYPES`
(`sessions/composer_operations.py:128`, `:141`), nor the frontend decoder's

`composer_mutation_authority_revoked` did in the overlay. Terminal projection
parity (`tests/unit/web/sessions/test_composer_operation_error_parity.py`)
is unchanged because Stop keeps `request_cancelled`. The client already
treats all three as definitive (`client.ts:1012–1021`). The two tool
codes join `_EMITTED_VALIDATION_ERROR_CODES`.

## 3. C7 — the v2 HTTP/SSE contract (U-41)

### 3.1 Design decisions

| # | Decision | Why |
|---|---|---|
| D-1 | The request header selects the lifecycle **only at admission**. For GET, cancel and stream, the stored row's `lifecycle_version` selects the projection, and the header only selects which projections the client can read. | A row has one lifecycle forever. Dispatching on the header would let a v1 reader reach `legacy_deadline_at` on a v2 row (§1 S10). |
| D-2 | On replay of an existing operation id, the **row's lifecycle is the version of record**. Admission computes the request hash for the existing row's lifecycle and compares that. A byte-identical body replays the existing row and echoes its version, whatever the header says. A different body is still `composer_operation_conflict`. | This closes a real race: an operator turns v2 off (or on) between an ambiguous POST and its retry, and without D-2 the retry is a 409 conflict and the user loses the send. It also covers a later same-epoch release whose replicas roll with different gate settings. The 0.8.9 → 0.8.10 upgrade is not such a case, because the epoch cut means old and new replicas never share a store (§3.10). This departs from the original plan, which returned 409 on any lifecycle difference. No second admission ever happens under D-2, so the plan's rule against automatic retry under another lifecycle still holds. |
| D-3 | **Custody records the echoed version, not the requested one.** A missing echo means 1. | An old server ignores the header, so only the echo says what was admitted. |
| D-4 | **Resume is state transfer, not event replay.** Every v2 status frame is a complete snapshot, and the SSE `id:` is the parent's `status_revision`. Any replica can serve any reconnect from SQL. Nothing is buffered per replica. | `status_revision` is SQL-authoritative (§1 S15, §2.7 R4). The private journal is not exposed: its tags and cardinality describe tool and provider internals. |
| D-5 | v2 status frames are sent **on change**, not every second, plus a heartbeat. | The v1 generator sends a full frame and runs live re-authorization every second per subscriber (`operations.py:370–381`, `composer_stream.py:218`). In an idle phase that is ten status frames per 10 s in v1 against one heartbeat in v2 (from reading the code; not measured, see case L-1). The 1 s database poll stays. **Wrapper change:** `BoundedComposerStreamResponse` bounds each generator read to 2 s and closes the stream when a read takes longer (`composer_stream.py:189–205`). The v2 generator therefore yields an empty tick after every poll, and the wrapper treats an empty tick as a completed read with nothing to send: no authorization, no send, read deadline reset. v1 never yields a tick, so its behaviour is unchanged. |
| D-6 | Terminal frames carry no `result` or `error`. The client fetches the terminal snapshot with GET. | `MessageWithStateResponse` carries a composition state, which can exceed the 64 KiB frame bound (§3.8). v1 already works this way (`schemas.py:799–800`). |
| D-7 | A v2-capable client selects its admission version from `/api/system/status`. There is no mid-operation downgrade and no fallback POST. | The server feature gate is the only authority. A 409 `composer_continuation_disabled` keeps the draft and refreshes the status, so the next send uses v1 (§3.5). |
| D-8 | U-41 adds `GET /api/sessions/{sid}/operations/active`. | Progress snapshots do carry `operation_id`, but only while a worker publishes them (§1 T7). Between v2 segments a tab or device without custody has no durable way to find the request. The endpoint reads the parent row, so it answers in every phase. |

### 3.2 Negotiation

- **Request header:** `Composer-Operation-Version: 1` or `2`. Surrounding
  whitespace is stripped; any other value is a 406 with
  `composer_operation_version_unsupported` and no side effect. A missing
  header means 1 (A8).
- **Response header:** every response from the five operation routes
  (`POST /messages`, `POST /recompose`, `GET /operations/{oid}`,
  `POST /operations/{oid}/cancel`, `GET /operations/{oid}/stream`) carries
  `Composer-Operation-Version: <version of the projection in the body>`,
  including refusals. The failure-history route (`GET /operations`) is
  lifecycle-neutral and unchanged.
- **Server gate:** `WebSettings.composer_continuation_enabled: bool = False`.
  v2 is admitted only when the header is 2, the flag is true and the U-38
  production policy is constructed (`app.py:2316` gains
  `continuation_policy=`). With the flag true and no policy, startup
  refuses, so a half-configured server cannot start.
- **Advertisement:** `/api/system/status` (`app.py:2817`) gains
  `composer_operation_admission_version: 1 | 2`, equal to 2 exactly when
  the gate admits v2. The frontend `SystemStatus` type adds it as optional;
  missing means 1.
- **Single client choke point:** the header is set in `submitComposerOperation`
  (`client.ts:1026`), the only function both compose POSTs pass through,
  from the custody descriptor's version. GET, cancel and stream send
  `Composer-Operation-Version: 2` from a v2-capable client, meaning "I can
  read 2". No caller passes a version. The tutorial's `composer.sendMessage`
  (§1 F8) therefore negotiates exactly as freeform does; §5 case A9-T pins it.

### 3.3 Routes by row lifecycle and header

| Route | Row | Header | Response |
|---|---|---|---|
| POST admit | new | missing or 1 | Existing v1 admission and 202 ACK, echo 1. Bytes of the body unchanged. |
| POST admit | new | 2, gate on | v2 admission, 202 `ComposerOperationSnapshotV2` ACK, echo 2. |
| POST admit | new | 2, gate off | 409 `composer_continuation_disabled` (exists), no row, no quota; echo 1. |
| POST admit | existing | any | D-2 replay: the identical body replays the existing row, 202, echo the row's version, provided the header says the client can read that version (header 2 reads both; header 1 or none reads only v1). A v2 row replayed with header 1 or none is 409 `composer_operation_version_required`, as for GET. A different body is 409 `composer_operation_conflict`. |
| GET / stream | v1 | any valid | Existing v1 contract, echo 1. A v2-capable client dispatches on the echo to its v1 decoder. |
| GET / stream | v2 | 2 | v2 snapshot or v2 stream, echo 2. |
| GET / stream | v2 | missing or 1 | 409 `composer_operation_version_required`, body `{"detail": {"error_type": ..., "required_version": 2, "operation_id": ...}}`, before any SSE byte; echo 1. |
| cancel | v1 | any valid | Existing v1 behaviour, echo 1. |
| cancel | v2 | 2 | Stop per §2.3, v2 snapshot (202 live, 200 terminal), echo 2. |
| cancel | v2 | missing or 1 | Stop is **persisted** per §2.3, then a v1-shaped acknowledgement: terminal rows project `status` and the sealed `result` or `error`, with `deadline_at` = `settled_at` and `deadline_remaining_ms=0` (the v1 projector cannot be reused, because it reads `legacy_deadline_at`, `operations.py:83`); live rows project `status` from the parent, `cancel_requested=true`, `deadline_at` = the cancel transaction's database time and `deadline_remaining_ms=0`. The old observer after a v1-shaped live cancel ACK sets `stop=false`
(`composerOperationObserver.ts:135`), then its GET receives the 409, which
is definitive (`client.ts:1012–1021`), and observation ends with Stop
persisted. Pending custody stays for a v2-capable reader to settle from the
real terminal. §5 case M-3 pins that exact sequence.

`GET /operations/active` returns 200
`{"operation_id", "kind", "lifecycle_version", "status"}` for the session's
single live operation of the caller, or 204 when there is none. It is
declared before `/{operation_id}` so FastAPI does not parse `active` as a
UUID. Same ownership checks and `no-store` as T1.

### 3.4 Shapes

Two closed models (strict, extra fields forbidden). **`ComposerOperationStatusV2`**
is the SSE `status` payload and has every field below except `result` and
`error`. **`ComposerOperationSnapshotV2`** is the POST ACK, GET and cancel
body: the same fields plus `result` and `error`. Keeping them separate means
no model carries a field whose presence depends on the transport.

| Field | Type and rule |
|---|---|
| `protocol_version` | `Literal[2]` |
| `operation_id`, `kind` | canonical UUID; `compose_message` or `compose_recompose` |
| `status` | `queued`, `running`, `completed`, `failed`. A stopped request is `failed` with `request_cancelled`. |
| `phase` | v2 parent phase. Live statuses take one of the five active phases; terminal statuses take `settled`. |
| `status_revision` | integer ≥ 0, from the parent row; never advanced by GET, heartbeat or progress |
| `created_at`, `observed_at` | aware datetimes: parent creation, and the database time of this projection |
| `poll_after_ms` | `composer_async_poll_after_ms`, 100..60000 (unchanged bound) |
| `cancel_requested` | from `cancel_requested_at`; always `false` when `completed` |
| `segment` | non-null while live, null when terminal: `sequence` ≥ 1, `generation` ≥ 1, `state` (`queued`, `running`, `interrupted`), `deadline_at` (non-null only when `running`) |
| `result`, `error` | snapshot only. Both null while live. A terminal snapshot carries exactly one: the existing `MessageWithStateResponse` or `ComposerOperationError`. |

There is no `deadline_remaining_ms` in v2. The client derives remaining
segment time from `deadline_at - observed_at`. There is no total deadline:
a v2 request ends by settlement, not by wall-clock expiry. No claim token,
lease token, fence id, checkpoint id or journal cursor appears in any
projection.

**SSE v2 frames** (closed union, `schema_version="composer-operation-stream.v2"`,
common `session_id`, `operation_id`, `sequence` per subscription, `event`):

| `event` | `id:` line | Payload | Sent when |
|---|---|---|---|
| `status` | `status_revision` | `ComposerOperationStatusV2` | first frame of every connection; then whenever the polled `status_revision` changes |
| `progress` | none | `ComposerOperationProgressV2`: `request_id`, `phase`, `headline`, `evidence`, `likely_next`, `reason`, `updated_at` with the v1 bounds (`schemas.py:803–828`), plus `segment_sequence` and `segment_generation`. It omits v1's `session_operation_id`, `session_operation_epoch` and `request_token`. | the progress registry entry for the current segment's fence changes |
| `heartbeat` | none | none | 10 s without another frame |
| `terminal` | `status_revision` | `{status, phase, status_revision}` | the parent is settled; the stream then ends |
| `reconnect` | none | none | the server is about to end a live stream for its lifetime or because the instance is draining (`instance_draining`, set at SIGTERM by U-37); the client reconnects at once with no backoff. This is the drain frame the runtime design §3.2 assigns to U-41. |

Progress binding keeps the v1 rule (`operations.py:324–336`) on the server:
a progress frame is sent only while the segment's `session_operation_id`,
epoch and request token still match, and live re-authorization runs before
every frame. Those identifiers stay server-side in v2. The v1 progress
frame already exposes them; that existing contract is unchanged.

### 3.5 Client selection and fallback

1. On load and after each `composer_continuation_disabled` refusal, the
   client reads `composer_operation_admission_version`.
2. A new submission's custody takes that value as its *requested* version.
   After the 202 its custody takes the *echoed* version (D-3).
3. A 409 `composer_continuation_disabled` is definitive with no row. The
   draft stays in the input, the status is refreshed, and the chat shows
   the copy in §4.2. The client does not resend by itself.
4. A reloaded custody record keeps its version. A pre-upgrade record has
   no version field and hydrates as 1 (§1 F4).
5. Observation dispatches on the echoed header of each GET and stream
   response, so one client reads both lifecycles.

### 3.6 Resume: `Last-Event-ID` and reconnect

- The client keeps the highest `status_revision` it has accepted for the
  operation and sends it as `Last-Event-ID` on every stream reconnect.
  It is sent by `fetch` (the stream needs an `Authorization` header, so
  `EventSource` is not used).
- The server validates it: 1–19 ASCII digits, value ≤ 2^63−1. A malformed
  value is a 422 with `composer_operation_resume_token_invalid` before any
  SSE byte. The server always sends the current `status` first, whatever
  the value. The value is recorded on the existing `composer_stream`
  structlog line as `resumed_from_revision`, so reconnect behaviour across
  replicas can be read from ECS and ACA logs.
- The client accepts a snapshot only if its revision is greater than the
  highest accepted. An equal revision is a duplicate and is ignored. A
  smaller one is stale and ignored. An equal revision with different
  `phase`, segment or `cancel_requested` is a protocol error: the client
  stops trusting the stream and reads the GET.
- `sequence` orders frames within one connection only. The client resets
  its per-connection sequence to −1 on every connect.
- The revision rules apply to state, not to the sealed result. After a
  `terminal` frame the client reads the GET for its `result` or `error`
  even though that GET carries the same revision. `observed_at` and the
  derived remaining time are not compared.

**Why this survives a replica change.** Admission, the parent, segments,
the progress registry (PostgreSQL, `app.py:2342`) and the authentication
token are all independent of the replica. Only `ComposerStreamPermits` is
per-process, and a new replica has its own budget. The SQLite progress
registry is in-process, but SQLite is refused on ACA
(`workload.bicep:295`, external PostgreSQL contract) and ECS uses Aurora.
Sticky sessions are neither needed nor assumed.

### 3.7 Stream lifetime, shutdown and the replica that goes away

| Event | Server | Client |
|---|---|---|
| Lifetime reached (120 s) | sends `reconnect`, then ends | reconnects at once with `Last-Event-ID` |
| Idle (no frame for 25 s) | — | closes and reconnects |
| 503 stream capacity (`Retry-After: 5`) | refuses before headers | polls the GET at `poll_after_ms` until `Retry-After` passes, then retries the stream |
| Replica receives SIGTERM | sees `instance_draining` on its next poll iteration (a 1 s sleep after that iteration's reads and sends; not measured), sends `reconnect`, ends | reconnects at once; the ingress routes it to a live replica |
| Stream ends with no `reconnect` or `terminal` | — | treated as a failure: reconnect with backoff |
| Two consecutive failed connects | — | one GET between attempts; backoff 1, 2, 4, 8 s (cap 8 s, the observer's existing schedule) |
| Terminal frame | ends | one GET for the result, then settles custody |

**Shutdown coupling (read from source, not run; affects U-37).** `elspeth web` starts uvicorn
without `timeout_graceful_shutdown` (`cli.py:5292`). In uvicorn 0.46.0
`Server.shutdown` (`uvicorn/server.py:271–301`) waits for every open
connection with no timeout, and an in-progress response only loses
keep-alive (`protocols/http/h11_impl.py:340–349`). Lifespan shutdown, which
holds `web_instance_membership.begin_drain` and
`composer_async_worker.stop` (`app.py:1214`, `:1221`), runs only after
that wait. So any open stream holds off the worker's drain and yield for
up to the 120 s stream lifetime, past both SIGKILL deadlines (ECS 30 s,
ACA 60 s). This already applies to v1. The fix is an explicit
`timeout_graceful_shutdown` from a validated setting, so streams are
cancelled and lifespan shutdown starts in bounded time. The runtime design
adopts this from the peer container-grace spec as its R1: U-37 sets
`instance_draining` at SIGTERM and bounds the HTTP drain with a new
`web_http_drain_seconds` setting (default 5) through a uvicorn `Server`
subclass (runtime design §3.1–§3.2). U-41's part is the `reconnect` frame
and the stream's drain check. Case R-SIG (§5) proves the pair.

### 4.3 Reconnect behaviour as the user sees it

- A lifetime close or replica change is designed to cost one reconnect
  (a target, not measured; case P-5 records it). Nothing visible changes; elapsed time continues from the
  snapshot's `created_at`, so it survives reload and replica change.
- Segment `deadline_at` passing triggers one GET. It never ends observation,
  never shows an error and never resubmits.
- An auth change (sign-out, another principal) detaches observation, as
  today. The request keeps running on the server.
- Stop intent survives reload: it is in `sessionStorage` already
  (`composerOperationCustody.ts:80`). On reload with a pending Stop the
  client resends the cancel before reading the stream.

### 4.4 Accessibility

- One polite live region. Its text changes only when the label or headline
  changes, so a revision bump with the same phase announces nothing. The
  elapsed readout stays `aria-hidden` (existing).
- The successor notice uses that region. It takes no focus and adds no
  transcript row.
- While Stop is pending the button keeps focus and takes
  `aria-disabled="true"` with the label "Stopping" instead of the
  `disabled` attribute, so keyboard and screen-reader users keep their
  place and hear the state. A second activation is a no-op.
- The pulse dot falls back to a static dimmed mark under
  `prefers-reduced-motion: reduce`. All colour comes from existing tokens,
  and any new custom property is defined in a barrel stylesheet (CSS barrel
  gate). The forced-colors block stays the single canonical block in
  `styles/themes.css`.
- Stop keeps the 36 px compact chrome-row target size it has today.

### 4.5 Client structure

- `types/composerOperations.ts`: `protocolVersion: 1 | 2` on both custody
  kinds (optional on read, default 1); `ComposerOperationSnapshotV2` and the
  v2 frame union beside the v1 types.
- New `api/composerOperationDecoderV2.ts`: strict v2 snapshot and frame
  decoding, and an SSE decoder that admits `id:` in addition to `event:`
  and `data:`. The v1 decoder is not changed and keeps rejecting `id:`.
- New `api/composerOperationObserverV2.ts`: the loop in §3.5–§3.7. It shares
  submission, custody and Stop with v1. `observeComposerOperation`
  dispatches on the custody version and the response echo. The v1 loop is
  unchanged, which keeps A8's v1 suites comparable.
- `api/client.ts`: the header in `submitComposerOperation`, a version
  argument on GET, cancel and stream, and `fetchActiveComposerOperation`.
- `stores/sessionStore.ts`: attach through the active endpoint on session
  open; the disabled-refusal path.

## 7. Open questions for the maintainer

Everything else in this note is decided. These are genuine trade-offs.

- **Q1. Should Revert stop a live request by itself?** This design refuses
  Revert while a request is live, which is the landing code's behaviour,
  so the user stops first and then reverts (§2.4). The alternative is the
  original plan's: Revert admission stops the request and reverts in one
  exclusion domain. That saves one click, but costs a transaction spanning
  two authorities and a new "stopped, then the revert failed" outcome.
  Default if unanswered: refuse.
- **Q2. Should Stop abandon a provider call already in flight?** The
  runtime design's v2 watcher cancels the owner task on Stop, as v1 does
  (§2.3), so Stop is fast, but the call's cost is still incurred and its
  effect is left `dispatched` for reconciliation. The alternative waits for
  the call to return before settling, which keeps the outcome exact but can
  hold "Stopping" for as long as that call's timeout. The protocol and UI
  are the same either way. Default if unanswered: the runtime design's
  behaviour (abandon and reconcile).
