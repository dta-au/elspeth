### 1.4 Successor-action selection

`next_continuation_action_policy` (`composer/continuation_next_action.py:18–277`)
sizes the next segment from the retained snapshot. It admits exactly these cuts
and raises `AuditIntegrityError` for anything else:

1. `InitializeFrame` at `title_pending` with the TITLE effect prepared, dispatched or committed (`:28–73`).
2. `InitializeFrame` at `ready` with the TITLE applied (`:74–98`).
3. `InitializeFrame` at `reserved`/`inserted`, and published `title_pending`/`ready` bootstrap cuts (`:99–138`).
4. **The first** `ComposeFrame` at `action_ready`: every slice, total and counter must be zero (`:139–178`).
5. `ComposeFrame` at `response_retained` with a committed primary effect (`:179–201`).
6. Four `ToolBatchFrame` cuts: attachment read pending or retained, attachment application complete, P4 pending or applied (`:202–277`).

`ContinuationFrameStack.is_handoff_safe` (`composer/continuation.py:237–249`)
defines the safe cut for a handoff: no pending settlement or owner result, no
`dispatched`/`unknown` effect, and a top frame at Initialize `ready`, Compose
`action_ready`, ToolBatch `tool_ready`, Advisor `input_ready` or any End phase.
Its only callers are tests (`test_continuation_frames.py:71–76, 214`,
`test_continuation_response.py:183`). **Verdict: partial.** The two sets do not
agree. Handoff-safe Compose `action_ready` after the first iteration, Advisor
`input_ready`, End and most ToolBatch `tool_ready` cuts are not sizeable, so a
yield at any of them would roll back (§2.4).

## 2. U-35b: the yield and atomic checkpoint+successor API

### 2.1 Shape

Five SQL transitions, each one locked session transaction. Names follow Sol's
storage plan (`…-storage.md:2805–3130`) wherever that draft exists.

| Transition | Public method (transaction owner) | Connection body (`sessions/continuation.py`) | Effect |
| --- | --- | --- | --- |
| **Yield** (handoff at a safe cut) | `commit_checkpoint_and_successor` on `_SessionOperationAuthorityRepository` (`repository.py`, beside `start_composer_segment`), declared on `SessionOperationAuthority` (`sessions/protocol.py:2437`) | `yield_segment_on_connection` | Handoff checkpoint, predecessor `yielded`, one queued successor at `(sequence + 1, generation + 1)`, parent pointer advanced, **fence released** |
| **Handover** (live owner gives up a recoverable but not handoff-safe cut) | `suspend_composer_segment` (same class) | `suspend_segment_on_connection` | Same sequence, generation + 1, segment `interrupted`, parent `reconciling` or `retry_waiting`, **fence released** |
| **Terminal** | `settle_composer_operation_on_connection` gains a V2 branch | `settle_continuation_on_connection` | Segment and attempt `settled`, parent `completed`/`failed` with `phase = 'settled'` |
| **Pre-start claim renew / release** | existing `renew_claim` / `release_claim` gain a V2 branch | (inline; already bound) | Segment claim expiry extended / cleared |
| **Read-back** | `read_yield_outcome`, `verify_recovery` | `verify_yield_on_connection`, `verify_recovery_on_connection` | Read only |

**Why the repository and not `ComposerAsyncOperationAuthority`.** The yield
must release the fence in the same transaction as the handoff checkpoint
(peer R2: a peer claims immediately, without waiting for lease expiry).
`session_operation_fences` belongs to `SessionOperationAuthority` (gate
`:217`). The only existing transactions that cross both authorities are
`start_composer_segment` and `recover_composer_segment` in
`_SessionOperationAuthorityRepository`. Sol's draft put the wrapper on
`ComposerAsyncOperationAuthority` with `locked_session_transaction`, which
cannot release the fence without duplicating fence DML under the wrong
authority. Under rule R-G the repository method orchestrates: fence DML goes in
a new private helper `_release_fence_on_connection` factored out of `release`
(`repository.py:6086–6097`, the same UPDATE under `_exact_active_predicates`),
and the continuation DML goes in the bound connection bodies.

### 2.2 Yield transaction, step by step

Signature (Sol's draft, with `reason` added and the action arguments removed):

```python
def commit_checkpoint_and_successor(
    self, running: ComposerOperationRunning, *, expected_head: UUID | None,
    expected_checkpoint_id: str, expected_cursor: int, snapshot_json: str,
    reason: ContinuationYieldReason,
) -> ComposerSegmentYieldReceipt: ...
```

`ContinuationYieldReason = Literal["quantum", "watermark", "action_fit",
"slice_limit", "shutdown"]` lives in the new pure module
`composer/continuation_handoff.py`. It is written to `rollover_reason`, which
has no CHECK (`models.py:3800`), so the vocabulary is enforced in Python.

All steps run on one connection under `self._locked_transaction(session_id)`,
with one `now = self._database_now(conn)` used for every written time.

The yielded event payload mirrors the `recovered` payload
(`repository.py:5113–5123`) and the `ContinuationControlHandoff` identity rule:
`{"version": 2, "reason", "predecessor_sequence", "predecessor_generation",
"successor_sequence", "successor_generation"}`, encoded with `canonical_json`
from a closed pydantic model in `continuation_handoff.py`.

**The successor is claimable at commit.** After step 11 the claim predicate
(`composer_operation_authority.py:134–188`) holds for the successor: the fence
is released (first arm of `available_fence`), the parent's sequence,
generation and checkpoint equal the successor's, the successor is `queued` with
`next_eligible_at = now` and no claim. Any replica, including the yielding one,
can claim it on its next scan.

**Why `allow_expired_segment=True`.** The segment hard deadline bounds action
admission. A yield admits no action and only reduces ownership. Refusing it
past the deadline would force the operation into lease-expiry recovery for no
safety gain. Cancellation is not allowed (`allow_cancel=False`): Stop wins over
yield, and the caller settles `request_cancelled` instead (§2.7).

**Defects in Sol's draft that this fixes** (the draft was written before
`recover_composer_segment` landed):

1. No slice roll. The successor's runtime read refuses unless
   `ComposeFrame.slice_sequence` equals the claimed sequence
   (`sessions/continuation_runtime.py:97–98`), so every successor would fail
   at start. Step 4 fixes it.
2. Caller-supplied `next_action_json` and `policy_sha256` without validation.
   The start would re-derive and refuse a wrong action
   (`sessions/continuation.py:645–651`) after the predecessor had already
   released, wedging the operation. Step 6 derives the action inside the
   transaction, as `recover_composer_segment` does.
3. No fence release. Step 11.
4. Identity-free event payload (`'{"version":2}'`). Fixed above.
5. `require_continuation_mutation` with the default `allow_expired_segment=False`.
6. The read-back required the successor to still be `queued` and the parent
   to still be `continuation_queued`. With the fence released at commit, a
   peer can start the successor before the yielder reads back, so a correct
   yield would fail verification. §2.3 fixes the read-back.
7. Rule R-G: the draft's wrapper sat under one authority and wrote both
   authorities' tables.

### 2.3 Fencing tokens, idempotency and read-back

**Fencing.** A yield is admitted only by the full current-owner tuple: fence
`(operation_id, lease_token, operation_epoch, kind = COMPOSE)` live; segment
`claim_token`; parent `attempt`; `(sequence, generation)`; snapshot
`(checkpoint_id, journal_cursor)`. Any stale element refuses before the first
write (steps 0–3) or makes a CAS miss that rolls the transaction back (steps
5–11). After commit, the predecessor's fence is released and its attempt
revoked, so a late write from that generation fails
`require_continuation_mutation` (no live attempt for its epoch) and the
fence's exact-active predicates.

**Idempotency key.** The natural key `(session_id, operation_id,
predecessor_sequence, predecessor_generation)`. No client token is needed: only
the owning worker can call this, and the key is enforced three ways: the
attempt's `revoked_at IS NULL` predicate, `uq_composer_segments_successor`,
and the parent CAS. A second call with the same `running` refuses with
`ComposerOperationFenceLost` and writes nothing.

**Ambiguous commit.** If the commit's outcome is unknown (connection lost after
`COMMIT` was sent), the caller never retries the yield. It calls
`read_yield_outcome(running) -> ComposerSegmentYieldReceipt | None`:

- `None` when the predecessor attempt is still unrevoked and bound to the
  caller's fence: the yield did not commit, and may be retried while the fence
  is live.
- The receipt when the predecessor attempt is `yielded`, the predecessor
  segment is `yielded` at the handoff checkpoint, that checkpoint has
  `kind = 'handoff'`, the event at its cursor is `yielded` with exactly these
  identities, and a successor row exists with `predecessor_sequence = seq` and
  `generation = gen + 1`.
- `AuditIntegrityError` for any other combination, for example the attempt
  revoked with outcome `interrupted`, which means a peer recovered it.

`verify_yield_on_connection` checks the same facts and **tolerates successor
progress**: the successor may be `queued`, `running`, `yielded`, `interrupted`
or `settled`; the parent may have moved to a later sequence or generation, or
be terminal; the snapshot head may be past the handoff checkpoint; the
released fence epoch may have been advanced by the successor's start. It never
compares against the current head.

### 2.5 Composition with the lease object

After step 11 commits, the lease's renewal task would hit `RELEASED`, and
`SessionOperationLease.close()` would try a second release. U-35b adds
`SessionOperationLease.consume_continuation_handoff(action)` to
`coordination/lifecycle.py`, modelled on `consume_archive`
(`lifecycle.py:1351–1440, 1549`):

1. Join owned child tasks; any failure refuses and falls back to an ordinary
   close.
2. Stop and join the renewal task. A recorded renewal error means `LOST`, and
   the handoff is refused.
3. Run `action`, the bound `commit_checkpoint_and_successor` or
   `suspend_composer_segment` call, in the worker pool.
4. On success, set disposition `CONSUMED` (`coordination/contracts.py:68`),
   so `__aexit__` makes no second release.
5. On `SessionOperationFenceLost`/`ComposerOperationFenceLost`, set `LOST`.
   On an unknown completion, set `UNKNOWN` and return to the caller, which
   calls `read_yield_outcome`.

**Lease validity margin.** Once renewal stops, the fence stays valid for at
least `lease − renew_interval` = 30 − 10 = 20 s at today's defaults. The
yield must commit inside that window, else step 1 or 11 refuses and the
operation falls to peer recovery, which is safe. §3.5 bounds the yield far
below 20 s.

## 3. U-37: worker yield, resume and restart

### 3.1 What U-37 adopts from the grace spec

From `0.8.10-continuation-container-grace.md` (peer, `48a308276`), unchanged:

- **R1.** `instance_draining` is set at SIGTERM, not in the lifespan
  `finally`, and the HTTP drain is bounded. Today `uvicorn.run` at
  `cli.py:5292` has no `timeout_graceful_shutdown`, so uvicorn waits without
  bound for open connections, and a Composer stream may stay open for
  `STREAM_LIFETIME_SECONDS = 120.0` (`composer_stream.py:20`).
- **R2.** On drain, a V2 segment at a committed cut writes a durable handoff
  and releases its fence inside the drain budget. It never depends on the
  segment's timing policy.
- **R3.** ECS `stopTimeout = 60` on the web container (proposed diff in the
  spec), ACA stays at 60.
- **R4/R5** are U-39 (§5).

Refinements this design makes, each argued below:

1. The worker drain starts at SIGTERM **concurrently** with the HTTP drain, so
   the budget is `max(H, D) + S + M`, not `H + D + S + M` (§3.5).
2. A live owner at a cut that is recoverable but not handoff-safe **hands
   over** (same sequence, generation + 1, fence released) rather than leaving
   the segment for lease-expiry recovery (§3.4, disposition B).
3. A live owner with an unresolved provider or business effect **settles the
   operation itself** while its fence is still live, through the same SQL body
   a peer uses after expiry (§3.4, disposition C). On ECS, with one task and no
   live peer, this is the fast path: the replacement task otherwise takes about
   150 s to become healthy.

### 3.3 Worker structure

`ComposerAsyncWorker` (`sessions/composer_async_worker.py`) keeps its V1
path byte-for-byte. U-37 adds a V2 path beside it.

- **Claim.** `_claim_once` (`:334–351`) calls `claim_next` (V1) and
  `claim_segment` (V2) and shares one `concurrency` budget. Each V2 claim
  starts `_job_v2(claim)`. V2 stays excluded from `claim_next`,
  `list_expired_queued`, `list_expired_running` and the V1 reaper, which
  already filter on `lifecycle_version == 1`.
- **Pre-start wait.** `_job_v2` reuses the lock-wait loop of `_job`
  (`:476–488`) unchanged. With §2.8's V2 branches, it renews the segment claim
  every `claim_lease_seconds / 3` and releases it on stop or drain, exactly as
  V1 does (`:479–481`).
- **Start and adoption.** `start_composer_segment`, then
  `SessionOperationLease.adopt` with the same failure custody as V1:
  `_adoption_recovery_cancellations`, `started_handoff` and
  `_begin_adoption_failure_custody` (`:498–555`). This is Sol's executable
  review finding E11. An adoption failure after the SQL start settles through
  `suspend_composer_segment(reason="adoption_failed")`, never through the V1
  terminal `_settle_failure`.
- **Driver.** A new module `sessions/continuation_driver.py` holds
  `run_continuation_segment(services, running, lease, observation) ->
  ContinuationSegmentOutcome`. The outcome is a closed sum:
  `ContinuationSegmentYielded(ComposerSegmentYieldReceipt)`,
  `ContinuationSegmentHandedOver(ComposerSegmentRecoveryReceipt)`, or
  `ContinuationSegmentSettled(ComposerOperationRecord)`. The driver restores
  the selected snapshot (`restore_continuation_runtime`,
  `composer/continuation_runtime.py:312`), dispatches the top frame to its
  phase owner (initialization, TITLE, first Compose, primary retention, P4,
  attachments: the owners U-44b and U-45 wire), and loops. The phase table is
  closed: a cut whose owner has not landed raises `AuditIntegrityError` and
  settles `failed`. While V2 is default-off this is reachable only from tests.
  U-40 and U-41 extend the table.
- **Outcome verification.** `_verify_terminal_before_release`
  (`:615–730`) becomes `_verify_outcome_before_release`. It accepts only a
  verified terminal record, a yield receipt checked by `verify_yield`, or a
  recovery receipt checked by `verify_recovery` (Sol C4a). A normal yield
  never calls failure settlement, never publishes an assistant row and never
  clears the request.
- **Stop after drain.** The lifespan calls `stop()` about `H` seconds after
  SIGTERM. Today `stop()` cancels every job at once (`:414–427`), which would
  cut the drain window from `D` to `H`. When `begin_drain()` has run, `stop()`
  first awaits the drain's completion, bounded by the drain deadline
  `t_SIGTERM + D`. Only then does it cancel what is left with
  `COMPOSER_SHUTDOWN` and wait as it does today. Without a prior
  `begin_drain()`, for example on a startup failure, it behaves as today.
- **Watch.** The V2 watcher reacts to lease loss and Stop as V1's `_watch`
  does (`:884–995`). It has no parent deadline. A drained Stop goes to the
  terminal `request_cancelled`, never to a handover (Sol's review E19).

### 3.4 The yield points and the three drain dispositions

The driver checks two conditions **between stages**, never inside one. A stage
is one `ContinuationActionClock.run` call (`continuation_clock.py:146`).

- **Cooperative rollover.** The frozen timing observation
  (`sessions/continuation_runtime.py:117–124`) says `yield_pending`, or
  `admit_action` returns `YIELD` for the next retained action. If the head is
  handoff-safe, the driver yields with reason `quantum`, `watermark` or
  `action_fit`. Otherwise it finishes the current action to the next
  handoff-safe cut first ("finish an already admitted healthy action and then
  yield", Sol plan §Independent time).
- **Drain.** `begin_drain()` sets a per-job drain event. At the next stage
  boundary the driver classifies the durable head with the pure
  `classify_drain_cut(selected) -> Literal["handoff", "handover", "unresolved"]`
  in `continuation_handoff.py`:

| Class | Test | Disposition | SQL |
| --- | --- | --- | --- |
| **A. handoff** | `stack.is_handoff_safe` | yield, reason `shutdown` | `commit_checkpoint_and_successor` (§2.2) |
| **B. handover** | not handoff-safe; no `dispatched`/`unknown` effect; the successor-action selector admits the cut (e.g. Compose `response_retained`, an attachment read retained) | same sequence, generation + 1, `next_eligible_at = now`, parent `reconciling` | `suspend_composer_segment(reason="shutdown", retry_delay_seconds=0)` |
| **C. unresolved** | a `dispatched`/`unknown` effect, or a pending settlement the selector refuses | settle the operation `failed`, `failure_code = 'worker_lost'`, one `effect_unknown` event per unresolved effect | `settle_continuation_on_connection` via the same `settle_lost_continuation` body U-39 uses (§5.3) |

To classify without swallowing real integrity failures, U-35b splits the
selector's refusals. The branches that refuse because a cut holds an
unresolved effect (`continuation_next_action.py:69, 197, 214, 268`) raise a new
`ContinuationCutNotResumable`. Every other refusal stays `AuditIntegrityError`
and still fails loudly. `recover_composer_segment` uses the same split, so U-39
can settle a not-resumable cut instead of crashing (§5.2).

**An in-flight stage at drain.** The driver does not cancel a running stage
when draining begins. It waits for the stage to finish until the cancel
instant `T_cancel` (§3.5). At `T_cancel` it cancels the stage task with
`COMPOSER_SHUTDOWN`, joins the required-work cohort
(`RequiredWorkCoordinator`), and classifies the durable head. A provider call
cancelled after its may-dispatch marker leaves a `dispatched` effect, so it is
class C. Its cost is real and its result is discarded. The alternative, a
retry after custody resolution, is §8 question 1.

**Composer invariants.** None of the three dispositions synthesises a reply,
a graph or a proposal. A successor resumes by calling the provider for its
next retained action. Resuming from a handoff or a handover makes **zero**
provider calls before the successor's first admitted action, and replaying a
retained response makes none (`continuation_next_action.py:198–201`). That
count is U-37's A9 instrument (§6). The driver has no tutorial branch: the
tutorial negotiates V2 exactly as freeform does (U-41's A9 case).

### 3.5 Time budget

Let `G` be the platform grace (ECS `stopTimeout`, ACA
`terminationGracePeriodSeconds`), `H` the HTTP drain, `D`
`composer_async_drain_seconds`, `Y` one disposition transaction, `S`
membership stop and exit, `M` the safety margin.

With R1 in place the HTTP drain and the worker drain both start at SIGTERM:

```text
t = 0            SIGTERM; instance_draining set; no new claims; begin_drain()
t ∈ [0, T_cancel] jobs reach a stage boundary on their own and dispose (A/B/C)
t = T_cancel     remaining stages cancelled; cohorts joined; dispose
t ≤ D            every V2 job disposed; leases consumed or closed
t ≤ max(H, D) + S + M ≤ G
```

`T_cancel = D − Y_budget − 1 s`, with `Y_budget = 2 s`: two sequential
disposition transactions at an assumed ≤ 1 s p99 each, as a disposition may
follow a CAS retry (§2.6). `Y` on PostgreSQL is **not yet measured** (peer
R3). U-37 measures it (§6, `test_yield_transaction_latency_is_recorded_postgres`)
and resizes `Y_budget` from the measured p99 if it exceeds 1 s.

| Setting | Default | ECS (`G = 60` after R3) | ACA (`G = 60`) | ECS without R3 (`G = 30`) |
| --- | --- | --- | --- | --- |
| `H` (`web_http_drain_seconds`) | 5 | 5 | 5 | 5 |
| `D` (`composer_async_drain_seconds`) | 10 | **30** (deploy env) | **30** (deploy env) | 10 |
| `T_cancel` | `D − 3` | 27 | 27 | 7 |
| `max(H, D) + S + M` | 16 | 36 | 36 | 16 |

**The cap `composer_async_drain_seconds ≤ 120`** (`web/config.py:406`) is a
setting bound, not a platform limit. It is harmless at these values. The real
limit is `G`: Fargate's maximum is 120 s; ACA documents none (peer §1).

**Why raise `D` to 30 where `G = 60`.** `D` decides how many in-flight actions
reach a clean cut instead of class C. With `D = 10`, any provider call more
than 7 s from completion at SIGTERM fails its request. With `D = 30`, calls
within 27 s of completion survive. Both stay well inside `G`, and other
shutdown work, such as the executor join (`web/app.py:1226`) that runs after
the composer worker, keeps about 24 s.

**A guard against a mis-declared grace.** U-37 adds `composer_shutdown_grace_seconds`
(default 30, the platform default on both targets). A settings validator
requires `max(H, D) + 1 + 5 ≤ composer_shutdown_grace_seconds`. The ECS module
and the ACA Bicep set it from their real grace values (60). This follows the
`composer_transport_idle_ceiling_seconds` precedent (`web/config.py:382–395`):
the operator declares the infrastructure bound, and a mismatch fails at
startup instead of at the first deploy.

**Lease interplay.** The physical lease keeps renewing every 10 s until a
disposition consumes it (§2.5). After renewal stops, the fence has at least
20 s of validity left, which is far more than `Y_budget`. The pre-start
segment claim keeps renewing every `claim_lease_seconds / 3` until it is
released. Neither period changes.

### 3.6 Resume and restart

A successor (after a yield) and an interrupted generation (after a handover or
a peer recovery) are claimed by the same `claim_segment` path on any replica,
and started by the same `start_composer_segment`. The start re-derives the
retained next action and refuses any substitution
(`sessions/continuation.py:640–651`). It sizes a fresh segment from the
retained policy and the new database time. The successor then gets a full
`size_segment` allowance, a fresh fence epoch and a fresh attempt row.
Nothing in-memory crosses a segment boundary: the cold-restore gate (U-36)
already proves restore under a genuinely new fence.

### 4.3 Versioned persisted payloads

The problem (M): every policy model is `extra="forbid"`, frozen, with every
field required. Adding a field later makes every retained payload fail

Either way the operation can never start again and wedges.

Design, mirroring `ContinuationFrameStack.schema_version`
(`composer/continuation.py:221`):

1. `ContinuationAdmissionPolicy` gains `schema_version:
   Literal["composer.continuation.policy.v1"]` as its first field. It is part
   of `model_dump`, so it is inside `policy_hash`.
2. `decode_continuation_policy` reads the raw strict-JSON object first. A
   missing or unknown `schema_version` raises `AuditIntegrityError`, never
   a default. Then it validates with the model for **that** version and checks
   the hash against that version's bytes.
3. A later change adds a new frozen model `…policy.v2`. The v1 model is never
   edited again. The decoder maps v1 to the current effective policy through a
   pure, total `upgrade_v1(policy) -> ContinuationAdmissionPolicy` that sets
   each new field to its documented v1 meaning. Persisted bytes and the hash
   are never rewritten. Step 2 verifies the original bytes.
4. Standalone action JSON (`segments.next_action_json`, the seed's
   `action_json`) has no tag of its own. It is decoded with the action model
   of the **retained admission policy's** version, which the start and the
   successor selector always hold (`sessions/continuation.py:640–651`).
   Adding a stage to `ContinuationActionPolicy` therefore means a new policy
   version, not a silent field addition.
5. A test pins the v1 encoding of the fixture (golden bytes and hash) and
   asserts that a payload with an added field, a removed field and an unknown
   version all refuse with `AuditIntegrityError`. The peer's proposed id
   `test_production_policy_from_settings_round_trips_and_is_versioned` (R6) is
   the umbrella name.

0.8.10 starts every store fresh at epoch 79 (plan §6 C2), so v1 is the first
persisted version and nothing older needs reading. The tag is not a schema
change: the policy is chunk content inside the snapshot, not a SQL column.

transaction, which is two orders of magnitude smaller. An in-flight action
longer than `T_cancel` cannot be saved by any grace up to the platform
maximums (peer R3). It goes through disposition C.

settings, so an operator can change them without a release.

`max(300, 290 + 25 + 120) = 435 s`; local-sized segments stay at 300 s.

### 4.5 The first-Compose fixture derives from the policy

Two requirements meet here. The plan says the U-45 fixture derives from the
U-38 policy (§4 U-45). The U-45 review ruled that the 1.0 s budget stays,
because padding it would hide a cost that grows with every turn (diagnosis §8,
§12).

Resolution:

```python
# tests/helpers/continuation_policy.py
TIGHT_TEST_OVERRIDES = {...}  # today's literals, documented as tripwire budgets

def minimal_continuation_policy() -> ContinuationAdmissionPolicy:
    settings = continuation_test_settings(composer_continuation_enabled=True, **TIGHT_TEST_OVERRIDES)
    policy = continuation_policy_from_settings(settings)
    assert policy is not None
    return policy
```

- **One construction path.** The fixture goes through the same settings
  model, validators, `from_settings` mapping and version tag as production.
  A field added to production without a fixture value fails the fixture.
- **The numbers do not change.** Every current literal, including
  `local.retention = 1.0`, is kept as an explicit override. Seven test modules
  use this fixture today (`git grep -l minimal_continuation_policy` over
  `tests`). Moving them to production numbers would re-time all of them and
  remove the tripwire that found U-45's inefficiency.
- **Never looser than production.** A test asserts that every fixture stage,
  and the fixture's segment sizing, is less than or equal to the production
  default, so a test can never pass on a budget production would not grant.

This differs from "production defaults with only `retention = 1.0` overridden":
the other tight values are tripwires too, and each one bounds how long a stuck
test takes to fail.
