### 1.4 Successor-action selection

`next_continuation_action_policy` (`composer/continuation_next_action.py:18–277`)
sizes the next segment from the retained snapshot. It admits exactly these cuts
and raises `AuditIntegrityError` for anything else:

1. `InitializeFrame` at `title_pending` with the TITLE effect prepared, dispatched or committed (`:28–73`).
2. `InitializeFrame` at `ready` with the TITLE applied (`:74–98`).
3. `InitializeFrame` at `reserved`/`inserted`, and published `title_pending`/`ready` bootstrap cuts (`:99–138`).
4. **The first** `ComposeFrame` at `action_ready`: every slice, total and counter must be zero (`:139–178`).
5. `ComposeFrame` at `response_retained` with a committed primary effect (`:179–201`).
6. Four `ToolBatchFrame` cuts: attachment read pending or retained, attachment application complete, P4 pending or applied (`:202–277`).

`ContinuationFrameStack.is_handoff_safe` (`composer/continuation.py:237–249`)
defines the safe cut for a handoff: no pending settlement or owner result, no
`dispatched`/`unknown` effect, and a top frame at Initialize `ready`, Compose
`action_ready`, ToolBatch `tool_ready`, Advisor `input_ready` or any End phase.
Its only callers are tests (`test_continuation_frames.py:71–76, 214`,
`test_continuation_response.py:183`). **Verdict: partial.** The two sets do not
agree. Handoff-safe Compose `action_ready` after the first iteration, Advisor
`input_ready`, End and most ToolBatch `tool_ready` cuts are not sizeable, so a
yield at any of them would roll back (§2.4).

## 2. U-35b: the yield and atomic checkpoint+successor API

### 2.1 Shape

Five SQL transitions, each one locked session transaction. Names follow Sol's
storage plan (`…-storage.md:2805–3130`) wherever that draft exists.

| Transition | Public method (transaction owner) | Connection body (`sessions/continuation.py`) | Effect |
| --- | --- | --- | --- |
| **Yield** (handoff at a safe cut) | `commit_checkpoint_and_successor` on `_SessionOperationAuthorityRepository` (`repository.py`, beside `start_composer_segment`), declared on `SessionOperationAuthority` (`sessions/protocol.py:2437`) | `yield_segment_on_connection` | Handoff checkpoint, predecessor `yielded`, one queued successor at `(sequence + 1, generation + 1)`, parent pointer advanced, **fence released** |
| **Handover** (a live owner gives up its segment at a recoverable cut) | `suspend_composer_segment` (same class) | `recover_segment_on_connection`, the **same body** peer recovery uses (§5.2), entered with the live owner's fence proof instead of the expiry proof | Same sequence, generation + 1, segment `interrupted`, parent `reconciling` (or `retry_waiting` with a delay), **fence released** |
| **Terminal** | `settle_composer_operation_on_connection` gains a V2 branch | `settle_continuation_on_connection` | Segment and attempt `settled`, parent `completed`/`failed` with `phase = 'settled'` |
| **Pre-start claim renew / release** | existing `renew_claim` / `release_claim` gain a V2 branch | (inline; already bound) | Segment claim expiry extended / cleared |
| **Read-back** | `read_yield_outcome`, `verify_recovery` | `verify_yield_on_connection`, `verify_recovery_on_connection` | Read only |

**Why the repository and not `ComposerAsyncOperationAuthority`.** The yield
must release the fence in the same transaction as the handoff checkpoint
(peer R2: a peer claims immediately, without waiting for lease expiry).
`session_operation_fences` belongs to `SessionOperationAuthority` (gate
`:217`). The only existing transactions that cross both authorities are
`start_composer_segment` and `recover_composer_segment` in
`_SessionOperationAuthorityRepository`. Sol's draft put the wrapper on
`ComposerAsyncOperationAuthority` with `locked_session_transaction`, which
cannot release the fence without duplicating fence DML under the wrong
authority. Under rule R-G the repository method orchestrates: fence DML goes in
a new private helper `_release_fence_on_connection` factored out of `release`
(`repository.py:6086–6097`, the same UPDATE under `_exact_active_predicates`),
and the continuation DML goes in the bound connection bodies.

### 2.2 Yield transaction, step by step

Signature (Sol's draft, with `reason` added and the action arguments removed):

```python
def commit_checkpoint_and_successor(
    self, running: ComposerOperationRunning, *, expected_head: UUID | None,
    expected_checkpoint_id: str, expected_cursor: int, snapshot_json: str,
    reason: ContinuationYieldReason,
) -> ComposerSegmentYieldReceipt: ...
```

`ContinuationYieldReason = Literal["quantum", "watermark", "action_fit",
"slice_limit", "shutdown", "model_request"]`. `model_request` is the yield the
model asks for through `checkpoint_and_continue` (U-40, protocol design R9). It
is defined here so U-40 adds a caller, not a vocabulary edit. lives in the new pure module
`composer/continuation_handoff.py`. It is written to `rollover_reason`, which
has no CHECK (`models.py:3800`), so the vocabulary is enforced in Python.

All steps run on one connection under `self._locked_transaction(session_id)`,
with one `now = self._database_now(conn)` used for every written time.

The yielded event payload mirrors the `recovered` payload
(`repository.py:5113–5123`) and the `ContinuationControlHandoff` identity rule:
`{"version": 2, "reason", "predecessor_sequence", "predecessor_generation",
"successor_sequence", "successor_generation"}`, encoded with `canonical_json`
from a closed pydantic model in `continuation_handoff.py`.

**Where a yield is allowed (review finding F3).** A yield starts a new
sequence. The landed phase readers walk only a same-sequence `recovered`
lineage over `transition` checkpoints. The pre-title reader refuses any
non-`transition` checkpoint (`sessions/continuation_bootstrap_source.py:119–120`)
and stops at the first event that is not an exact `recovered` event
(`:154–171`). The first-Compose reader requires its initialization creator
sequence to equal the **current** segment sequence
(`sessions/continuation_composition_initialization.py:582`). A handoff at any
cut those owners read would fail at the successor's start. Therefore:

- U-35b adds `sessions/continuation_lineage.py`: a verified reader that walks
  back through `yielded` events and `handoff` checkpoints, checks `sequence + 1`
  and `generation + 1` per step and the slice roll, and returns each original
  creator's `(sequence, generation)`.
- A yield is allowed only when the head is handoff-safe **and** the top frame's
  phase owner reads its predecessors through that lineage reader. Each owner
  declares this in the driver's phase table (§3.3). **No landed owner does**,
  so in 0.8.10 the yield transaction is exercised by U-35b's library tests and
  enabled by the owners U-40 writes (later Compose iterations, Advisor, End).
- Every drain at a landed owner's cut uses the handover (disposition B, §3.4).
  It writes recovery's exact transition, so the existing readers accept it
  unchanged.

**The successor is claimable at commit.** After step 11 the claim predicate
(`composer_operation_authority.py:134–188`) holds for the successor: the fence
is released (first arm of `available_fence`), the parent's sequence,
generation and checkpoint equal the successor's, the successor is `queued` with
`next_eligible_at = now` and no claim. Any replica, including the yielding one,
can claim it on its next scan.

**Why `allow_expired_segment=True`.** The segment hard deadline bounds action
admission. A yield admits no action and only reduces ownership. Refusing it
past the deadline would force the operation into lease-expiry recovery for no
safety gain. Cancellation is not allowed (`allow_cancel=False`): Stop wins over
yield, and the caller settles `request_cancelled` instead (§2.7).

**Defects in Sol's draft that this fixes** (the draft was written before
`recover_composer_segment` landed):

1. No slice roll. The successor's runtime read refuses unless
   `ComposeFrame.slice_sequence` equals the claimed sequence
   (`sessions/continuation_runtime.py:97–98`), so every successor would fail
   at start. Step 4 fixes it.
2. Caller-supplied `next_action_json` and `policy_sha256` without validation.
   The start would re-derive and refuse a wrong action
   (`sessions/continuation.py:645–651`) after the predecessor had already
   released, wedging the operation. Step 6 derives the action inside the
   transaction, as `recover_composer_segment` does.
3. No fence release. Step 11.
4. Identity-free event payload (`'{"version":2}'`). Fixed above.
5. `require_continuation_mutation` with the default `allow_expired_segment=False`.
6. The read-back required the successor to still be `queued` and the parent
   to still be `continuation_queued`. With the fence released at commit, a
   peer can start the successor before the yielder reads back, so a correct
   yield would fail verification. §2.3 fixes the read-back.
7. Rule R-G: the draft's wrapper sat under one authority and wrote both
   authorities' tables.
8. The draft's `suspend_segment_on_connection` wrote a `recovered` event with
   `{"reason", "same_sequence"}`. The landed lineage reader accepts only
   recovery's exact bytes `{"version": 2, "same_sequence",
   "previous_generation", "generation"}` (`continuation_bootstrap_source.py:167–171`).
   The handover therefore reuses `recover_segment_on_connection` unchanged.
   A reason is recorded only on the segment's `rollover_reason`.

### 2.3 Fencing tokens, idempotency and read-back

**Fencing.** A yield is admitted only by the full current-owner tuple: fence
`(operation_id, lease_token, operation_epoch, kind = COMPOSE)` live; segment
`claim_token`; parent `attempt`; `(sequence, generation)`; snapshot
`(checkpoint_id, journal_cursor)`. Any stale element refuses before the first
write (steps 0–3) or makes a CAS miss that rolls the transaction back (steps
5–11). After commit, the predecessor's fence is released and its attempt
revoked, so a late write from that generation fails
`require_continuation_mutation` (no live attempt for its epoch) and the
fence's exact-active predicates.

**Idempotency key.** The natural key `(session_id, operation_id,
predecessor_sequence, predecessor_generation)`. No client token is needed: only
the owning worker can call this, and the key is enforced three ways: the
attempt's `revoked_at IS NULL` predicate, `uq_composer_segments_successor`,
and the parent CAS. A second call with the same `running` refuses with
`ComposerOperationFenceLost` and writes nothing.

**Ambiguous commit.** If the commit's outcome is unknown (connection lost after
`COMMIT` was sent), the caller never retries the yield. It calls
`read_yield_outcome(running) -> ComposerSegmentYieldReceipt | None`:

- `None` when the predecessor attempt is still unrevoked and bound to the
  caller's fence: the yield did not commit, and may be retried while the fence
  is live.
- The receipt when the predecessor attempt is `yielded`, the predecessor
  segment is `yielded` at the handoff checkpoint, that checkpoint has
  `kind = 'handoff'`, the event at its cursor is `yielded` with exactly these
  identities, and a successor row exists with `predecessor_sequence = seq` and
  `generation = gen + 1`.
- `AuditIntegrityError` for any other combination, for example the attempt
  revoked with outcome `interrupted`, which means a peer recovered it.

`verify_yield_on_connection` checks the same facts and **tolerates successor
progress**: the successor may be `queued`, `running`, `yielded`, `interrupted`
or `settled`; the parent may have moved to a later sequence or generation, or
be terminal; the snapshot head may be past the handoff checkpoint; the
released fence epoch may have been advanced by the successor's start. It never
compares against the current head. **The successor's generation is not
fixed (F7):** recovery increments the generation on the same successor row
(`repository.py:5160–5163`; the segment key is the sequence,
`models.py:3780–3782`). So the successor's initial generation comes from the
immutable `yielded` event payload. The row's current generation must be at
least that, and every step above it must be an `interrupted` attempt in that
sequence. `read_yield_outcome` applies the same rule.

### 2.5 Composition with the lease object

After step 11 commits, the lease's renewal task would hit `RELEASED`, and
`SessionOperationLease.close()` would try a second release. U-35b adds
`SessionOperationLease.consume_continuation_handoff(action)` to
`coordination/lifecycle.py`, modelled on `consume_archive`
(`lifecycle.py:1351–1440, 1549`):

1. Join owned child tasks; any failure refuses and falls back to an ordinary
   close.
2. Stop and join the renewal task. A recorded renewal error means `LOST`, and
   the handoff is refused.
3. Run `action`, the bound `commit_checkpoint_and_successor` or
   `suspend_composer_segment` call, in the worker pool.
4. On success, set disposition `CONSUMED` (`coordination/contracts.py:68`).
   The disposition alone does not stop a release: ordinary `_close()` releases
   without consulting it (`lifecycle.py:1096–1099`). What prevents the second
   release is the archive mechanism itself (F9): `consume_continuation_handoff`
   sets `_finish_mode = "consume"` and runs steps 1–5 as the one retained
   `_close_task` (`:1558–1569`), and `close()` only joins that task
   (`:1505–1528`). A later `close()` therefore cannot start a second finish.
5. On `SessionOperationFenceLost`/`ComposerOperationFenceLost`, set `LOST`.
   On an unknown completion, set `UNKNOWN` and return to the caller, which
   calls `read_yield_outcome`.

**Lease validity is checked, not assumed (F11).** Renewal sleeps for the
interval and then runs SQL (`lifecycle.py:909–920`), so the age of the last
successful extension is not bounded by the interval. Correctness never depends
on a margin: steps 1 and 11 re-check `lease_expires_at > now` by the database
clock and refuse otherwise, and the operation then falls to peer recovery,
which is safe. The disposition transaction records the remaining validity it
observed (`lease_expires_at − now`) in its receipt, and U-37's latency case
reports its distribution instead of inferring it.

### 2.7 V2 terminal settlement and the cancel defect

`settle_continuation_on_connection(conn, running, *, outcome,
authoritative_failure=False)`, reached from a new V2 branch at the top of
`settle_composer_operation_on_connection` (dispatch on
`running.claim.segment_sequence is not None`, as Sol's END plan names it,
`…-end.md:2136`):

1. `require_continuation_mutation(conn, ctx, allow_cancel=<outcome is request_cancelled>, allow_expired_segment=True)`.
2. Load the head; append one `settled` event (payload: version, sequence,
   generation, outcome kind, `failure_code`) and a transition checkpoint.
3. Attempt `revoked_at = now` **and** `outcome = 'settled'` together, because
   the CHECK pairs them (`(revoked_at IS NULL) = (outcome IS NULL)`,
   `models.py:3869`; F8). Segment `state = 'settled'`. Both run under the same
   exact-owner predicates as the yield.
4. Parent: `_terminal_values(...)` **plus `phase = 'settled'`**, under V2
   running predicates that do not reference `jobs.claim_token` (always NULL
   for V2). A `completed` outcome also requires `user_message_id` to be set,
   as the bundle demands (`models.py:3710–3712`).
5. `_select_failure_on_connection` gains a V2 branch with no `deadline_at`
   arm: V2 has no parent deadline.

**Saved-revision attribution across segments (protocol design R8).**
`_saved_failure_revisions` aggregates only each record's current
`session_operation_id` (`composer_operation_authority.py:259–293`, the
fence tuple at `:263`). A V2 operation writes under one fence per segment
attempt, so saves made in earlier segments would vanish from a stopped or
failed request's count. U-35b gives V2 records a branch that collects every
`composer_segment_attempts.session_operation_id` for the operation and folds
them into one `ComposerOperationSavedRevisions`: the summed count, and the
latest state by maximum version. V1 is unchanged. Test:
`test_v2_saved_revisions_aggregate_every_segment_fence` (control: key on the
parent's current fence only).

The fence is left for the lease close, as V1 does: the worker verifies the
terminal before releasing (`composer_async_worker.py:615`). END publication
checks (Sol's END plan `:908`) are U-40's to add inside step 2. U-35b provides
the failure and success CAS only.

`request_cancel` gains a V2 branch: it sets `cancel_requested_at` only and
never settles directly. In the same transaction it:

- increments `status_revision` in the same UPDATE as `cancel_requested_at`.
  The V2 snapshot projects the Stop, and the protocol design keys stream
  resume on `status_revision`, so a marker without a bump would be invisible to
  observers. The trigger refuses only decreases (`models.py:4038`);
- sets `next_eligible_at = now` on the current segment when it is `queued` or
  `interrupted` with no live claim. A `retry_waiting` segment can otherwise sit
  up to 30 s behind its backoff (Sol storage plan's `(1, 2, 4, 8, 16, 30)` s
  schedule) before any worker claims it and settles the Stop. This is a segment
  write inside an already bound `ComposerAsyncOperationAuthority` method, so
  the gate needs only a re-derived fingerprint.

**`status_revision` is monotonic, not contiguous.** One durable transition can
raise it by more than one: `append_complete_snapshot` bumps it
(`sessions/continuation.py:437`), and the parent-pointer update in the same
transaction bumps it again (yield step 10; the landed
`recover_composer_segment` does the same, `repository.py:5105–5190`).
`claim_segment` bumps it on a claim (`composer_operation_authority.py:1307`).
Readers must treat it as strictly increasing per committed change, never as
"+1 per transition". It is database-authoritative and replica-independent. Settlement happens through the owning worker's terminal
path, or through §5.3 if no owner remains. The existing
`test_cancelled_v2_can_start_cleanup_but_business_guard_still_refuses`
(`test_composer_continuation_claim_start.py:208`) already fixes the intended
behaviour that a cancelled V2 can start cleanup.

### 2.8 Pre-start claim renew and release

`renew_claim` and `release_claim` gain a V2 branch selected by
`claim.segment_sequence is not None`. Renew extends `segments.claim_expires_at`
under `(sequence, generation, claim_token, claim_owner_instance_id, state IN

## 3. U-37: worker yield, resume and restart

### 3.1 What U-37 adopts from the grace spec

From `0.8.10-continuation-container-grace.md` (peer, `48a308276`), unchanged:

- **R1.** `instance_draining` is set at SIGTERM, not in the lifespan
  `finally`, and the HTTP drain is bounded. Today `uvicorn.run` at
  `cli.py:5292` has no `timeout_graceful_shutdown`, so uvicorn waits without
  bound for open connections, and a Composer stream may stay open for
  `STREAM_LIFETIME_SECONDS = 120.0` (`composer_stream.py:20`).
- **R2.** On drain, a V2 segment at a committed cut writes a durable handoff
  and releases its fence inside the drain budget. It never depends on the
  segment's timing policy.
- **R3.** ECS `stopTimeout = 60` on the web container (proposed diff in the
  spec), ACA stays at 60.
- **R4/R5** are U-39 (§5).

Refinements this design makes, each argued below:

1. The worker drain starts at SIGTERM **concurrently** with the HTTP drain, so
   the budget is `max(H, D) + S + M`, not `H + D + S + M` (§3.5).
2. A live owner at a cut that is recoverable but not handoff-safe **hands
   over** (same sequence, generation + 1, fence released) rather than leaving
   the segment for lease-expiry recovery (§3.4, disposition B).
3. A live owner with an unresolved provider or business effect **settles the
   operation itself** while its fence is still live, through the same SQL body
   a peer uses after expiry (§3.4, disposition C). On ECS, with one task and no
   live peer, this is the fast path. Otherwise the request waits for the
   replacement task's startup sweep. Its latency is unmeasured; the 150 s
   often quoted is the health-check grace allowance (`ecs.tf:582`), not a
   measured start time (F19).

### 3.3 Worker structure

`ComposerAsyncWorker` (`sessions/composer_async_worker.py`) keeps its V1
path byte-for-byte. U-37 adds a V2 path beside it.

- **Claim.** `_claim_once` (`:334–351`) calls `claim_next` (V1) and
  `claim_segment` (V2) and shares one `concurrency` budget. Each V2 claim
  starts `_job_v2(claim)`. V2 stays excluded from `claim_next`,
  `list_expired_queued`, `list_expired_running` and the V1 reaper, which
  already filter on `lifecycle_version == 1`.
- **Pre-start wait.** `_job_v2` keeps the shape of `_job`'s lock-wait loop
  (`:476–488`): poll the lock at `min(0.25, lease/3)`, renew the segment claim
  every `claim_lease_seconds / 3` (§2.8), and release it on stop or drain. It
  **cannot** reuse `_queued_outcome` (F1). That helper returns at once for a
  `running` parent, which is exactly a successor's parent state, and it reads
  `legacy_deadline_at`, which raises for V2 (`composer_operations.py:333–335`).
  Its cancel path, `settle_unstarted`, also refuses V2
  (`composer_operation_authority.py:1468–1470`). A new `_segment_outcome(claim)`
  checks that the claimed segment is still current at its generation and claim
  token, accepts a nonterminal `running` parent, and routes a pending Stop to
  the V2 terminal (§2.7) after the start.
- **Start and adoption.** `start_composer_segment`, then
  `SessionOperationLease.adopt` with the same failure custody as V1:
  `_adoption_recovery_cancellations`, `started_handoff` and
  `_begin_adoption_failure_custody` (`:498–555`). This is Sol's executable
  review finding E11. An adoption failure after the SQL start hands over through
  `suspend_composer_segment` with a retry delay, never through the V1
  terminal `_settle_failure`.
- **Driver.** A new module `sessions/continuation_driver.py` holds
  `run_continuation_segment(services, running, lease, observation) ->
  ContinuationSegmentOutcome`. The outcome is a closed sum:
  `ContinuationSegmentYielded(ComposerSegmentYieldReceipt)`,
  `ContinuationSegmentHandedOver(ComposerSegmentRecoveryReceipt)`, or
  `ContinuationSegmentSettled(ComposerOperationRecord)`. The driver dispatches **by frame family first** (F2). An admitted operation
  starts with only an `InitializeFrame` (`composer/continuation.py:378`), and
  `restore_continuation_runtime` (`composer/continuation_runtime.py:312–337`)
  reads the Compose runtime, which requires exactly one `ComposeFrame`
  (`sessions/continuation_runtime.py:93–96`). So Initialize and TITLE cuts go
  to their own source readers and owners; only Compose-family cuts restore the
  Compose runtime. The phase owners are those U-44b and U-45 wire
  (initialization, TITLE, first Compose, primary retention, P4, attachments).
  Each phase-table entry also declares whether its owner reads handoff
  lineage (§2.2). The driver loops until a disposition. The phase table is
  closed: a cut whose owner has not landed raises `AuditIntegrityError` and
  settles `failed`. While V2 is default-off this is reachable only from tests.
  U-40 and U-41 extend the table.
- **Outcome verification.** `_verify_terminal_before_release`
  (`:615–730`) becomes `_verify_outcome_before_release`. It accepts only a
  verified terminal record, a yield receipt checked by `verify_yield`, or a
  recovery receipt checked by `verify_recovery` (Sol C4a). A normal yield
  never calls failure settlement, never publishes an assistant row and never
  clears the request.
- **Stop after drain.** The lifespan calls `stop()` about `H` seconds after
  SIGTERM. Today `stop()` cancels every job at once (`:414–427`), which would
  cut the drain window from `D` to `H`. When `begin_drain()` has run, `stop()`
  first awaits the drain's completion, bounded by the drain deadline
  `t_SIGTERM + D`. Only then does it cancel what is left with
  `COMPOSER_SHUTDOWN` and joins **against the same absolute deadline**. It
  never restarts `_drain_seconds` (today's second wait, `:424`), so shutdown
  cannot spend `2 × D` (F10). Without a prior
  `begin_drain()`, for example on a startup failure, it behaves as today.
- **Watch.** The V2 watcher reacts to lease loss and Stop as V1's `_watch`
  does (`:884–995`). It has no parent deadline. A drained Stop goes to the
  terminal `request_cancelled`, never to a handover (Sol's review E19).
  **Stop does not wait behind a provider call.** On Stop the watcher cancels
  the in-flight stage, as V1 does, so Stop latency is the cancellation join,
  not the provider's remaining time. A cancelled call after its may-dispatch
  marker is recorded `unknown` with its real cost, and the operation settles
  `request_cancelled`. No new dispatch is admitted once Stop is set:
  `require_continuation_mutation` refuses it (`sessions/continuation.py:188–198`).
  Stop against a final commit is decided by transaction order under the
  session lock: whichever commits first wins, and a completed operation is
  never cancelled afterwards.

### 3.4 The yield points and the three drain dispositions

The driver checks two conditions **between stages**, never inside one. A stage
is one `ContinuationActionClock.run` call (`continuation_clock.py:146`).

- **Cooperative rollover.** The frozen timing observation
  (`sessions/continuation_runtime.py:117–124`) says `yield_pending`, or
  `admit_action` returns `YIELD` for the next retained action. If the head is
  handoff-safe, the driver yields with reason `quantum`, `watermark` or
  `action_fit`. Otherwise it finishes the current action to the next
  handoff-safe cut first ("finish an already admitted healthy action and then
  yield", Sol plan §Independent time).
- **Drain.** `begin_drain()` sets a per-job drain event. At the next stage
  boundary the driver classifies the durable head with the pure
  `classify_drain_cut(selected) -> Literal["handoff", "handover", "unresolved"]`
  in `continuation_handoff.py`:

| Class | Test | Disposition | SQL |
| --- | --- | --- | --- |
| **A. handoff** | handoff-safe **and** the top frame's owner reads handoff lineage (§2.2) | yield, reason `shutdown` | `commit_checkpoint_and_successor` (§2.2) |
| **B. handover** | the classifier returns an allowance for the cut (every recovery-admitted cut in §1.4, including handoff-safe cuts of landed owners) | same sequence, generation + 1, `next_eligible_at = now`, parent `reconciling` | `suspend_composer_segment(retry_delay_seconds=0)` → `recover_segment_on_connection` |
| **C. unresolved** | a `dispatched`/`unknown` effect, or a pending settlement the selector refuses | settle the operation `failed`, `failure_code = 'worker_lost'`, one `effect_unknown` event per unresolved effect | `settle_lost_segment_on_connection`, the shared terminal body (U-35b, §5.3) |

**Classification is explicit, not by exception site (F4).** Changing the
type raised at a few selector lines would misclassify in both directions. A
PRIMARY call in flight leaves Compose at `awaiting_response` with a `prepared`
or `dispatched` effect (`sessions/continuation_primary.py:352–363, 454–480`),
which reaches the generic refusal at `continuation_next_action.py:202–203`,
outside any named site. A dispatched TITLE is resumable (`:51–57, 73`). The
refusal at `:197` mixes unresolved-effect checks with codec, locator and
frontier checks (`:181–195`). U-35b therefore restructures the selector into
three ordered steps:

1. **Validate structure.** Codec, locator, frontier and frame-shape
   invariants. Any violation is `AuditIntegrityError`, as today.
2. **Classify** a structurally valid stack against an explicit table of
   in-flight shapes (Compose `awaiting_response` with a `prepared`/`dispatched`
   primary effect; a ToolBatch with a `prepared`/`dispatched` business effect;
   any `unknown` effect). Each match returns
   `ContinuationCutNotResumable(effect_ids)`.
3. **Select** the allowance for the remaining resumable cuts (§1.4, §2.4).

`ContinuationCutNotResumable` subclasses `AuditIntegrityError`, so every
existing caller and test that expects `AuditIntegrityError` keeps passing
(for example `test_continuation_p4_recovery_start.py:225–234`). The reaper and
the drain catch the subclass specifically. Each in-flight shape has a test.

**An in-flight stage at drain.** The driver does not cancel a running stage
when draining begins. It waits for the stage to finish until the cancel
instant `T_cancel` (§3.5). At `T_cancel` it cancels the stage task with
`COMPOSER_SHUTDOWN`, joins the required-work cohort
(`RequiredWorkCoordinator`), and classifies the durable head. A provider call
cancelled after its may-dispatch marker leaves a `dispatched` effect, so it is
class C. Its cost is real and its result is discarded. The alternative, a
retry after custody resolution, is §8 question 1.

**Composer invariants.** None of the three dispositions synthesises a reply,
a graph or a proposal. A successor resumes by calling the provider for its
next retained action. Resuming from a handoff or a handover makes **zero**
provider calls before the successor's first admitted action, and replaying a
retained response makes none (`continuation_next_action.py:198–201`). That
count is U-37's A9 instrument (§6). The driver has no tutorial branch: the
tutorial negotiates V2 exactly as freeform does (U-41's A9 case).

### 3.5 Time budget

Let `G` be the platform grace (ECS `stopTimeout`, ACA
`terminationGracePeriodSeconds`), `H` the HTTP drain, `D`
`composer_async_drain_seconds`, `Y` one disposition transaction, `S`
membership stop and exit, `M` the safety margin.

With R1 in place the HTTP drain and the worker drain both start at SIGTERM:

```text
t = 0            SIGTERM; instance_draining set; no new claims; begin_drain()
t ∈ [0, T_cancel] jobs reach a stage boundary on their own and dispose (A/B/C)
t = T_cancel     remaining stages cancelled; cohorts joined; dispose
t ≤ D            every V2 job disposed; leases consumed or closed
t ≤ max(H, D) + S + M ≤ G
```

**What is guaranteed and what is bounded (F11).** *Safety* is unconditional:
if any step overruns and the process is killed at `G`, the segment stays
`running` under an expiring fence, and U-39's recovery or settlement takes it
with no duplicate effect. *The time bound* is conditional, because three waits
in the drain path are not bounded today: required SQL absorbs cancellation
until its physical future completes (`async_workers.py:418–422`); the
PostgreSQL session lock blocks (`sessions/locking.py:275–280`); and joining the
renewal task has no timeout (`lifecycle.py:1039–1047`). There is no
`statement_timeout` or `lock_timeout` anywhere under `src/elspeth/web`
(`git grep`). U-37 therefore:

- runs each disposition transaction on PostgreSQL with `SET LOCAL
  lock_timeout` and `SET LOCAL statement_timeout` derived from the remaining
  drain time. A timeout rolls the transaction back, leaving no partial state,
  and the segment falls to recovery;
- joins cancelled stages, the cohort and the renewal task against the one
  absolute drain deadline, and abandons the disposition when the deadline
  passes. The process then exits, and recovery owns the segment;
- measures the whole drain under a real SIGTERM, not only the yield
  transaction (§6.2).

`T_cancel = D − Y_budget − 1 s`, with `Y_budget = 2 s`: two sequential
disposition transactions at an assumed ≤ 1 s p99 each, as a disposition may
follow a CAS retry (§2.6). `Y` on PostgreSQL is **not yet measured** (peer
R3). U-37 measures it (§6, `test_yield_transaction_latency_is_recorded_postgres`)
and resizes `Y_budget` from the measured p99 if it exceeds 1 s.

| Setting | Default | ECS (`G = 60` after R3) | ACA (`G = 60`) | ECS without R3 (`G = 30`) |
| --- | --- | --- | --- | --- |
| `H` (`web_http_drain_seconds`) | 5 | 5 | 5 | 5 |
| `D` (`composer_async_drain_seconds`) | 10 | **30** (deploy env) | **30** (deploy env) | 10 |
| `T_cancel` | `D − 3` | 27 | 27 | 7 |
| `max(H, D) + S + M` | 16 | 36 | 36 | 16 |

**The cap `composer_async_drain_seconds ≤ 120`** (`web/config.py:406`) is a
setting bound, not a platform limit. It is harmless at these values. The real
limit is `G`: Fargate's maximum is 120 s; ACA documents none (peer §1).

**Why raise `D` to 30 where `G = 60`.** `D` decides how many in-flight actions
reach a clean cut instead of class C. With `D = 10`, any provider call more
than 7 s from completion at SIGTERM fails its request. With `D = 30`, calls
within 27 s of completion survive. Both stay well inside `G`, and other
shutdown work, such as the executor join (`web/app.py:1226`) that runs after
the composer worker, keeps about 24 s.

**A guard against a mis-declared grace.** U-37 adds `composer_shutdown_grace_seconds`
(default 30, the platform default on both targets). A settings validator
requires `max(H, D) + 1 + 5 ≤ composer_shutdown_grace_seconds`. The ECS module
and the ACA Bicep set it from their real grace values (60). This follows the
`composer_transport_idle_ceiling_seconds` precedent (`web/config.py:382–395`):
the operator declares the infrastructure bound, and a mismatch fails at
startup instead of at the first deploy.

**Lease interplay.** The physical lease keeps renewing every 10 s until a
disposition consumes it (§2.5). The disposition re-checks lease validity by
the database clock and records what remained (§2.5). The pre-start segment
claim keeps renewing every `claim_lease_seconds / 3` until it is released.
Neither period changes.

### 3.6 Resume and restart

A successor (after a yield) and an interrupted generation (after a handover or
a peer recovery) are claimed by the same `claim_segment` path on any replica,
and started by the same `start_composer_segment`. The start re-derives the
retained next action and refuses any substitution
(`sessions/continuation.py:640–651`). It sizes a fresh segment from the
retained policy and the new database time. The successor then gets a full
`size_segment` allowance, a fresh fence epoch and a fresh attempt row.
Nothing in-memory crosses a segment boundary: the cold-restore gate (U-36)
already proves restore under a genuinely new fence.

### 4.3 Versioned persisted payloads

The problem (M): every policy model is `extra="forbid"`, frozen, with every
field required. Adding a field later makes every retained payload fail
`model_validate_json`. Removing one makes new payloads fail on old code.
Either way the operation can never start again and wedges.

Design, mirroring `ContinuationFrameStack.schema_version`
(`composer/continuation.py:221`):

1. `ContinuationAdmissionPolicy` gains `schema_version:
   Literal["composer.continuation.policy.v1"]` as its first field. It is part
   of `model_dump`, so it is inside `policy_hash`.
2. `decode_continuation_policy` reads the raw strict-JSON object first. A
   missing or unknown `schema_version` raises `AuditIntegrityError`, never
   a default. Then it validates with the model for **that** version and checks
   the hash against that version's bytes.
3. A later change adds a new frozen model `…policy.v2`. The v1 model is never
   edited again. **Persisted identity and effective values are separate (F15).**
   `policy_hash` recomputes from the returned model
   (`continuation_policy.py:92–94`), and the segment start CAS compares that
   recomputed hash with the persisted pointer (`sessions/continuation.py:704`).
   An upgraded model would hash differently and fail the start. So the decoder
   returns `RetainedContinuationPolicy(persisted_sha256, schema_version,
   effective)`. Every CAS and pointer comparison uses `persisted_sha256`, and
   only stage timing reads `effective`. Persisted bytes and the hash are never
   rewritten. Step 2 verifies the original bytes.

   **0.8.10 ships v1 only.** The decoder knows one version and upgrades
   nothing, so `persisted_sha256` equals the recomputed hash, and the call
   sites at `sessions/continuation.py:541, 643, 647, 704` stay as they are.
   Switching them to `RetainedContinuationPolicy` is an obligation of the change
   that introduces v2, with an old-version start test. This keeps U-38 out of
   U-35b's file.
4. Standalone action JSON (`segments.next_action_json`, the seed's
   `action_json`) has no tag of its own. It is decoded with the action model
   of the **retained admission policy's** version, which the start and the
   successor selector always hold (`sessions/continuation.py:640–651`).
   Adding a stage to `ContinuationActionPolicy` therefore means a new policy
   version, not a silent field addition.
5. A test pins the v1 encoding of the fixture (golden bytes and hash) and
   asserts that a payload with an added field, a removed field and an unknown
   version all refuse with `AuditIntegrityError`. The peer's proposed id
   `test_production_policy_from_settings_round_trips_and_is_versioned` (R6) is
   the umbrella name.

0.8.10 starts every store fresh at epoch 79 (plan §6 C2), so v1 is the first
persisted version and nothing older needs reading. The tag is not a schema
change: the policy is chunk content inside the snapshot, not a SQL column.

## 5. U-39: the recovery gate

### 5.1 The production caller (R4)

The peer spec's R4 needs a caller, and none exists (§1.2). U-39 adds
`sessions/continuation_recovery.py`:

```python
async def reap_continuations_once(worker: ComposerAsyncWorker) -> int: ...
```

It runs from the worker loop next to the V1 `reap_once`
(`composer_async_worker.py:326–333`) and once at startup next to
`app.state.composer_async_worker.reap_once()` (`web/app.py:1157`). The startup
call is what makes ECS work: there, the recoverer is the replacement task, and
it recovers before it claims anything.

1. **Discover.** A new read-only authority method
   `ComposerAsyncOperationAuthority.list_recoverable_segments(limit)` returns
   V2 parents that are `queued`/`running` and whose current segment is
   `running` under a fence that is **either released, or** lease-expired with
   the owner's `web_instances` lease also expired on PostgreSQL (F5). A released
   fence over a `running` segment is reachable: an ordinary lease close releases
   without a terminal (`repository.py:6064–6090`, `lifecycle.py:1096–1098`),
   for example after a refused handoff falls back to close. Recovery already
   accepts it (`repository.py:5099–5103`). Exact ownership is re-validated
   under the lock. This is
   the claim predicate's takeover arm (`composer_operation_authority.py:135–150`)
   applied to running segments. It skips keys this worker owns locally, as the
   V1 reaper does (`:1450–1451`). It is a read, so it adds no gate row.
2. **Recover.** For each candidate, read the parent's `actor_user_id` and
   `ownership_generation`, then call `recover_composer_segment(session_id=…,
   operation_id=…, expected_generation=…, actor_user_id=…,
   auth_provider_type=settings.auth_provider)`. The method needs both identity
   arguments (`repository.py:5014–5022`), which is why the reaper reads the
   parent first.
3. **Settle what cannot be recovered (R5).** If recovery reports the cut not
   resumable, or the session is archived, call `settle_lost_continuation`
   (§5.3).
4. **Stop beats recovery.** If the parent already has `cancel_requested_at`,
   the reaper does not recover it. It calls `settle_lost_continuation` with the
   `request_cancelled` outcome, so a stopped operation is never resumed only
   to be cancelled. Unresolved effects are still recorded as `unknown`. This is
   the protocol design's R3.

### 5.2 Changes to `recover_composer_segment`

- **Rule R-G.** Its three UPDATEs move into `recover_segment_on_connection` in
  `sessions/continuation.py`, bound to `ComposerAsyncOperationAuthority`. The
  repository method keeps the lock, the owner and liveness proof, and the
  orchestration. This turns its three gate rows green (§1.8).
- **Classify before writing.** Today `_retained_successor_action` runs after
  the `recovered` event is appended (`repository.py:5105–5134`), so a
  not-resumable cut can only surface as an exception that rolls everything
  back. U-39 calls the selector on the stored head first. The `recovered`
  event does not change the frames it reads, so the result is the same.
- **Result, without breaking callers (F17).** 19 test call sites use the
  boolean result, some by truthiness (for example
  `test_continuation_title_application.py:428–434`), so a string result would
  make `"owner_live"` read as success. The method keeps its `bool` contract:
  `True` recovered, `False` owner live or generation moved. A not-resumable cut
  raises `ContinuationCutNotResumable`, an `AuditIntegrityError` subclass, so
  the existing expectations at `test_continuation_p4_recovery_start.py:225–234`
  still hold. That test also matches the message `"prepared or unknown business
  effect"`, so the P4 in-flight shape keeps that exact text. The reaper catches
  the subclass and settles.

### 5.3 `settle_lost_continuation` (R5)

A V2 parent that stays `queued`/`running` blocks every other fence acquire for
its session (`repository.py:4950–4960`). So an operation killed with an
unresolved effect must be **settled**, or Composer is dead for that session.

`_SessionOperationAuthorityRepository.settle_lost_continuation(*,
session_id, operation_id, expected_generation, actor_user_id,
auth_provider_type)`, one transaction:

1. The same proof as recovery: the exact unrevoked attempt and its fence;
   the fence released, or lease-expired with `_expired_owner_allows_takeover`.
2. Advance the fence (`_advance_exclusive_fence_on_connection`, epoch + 1,
   `composer_operation_id` = the parent). Any surviving task of the dead owner
   now fails every CAS.

   **Archived sessions take a separate path (F6).** The fence helper refuses
   any archived session (`repository.py:4967–4970`). So
   `settle_lost_inactive_continuation` proves `archived_at IS NOT NULL` and the
   exact historical attempt instead, and skips the fence advance: no writer can
   acquire an archived session's fence anyway. A **never-started** operation
   (segment `queued`, no attempt row) is settled by changing the parent only,
   with no attempt row and the segment left `queued`. Moving a never-started
   segment to `settled` would violate its time CHECK (`models.py:3813–3815`).
3. `settle_lost_segment_on_connection` (`sessions/continuation.py`): every
   effect in `dispatched` becomes `unknown`, with one `effect_unknown` event
   each (the tag exists, `continuation_events.py:15`); one `settled` event; the
   attempt `revoked_at = now` with `outcome = 'interrupted'` (paired, F8); the
   segment `settled`; the parent `failed`,
   `phase = 'settled'`, `failure_code = 'worker_lost'` (or `'request_cancelled'`
   when a Stop is pending, §5.1 step 4), `settled_by = 'settle_lost'` (or
   `'settle_lost_inactive_session'`). All values are in the
   existing CHECK lists (`models.py:3678–3685, 3868, 3811`).
4. Release the fence (`_release_fence_on_connection`).

The physical quota attempt of an unknown dispatch stays in the ledger as
unknown cost. It is never zeroed or removed (Sol C4b).

The dying owner's disposition C (§3.4) uses the same body: step 1 is replaced
by its own live-fence proof, and step 2 is skipped because it already holds the
fence. **The body is U-35b's (F16)**, so U-37's disposition C does not wait
for U-39. U-39 adds only the expiry proof, discovery and the archived path
around it.

### 5.4 No-duplicate-effects proof obligations

| # | Obligation | Mechanism | Proved by (§6) |
| --- | --- | --- | --- |
| O1 | At most one recoverer commits | session advisory lock + `FOR UPDATE` on fence and membership row; CAS on generation, checkpoint and cursor | two-process race |
| O2 | No recovery while the owner may be alive | fence lease unexpired, or (PostgreSQL) membership lease unexpired, means `owner_live`, by the database clock | SIGKILL with both leases staggered |
| O3 | A revoked generation cannot write | attempt revoked, so `require_continuation_mutation` finds no live attempt for the old epoch; the successor's start advances the fence epoch | zombie write after recovery |
| O4 | No re-dispatch of a `dispatched`/`unknown` provider or business effect | the selector refuses the cut (`not_resumable`), and the operation is settled | provider-call and ledger counts after restart |
| O5 | A committed effect is never repeated | the restored owners read retained results from SQL (primary result, P4 application, attachment read); no owner re-executes a committed effect | business-row and ledger counts equal to an uninterrupted oracle |
| O6 | Accounting is honest | replaying a retained result adds no quota attempt or charge; an unknown dispatch keeps its attempt as unknown cost | ledger assertions per cut |
| O7 | Exactly one transition record | one `recovered` event and one checkpoint per recovery; one `settled` event per operation | event and checkpoint counts |
| O8 | Takeover is not blocked by a reused identity (R7) | on PostgreSQL, startup refuses a pinned `WebSettings.instance_id` (`web/config.py:244–248`: documented for a single-process harness; neither deployment sets `ELSPETH_WEB__INSTANCE_ID`, 0 files against a control of 5) | startup refusal test |

O8 picks the first of the peer's two R7 options. The second option, treating a
newer re-registration as proof of death, would change
`_expired_owner_allows_takeover`, the liveness rule that all fence takeover
depends on, to serve a configuration no deployment uses.

### 5.5 Relationship to cold restore (U-36, the B2 62-case set)

U-36 proves that the pure codec and frame promise survives a real SQL identity
and custody change: commit under one fence, drop every in-memory owner,
restore under a genuinely new fence, and continue
(`test_continuation_cold_restore.py`, 622 lines at `255f1cff3`).

Every path in this design ends in that same restore: a successor's start after
a yield, an interrupted generation's start after a handover or a peer recovery.
So:

- **Order.** U-36 lands and its 62 recorded node ids pass before U-35b (plan §5:
  U-35a → U-36 → U-35b). U-39 depends on it transitively.
- **Rerun, do not substitute.** U-39's gate reruns the 62 recorded ids
  unchanged, serially and then under xdist, with the tree hash recorded before
  and after (plan §4 U-36). U-39's new cases sit beside them.
- **Extension.** For each recovery-admitted cut in §1.4 and each handoff-safe
  cut in §2.4, U-39 adds one PostgreSQL case: dispose (yield, handover or peer
  recovery), restore cold in a new process, and assert O3–O7.

### 5.6 Recovery shape per platform (from the peer spec)

- **ACA**, 2–4 replicas: a live peer recovers after the dead owner's fence
  lease (30 s) and membership lease (30 s) have both expired, within about
  one more 10 s renewal period and one scan interval.
- **ECS**, one task with zero overlap: there is never a live peer. The
  replacement task recovers in its startup sweep (§5.1). Its start latency is
  unmeasured; the 150 s health-check grace (`ecs.tf:582`) is an allowance, not
  a start time (F19). It has a fresh random instance id, so the membership condition is
  met once the old row's 30 s lease has passed.
- **Graceful stop on either target:** dispositions A and B release the fence
  in-transaction, so a peer or the replacement claims at once, with no lease
  wait. Disposition C leaves nothing to recover.

## 7. Build order and file ownership

### 7.1 Order

Plan §5, Lane 4, runs `… U-34 → U-35a → U-36 → U-35b → U-37 → U-38 → U-39 …`.
This design keeps that order with one change: **U-38 runs in parallel with
U-35b, and both land before U-37.**

```text
U-34 ─► U-35a ─► U-36 ─┬─► U-35b ─┐
                       └─► U-38  ─┴─► U-37 ─► U-39 ─► U-40 …
```

Why:

- U-37's PROC tests run a real `elspeth web` against PostgreSQL, so the
  server's authority needs a production policy (`web/app.py:2316–2320`).
  That is U-38. Without it the server can claim nothing V2.
- U-35b and U-38 touch disjoint files (§7.2), so they can be built at the same
  time without collision. U-38 is size M and depends only on the policy models
  carried by U-33/U-34.
- Plan §5 already needs U-38 early for U-44a (`U-35a + U-38 → U-44a`).
- Until U-41 adds `Composer-Operation-Version` negotiation, the PROC tests admit
  V2 operations by calling the authority's `admit` directly against the shared
  test database. The server process then claims them from SQL. No route change
  is needed before U-41.

**Gate debt that must be paid first (rule R-G).** The Sessions gate is red on
the overlay (§1.8). Each unit binds the writers it lands, in the commit that
lands them:

- U-34 binds `initialize_continuation`, `put_chunk` and `append_complete_snapshot`.
- U-35a binds `start_segment_on_connection` and the claim writers.
- `recover_composer_segment`'s three UPDATEs move into
  `recover_segment_on_connection` **in the unit that first lands that method**.
  That is U-35a, per the carve partition §4 (the v152 `repository.py` hunk).
  U-39 then builds on the moved form.

## 8. Open questions for the maintainer

Everything else in this document is decided. This one is a genuine
trade-off with a user-visible cost.

Decided rather than asked, because the peer spec already weighed it: U-37
applies the peer's ECS `stopTimeout = 60` diff and sets
`composer_async_drain_seconds = 30` on both targets (§3.5). The cost the peer
identified (by reasoning from the zero-overlap deployment, not by measurement)
is at most 30 s of extra ECS downtime, and only when a shutdown
hangs. Without the diff, `D = 10` still fits the 30 s default with a 14 s
margin.

1. **An unknown provider dispatch at kill: fail, or retry later?** When a
   replica dies or drains in the middle of a provider call, the effect is
   `dispatched`, and its result is unknown. This design settles the operation
   `failed`/`worker_lost` and records the effect and its cost as unknown
   (disposition C, §5.3, the peer's R5). On ECS a deploy during a call
   therefore fails that request, and the user resubmits it.
   The alternative is Sol's C4b path: interrupt the segment, resolve the
   attempt's custody, then allow one new physical attempt, with real and
   possibly doubled cost. That keeps the request alive across a deploy, but it
   needs a custody-resolution owner that does not exist yet.
   **Default if not answered:** ship settle-as-failed in 0.8.10, and record
   the retry path as a later improvement. V2 is default-off in 0.8.10, so the
   exposure is limited to operators who enable it.
