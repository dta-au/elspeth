# `delete_blob` — retire an unretained session artifact

Assessment baseline: `3b28d537be98234da8135c418bf185a998c18b68` (0.8.9). Reconnaissance only. **Overall confidence: High for traced custody semantics and focused tests. The identity-spelling guard miss (delete_blob-N1), the unconverted staging `ValueError` (N3) and the unpreviewed bound-blob proposal (N2) are demonstrated by lane-private probe runs (§7.1).**

## 1. Purpose and usage

Select this tool to delete a session artifact after removing composition bindings and when durable work no longer retains it. It deletes artifact storage and metadata, not graph components or historical audit records. Requires session engine/ID, data root, and a live exact operation authority. Composer MCP excludes it and the default planner does not advertise it; only the freeform loop does. Destruction is subject to explicit approval when the session's `trust_mode` is `explicit_approve` ([gate](../../../../src/elspeth/web/composer/tool_batch.py#L1728)); otherwise it runs immediately.

## 2. Contract

Required `blob_id: string`; extra fields are forbidden ([`BlobIdArgumentsModel`](../../../../src/elspeth/web/composer/tools/blobs.py#L115)). A non-string or extra field fails the model and raises a `ToolArgumentError`. A string that does not parse as a UUID returns a repairable failure from the [UUID boundary](../../../../src/elspeth/web/composer/tools/blobs.py#L518). That boundary accepts every spelling Python's `UUID()` accepts: upper case, braces, `urn:uuid:` and unhyphenated hex. Success returns `{"blob_id": <the caller's raw string>, "deleted": true}` with the original composition state/version, `affected_nodes=()` and a fresh `state.validate()` ([`_discovery_result`](../../../../src/elspeth/web/composer/tools/_common.py#L1279)). It is an uncached `BLOB_MUTATION`, blob-store-only effect, and has no selected response contract (measured: `response_contract=None`). It must not be classified as a read just because its result is built with a discovery-shaped envelope.

Deletion is refused for current-composition references (checked by the handler only), active runs, pending proposals and in-progress forks (checked by the repository). Each refusal returns `success=false` with a free-text `rejected_mutation` message and **no `error_code`** ([catch](../../../../src/elspeth/web/composer/tools/blobs.py#L1854)). Ownership uses exact session authority, not an ambient blob ID. Missing context or data root returns failure. Stale or mismatched authority raises `AuditIntegrityError` ([authority](../../../../src/elspeth/web/composer/tools/blobs.py#L1487)). Byte/hash disagreement raises `BlobIntegrityError` or `AuditIntegrityError` and is not softened. A missing or foreign blob returns failure `Blob <uuid> not found`. On this tool that is not a successful no-op, although the REST route treats the same case as an idempotent 204 (§3.1). A durable deletion that was committed but still awaits cleanup is completed by a retry through the deletion ledger. Thus “retry after interrupted committed deletion” and “repeat an already completed deletion with no receipt” are different paths.

## 4. Alternative paths

Deletion of an unbound, unretained blob goes through the shared ledger and reports completion only after the driver returns. A blob bound in the current composition under its canonical or upper-case ID is refused without altering the graph. A bound blob named by a braced, `urn:uuid:` or unhyphenated spelling is **not** refused: its bytes and metadata row are deleted (delete_blob-N1, demonstrated in §7.1 P1). A missing metadata row can still have a committed cleanup obligation, atomic or ledger; the driver distinguishes that from genuine absence. If filesystem cleanup was interrupted after the metadata commit, a retry can finish the tombstone purge. Foreign-session IDs read as not found. A caller may not supply a proposal ID to bypass retention: it comes only from server-owned execution context, and [`pending_proposal_reference_id`](../../../../src/elspeth/web/sessions/proposal_blob_refs.py#L183) revalidates it. A pending `delete_blob` proposal is itself a retention reference to its target (`delete_blob` is in `_TOP_LEVEL_BLOB_TOOLS`). So two pending deletes of one blob block each other's acceptance until one is rejected, and a direct REST delete of that blob returns 409. This is the same intended behaviour tested for update ([second pending reference](../../../../tests/unit/web/sessions/test_blob_proposal_accept.py#L268), [direct delete retained](../../../../tests/unit/web/blobs/test_service.py#L852)).

## 5. Usability assessment

The terse model description does not explain retention eligibility, approval gating, the unchanged version, or the difference between completed deletion and recoverable cleanup. **BOS-04 — source-established lifecycle limitation, High confidence, narrowed:** on the freeform `auto_commit` route, a fresh model call carries no advertised replay identity or declared retry category for an interrupted committed effect, although the storage driver records that state. The proposal-accept route **does** have receipt-backed replay: an applied-effect receipt is written in the metadata commit, and a retried accept returns the prior outcome without re-executing. [`test_retry_after_blob_effect_before_proposal_settlement_does_not_reexecute`](../../../../tests/unit/web/sessions/test_blob_proposal_accept.py#L412) tests this, parameterised over `delete_blob`. A version comparison alone cannot establish whether deletion happened; the orchestrator must inspect the semantic result.

**delete_blob-N1 — retention-guard miss on non-canonical UUID spelling.** *Demonstrated* end to end at the `execute_tool` dispatch level (§7.1 P1); a full freeform compose-loop turn was not driven. High confidence. The handler admits any `UUID()`-parseable string, reads and deletes by `UUID(blob_id)`, but compares the **raw** string in the live-composition guard. The guard uses [`names_same_blob`](../../../../src/elspeth/contracts/blobs.py#L929), which is case-insensitive equality and is documented as requiring the canonical ID from owned metadata. Measured against a state whose source carries `blob_ref=<id>`, and separately `path="blob:<id>"`:

```text
canonical  validation_error=None UUID==True blob_ref_guard=True  sentinel_guard=True
upper      validation_error=None UUID==True blob_ref_guard=True  sentinel_guard=True
nohyphen   validation_error=None UUID==True blob_ref_guard=False sentinel_guard=False
braced     validation_error=None UUID==True blob_ref_guard=False sentinel_guard=False
urn        validation_error=None UUID==True blob_ref_guard=False sentinel_guard=False
```

Only a raw `path` equal to `storage_path` is still caught, because it is compared against the row's own path. The repository guards check forks, proposals and active runs only, so nothing downstream catches a binding in the current, not-yet-run composition. Consequence, measured (§7.1 P1): with the source bound by `blob_ref` or by `path="blob:<id>"`, `delete_blob` called through `execute_tool` with a hyphenless, braced or `urn:uuid:` spelling returned `success=True`, removed the storage file and the metadata row, and left the passed composition binding the deleted ID. The canonical and upper-case spellings were refused with bytes and row intact. That `execute_tool` call is what freeform `auto_commit` dispatches, so an accepted composition there can be left with a dangling binding. `update_blob` has the identical pattern ([L1741](../../../../src/elspeth/web/composer/tools/blobs.py#L1741)) and is also demonstrated: the same three spellings returned `success=True` and replaced the bound blob's bytes. In `explicit_approve`, staging compares raw text to `blobs.id` and refuses the non-canonical spelling, so the bypass is not reachable there (measured, §7.1 P2: no proposal is created). That refusal is a raw `ValueError` that ends the turn; see delete_blob-N3. This is the inverse of BOS-03: one helper accepts a spelling that a later comparison does not normalise.

**delete_blob-N2 — demonstrated (§7.1 P3, two halves), High confidence:** in `explicit_approve`, a destructive blob-only call is staged without preview. Staging half: a `delete_blob` of a blob bound by the persisted current state ran no handler (`handler_calls == []`), created a pending proposal and returned `APPROVAL_REQUIRED` to the model; the `set_metadata` control in the same mode did run its one preview. Accept half: accepting such a proposal through the real accept route returned 422 `proposal_validation_failed` with “is referenced by the current composition and cannot be deleted; unbind it first”, marked the proposal `rejected` and left the bytes intact. The halves ran in separate harnesses, not as one chained session. So the user is asked to approve a deletion that the accept route then refuses, while the model was told `APPROVAL_REQUIRED … stop`. It is not known whether the absent preview is a deliberate choice, since preview would perform the effect. A read-only eligibility check is what is missing.

**delete_blob-N3 — demonstrated (§7.1 P2), High confidence:** under `explicit_approve`, an unknown, foreign or non-canonical (including upper-case) `blob_id` makes [`create_composition_proposal`](../../../../src/elspeth/web/sessions/mutation_capabilities.py#L129) raise `ValueError` from `validate_proposal_blob_references`. No handler in the [staging block](../../../../src/elspeth/web/composer/tool_batch.py#L2179) converts it, and [`_await_started_tool_stage`](../../../../src/elspeth/web/composer/tool_batch.py#L931) handles only cancellation. Measured for a random UUID, the upper-case spelling and the hyphenless spelling of an existing ready blob: `builtins.ValueError: Proposal references blob '<raw>', but that blob does not exist` escapes `_compose_loop`. No `ComposerToolInvocation` is recorded for the call id (measured). By source, the dispatch had already begun, because `audit` is bound at the staging call, so it is left open. No tool chat row and no proposal are written. The canonical control created a pending proposal with a `success` invocation. The turn therefore ends instead of returning a repairable tool failure. How the route or async operation then reports the escaped `ValueError` was not run. Foreign-session IDs were not probed separately; they take the same `ValueError` path by source.

**delete_blob-N4 — source-established route divergence; whether it is a defect is unverified:** the REST delete has no current-composition guard. A user can delete a blob the current graph binds. The tool cannot do this for canonical spellings. This may be an intended user-authority difference: the route docstring covers idempotency, not bindings.

**delete_blob-N5 — result-shape inconsistency, Low; the raw echo is demonstrated (§7.1 P1, e.g. `data.blob_id='urn:uuid:…'`), the rest source-established:** success echoes the caller's raw spelling of `blob_id`, while `update_blob` returns `str(result.id)` and `BlobNotFoundError` text uses the canonical form. Refusals carry no `error_code`, so the model cannot distinguish retention reasons without parsing prose.

**delete_blob-N6 — source-established audit-documentation defect, Low:** the [redaction justification](../../../../src/elspeth/web/composer/redaction.py#L3537) cites `tools.py:1432-1441`, a file that does not exist (`ls` fails). It describes the response as including “the affected node id list reflecting any pipeline references to the now-removed blob”. The actual payload is `{blob_id, deleted}` with `affected_nodes=()`. The safety conclusion (no content echoed) still holds.

Current composition, run, proposal and fork refusal is an **intended restriction**. Apart from N1, no defect in durable deletion itself was demonstrated by this lane. The workaround for a refusal is to release the actual retaining workflow through its normal lifecycle; repeatedly asking to delete must not weaken retention. Until N1 is fixed, pass only the exact ID returned by inventory or create.

## 6. Structural remediation

Expose a shared artifact-effect outcome with operation identity and states such as refused, committed and cleanup pending, backed by the existing ledger. For the proposal route, wrap the existing `proposal_blob_effect_receipts` receipt rather than recreating it. Keep eligibility and cleanup ownership in the blob custody service. Normalise blob identity once at admission (R2, shared with BOS-03) so every downstream comparison sees the canonical ID. Tool declarations should advertise destructive approval and retry semantics, and orchestration should recover through the receipt rather than guessing from missing rows or graph state.

Acceptance: deletion of a valid unretained blob removes storage and metadata. Each independent retention reason refuses without storage change, **including the current-composition reference under every accepted spelling of the ID**. Cross-session and stale-fence requests fail closed. Deaths before and after the metadata commit reconcile correctly. Replay of a committed deletion returns its prior outcome on every route, as the proposal route already does. Malformed IDs do not enter durable work. Compatibility risk is Medium for new result/receipt semantics, especially changing current missing-row failures into idempotent outcomes. Preserve current retention restrictions and historical audit evidence.
