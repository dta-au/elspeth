## 1. Purpose and usage

Discover the sink plugins that this request's policy snapshot makes selectable. This feeds the orchestrator's capability search for terminal publication. It does not reserve a plugin, and it does not prove that a particular configuration can execute.

*Corrected:* the first pass said the listing covers plugins the request is "permitted and locally equipped to configure". The only credential readiness the snapshot checks is a plugin's *unconditional* secret requirements ([availability.py:44](../../../../src/elspeth/web/plugin_policy/availability.py#L44), [:146](../../../../src/elspeth/web/plugin_policy/availability.py#L146)). No installed sink declares any (see `list_sinks-N2`). So for sinks, "available" means installed, authorised, not web-prohibited and, for `power_automate`, configured with allowed origins. It does not mean credentialed.

Call it before choosing a sink implementation. Dispatch requires a `PolicyCatalogView` and the identical `PluginAvailabilitySnapshot`: a mismatch raises `ValueError("plugin_snapshot_catalog_mismatch")` ([_dispatch.py:909](../../../../src/elspeth/web/composer/tools/_dispatch.py#L909)). It needs no blob, secret-service or execution context. Gates, queues and other structural nodes are not plugins, so these listings do not include them. In practice the freeform prompt and the planner request already carry a sink *selection index* (names, purpose, required-option names, `not_for`, capability tags, prohibited entries; see §3.1 R6). That makes `list_sinks` mainly a *detail* read: it returns usage guidance, example YAML, per-field types and defaults, composer hints, capability declarations and audit characteristics, which the digest omits.

## 2. Contract

Arguments must be exactly an empty object, and extra keys are rejected. How the rejection reaches the caller depends on the route (*Corrected*: the first pass gave one outcome). Demonstrated in memory:

| Caller flags | `{"x": 1}` outcome |
|---|---|
| `validate_arguments=True, raise_schema_argument_errors=True` (freeform, planner, MCP) | raises `ToolArgumentError` category `schema_shape` → audited ARG_ERROR |
| `validate_arguments=True` only | failed `ToolResult`, message `Invalid arguments for tool 'list_sinks': arguments contains unsupported properties.` |
| neither flag (direct internal caller; none exist in production) | handler's own `_validate_mutation_arguments` raises `ToolArgumentError` category `model_validation` ([transforms.py:200](../../../../src/elspeth/web/composer/tools/transforms.py#L200)) |

Under `openai_strict` the provider must send `{"_elspeth_no_arguments": true}` exactly. `decode_wire_arguments` turns that into `{}` and rejects any other shape as `wire_envelope` ([wire_projection.py:930](../../../../src/elspeth/web/composer/tools/wire_projection.py#L930)).

The result is a `ToolResult` with keys `success`, `version`, `validation`, `affected_nodes` and `data`. These were measured with `to_dict()`. `data` holds `{available, prohibited}`. Each `available` entry is a full `PluginSummary` with exactly 14 keys ([inventory_response_contracts.py:161](../../../../src/elspeth/web/composer/inventory_response_contracts.py#L161)): `name`, `description`, `plugin_type`, `config_fields`, `usage_when_to_use`, `usage_when_not_to_use`, `example_use`, `capability_tags`, `aggregation_output_modes`, `web_config_authority`, `policy_capabilities`, `audit_characteristics`, `composer_hints` and `secret_requirements`. `prohibited` lists only the categorical `WEB_SURFACE_PROHIBITED` reason (`plugin_not_allowed_on_web`), each entry with one static explanation ([plugin_policy_disclosure.py:11](../../../../src/elspeth/web/composer/plugin_policy_disclosure.py#L11)). Other unavailable plugins are omitted by design. Demonstrated: `azure_blob` declined as `credential_unavailable` or `plugin_not_enabled` is absent from both arrays, while declined as `plugin_not_allowed_on_web` it appears only under `prohibited`.

There is no write, approval requirement, provider call or retry. `validation` is the current composition's full validation, which is not about the listing. On an empty state it is `is_valid=false`, measured. *Corrected:* successful responses are cached **only by the freeform compose loop**, within one compose call ([service.py:2500](../../../../src/elspeth/web/composer/service.py#L2500)). The planner and MCP execute the handler on every call, and failures are never cached. The policy/plugin set is a per-request snapshot. Each compose call, and each REST catalogue request, builds its own snapshot ([routes.py:33](../../../../src/elspeth/web/catalog/routes.py#L33)), so repeated calls are observationally idempotent within one snapshot only. This is discovery at that scope, not a live credential-health probe.

This is discovery: the handler returns the composition state unchanged, and the planner asserts this ([pipeline_planner.py:4909](../../../../src/elspeth/web/composer/pipeline_planner.py#L4909)). On the **web** routes, successful inventory data is admitted under `PLUGIN_INVENTORY_RESPONSE_CONTRACT` before audit and disclosure ([tool_batch.py:3053](../../../../src/elspeth/web/composer/tool_batch.py#L3053), planner `admit_discovery_result`). *Corrected:* the MCP route does **not** admit through that contract. It serializes `result.to_dict()` with `_ensure_serializable` ([server.py:420](../../../../src/elspeth/composer_mcp/server.py#L420)). The output is byte-equal to the web wire for today's catalogue (demonstrated), but no test pins that equality (`list_sinks-N7`). In both provider dialects the wire projection is decoded to canonical arguments before dispatch, and the strict transport representation grants no different authority. `ToolResult.success` records operation admission; `validation.is_valid`, runtime preflight, review and execution admission answer separate questions. Owned-code and audit-integrity failures (malformed producer data raises `FrameworkBugError`, [inventory_response_contracts.py:21](../../../../src/elspeth/web/composer/inventory_response_contracts.py#L21)) escape as faults rather than being reclassified as ordinary invalid model input.

## 4. Alternative paths

Normal operation projects `available` entries from plugin-owned declarations through the policy and operator-profile views. An empty `available` is a valid discovery result, not an error. An absent SDK, an unapproved plugin, a missing operator profile, missing `power_automate` origins, or a missing *unconditional* credential can each remove an entry without placing it in `prohibited`. Invalid arguments are rejected before any requested access (route-specific form in §2). A fault in an admitted catalogue or schema remains an owned-code failure and must not be disguised as an unknown plugin. Freeform cache hits rebuild the current state envelope and re-admit the cached producer response ([discovery_cache.py:107](../../../../src/elspeth/web/composer/discovery_cache.py#L107)). MCP uses a trained-operator policy view, so a name visible there need not be selectable in an authenticated web request.

*Corrected (named-probe workaround):* the non-mutating way to learn why a specific sink is absent is `get_plugin_schema(plugin_type="sink", name=…)`. Demonstrated in memory: for `azure_blob` it returns `success=false` with closed error code `credential_unavailable`, `plugin_not_enabled` or `plugin_not_allowed_on_web` matching the snapshot reason, and `plugin_not_enabled` when the plugin is installed but absent from `available` with no recorded reason. This is pinned for transforms by [test_tools_discovery.py:299](../../../../tests/unit/web/composer/test_tools_discovery.py#L299). The first pass named only "a named selection attempt or operator inspection".

## 5. Usability assessment

**SG-05: intended disclosure restriction with a planning limitation; high confidence.** The orchestrator sees selectable plugins and categorical bans, but not every temporarily unavailable capability or its repairable prerequisite, so it cannot tell from an absent name whether installation, credentials, a profile or authorisation is missing. The policy view documents this as a deliberate choice ([policy_view.py:126](../../../../src/elspeth/web/catalog/policy_view.py#L126)); it is not evidence of a registry defect. Workaround: `get_plugin_schema` on the named sink returns the closed reason (§4). Flat options are mostly usable from the listing, but it is not sufficient for configuring any sink on its own (`list_sinks-N1`). No defect in this handler's own control flow was demonstrated. The findings below concern result fidelity, guidance and adjacent surfaces.

## 6. Structural remediation

Keep authoritative configuration and capability declarations on the sink plugins, policy visibility in the policy layer, and capability selection in the orchestrator. If capability planning needs repairable absences, add a deliberately bounded availability query or report rather than bypassing policy or making each list disclose private bindings. All three inventory tools, schema/assistance lookup and mutation failures must share the same snapshot and closed reason vocabulary. Acceptance: a selectable plugin appears with plugin-owned defaults; a banned plugin appears only under `prohibited`; a missing local prerequisite is reported through the authorised availability surface without exposing secret values; cache reuse cannot transplant another principal's snapshot. Compatibility: preserve `available`/`prohibited` and make additional availability evidence explicitly versioned or additive. Implementation risk is medium because disclosure and cache scope are security boundaries.

Added by this review. (i) Make *conditional* credential needs a plugin-owned declaration, for example per-auth-mode secret requirements, rather than having the catalogue infer them from top-level names (`list_sinks-N2`). The owner is the sink plugins and `CatalogServiceImpl._secret_requirements`, not the composer. (ii) Choose one honest role for the listing, either selection detail or configuration contract, and make the description, digest guidance and field projection agree (`list_sinks-N1`, G1/G2). The smaller option is to describe it as a selection/detail index and leave option authoring to `get_plugin_schema`. (iii) Make the cache-hit audit row carry the same envelope the model received (`list_sinks-N5`); this is cross-cutting for every cacheable discovery tool.
