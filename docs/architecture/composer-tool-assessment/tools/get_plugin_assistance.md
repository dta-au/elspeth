# `get_plugin_assistance` assessment

Baseline: `3b28d537be98234da8135c418bf185a998c18b68` — 0.8.9. Reconnaissance and design only.

## 1. Purpose and exposure

Retrieve plugin-owned guidance and examples, either discovery guidance or issue-specific repair advice. Plugins remain the author of these facts; the orchestrator consumes them. It is a cacheable discovery tool, separate from generic validation-code explanation.

It is the only Composer tool that returns a plugin's `examples` (before/after configuration sketches). `PluginSchemaInfo` and `PluginSummary` carry the same discovery-time `composer_hints` but no examples ([src/elspeth/web/catalog/schemas.py:85](../../../../src/elspeth/web/catalog/schemas.py#L85), [src/elspeth/web/catalog/service.py:331](../../../../src/elspeth/web/catalog/service.py#L331)). Measured over the installed registry (60 source/transform/sink classes, not the web-visible set): all 60 publish discovery assistance, only `llm` publishes discovery examples (3), and six plugins publish issue-code guidance for exactly six codes (see §7).

## 2. Contracts and authority

Requires plugin_type and plugin_name; optional issue_code may be omitted or null. The owned argument model is `GetPluginAssistanceArgumentsModel` (`extra="forbid"`, `issue_code: str | None = None`, no length or emptiness bound) ([src/elspeth/web/composer/tools/generation.py:296](../../../../src/elspeth/web/composer/tools/generation.py#L296)). The response names plugin identity and issue code, with summary, suggested fixes, examples and composer hints. No published assistance is a successful empty-guidance result. The handler first validates arguments against that model ([generation.py:2335](../../../../src/elspeth/web/composer/tools/generation.py#L2335)), then admits the plugin selection against the request policy snapshot ([generation.py:2340](../../../../src/elspeth/web/composer/tools/generation.py#L2340)), before any catalog, manager or plugin access.

The selected response contract is `AssistanceResponse` (strict, `extra="forbid"`, exact wire order; examples must be exactly `{title, before, after}` with JSON-closed leaves) ([src/elspeth/web/composer/tools/_generation_responses.py:154](../../../../src/elspeth/web/composer/tools/_generation_responses.py#L154), [_generation_responses.py:121](../../../../src/elspeth/web/composer/tools/_generation_responses.py#L121)). It is enforced only on routes that call `admit_discovery_result` (freeform loop and planner), not on Composer MCP (§3.1).

Result identity sources differ by branch: the empty branch echoes the request's `plugin_name` and `issue_code` ([generation.py:2357](../../../../src/elspeth/web/composer/tools/generation.py#L2357)); the populated branch takes `plugin_name` and `issue_code` from the returned `PluginAssistance` while `plugin_type` comes from the request ([generation.py:2371](../../../../src/elspeth/web/composer/tools/generation.py#L2371)). Nothing checks that the returned identity agrees with the request. Measured at baseline: every discovery payload's `plugin_name` equals the class name and `issue_code` is `None`, and every issue-code payload echoes the requested code, so no live divergence exists.

## 3. Source trace to the user

Handler validates arguments → checks policy → probes the projected schema (`context.catalog.get_schema`, result discarded, used only to raise for an inconsistent catalog) → resolves the concrete plugin class from the shared plugin manager → calls `get_agent_assistance(issue_code=...)` → applies `PolicyCatalogView.project_agent_assistance` (only when the hook returned non-`None`) → encodes examples → admits selected response contract ([src/elspeth/web/composer/tools/generation.py:2335](../../../../src/elspeth/web/composer/tools/generation.py#L2335), [generation.py:2343](../../../../src/elspeth/web/composer/tools/generation.py#L2343), [generation.py:2353](../../../../src/elspeth/web/composer/tools/generation.py#L2353), [src/elspeth/web/catalog/policy_view.py:203](../../../../src/elspeth/web/catalog/policy_view.py#L203)).

`project_agent_assistance` returns raw assistance unless the view has a profile registry *and* the principal has usable aliases for that plugin; then `OperatorProfileRegistry.public_assistance` replaces it only for three exact resolver types (S3 source, Textract document analysis, Azure AI Search), returning a fixed profile summary and hints and dropping `suggested_fixes` and `examples` ([src/elspeth/web/plugin_policy/profiles.py:1690](../../../../src/elspeth/web/plugin_policy/profiles.py#L1690)). The other operator-profiled resolvers (`llm` source/transform, the two Bedrock guardrails) fall through to `return full_assistance` ([profiles.py:1730](../../../../src/elspeth/web/plugin_policy/profiles.py#L1730)).

The freeform exposure is `get_tool_definitions` → wire projection → `composer_loop_tool_definitions`; the planner selects an ordered discovery subset, so exposure can narrow by phase ([src/elspeth/web/composer/tools/_dispatch.py:311](../../../../src/elspeth/web/composer/tools/_dispatch.py#L311), [src/elspeth/web/composer/provider_gateway.py:391](../../../../src/elspeth/web/composer/provider_gateway.py#L391), [src/elspeth/web/composer/pipeline_planner.py:1647](../../../../src/elspeth/web/composer/pipeline_planner.py#L1647)). Public freeform calls pass credential/batch admission, wire decoding and closed semantic-schema admission before `execute_tool` ([src/elspeth/web/composer/tool_batch.py:1010](../../../../src/elspeth/web/composer/tool_batch.py#L1010), [src/elspeth/web/composer/tool_batch.py:1399](../../../../src/elspeth/web/composer/tool_batch.py#L1399), [src/elspeth/web/composer/tool_batch.py:3008](../../../../src/elspeth/web/composer/tool_batch.py#L3008)). Dispatch-level JSON-schema validation is route-conditional (`validate_arguments` / `raise_schema_argument_errors` on `execute_tool`; always on in `execute_discovery_tool_with_context` and Composer MCP), but the handler's own argument model applies on every route, including direct handler calls ([src/elspeth/web/composer/tools/_dispatch.py:925](../../../../src/elspeth/web/composer/tools/_dispatch.py#L925), [_dispatch.py:1027](../../../../src/elspeth/web/composer/tools/_dispatch.py#L1027)).

After the handler, `finalize_tool_result` normalizes validation; discovery result admission selects the declared response contract before serialization ([src/elspeth/web/composer/tools/_dispatch.py:752](../../../../src/elspeth/web/composer/tools/_dispatch.py#L752), [src/elspeth/web/composer/tool_batch.py:3052](../../../../src/elspeth/web/composer/tool_batch.py#L3052)). The loop records the invocation, sends a tool result back to the model, stores successful results in the within-compose discovery cache, and persists its redacted tool-turn cohort; subsequent operation settlement owns user-facing success/failure ([src/elspeth/web/composer/tool_batch.py:3344](../../../../src/elspeth/web/composer/tool_batch.py#L3344), [tool_batch.py:3368](../../../../src/elspeth/web/composer/tool_batch.py#L3368), [src/elspeth/web/composer/service.py:1515](../../../../src/elspeth/web/composer/service.py#L1515), [src/elspeth/web/sessions/composer_turn.py:1051](../../../../src/elspeth/web/sessions/composer_turn.py#L1051)). ToolCallCard renders the recorded outcome and explanatory tooltip rather than giving this tool its own direct action button ([src/elspeth/web/frontend/src/components/chat/ToolCallCard.tsx:90](../../../../src/elspeth/web/frontend/src/components/chat/ToolCallCard.tsx#L90)). A completed lookup does not imply pipeline readiness.

## 4. Branches, failures and recovery

Discovery and issue-code modes share the plugin-owned hook. Missing guidance returns null summary and empty lists. At baseline every installed plugin publishes discovery guidance, so the empty branch is reached in practice by an issue code the plugin does not recognize, including `""` (measured: every plugin returns `None` for `""`, `"general"` and an unknown code). In issue-code mode the plugin's discovery `composer_hints` are not included, so an unrecognized code returns *less* than discovery mode. Policy refusal must not leak blocked configuration through examples: the refusal returns before the schema probe, manager lookup or hook. A manager/catalog inconsistency after admission is a controlled-code error, not a fabricated no-assistance result. Argument rejection raises `ToolArgumentError` from the handler's own model even when dispatch-level schema validation is off (`test_invalid_plugin_type_returns_failure` calls `execute_tool` without dispatch flags and expects the raise; its docstring says "surfaces as failure"). Expected policy/semantic refusal is a failed result on the current state; controlled-code exceptions remain framework/plugin failures, with the executed prefix and audit evidence retained by the common loop. Cancellation, timeout and final persistence failure belong to the request/operation owner, not a handler-local retry. None of these discovery handlers commits graph changes or needs a proposal approval step. Retrying a lookup can recover an argument or infrastructure problem but cannot repair the graph by itself.

**Cache, idempotency, concurrency and retry:** `ToolKind.DISCOVERY`, `cacheable=True`. The freeform cache is per compose call and only successful results are stored (`cached_discovery_payload` raises on a failure), so a policy refusal is never cached. Successful no-assistance responses are cached too; they mean this plugin published no guidance for that request, not that help can never exist. The cache key is `tool_name + json.dumps(decoded_arguments, sort_keys=True)` ([src/elspeth/web/composer/discovery_cache.py:121](../../../../src/elspeth/web/composer/discovery_cache.py#L121)), so it includes plugin identity and `issue_code` when present. On `openai_strict` omitted and `null` share a key (null is stripped at decode); on `none` they are two keys for one request, which costs an extra handler run but is not incorrect. The planner route has no cache. Same-input repetition has no graph/store effect but creates another audit record. The handler owns no lock or retry loop; request policy projection remains snapshot-bound, while plugin code is process-loaded. Future hot reload would require explicit cache/version invalidation rather than assuming this cache observes it.

## 5. Defects, restrictions and hypotheses

The probe runs in §7.1 demonstrated N1, N3, N4 and N5. None of them shows the handler emitting unsafe output: N3 is an admission gap, N4 needs a test double to diverge, and N1 and N5 are route and guidance defects. Structural limitation: helpfulness and breadth depend on each plugin publishing meaningful assistance; empty guidance is truthful but does not solve an authoring problem. The shared plugin manager and policy catalog are distinct collaborators, so their identity agreement remains a required invariant. This is a review lens rather than a proven divergence.

Findings from this review (provisional IDs; the coordinator renumbers):

- **get_plugin_assistance-N1 — demonstrated route gap (§7.1 P1, P5).** The planner cannot obtain the `issue_code` it is told to pass. A `semantic_contract_violation` entry there gets a static explanation/fix, plus `contract` = `SchemaContractDetail(producer, consumer)` with no code ([src/elspeth/web/composer/_semantic_validator.py:446](../../../../src/elspeth/web/composer/_semantic_validator.py#L446), [pipeline_planner.py:2530](../../../../src/elspeth/web/composer/pipeline_planner.py#L2530)). ### 5.1 Guidance parity

What the model is told, compared with what the handler does (grep instrument: `grep -n "get_plugin_assistance\|issue_code\|requirement_code\|plugin assistance\|composer_hints"` over both skills, `prompts.py`, `pipeline_planner.py`; known positives matched in each file except `prompts.py`, where `get_plugin_schema` matched and this tool did not):

- **G1 (wrong for the planner route; see N1).** `pipeline_composer.md:455-457` says "a `requirement_code` is the `issue_code` to pass to `get_plugin_assistance`". That is true in freeform. The planner is told the same thing in `planner_authoring_aids.py:1937` ("Use get_plugin_assistance and explain_validation_error for structured repair when a proposal is rejected") and `pipeline_capabilities.md:35`, but its rejection feedback never contains the code. Neither skill says to address the entry's `consumer_plugin` or how to derive `plugin_type` (sink consumers appear as `output:<name>`). ## 6. Ownership, remediation and dependencies

Plugin maintainers own assistance content; catalog policy owns safe projection; tool owner owns shape. First-class plugin work should standardize usable capabilities/examples alongside runtime contracts and preserve the ability to report no assistance honestly. Test examples by validating their after-configurations through plugin configuration admission, not just checking they are dictionaries.

Structural items arising from this review: carry the semantic `requirement_code` (and consumer plugin identity/family) as a closed structured fact in planner candidate feedback, under the same custody rules as `SchemaContractDetail` (N1, R2-class observation completeness). Decide whether producer `fact_code` guidance is a supported channel; if so, publish the code in `semantic_contracts`; if not, re-key or remove `web_scrape`'s orphaned guidance (N2). Give every `OPERATOR_PROFILED` resolver an explicit `public_assistance` arm (or make the absent arm fail closed) and route the validation-suggestion caller through the same projection (N5, N7).

**Implementation risk:** Medium for shared assistance/policy changes because examples can expose forbidden configuration. Preserve policy projection before disclosure.
