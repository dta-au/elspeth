# `remove_node` — independent tool assessment

Baseline: ELSPETH **0.8.9**, `3b28d537be98234da8135c418bf185a998c18b68`. Reconnaissance and remediation design only. Incoming `.10 lite` changes are outside this assessment and require affected-source reinspection.

## 1. Purpose and usage

Remove one node and every explicit edge touching it. It is deletion, not a model-independent bypass or reconnect operation.

Select when a requested component should disappear. The orchestrator must plan the resulting runtime connection changes and downstream review consequences.

## 2. Contract

Required id:string; unknown keys reject. Missing node returns node_not_found and original state/version. Existing removal drops that NodeSpec and every EdgeSpec whose `from_node` or `to_node` string equals the id, increments version once, reports the removed id and the visual edge endpoints as `affected_nodes`, and reconciles reviews. It does not rewrite surviving input/on_success/on_error/routes/fork/branch/scope references or create a replacement edge. The handler never calls a plugin or deletes source/blob/output artifacts; the post-removal `CompositionState.validate()` in `_mutation_result` does read plugin collision surfaces ([state.py:5254](../../../../src/elspeth/web/composer/state.py#L5254)), so "no plugin involvement" is true of the handler, not of the result. A repeated removal is a failed call, not idempotent success. Validation can report an incomplete graph after successful deletion; public explicit approval applies.

Measured in this review (in-memory `execute_tool` through the test-fixture dispatcher, not a service run): a linear `source → t1 → t2 → out` removal of `t1` advanced version 8 → 9 exactly once; a removal that reopens a resolved review (`_reviewed_shield_state`, remove `mid`) advanced 1 → 2, so reconciliation does not add a second bump. The success envelope keys were `affected_nodes, applied_component, success, validation, validation_delta, version`; there is no `data` and the removed NodeSpec is not returned.

The handler returns an immutable candidate; it does not itself durably save the conversation. In web explicit_approve mode, the operation is staged as a proposal and re-admitted on acceptance. Otherwise the enclosing tool batch applies the accepted state, and the session turn persists it under its operation authority. Across both provider dialects, the provider wire projection is decoded to canonical arguments before dispatch; strict transport representation does not grant different authority. A ToolResult's `success` records operation admission, while `validation.is_valid`, runtime preflight, review and execution admission answer separate questions. Audit-integrity failures escape as faults; note, however, that `_reconcile_graph_mutation_reviews` maps any `KeyError`/`TypeError`/`ValueError` raised inside review reconciliation to an ordinary `review_reconciliation_failed` rejection ([transforms.py:1610](../../../../src/elspeth/web/composer/tools/transforms.py#L1610)), see remove_node-N8.

## 4. Alternative paths

Normal deletion preserves all unrelated nodes and outputs. Runtime consumers that read the removed node's connection may dangle; removed scope openers or barriers can leave structural obligations for validation (for example `scope_opener_unknown`, [state.py:1208](../../../../src/elspeth/web/composer/state.py#L1208)). Review reconciliation reopens stale downstream evidence or rejects malformed retained authority. If reconciliation fails, the tool returns the original immutable state. Affected_nodes is collected from visual edges, so it is an edit/projection aid rather than a complete semantic dependency inventory. Missing node rejection must not be confused with already-removed receipt recovery.

When the removed id collides with a source or output name (a draft that already carries `node_id_collides_with_source_or_sink`), the endpoint-string filter also deletes that source's or output's edges (remove_node-N3). Removing a node whose plugin is now policy-hidden is permitted ([test_tools.py:564](../../../../tests/unit/web/composer/test_tools.py#L564)). Removing a deployment-REQUIRED control node leaves its producer and consumer dangling, so the graph is invalid and finalization does not run. `required_control_coverage` appears only as a medium-severity warning. The next mutation that makes the graph valid re-splices the control under the same id (measured, remove_node-N5).

## 5. Usability assessment

**SG-01 — deletion limitation; demonstrated in memory and through the REST accept route.** Accepting a `remove_node` proposal through `POST …/proposals/{id}/accept` returned 200 `committed`. It deleted `t1` and both incident edges and persisted a state with `source_on_success_dangling` (§7.1 probe 2). Removing all incident diagram edges does not repair runtime connection fields. That is a legitimate draft operation, but an orchestrator cannot interpret the response's visual affected_nodes as all runtime dependants. In-memory dispatch with no visual edges returned `affected_nodes=["t1"]` and no `applied_component`, while `source.on_success="rows"` and `t2.input="mid"` were left dangling. The usable repair signal is `validation_delta.new_errors`, which named `source_on_success_dangling` (component `source`) and `node_input_not_reachable` (component `node:t2`). With visual edges present, `affected_nodes` was `["source","t1","t2"]` and the echo carried the source and `t2`. **SG-06 — shared graph/review contract need.** Direct graph deletion and bulk replacement should compute the same affected review anchors. Workaround: read `validation_delta.new_errors` after deletion and explicitly reconnect or remove downstream consumers using model-authored edits; read full state only when the delta is ambiguous (for example, a dependant that was already invalid for the same code).

## 6. Structural remediation

Define a graph deletion candidate with separate deleted components, dangling runtime dependants, visual changes and invalidated reviews. A model-selected bypass/rewire command can be added as a distinct operation with explicit preconditions, rather than make remove_node invent intent. Regression: deletion removes only intended node/incident edges, reports semantic dependants even without visual edges, reopens upstream-bound reviews, refuses malformed authority without partial state, and distinguishes missing-node rejection from completed operation receipt. Endpoint matching must be kind-qualified (node versus source versus output) so that a namespace collision cannot delete another component's edges (N3). Compatibility risk medium/high if affected_nodes or deletion cascades change; retain current deletion semantics during introduction.
