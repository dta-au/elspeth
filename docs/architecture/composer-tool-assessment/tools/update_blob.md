# `update_blob` — replace unbound artifact bytes

Assessment baseline: `3b28d537be98234da8135c418bf185a998c18b68` (0.8.9). Reconnaissance only. **Overall confidence: High for source, focused custody tests, and admission semantics; Medium for the turn-level consequences of the proposal-path findings, which are source-traced, not run.**

## 1. Purpose and usage

Use this tool to replace the UTF-8 content of an existing, **ready** session artifact before it is bound into a composition or retained by active work. It keeps the artifact's identity and the record fields `filename`, `mime_type`, `storage_path`, `created_at`, `created_by`, `source_description` and `status` (the [immutable projection](../../../../src/elspeth/web/coordination/repository.py#L2299)). It rewrites `size_bytes`, `content_hash`, `creation_modality`, `created_from_message_id` and all five `creating_*` provenance columns. It is not a way to silently edit inputs of a graph under review. It requires a session engine and ID, a data root, exact server-owned operation authority, and complete composer provenance context when the bytes are LLM-authored. It is web-only, reached through the freeform loop and proposal acceptance. It is absent from the planner and Composer MCP, and there is no REST replace route (see §3.1).

## 2. Contract

Required arguments are `blob_id: string` and `content: string`; extra fields are rejected. The three argument faults use three channels. A non-UUID `blob_id` returns a failed `ToolResult` (`rejected_mutation`) whose message names `list_blobs`/`list_composer_blobs`/`create_blob` ([`_blob_id_uuid_validation_error`](../../../../src/elspeth/web/composer/tools/blobs.py#L518)). A malformed argument shape raises `ToolArgumentError(MODEL_VALIDATION)`, after the dispatcher's closed-schema check. Non-encodable text (for example a lone surrogate) raises `ToolArgumentError` with no explicit category ([handler](../../../../src/elspeth/web/composer/tools/blobs.py#L1719)). The handler parses a hex-case-variant UUID with `UUID()`, and the repository queries `str(UUID)`, so an upper-case ID resolves to the canonical blob. An in-memory run confirmed this. It differs from the raw-text lookups in BOS-03.

When the tool runs immediately, success returns `blob_id` (canonical), `filename`, `mime_type`, the new `size_bytes` and `content_hash`. The result omits the post-write `creation_modality`/`created_by` and the `originated_in` self-authorship marker that `create_blob` returns. Under `explicit_approve` the model instead receives a successful `APPROVAL_REQUIRED` proposal payload, and the handler has not run (see §3.1 and N5). The declaration is `BLOB_MUTATION` with blob-store-only effects (`ToolEffects((BLOB_STORE,))`, measured). Composition version is unchanged; an in-memory run left version 1 at version 1. There is no authored graph delta. The tool is not cached, and no blob discovery tool is cacheable either, so the discovery cache cannot hold stale blob content after an update (measured: only nine non-blob discovery declarations set `cacheable=True`).

Unlike creation, replacement requires a proposal under `explicit_approve`. The handler refuses a blob referenced anywhere in the supplied composition. Durable custody also guards active runs, pending proposals, in-progress forks and quota, each as a model-visible refusal. **Lifecycle is not a refusal:** a blob whose status is not `ready` (`pending`/`error`, null hash) raises `AuditIntegrityError` (N1). Proposal execution supplies its server-owned proposal ID so that only the proposal being accepted is excluded. Provenance is recalculated for the replacement bytes, and the model cannot write origin metadata directly. When the content is not a substring of the current user message, the result is `llm_generated` with `created_by` unchanged. A user upload therefore records the pair `created_by=user`, `creation_modality=llm_generated` (demonstrated, N10).

The tool takes no caller-supplied expected hash or idempotency key. The handler snapshots metadata, and the replacement coordinator compares the exact record under the custody lock before publication. A mismatch raises `AuditIntegrityError("blob metadata changed before durable replacement")` ([coordinator](../../../../src/elspeth/web/blobs/replacement.py#L260), [test](../../../../tests/unit/web/composer/test_tools_blobs.py#L1542)) rather than a retryable conflict. An identical repeated immediate call succeeds again and rewrites provenance. An in-memory run showed the same `content_hash` and a changed `creating_arguments_hash`. Internal reconciliation of an interrupted replacement is distinct from semantic idempotency of a new call. **The proposal route does have exactly-once replay:** the receipt `proposal_blob_effect_receipts` is written in the commit transaction ([`_record_applied_blob_proposal_effect`](../../../../src/elspeth/web/coordination/repository.py#L3174)). A re-accept that finds the receipt settles the proposal without re-executing the replacement ([route](../../../../src/elspeth/web/sessions/routes/composer/proposals.py#L385), [test](../../../../tests/unit/web/sessions/test_blob_proposal_accept.py#L412)). Owned corruption or stale custody must not be treated as an argument retry.

## 3. Implementation trace

The [handler](../../../../src/elspeth/web/composer/tools/blobs.py#L1694) and [declaration](../../../../src/elspeth/web/composer/tools/blobs.py#L1782) admit [`UpdateBlobArgumentsModel`](../../../../src/elspeth/web/composer/redaction.py#L1610). The handler then checks the UUID, encodes the content, acquires [exact authority](../../../../src/elspeth/web/composer/tools/blobs.py#L1487) and classifies provenance, failing closed without composer context ([line 1728](../../../../src/elspeth/web/composer/tools/blobs.py#L1728)). Next it reconciles interrupted replacements ([line 1735](../../../../src/elspeth/web/composer/tools/blobs.py#L1735)), reads the authoritative blob, and checks [composition references](../../../../src/elspeth/web/composer/tools/blobs.py#L1326) through the per-component walker [`_state_options_reference_blob`](../../../../src/elspeth/web/composer/tools/blobs.py#L1255). That walker is the only guard over the live authored state; the durable layer checks only active-run compositions. [`BlobReplacementCoordinator.replace_blob`](../../../../src/elspeth/web/blobs/replacement.py#L229) owns, in this order:

1. Storage-root validation.
2. The exact-record comparison.
3. Old-byte verification ([L277](../../../../src/elspeth/web/blobs/replacement.py#L277)). This step raises `AuditIntegrityError` when the bytes or hash are absent, before any retention check.
4. [`prepare_blob_replacement`](../../../../src/elspeth/web/coordination/repository.py#L2254): the deletion-ledger check, the ready check, the immutable projection, the [retention edges](../../../../src/elspeth/web/coordination/repository.py#L3116) and quota.
5. The durable stage, swap, commit and purge phases, with fencing, rollback and recovery.

The handler maps `SessionDerivedCustodyError` to not-found, and maps active-run, pending-proposal, fork, quota and `BlobStateError` to the exception text ([L1766–1769](../../../../src/elspeth/web/composer/tools/blobs.py#L1766)). No step of the replacement path raises `BlobStateError`. All other exceptions, including `AuditIntegrityError` and `BlobIntegrityError`, escape the tool-result channel.

The [registry](../../../../src/elspeth/web/composer/tools/_registry.py#L94) and [model catalogue](../../../../src/elspeth/web/composer/tools/_dispatch.py#L311) expose the tool. [Public dispatch](../../../../src/elspeth/web/composer/tools/_dispatch.py#L795) enforces the closed schema and the credential guard; the guard deliberately replaces `content` with `<data-plane-content>` before scanning ([credential guard](../../../../src/elspeth/web/credential_guard.py#L261)), so blob bytes are out of credential-scan scope by design. [Approval classification](../../../../src/elspeth/web/composer/tools/discovery.py#L111) and the [tool-batch approval decision](../../../../src/elspeth/web/composer/tool_batch.py#L1728) precede effect execution. The worker supplies proposal and provenance context, and [audit finalization](../../../../src/elspeth/web/composer/audit.py#L812) records result evidence. [Frontend cards](../../../../src/elspeth/web/frontend/src/components/chat/ToolCallCard.tsx#L84) distinguish completion from graph application.

## 4. Alternative paths

An unbound ready artifact can be replaced. A currently referenced artifact is rejected before replacement with "referenced by the current composition … unbind it first". The message names no tool. Under `explicit_approve` the unbind-then-update route cannot finish within one turn (N6). Shared durable authority checks active-run, proposal and fork retention even when local composition inspection misses it. A missing or other-session record maps to a safe not-found (demonstrated with a fresh UUID). Invalid UTF-8 or a quota denial leaves storage untouched. Interrupted swaps reconcile to the committed version before the next update or read, and readers use the same custody lock, so they cannot pair old metadata with new bytes.

Integrity anomalies escalate rather than becoming retry guidance. That set currently includes two ordinary states. A `pending` or `error` blob, which `list_blobs` advertises with its `status`, escalates (N1). So does a blob with an unretired deletion ledger row (N8, hypothesis). Both reach `tool_batch`'s [`except AuditIntegrityError: raise`](../../../../src/elspeth/web/composer/tool_batch.py#L3195) and fail the turn instead of returning a refusal.

## 5. Usability assessment

**BOS-04 — source-established limitation, High confidence:** the compact model description says the tool overwrites content "while preserving metadata". In fact eligibility depends on readiness and four retention domains, and provenance changes. Those restrictions are valid safeguards. However, the orchestrator has no structured preflight eligibility query or declared retry class, so it learns retention constraints from a failed mutation. Under `explicit_approve` it learns them only after the user has approved (N5). Workaround: inspect bindings, status and run/proposal state before proposing a replacement, then follow the returned refusal. Repeating the call does not resolve a denial.

No data-corruption defect was demonstrated in the replacement protocol. Focused tests exercise rollback, active-work guards and mixed-version read protection. The missing caller optimistic identity is a design limitation; the internal exact-record comparison already supplies a concurrency safeguard, by escalation.

**New findings (provisional IDs).** N1–N4 and N10 were shown by in-memory `execute_tool` runs through the `test_tools_blobs.py` fixtures (SQLite `:memory:`, scratch data root, no provider). They are dispatch/handler runs, not end-to-end service runs.

- **update_blob-N1 — demonstrated, High:** a blob with `status` `error` or `pending` and a null hash raises `AuditIntegrityError("replacement requires existing canonical content with a hash")` from [replacement.py L277](../../../../src/elspeth/web/blobs/replacement.py#L277). This happens before the repository's own ready check ([L2298](../../../../src/elspeth/web/coordination/repository.py#L2298)) and before retention. A `pending` blob linked to a *running* run raised `AuditIntegrityError`, while the ready control on the same fixture returned the active-run refusal. Both states occur in production: [`mark_run_output_blob_error`](../../../../src/elspeth/web/coordination/repository.py#L3947) writes `status="error", content_hash=None`. [`list_blobs`](../../../../src/elspeth/web/composer/tools/blobs.py#L534) lists every status, and its description advertises `status`. The declaration does not state the ready precondition. An agent can therefore select a listed blob and crash the compose turn. No test sets a non-ready status on an update path: `grep` for either integrity message in `tests/` returns nothing, while the control string "metadata changed before durable replacement" matches [L1572](../../../../tests/unit/web/composer/test_tools_blobs.py#L1572).
- **update_blob-N2 — demonstrated:** retention refusals say "cannot be **deleted**" on an update, for example "Blob … is linked to active run … and cannot be deleted". The three exception classes hard-code the verb ([contracts L259/273/287](../../../../src/elspeth/contracts/blobs.py#L259)), and the handler returns `str(exc)` verbatim. The existing test asserts only `"active run" in message` ([test](../../../../tests/unit/web/composer/test_tools_blobs.py#L3664)), so it cannot catch this.
- **update_blob-N3 — demonstrated:** the quota refusal reports the current total, not the projected one. With a 7-byte blob, a 20-byte replacement and a 10-byte quota, it returned "blob storage (7 bytes) would exceed quota (10 bytes)". The repository passes `current_bytes=current_total` ([L2327](../../../../src/elspeth/web/coordination/repository.py#L2327)); `create_blob` composes its own projected message ([L1541](../../../../src/elspeth/web/composer/tools/blobs.py#L1541)).
- **update_blob-N4 — demonstrated (confirms §2):** an identical repeat succeeds with the same `content_hash` and rewrites `creating_arguments_hash`, which repeats the durable work.
- **update_blob-N5 — source-established; consequence not run end-to-end:** under `explicit_approve`, staging never calls the handler. A bound, retained, over-quota or non-ready blob is staged and returned to the model as successful `APPROVAL_REQUIRED` (`anti_anchor.record_success()`, `turn_has_mutation=True`). The user approves; the accept route then runs the handler, refuses, and auto-rejects the proposal with 422 ([route](../../../../src/elspeth/web/sessions/routes/composer/proposals.py#L610)). Immediate mode refuses in the same turn. The two routes diverge on the same arguments, and the approval is spent.
- **update_blob-N6 — source-established:** the accept route applies the `base_state_id` staleness 409 to blob-store-only proposals unless a receipt exists ([L407–418](../../../../src/elspeth/web/sessions/routes/composer/proposals.py#L407)), even though the handler revalidates against the persisted current state. No tool rebases a blob proposal, and the frontend deliberately leaves Accept enabled ([DecisionPanel test](../../../../src/elspeth/web/frontend/src/components/chat/DecisionPanel.test.tsx#L146)). The two halves compound. The model issues `clear_source` then `update_blob`, the "unbind it first" route, as two proposals in one turn. Accepting `clear_source` first makes `update_blob` stale (409). ## 6. Structural remediation

Make artifact mutation eligibility, retry class and committed effect identity part of a shared artifact lifecycle contract used by the tool, the proposal executor and the orchestrator. A REST replace route does not exist today; any future one should join the contract rather than reimplement it. Keep the replacement coordinator as the owner of durable phases, and do not reimplement its checks in prompts. Add a structured refusal category that separates lifecycle-ineligible (not ready), retention, missing dependency and integrity failure. Proposal staging should run the same admission preflight as immediate dispatch, without executing the effect, so that both routes refuse identically. The blob-proposal staleness rule should be expressed in terms of the facts the handler revalidates, not graph base identity. An optional expected hash can bind user intent. The proposal route already resolves uncertain completion through its receipt; extend an equivalent operation key to the immediate route instead of redoing the replacement.

Acceptance:

- A valid unbound replacement changes exactly the intended blob.
- Graph, active-run, pending-proposal and in-progress-fork references each reject before publication, with an update-specific message, on both the immediate and the staging route.
- A `pending` or `error` blob is refused, not escalated.
- A concurrent replacement cannot apply to an unexpected version.
- Reads that cross a swap or commit see one complete version.
- Injected deaths at each phase recover coherently.
- Result replay returns the committed operation outcome.

Compatibility risk is Medium for optimistic identity and receipt additions and for staging preflight, which changes which proposals can exist. It is Low for richer eligibility disclosure and message fixes. Preserve all current retain/refuse contracts.
