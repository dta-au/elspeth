# `remove_edge` — independent tool assessment

Baseline: ELSPETH **0.8.9**, `3b28d537be98234da8135c418bf185a998c18b68`. Reconnaissance and remediation design only. Incoming `.10 lite` changes are outside this assessment and require affected-source reinspection.

## 1. Purpose and usage

Remove one explicit diagram edge and, when its target is a declared output and no other edge with a different id still draws the same producer/edge-type/sink route, clear the producer scalar the edge mirrors. Clearing is keyed only on the edge's shape and target ([`_clear_removed_sink_edge_route`](../../../../src/elspeth/web/composer/tools/transforms.py#L1068)); it does not check that the edge was a lowerable (supported) route, so removing an edge that validation already reports as `edge_not_lowerable` can still clear a real node-level policy (remove_edge-N1).

Select for intentional relationship removal. A non-sink visual edge deletion does not disconnect processing-node runtime connection strings, and the web graph view redraws the relationship from those strings anyway; the orchestrator must choose the appropriate route edit separately. A sink-edge deletion is a runtime routing change: the source's `on_success` becomes the placeholder `"discard"`, and a node's slot becomes unset.

## 2. Contract

Required id:string. The handler finds the first EdgeSpec with that id or returns `edge_not_found` unchanged. It removes **every** edge carrying that id ([`without_edge`](../../../../src/elspeth/web/composer/state.py#L8271)), conditionally clears the sink-route mirror of the first match only, reconciles reviews and returns that first match's two endpoints plus validation/new version. Remaining different-id semantic duplicates (legacy persisted states) can preserve the route they still express. Same-id duplicates are a separate case: all are deleted, but only the first is cleared and reported (remove_edge-N2). No blob/plugin/external action occurs. Repeating after successful removal fails with `edge_not_found` at unchanged version; no retry receipt or no-op success is provided. Accepted deletion can leave graph-invalid routes; these usually remain visible in validation, but not in the N1 case, where the result is valid. Unlike `upsert_edge`, the handler does not call `_post_mutation_invariant_error`. Those blocking codes are node-shape invariants that clearing a routing scalar does not introduce, so this is a design asymmetry, not a demonstrated gap. The version advances by 2 when a producer scalar is actually rewritten (edge removal, then scalar write; measured for source, transform and gate sink edges) and by 1 otherwise (processing edges, still-expressed duplicates, or a scalar that already disagrees with the edge). No cache; public explicit approval applies.

The handler returns an immutable candidate; it does not itself durably save the conversation. In web explicit_approve mode, the operation is staged as a proposal and re-admitted on acceptance. Otherwise the enclosing tool batch applies the accepted state, and the session turn persists it under its operation authority. Across both provider dialects, the provider wire projection is decoded to canonical arguments before dispatch; strict transport representation does not grant different authority. A ToolResult's `success` records operation admission, while `validation.is_valid`, runtime preflight, review and execution admission answer separate questions. Owned-code/audit integrity failures escape as faults rather than being reclassified as ordinary invalid model input. The one deliberate mapping is that `KeyError`/`TypeError`/`ValueError` raised by review reconciliation become a repairable `review_reconciliation_failed` rejection on the saved state ([transforms.py:1610](../../../../src/elspeth/web/composer/tools/transforms.py#L1610)).

## 4. Alternative paths

Removing a source-to-sink success edge sets the source scalar to the placeholder `"discard"`. `SourceSpec.on_success` is a required string, so it cannot be unset, and validation then reports `source_on_success_dangling` naming `'discard'` (remove_edge-N3). Removing a transform/aggregation success/error sink edge unsets that slot (`transform_missing_on_success` follows for `on_success`). Gate route/fork mirrors use kind-specific rules. Non-sink edges are annotations relative to runtime connection strings; their removal leaves nodes and sources byte-identical and produces an empty `validation_delta`. A non-lowerable sink-targeting edge is cleared like a supported one (N1). Reconciliation reopens impacted review anchors; failure returns the old state. A removed edge does not itself delete a node or an output. This tool's successful result concerns mutation admission, not proof that the path was runtime-disconnected.

## 5. Usability assessment

**SG-01 — intended split semantics; high confidence.** Visually identical removal gestures can change runtime for a sink edge while merely changing the display for a processing edge. In the web graph view the processing-edge removal may not even change the display, because the edge is re-inferred from connection strings. Existing tests prove sink clearing, but that does not establish uniform disconnect semantics. Workaround: inspect surviving producer/consumer connection fields, then author the intended runtime edit and preview it. No corrupted *supported* sink route was demonstrated; N1 below is a policy change through an *unsupported* edge.

**remove_edge-N1 — demonstrated (in-memory dispatch); silent runtime-policy change.** `set_pipeline` persists a gate→sink `edge_type="on_error"` edge with `success=True` and a standing `edge_not_lowerable` error, while the gate's node-level `on_error="errs"` matches it. `upsert_edge` refuses to create this edge. Removing it is the natural repair for that error, but `_clear_removed_sink_edge_route` matches `on_error` and sets the gate's `on_error` to `None`, which the runtime treats as fail-fast ([config.py:779](../../../../src/elspeth/core/config.py#L779)). The result is `success=True`, `validation.is_valid=True`. The only signal is `resolved_errors: [edge_not_lowerable]` plus a medium "Output 'errs' is not referenced" warning. Meanwhile the `edge_not_lowerable` guidance tells the model to "Preserve intentional gate and coalesce policies" ([generation.py:1578](../../../../src/elspeth/web/composer/tools/generation.py#L1578)). The general class is any sink-targeting edge that fails `edge_lowering_error` but whose shape matches a scalar the producer really carries. The gate is the clean instance; for the coalesce/collector/queue/row_union kinds that `edge_lowering_error` rejects, it was not probed whether the corresponding scalar can actually hold a sink.

**remove_edge-N2 — demonstrated (in-memory dispatch); same-id duplicates.** `set_pipeline` persists two edges with id `d` (gate `route_true` and `route_false` to `main`) with `success=True` and `duplicate_edge_id`. `remove_edge({"id":"d"})` deletes both edges, clears only `routes["true"]` (leaving `{"false":"main"}`), and reports `affected_nodes=("g1","main")` for the first match only. With different producers, the second duplicate's endpoints are not reported at all and its scalar is left without a drawn edge. The model cannot remove just one of two same-id edges with this tool.

**remove_edge-N3 — demonstrated (in-memory dispatch); placeholder token in the source slot.** Removing `source→main` writes `on_success="discard"`. The model then receives `source_on_success_dangling` ("Source on_success 'discard' is neither a sink nor a known connection") and a warning, both naming a value it never authored. The value also looks like the legitimate `discard` policy of `on_validation_failure`/`on_error`. Validation does block it, so this is a clarity defect, not a runtime hazard.

**remove_edge-N4 — source-established; approval UI omits the consequence.** In explicit_approve, the proposal card text and diff show only the edge removal ([ProposalDiff.tsx:622](../../../../src/elspeth/web/frontend/src/components/chat/ProposalDiff.tsx#L622)). The user approves a source/node routing change they are not shown. The diff's own honesty contract explains why (no client simulation), so the gap is in what the server provides to the proposal, not a diff bug. The same applies to `upsert_edge`'s scalar write. No browser run was made.

**remove_edge-N5 — demonstrated observation; feeds SG-03/R4, not a defect alone.** Version advances +2 for a sink edge and +1 for a processing edge, and the processing-edge result carries an empty `validation_delta` with no field saying "runtime routing unchanged". From the envelope alone the model cannot tell an annotation removal from a disconnect except by reading `applied_component`.

## 6. Structural remediation

Separate annotation removal from executable disconnect in the graph contract, sharing route-slot ownership with upsert_edge and deriving visual state from accepted runtime relationships where possible. Define legacy duplicate resolution explicitly, including same-id duplicates. Regression: disconnect clears only the intended runtime slot; retained duplicate semantics are preserved until migration; processing-edge annotation removal never claims runtime disconnection; missing IDs refuse; review invalidation is consistent; every rejection retains state/version. Compatibility risk high for saved dual representations; use explicit versioning/adapters rather than reinterpret existing edges silently.
