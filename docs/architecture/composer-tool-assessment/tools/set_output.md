# `set_output` — add or replace a configured sink

Assessment baseline: `3b28d537be98234da8135c418bf185a998c18b68` (0.8.9). Reconnaissance/design only. **Overall confidence: High for inspected source and focused tests.**

## 1. Purpose and usage

Use this tool when a sink instance must be created or wholly replaced. Discover allowed sink plugins and inspect their configuration schema first. The sink's name is also the upstream connection name it consumes; it must match an upstream `on_success`/route, not necessarily a node ID. The graph may be incomplete while editing. A new sink requires an explicit write-failure choice. It is available through web Composer and the common Composer MCP surface, with different storage/authority contexts.

## 2. Contract

Required arguments: `sink_name: string`, `plugin: string`, `options: object`. Optional `on_write_failure` preserves the existing same-name sink's choice only when omitted; a new sink needs a nonempty value such as `discard` or an eligible sink diversion. Explicit null/empty is invalid despite null being admitted by the outer schema. Optional `description` defaults to null. This is replacement, not merge: omitted old options are removed and omitted description is cleared.

The plugin's own config model controls option shape. The web additionally enforces plugin policy/availability, secret reference placement, session-local path rules, AWS S3 endpoint policy, and explicit collision policy for file sinks in runnable web contexts. The file-sink rule requires **both** `options.mode` and `options.collision_policy` to be present and consistent ([validator](../../../../src/elspeth/web/composer/tools/_common.py#L3435)); the declaration names only `collision_policy` (see §5.1). Success adds/replaces the named output and increments composition version; it returns `affected_nodes`, `validation`, `validation_delta`, `version` and an `applied_component` echo of the stored output (including `on_write_failure` and `description`). Unlike every sibling creation/patch tool, it attaches **no** `post_call_hints` (see `set_output-N2`). Valid authoring can still leave graph validation false. No sink bytes or remote writes occur in this handler.

It is uncached `MUTATION` with graph/validation/YAML effects. Under `explicit_approve`, the web prepares a proposal before applying; `auto_commit` applies admitted edits. Repeating identical arguments advances version again, so it is not version-idempotent. Declaration-schema failures are safe argument errors, but `options` is a free-form object at that layer: a non-string `path`/`file`/`persist_directory` value passes schema admission and, in any web context with a data root, escapes the handler as a raw `TypeError` (`set_output-N1`, demonstrated). Failure-route, path, policy, credentials, config, collision, or blocking-invariant failures preserve the old graph and carry typed validation codes; relevant option failures receive plugin schema repair context. Unexpected owned config/schema exceptions propagate as framework/plugin failures rather than being blamed on model input. The post-mutation invariant check blocks only the fixed [`_MUTATION_BLOCKING_INVARIANT_CODES`](../../../../src/elspeth/web/composer/tools/_common.py#L3905) set; for an output the directly relevant member is `row_union_on_success_must_be_connection` (a sink named after a `row_union`'s `on_success`), and a pre-existing blocking code elsewhere in the graph also refuses the call with `rejected_component=None` (pinned by the [whole-state invariant test](../../../../tests/unit/web/composer/test_output_rejection_contracts.py#L310)). Failsink reference errors (`failsink_unknown_output`, `failsink_self_reference`, `failsink_ineligible_plugin`, `failsink_chain`) and `output_name_invalid` are **not** blocking: the edit is stored with `success=true` and those codes appear only in standing validation.

## 3. Implementation trace

The [declaration and handler](../../../../src/elspeth/web/composer/tools/outputs.py#L48) feed the [registry](../../../../src/elspeth/web/composer/tools/_registry.py#L94) and [canonical model definitions](../../../../src/elspeth/web/composer/tools/_dispatch.py#L311). [`_execute_set_output`](../../../../src/elspeth/web/composer/tools/outputs.py#L137) resolves write-failure semantics, policy, catalog schema, credential placement, path policy, [`_prevalidate_sink`](../../../../src/elspeth/web/composer/tools/_common.py#L3631), collision policy, `OutputSpec`, and the post-mutation invariant. [Plugin option admission](../../../../src/elspeth/web/composer/tools/_common.py#L2514) selects the plugin config model and handles deferred secret/blob values without exposing real secrets.

[`CompositionState.with_output`](../../../../src/elspeth/web/composer/state.py#L8278) replaces by name and increments version. [Dispatch finalization](../../../../src/elspeth/web/composer/tools/_dispatch.py#L752) normalizes policy validation and attaches repair schema/guidance. [Web batch approval/execution](../../../../src/elspeth/web/composer/tool_batch.py#L1728), [audit](../../../../src/elspeth/web/composer/audit.py#L812), and [frontend proposal/outcome cards](../../../../src/elspeth/web/frontend/src/components/chat/ToolCallCard.tsx#L74) manage publication. [MCP dispatch](../../../../src/elspeth/composer_mcp/server.py#L363) uses the shared tool but a trained-operator policy view and no web data root; it also applies its file-sink collision control.

Handler check order, as written in [`_execute_set_output`](../../../../src/elspeth/web/composer/tools/outputs.py#L137): argument model → [failure-route resolution](../../../../src/elspeth/web/composer/tools/_common.py#L1910) (omitted preserves the same-name prior choice; supplied null/blank refuses; supplied text is `.strip()`ped) → AWS S3 `endpoint_url` policy → plugin selection policy → schema read (result discarded; faults propagate) → literal-credential refusal → [sink path policy](../../../../src/elspeth/web/composer/tools/_common.py#L2344) (skipped entirely when `data_dir` is `None`) → `_prevalidate_sink` → collision/mode policy (only when `data_dir` is set) → `OutputSpec` → `with_output` → blocking-invariant check → `_mutation_result`. The first failing step wins, so a call with several defects learns of one per round trip. The sink path refusal deliberately replaces the detailed helper message (which embeds the deployment data root) with a generic one.

## 4. Alternative paths

New sink with omitted failure choice refuses; replacing an existing sink can preserve that choice. Unknown, unavailable, prohibited, or profile-restricted plugin fails before schema disclosure beyond allowed policy context. Literal credential repair returns structured reference guidance. Bad plugin options carry the admitted plugin's schema; a broken schema provider raises rather than fabricating an unavailable plugin. Web output paths are session-authorized. MCP can author operator-controlled destinations according to its separate context. Successful replacement does not prove route completeness, secret resolution, runtime preflight, or external write acceptance. An `on_write_failure` naming an unknown sink, the sink itself, an ineligible plugin (eligible: `FAILSINK_ELIGIBLE_PLUGIN_TEXT`, measured `csv or json`) or a non-`discard` target is stored as a successful edit with a standing `failsink_*` error. An invalid `sink_name` (empty, uppercase, reserved `continue`/`fork`/`on_success`, `__`-prefixed) is likewise stored with a standing `output_name_invalid`, whereas `set_source` refuses an invalid `source_name` as a `ToolArgumentError` ([`_validate_source_name_argument`](../../../../src/elspeth/web/composer/tools/sources.py#L785)).

## 5. Usability assessment

The original scoped review demonstrated no defect. The 2026-11-09 sheet review found the defects and limitations below. "Demonstrated" means an in-memory `execute_tool` dispatch against the real catalog and a trained-operator policy view, with a lane-local scratch `data_dir`. The later probe run (§7.1) added scripted-model compose turns for N1 and N3. No run was an end-to-end deployed-service, live-provider or browser run.

- **`set_output-N1` — demonstrated: Tier-3 option value crashes the dispatcher instead of refusing.** With a data root set, `options.path` = `null` or `123` (likewise `file`/`persist_directory`) reaches [`resolve_sink_data_path(options[key], ...)`](../../../../src/elspeth/web/composer/tools/_common.py#L2364) → [`Path(value)`](../../../../src/elspeth/web/paths.py#L117) and raises `TypeError` out of `execute_tool`. With `data_dir=None` (MCP) the same arguments give a clean `plugin_options_invalid` ("path: Input should be a valid string"). The nested transform-path helper in the same file already skips `None` ([`_common.py:2409`](../../../../src/elspeth/web/composer/tools/_common.py#L2409)); the sink helper does not. The compose loop catches only `ToolArgumentError` ([`protocol.py:1313`](../../../../src/elspeth/web/composer/protocol.py#L1313), [tool-batch dispatch comment](../../../../src/elspeth/web/composer/tool_batch.py#L2952)), so the consequence is a recorded `PLUGIN_CRASH`/`ComposerPluginCrashError` that ends the turn and blames our code for model input. The turn consequence is **demonstrated** in a scripted-model compose turn (§7.1 probe 2): `path` `null` and `123` each raised `ComposerPluginCrashError` wrapping `TypeError` after one model call, with `partial_state=None` and audit status `plugin_crash`; the persisted tool row has `error_class=TypeError` and no `validation`. The string-path controls ran normally. The same crash was reproduced for `patch_output_options` (`patch: {"path": 123}`) and `set_source` (`path: null`); see the cross-cutting note in the review report.
- **`set_output-N2` — demonstrated: no post-call hints on sink creation.** `_handle_set_output` returns `_execute_set_output` directly. `set_source`, `upsert_node`, `splice_transform` and every `patch_*` handler call `_attach_post_call_hints`. A successful `set_output` of `database` with `if_exists: "replace"`, or of `json` with `format: "json"`, returned `post_call_hints=()`. The catalog returns the table-drop warning and the non-resumable-array warning for the same configs. Sink hints are therefore reachable only through `patch_output_options`. The [integration hint test](../../../../tests/integration/web/test_composer_tools.py#L39) covers sinks only under `patch_output_options` and drives `_attach_post_call_hints` directly, so it cannot see the gap. Caveat for any fix: the [json sink hint](../../../../src/elspeth/plugins/sinks/json_sink.py#L629) keys "on_write_failure is not set" off the options snapshot. `on_write_failure` is a top-level `OutputSpec` field, and putting it inside `options` is refused (`plugin_options_invalid`, measured). That hint is already emitted falsely on every successful json `patch_output_options` (measured with a stored `on_write_failure="discard"`).
- **`set_output-N3` — demonstrated for `set_output` (compose turn + accept route); cross-tool scope source-established: deterministic refusals become pending approvals under `explicit_approve`.** The preview dispatch branches only on valid success (required-control conversion) and on `ToolArgumentError` (deliberately ignored). Nothing handles `preview_result.success is False`. A `set_output` that will certainly refuse is still [published as a proposal](../../../../src/elspeth/web/composer/tool_batch.py#L2127). In §7.1 probe 3 the in-turn preview refused with `failure_route_required` (no failure choice), `sink_path_policy_invalid` (`../escape.json`) and `file_sink_write_policy_invalid` (no `collision_policy`). Each arm still created exactly one pending `set_output` proposal, and the model saw the same payload as the valid positive control: `success=true`, `APPROVAL_REQUIRED`, "pending human approval and has not been applied", and no refusal code. The negative control (`set_pipeline` with an uninstalled plugin) created no proposal and returned `PREVALIDATION_REJECTED`. The refusal surfaces only when the human accepts and [the accept route](../../../../src/elspeth/web/sessions/routes/composer/proposals.py#L493) re-executes: 422 `proposal_validation_failed`, proposal auto-`rejected` (valid control: 200 `committed`). The same staging behaviour has also been demonstrated by the sibling probe runs for `clear_source`, `patch_output_options`, `remove_output`, `remove_node`, `patch_node_options` and `patch_source_options` (the last answered 409 at accept, not 422). It remains source-established for any incremental mutation tool not yet probed. Whether domain refusals are meant to share the documented argument-error contract needs a ruling.
- **`set_output-N4` — demonstrated: repair guidance gaps for the codes this tool leaves standing.** `explain_validation_code` returns `None` for `failsink_unknown_output`, `failsink_self_reference`, `failsink_ineligible_plugin`, `failsink_chain` and `output_name_invalid`. The controls were `file_sink_write_policy_invalid` (present) and an invented code (`None`). These codes are produced by this tool's ordinary success path, so the model gets a closed code with no `validation_guidance`.
- **`set_output-N5` — demonstrated, intended-vs-sibling inconsistency: invalid sink identity is stored, not refused.** `sink_name` values `""`, `Main`, `continue` and `__x` all returned `success=true`, were stored, and raised standing `output_name_invalid`. `set_source` refuses the equivalent name before mutation, and `upsert_node` stores an invalid id with standing `node_id_invalid` ([`state.py:8540`](../../../../src/elspeth/web/composer/state.py#L8540)). Because the name is also the identity used by `patch_output_options`/`remove_output` and the routing label, a stored invalid name has to be repaired by remove-and-recreate. Whether incremental tools should refuse invalid identities is a policy choice; the inconsistency is the finding.
- **`set_output-N6` — source-established result-shape divergence on MCP.** The MCP collision pre-check returns `{"success": false, "error": ..., "state": ...}` with no `error_code`, validation or guidance ([`server.py:249`](../../../../src/elspeth/composer_mcp/server.py#L249), [`:393`](../../../../src/elspeth/composer_mcp/server.py#L393)). The same defect on the web returns `file_sink_write_policy_invalid` in a `ToolResult`. The check also runs before failure-route and policy checks, so the precedence of refusals differs by route.
- **`set_output-N7` — hypothesis: a sink named `discard` is ambiguous as a divert target.** `discard` passes both the composer and runtime sink-name validators ([`validate_sink_name`](../../../../src/elspeth/core/config.py#L261) reserves only `continue`, `fork` and `on_success`). Probe: stored with no name error. Every `on_write_failure`/`on_validation_failure`/`on_error` value of `"discard"` is read as the drop sentinel before any sink lookup (e.g. [`validation.py:188`](../../../../src/elspeth/engine/orchestrator/validation.py#L188)), so such a sink can never receive diverted rows. Whether this causes unintended row drops in a real authored graph was not traced.

**Intended editor semantics:** `success=true` can accompany invalid graph validation; the output was stored as an authored edit, not certified runnable. The name/connection dual role, replacement semantics, and contextual collision/failure-route requirements create a substantial reasoning burden, but current guidance explicitly covers the main distinctions. Workaround: read the applied echo and validation, preserve full options when replacing, and use preview before claiming readiness.

**Source-established structural limitation:** admission logic is repeated across set/patch/wire/whole-pipeline paths, while deferred values are validated differently before and after resolution. The focused rejection parity tests are valuable existing controls; their success does not prove every future plugin/provider option has complete parity.

## 6. Structural remediation

Consolidate candidate output admission around plugin-owned authoring/deferred-value contracts and a web-owned policy/review finalizer, reused by creation, patch, secret/blob wiring, YAML, and whole-pipeline authoring. Separate outcomes for edit accepted, validation failed, review pending, and runtime-ready. Keep plugin execution separate from authoring and keep route validation authoritative.

Acceptance: the same effective output candidate yields the same policy/config/credential/collision decision through every authoring route; missing explicit failure routes reject; allowed deferred refs remain authored without secret material; invalid provider responses/framework faults do not masquerade as argument errors; valid incremental edit returns exact effective options and a truthful readiness state. Compatibility risk is Medium for changing output result semantics and High if persisted route/config meaning changes. Preserve existing failure routes, session path restrictions, and refuse contracts.
