# `list_secret_refs` — discover credential reference metadata

Assessment baseline: `3b28d537be98234da8135c418bf185a998c18b68` (0.8.9). Reconnaissance/design only. **Overall confidence: High for inspected metadata and custody contracts; High for the user-scope availability mismatch (demonstrated by an in-memory dispatch run, not an end-to-end service run).**

## 1. Purpose and usage

Select this tool before credential wiring when the orchestrator needs to know which named references are visible to the current authenticated user. It discovers names, scopes and a metadata availability flag, never values. It does not grant permission to place any reference in any plugin option, and it does not approve execution. For user-scoped entries its `available` flag is not a resolvability check (see §2 and LSR-N1); `validate_secret_ref` is the per-name resolvability check. Requires the server-supplied scoped secret resolver and current user ID; production always supplies the resolver, while `user_id` is typed optional on the dispatch contexts (§3.1). Web Composer exposes it on the freeform and planner surfaces; Composer MCP deliberately excludes secret tools.

## 2. Contract

Arguments are exactly `{}`; extra keys reject. Successful `data` is a list of metadata objects with exactly `name`, `scope`, `available`, `source_kind`, and `reason`, sorted by name. Real secret bytes never enter the payload or tool argument model.

Field vocabularies, as produced at this baseline:

| Field | Contract type | Values actually emitted by the stores |
|---|---|---|
| `scope` | closed `Literal["user", "server", "org"]` ([`contracts/secrets.py:12`](../../../../src/elspeth/contracts/secrets.py#L12)) | `user` ([user store](../../../../src/elspeth/web/secrets/user_store.py#L390)), `server` ([server store](../../../../src/elspeth/web/secrets/server_store.py#L139)); no store emits `org` |
| `source_kind` | open `str` ([`contracts/secrets.py:173`](../../../../src/elspeth/contracts/secrets.py#L173)) | `user_store` (user), `env` (server) |
| `reason` | closed `Literal` of three values ([`contracts/secrets.py:16`](../../../../src/elspeth/contracts/secrets.py#L16)) | server: `fingerprint_resolver_not_configured`, `env_var_not_set`; user: `fingerprint_resolver_not_configured` only. **`value_decryption_failed` is never emitted by this tool**; only `validate_secret_ref` produces it ([`secrets.py:188-193`](../../../../src/elspeth/web/composer/tools/secrets.py#L188)) |
| `available` | `bool`, with `available ⟺ reason is None` enforced at construction ([`contracts/secrets.py:176-186`](../../../../src/elspeth/contracts/secrets.py#L176)) | see below |

**What `available` means differs by scope.** For a server entry it means allowlisted, env var set and non-empty, and fingerprint key configured — the same predicate `get_secret` succeeds on ([`server_store.py:113-165`](../../../../src/elspeth/web/secrets/server_store.py#L113)). For a user entry it means only "a stored row exists and the deployment fingerprint key is set"; the listing deliberately selects no ciphertext and performs no decrypt ([`user_store.py:346-405`](../../../../src/elspeth/web/secrets/user_store.py#L346)). A user row that cannot be decrypted after master-key rotation or corruption is therefore listed `available: true, reason: null` while `validate_secret_ref` and resolution report it unavailable. The store behaviour is an intended, test-pinned performance/custody restriction ([`test_user_store.py` rotation and corruption tests](../../../../tests/unit/web/secrets/test_user_store.py#L394)); the tool's declaration text does not disclose it (LSR-N1).

The underlying resolver merges curated server and user inventories, sorts names, and lets a user-scoped record replace a same-name server record in the listing, even when the user record cannot resolve ([`service.py:169-178`](../../../../src/elspeth/web/secrets/service.py#L169)). The shadowed server entry is dropped from the result entirely; no field records that it exists (LSR-N2). Server-only deployments (`user_secrets_enabled=False`) omit user records from listing and resolution ([`service.py:145-178`](../../../../src/elspeth/web/secrets/service.py#L145)). Server inventory only contains operator-allowlisted names; reserved `ELSPETH_*` names are refused when the allowlist is constructed ([`server_store.py:52-57`](../../../../src/elspeth/web/secrets/server_store.py#L52)), so the reserved-name skip inside `list_secrets` ([L133](../../../../src/elspeth/web/secrets/server_store.py#L133)) is a defensive duplicate. A missing fingerprint key makes every entry in both scopes unavailable with `fingerprint_resolver_not_configured` (fingerprint-key-first precedence); the correct response is to surface that deployment condition, not invent another secret. A false availability is a successful discovery fact, not a failed tool operation; a true availability on a `user` entry is a record-existence fact, not a resolvability guarantee.

This is uncached `SECRET_DISCOVERY` (SECRET_DISCOVERY declarations cannot opt into caching, [`declarations.py:221`](../../../../src/elspeth/web/composer/tools/declarations.py#L221)) with a selected response contract, no authored effects ([`declarations.py:193`](../../../../src/elspeth/web/composer/tools/declarations.py#L193)), unchanged composition version, and no mutation approval. Missing resolver/user context returns `secret_context_unavailable` and the prior graph findings. Malformed owned metadata (wrong scalar type, unknown scope/reason, extra/missing field, incoherent availability) fails response admission with `FrameworkBugError` rather than serializing arbitrary data. A store/database exception from `list_refs` is not caught by the handler and propagates out of it, consistent with Tier-1 handling of our own store; how the compose loop classifies that exception was not traced for this sheet. A result is an observation, not a lock or reservation: rotation/deletion can change availability before validation, wiring, or execution. Repeating the discovery is safe and fresh on both surfaces (no cache; the planner records `secret.index` as supplied but does not refuse a reread — §3.1); there is no automatic retry or idempotency receipt for this read.

## 4. Alternative paths

Empty inventory succeeds. Listed but unavailable references remain visible with their reason. Same-name user records shadow server records; a failing user record must not silently fall back to a server credential, and does not (demonstrated: resolution returns `None` while the server env var is set). Missing context refuses without calling the resolver. A malformed owned status/reason/extra payload fails admission rather than serializing arbitrary data. Availability can change after listing; execution therefore resolves again. A destination allowlist denial cannot be repaired by repeatedly listing or choosing another spelling of the same reference.

Undecryptable user row: listed `available: true`; `validate_secret_ref` returns `available: false, reason: value_decryption_failed`; freeform `wire_secret_ref` refuses it with `missing_secret_ref` (§7.1); repair is re-saving (or deleting) the user secret through the Secrets panel, not a composer tool. Shadowed working server secret: invisible in the listing; the user's own row must be re-saved or deleted before the server credential is used.

## 6. Structural remediation

Expose a value-free secret capability view that combines resolver metadata with only the destination authorization information the current user may see. Keep credential storage/resolution in the secret service, plugin secret-field semantics in the plugin contract, deployment allowlist in web policy, and run approval outside model control. Reuse that view in discovery, wiring, validation, and execution disclosure without allowing a discovery answer to grant authority.

Make availability honest per scope in the same view: either a distinct field for "resolvability checked" versus "record present", or a per-entry flag that a user record shadows a server record of the same name (LSR-N1, LSR-N2). Do not decrypt every user row in the listing; the store's metadata-only contract is a deliberate custody/cost choice. These are additive response fields: they touch the selected response contract and its payload type, the redaction manifest entry, the REST `SecretInventoryResponse`, the frontend `SecretInventoryItem` type, and the legacy wire fixture `secret_response_legacy_wire.json` — bounded, but not trivial.

Acceptance: inventories never expose values/reserved names; shadowing and server-only modes remain consistent; a user entry's availability claim is either qualified or verified, and an undecryptable row is distinguishable from a working one without a separate guess; a shadowed server record is disclosed only as name/scope metadata the user could already see; allowed and denied destinations are explainable without resolving credentials; rotation/deletion causes revalidation; unknown/malformed response shapes fail closed; available metadata alone cannot bypass authorization or run acknowledgement. Compatibility risk is Low for additive capability metadata and Medium for expanding the response envelope/redaction policy (REST clients of `/api/secrets` consume the same shape). No migration or secret-store reset is proposed.
