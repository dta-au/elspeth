## Main assessment

Establish the first-class orchestrator by strengthening the existing invocation,
observation, candidate-admission and settlement contracts. Preserve the current
provider authorship, plugin-owned schema emission, policy snapshots, required
controls, review evidence, session fencing and durable operation replay.
The evidence supports bounded structural changes around those seams, not a
replacement agent framework.

The orchestrator needs dependable answers to four questions: what capabilities
and resources are actually available, whether their observations are complete,
what a tool changed or refused, and which approval/evidence/effect obligations
remain before completion. The current system provides many safeguards, but
route-specific optional context and uneven tool/result semantics leave those
answers inconsistent in the cases below. The review wave adds a fifth: whether
the guidance the model receives describes the palette and behaviour of the route
it is actually on. The probe wave adds a sixth: whether the model and the
approving user can see what server-owned steps (required controls, approval
rewrites, review reconciliation) did to their edit.

## Findings register

These are finding identifiers, not a count of bugs. Classification vocabulary:
**demonstrated** (a run observed it; the row says which form: "in memory" means
handler/dispatch/service objects driven in-process, "compose turn" a real
`compose()` or planner loop with a scripted provider, "accept route" the REST
proposal-accept route driven in process, "jsdom" a frontend component test; none
is a deployed route, live provider or real browser), **source-established**
(traced through source, not run), **intended** (deliberate restriction),
**hypothesis** (plausible, unverified), **refuted** (a run showed it wrong).
Sheet-scoped IDs (`<tool>-N<n>`, or the sheet's own prefix such as `LSR-`,
`PO-`, `METADATA-`, or a bare `N<n>` on the
[`handoff_to_user`](tools/handoff_to_user.md) sheet) are defined in the named
sheet; findings that touch only one tool stay there. The probe outcome behind
each upgrade is in the [probe-wave table](evidence.md#probe-wave-outcomes-2026-11-09).

## Review and verification

**Initial assessment.** Independent lanes investigated source/graph,
blob/output/secret, and generation/session/async tools. The parent traced
orchestration and the three recovery/planner controls, reconciled the runtime
inventory and checked decisive claims. Astra challenged the method and
synthesis/plan. Peer reviews crossed authorship boundaries; corrections were
integrated.

**Per-sheet review wave (2026-11-09).** One Opus reviewer per tool sheet, 46 in
all, re-traced each sheet against source, corrected it in place, and added §3.1
route inventories, §5.1 guidance parity, §6.1 simple enhancements and new
sheet-scoped findings. Their evidence is source tracing, read-only Python
introspection, and in-memory handler/dispatch/service runs (some with a
scripted fake LLM or stubbed provider). They did not run pytest, a live
provider, PostgreSQL, a deployed service or a browser. The coordinator ran one
maintainer-approved pytest mutation probe ([evidence](evidence.md#per-sheet-review-wave-2026-11-09)).

**Probe wave (2026-11-09).** One lane per sheet then ran the 141 proposed
probes on 44 sheets, recording each run in the sheet's §7.1. Run forms were
in-memory handler and service runs, real `compose()` and planner loops with a
scripted provider, the REST proposal-accept route driven in process, the
Composer MCP `call_tool` handler from the shipped stdio construction, named
pytest ids, jsdom vitest files, and lane-private source copies for mutation
controls. Outcomes over 148 rows (seven proposals split): 121 confirmed, 8
refuted, 2 inconclusive, 16 not runnable here (browser, running server,
PostgreSQL/Docker or live provider) and 1 not run
([table](evidence.md#probe-wave-outcomes-2026-11-09)). One early probe made one
unintended provider request (an `AuthenticationError`; nothing ran); a
fail-closed rule followed, and no other outbound request is known, judged from
scripted providers, guard logs and call counts rather than packet capture
([network record](evidence.md#probe-wave-method-and-network-record)). The shared
documents were integrated from the sheets' records, with the lanes' reports
treated as claims and the decisive ones re-checked against the sheets and the
baseline source.

This independence supports the assessment, not a claim of exhaustive
correctness. The [evidence record](evidence.md) reports completed local tests
separately. No full suite, PostgreSQL contention selection, live provider,
deployed service or real-browser acceptance was run. No production source, test
suite, policy, dependency manifest or lockfile changed. None of the proposed
fixes has been implemented by this task.

Re-measure live tool names and compare affected handlers, callers, contracts and
test bodies against this baseline. Classify each selected finding as remaining,
changed, corrected or still unverified. Re-run its good/bad controls on the
receiving branch before implementing remediation; the probe-wave table names
the control each sheet ran. A line moving or a newer release number is not
