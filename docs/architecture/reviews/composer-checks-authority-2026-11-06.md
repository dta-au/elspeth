# Composer checks: authority, dispatch, timing and accounting

Read-only source review, 6 November 2026. Observed branch: `release/0.8.10-assembly`; `git rev-parse HEAD` returned `c9f568e63b8df0cdac3ea07763c41192d194fa17`. The working tree contained concurrent implementation changes, including `continuation_primary.py`, `continuation_semantic_advisor.py`, and codec/evidence modules. Findings refer to the observed working source, not a claim that HEAD alone contains it. No tests, imports, services, databases or profiles were run. Test bodies below were inspected, not executed.

Decision: which checks earn their place under hostile users/external providers, trusted operators/developers, and accidental programming errors? Boundary: Composer admission through worker dispatch and SQL settlement; time horizon: one live segment plus recovery and retained paid evidence. A check needed after an asynchronous boundary is materially different from recomputing an already admitted immutable value inside one call. None of the findings establishes a latency contribution or predicts that it meets the five-second acceptance target.

## Findings

### 1. SIMPLIFY the current-authority API; KEEP the live SQL decision

**Intervention level: ownership/API boundary, not cache tuning or deleting individual predicates.** `require_continuation_mutation` reads attempt, parent, segment, fence and principal, then checks current generation, lease, archive/ownership, deadline and Stop ([continuation.py:139](../../../src/elspeth/web/sessions/continuation.py#L139)). `_require_current_continuation_running` immediately invokes it and re-reads attempt and segment to compare the logical claim tuple ([continuation.py:2837](../../../src/elspeth/web/sessions/continuation.py#L2837)). The second segment predicate includes generation, but the first function already established `segment.generation == history.generation`.

The actor/failure is an old worker, a competing current worker, or a user stopping/changing the session while work awaits. Admission to a valid claim earlier does not prove the claim is current now. Keep one fresh authority decision under the actual session transaction; return its admitted attempt/segment/parent facts to the immediate internal caller, and perform the claim comparison against those same rows. Do not return a reusable authorization token valid across awaits. Keep the existing boolean public behavior only where current callers require it; pre-1.0 does not justify compatibility scaffolding.

This removes duplicated row acquisition while retaining every accepted-state invariant. `locked_session_transaction` establishes the common session exclusion ([locking.py:556](../../../src/elspeth/web/sessions/locking.py#L556)); this is a transaction-scoped refactor, not permission to reuse yesterday's lease. Tests directly exercise Stop/deadline inside the transaction ([test_composer_operation_authority.py:363](../../../tests/unit/web/coordination/test_composer_operation_authority.py#L363)) and Stop arriving between an earlier read and a later retry lock ([same file:1960](../../../tests/unit/web/coordination/test_composer_operation_authority.py#L1960)). The latter is a real ordering counterexample to removing the later check.

**Peer falsification changed the recommendation.** I initially considered deleting the historical-reference facade's extra principal reads ([composer_operation_authority.py:1562](../../../src/elspeth/web/coordination/composer_operation_authority.py#L1562)). Reconstruction reviewer identified that a normally constructed `ComposerOperationRunning` can combine a same-session claim and context from different logical operations; its constructor binds session/kind, not logical operation. The first guard follows context history; the later queries follow claim. Therefore unconditional local deletion is unproved. Bind claim and context through the one admitted-row API first. The peer agrees with that narrower intervention and requires mismatched operation/token/generation and later Stop opponents. Direct-name source search found this historical facade's direct call sites in tests, so it is not a demonstrated production latency target.

**Confidence:** High for duplicate reads and need for fresh authority; Moderate for the replacement API until all current callers are reviewed. **Risk:** High if transaction scope or claim binding is weakened; Medium for the bounded refactor.

### 2. KEEP transaction-local mutation ceilings; do not treat the initial mode as enduring consent

**Intervention level: policy enforcement at the mutation owner.** `ComposerMutationCeiling` admits an initial request mode and permits automatic work only when both initial and current modes are `auto_commit` ([composer_mutation.py:16](../../../src/elspeth/contracts/composer_mutation.py#L16)). `check_auto_mutation_on_connection` reads current mode inside the write transaction ([composer_mutation_guard.py:16](../../../src/elspeth/web/coordination/composer_mutation_guard.py#L16)); repository mutation invokes it before the business callback ([repository.py:6322](../../../src/elspeth/web/coordination/repository.py#L6322)). P4 persistence likewise reads it before publishing graph rows ([service.py:2587](../../../src/elspeth/web/sessions/service.py#L2587)).

The relevant hostile action is an unauthorized automatic mutation; the relevant legitimate action is a user downgrading authority while the provider works. Initial authorization proves a ceiling, not current consent. The preference writer deliberately avoids the long compose lock and orders changes against settlement using the session write lock ([service.py:3820](../../../src/elspeth/web/sessions/service.py#L3820)). That is an actual product concurrency mechanism, not malicious Python.

Meaningful tests cover all initial/current mode pairs and refusal before callback entry ([test_common_mutation_business_custody.py:147](../../../tests/unit/web/composer/test_common_mutation_business_custody.py#L147)). Be precise about the separate blob-transition test: it intentionally bypasses real custody with SQL to isolate the predicate ([same file:345](../../../tests/unit/web/composer/test_common_mutation_business_custody.py#L345)); that test alone does not establish that the real preference API can interleave inside a blob custody interval. The direct production preference path is the stronger evidence for keeping commit-boundary consent.

No source-backed removal is recommended. A shared mutation API may consolidate duplicate mode reads inside the *same* transaction, but a mode check before an await cannot replace the commit check. **Confidence:** High. **Risk of removal:** High; keep behavior while simplifying callers only when identical transaction scope is proved.

### 3. KEEP fresh clock/owner observations; separate immutable policy reconstruction from current time

**Intervention level: separate the stable policy input from the changing observation API.** `read_continuation_timing` takes the session transaction, verifies current running authority, loads/decodes the snapshot and admitted policy, reads the current segment and database clock, then freezes remaining time ([composer_operation_authority.py:850](../../../src/elspeth/web/coordination/composer_operation_authority.py#L850)). The driver already decodes and compares policy with its original SQL deadline owner's policy before requesting this timing observation; it subtracts elapsed read time before action fit ([continuation_driver.py:1690](../../../src/elspeth/web/sessions/continuation_driver.py#L1690)).

This is not merely a duplicate check: asynchronous work consumes the remaining budget, and ownership/Stop may change. The elapsed-boundary test waits outside the transaction and obtains another real SQL observation, demonstrating that cooperative time can expire while sufficient hard time remains ([test_continuation_action_fit_successor.py:348](../../../tests/unit/web/sessions/test_continuation_action_fit_successor.py#L348)). Preserve fresh database time, current segment generation/deadline and actual writer admission.

**Conditional simplification:** let a coherent selection operation deliver the admitted policy and its source identity to timing, so timing need not reconstruct unchanged policy solely to retrieve the watermark. This needs an exact selected-root binding and a current snapshot check; passing an arbitrary watermark is not equivalent. A new cross-stage cache or trusting a policy object merely because it is nominally typed would add invalidation burden. No current cost attribution proves this reconstruction is worth changing. The no-change option is reasonable until source-work measurement identifies it as material.

**Confidence:** High for the freshness requirement; Moderate for the proposed stable/current split. **Risk:** High if it reuses a stale clock or deadline; Medium if limited to admitted immutable policy under exact source binding.

### 4. KEEP physical Future ownership and finish-once admission; challenge anti-forgery additions separately

**Intervention level: executor lifecycle design.** `_submit_shared` registers a reservation, submits a gated wrapper, binds the actual Future and completion callback, and only then arms the callable ([async_workers.py:536](../../../src/elspeth/web/async_workers.py#L536)). `RequiredInvocationWitness` implements waiting/armed/aborted states; `InvocationReservation.release_future` requires its actual completed Future and releases admission once ([required_executor.py:72](../../../src/elspeth/web/required_executor.py#L72), [same file:153](../../../src/elspeth/web/required_executor.py#L153)).

An awaiting coroutine's cancellation does not imply its SQL thread has finished. Real blocked-thread tests cancel repeatedly while proving that completion has not occurred, then release the thread and observe termination ([test_composer_stream_worker_custody.py:12](../../../tests/unit/web/test_composer_stream_worker_custody.py#L12)). Releasing capacity or operation custody on coroutine exit would admit overlapping work and lose late failures. Keep actual Future completion, idempotent release, draining and bounded recovery.

Do not use every adversarial identity test as a security justification. The completion-identity tests directly replace/delete private registry entries ([test_required_executor_completion_identity.py:45](../../../tests/unit/web/test_required_executor_completion_identity.py#L45)); those are useful accidental-corruption controls, not proof of a hostile-user entry path. Conversely, the queue-then-raise executor test ([test_required_executor_custody.py:19](../../../tests/unit/web/test_required_executor_custody.py#L19)) models ambiguous submission with a substituted executor: it is evidence of the required recovery behavior, not by itself evidence that every exact synthetic failure occurs in the shipped executor. A removal proposal must trace concrete supported submission/callback failures and preserve physical ownership, rather than dismiss the entire design because the tests use fault injection.

I did not establish a narrower removable witness/registry predicate whose benefit outweighs implementation risk. Keep the current lifecycle; classify per-field anti-forgery checks as accidental-misuse assertions unless a genuine external path is demonstrated. **Confidence:** High for physical completion; Moderate for necessity of every corruption-specific branch. **Removal risk:** High. No latency claim.

### 5. KEEP paid-attempt/ledger binding and Stop-safe settlement; MOVE repeated immutable request work to one admission result

**Intervention level: split live accounting authority from immutable request materialization.** Before PRIMARY dispatch, the current guard, selected effect and requested model are checked, then `begin_provider_attempt_on_connection` assesses current identity/role/quota and inserts the physical attempt in the same transaction ([continuation_primary.py:960](../../../src/elspeth/web/sessions/continuation_primary.py#L960), [quota_authority.py:151](../../../src/elspeth/web/coordination/quota_authority.py#L151), [chargeable_admission_authority.py:27](../../../src/elspeth/web/coordination/chargeable_admission_authority.py#L27)). Unknown prior usage cannot become free budget; tests distinguish unknown usage from an empty zero ledger and same-fence pending work from a different operation ([test_quota_authority.py:442](../../../tests/unit/web/coordination/test_quota_authority.py#L442), [same file:615](../../../tests/unit/web/coordination/test_quota_authority.py#L615)).

External providers can return incomplete/invalid output after incurring cost; an accidental cross-attempt join can charge the wrong identity or permit an unsafe retry. The paid PRIMARY finalizer reloads current effect/hold/physical rows and retained input before matching call/model/request/creator ([continuation_primary_paid_incomplete_finalization.py:76](../../../src/elspeth/web/sessions/continuation_primary_paid_incomplete_finalization.py#L76)). The request proof reconstructs wire/tools and compares the actual call's original messages/tools/context and physical identity ([continuation_primary_paid_overflow_source.py:21](../../../src/elspeth/web/sessions/continuation_primary_paid_overflow_source.py#L21)). Historical attribution is an accounting invariant even when all programmers have trusted intent.

Stop must deny new business work while allowing already incurred accounting obligations to settle under still-valid ownership. The checkpoint test invokes authenticated owner Stop *after the actual scripted provider return*, then verifies consumed hold, one ledger entry, preserved cost/tokens and failed parent ([test_continuation_checkpoint_paid_stop.py:113](../../../tests/unit/web/sessions/test_continuation_checkpoint_paid_stop.py#L113)). Replacing this with a blanket “cancel means refuse every write” would lose the product's accounting guarantee.

The supported simplification is a single named admitted request result carrying descriptor, canonical wire/tools and context through the immediate operation; consumers should not discard an already constructed request and rebuild it purely to recover the same fields. Keep fresh hold/effect/ledger state and historical joins at SQL entry. This recommendation is conditional on inspecting every cross-module caller and retaining mutation isolation. A shared private tuple is still a real API: changing its shape without all callers is an accidental-human-error risk, not a malicious-code attack. No blanket removal of paid-history comparisons or weak-issued observations is justified by this review. **Confidence:** High for accounting checks; Moderate for reusable request materialization. **Risk:** High for wrong-attempt settlement; Medium for the named-result refactor with complete caller coverage.

## Peer review and dispositions

- Reconstruction reviewer falsified the unconditional historical principal-read removal through a normally representable mixed claim/context. Accepted; recommendation changed to an admitted-row API with explicit logical binding. The peer then accepted same-transaction attempt/segment reuse while requiring stale/mixed-owner and later-Stop opponents.
- I critically reviewed the evidence reviewer's recorder proposal against `ApplicationRecorderSource.__init__` and `decode_recorder_snapshot`. The same-call duplicate raw verification is a real simplification candidate, but memo `_admit_recorder_data` deliberately performs current admission on each hit and has other decoder callers. I opposed deleting that callback generally, and opposed equating frozen outer snapshots with deep immutability. Recommendation returned: one raw-boundary admission plus an internal already-verified decode path; retain roundtrip/credential guarantees and independent mutation tests before wider reuse.
- I flagged the codec's crypto-function identity pins to the evidence reviewer as a potential trusted-developer threat-model mismatch, not a finding established here. Actual digest checks remain necessary; supported monkeypatch/customization behavior was not established.

## Confidence Assessment

**Overall Confidence: Moderate.** Fresh SQL authority, mutation consent, physical completion and accounting obligations have direct production and meaningful test-body evidence. API simplifications are source-grounded proposals, not validated implementations. No runtime performance or current gate result is claimed.

## Risk Assessment

**Implementation Risk: High** for blanket deletion; **Medium** for bounded ownership/API consolidation. **Reversibility: Moderate**: code rollback is straightforward, but wrong accounting/publication effects are not safely undone by rolling back code. Main hazards are stale authority across awaits, mixed claim/context, mutable borrowed request graphs, and lost accounting after Stop. Mitigate with transaction-local facts, exact source identity, explicit named inputs and focused race/negative opponents; do not migrate or delete persisted records.

## Information Gaps

- No source-work measurements attribute time to these authority/timing checks; no speedup estimate is justified.
- Complete caller inventories and dialect behavior must be rechecked before changing shared private APIs. This review sampled the live cross-module paths named above.
- The exact necessity of every executor anti-corruption branch requires supported-failure analysis; fault injection alone is not an external threat model.
- Concurrent mainline edits mean final line numbers and request-helper contracts need a final source check before implementation.

## Caveats and Required Follow-ups

Before implementation, choose one bounded API contract, inspect its complete caller set, preserve synchronous transaction lifetime and establish exact retained-data mutation semantics. Validate mixed owner/claim, stale generation, late Stop, policy downgrade, delayed timing observation, canceled SQL await with a still-running thread, unknown usage, wrong paid attempt and already-paid Stop settlement. SQL/locking changes require serial PostgreSQL proofs as well as focused tests. Preserve the ordinary provider path and tutorial parity; no synthetic planner, migration, record deletion or compatibility path follows from this review.
