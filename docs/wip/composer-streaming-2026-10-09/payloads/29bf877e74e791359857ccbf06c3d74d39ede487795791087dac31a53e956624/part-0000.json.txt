Stop sets `owner.stop`, but the next iteration dispatches the queued POST before checking `owner.stop`. A cancel returning `operation_missing` also clears the boolean at line 103. That 404 establishes neither durable cancellation nor absence of a still-running admission SQL thread.\n\nMeasured trace from `frontend-astra-probe-evidence.json`:\n\n```\nPOST A -> network ambiguity\nGET A -> operation_missing; user invokes Stop\nCANCEL A -> operation_missing\nPOST A -> queued acknowledgement          # after Stop\nCANCEL A -> operation_missing\nSTREAM A -> unavailable\nGET A -> completed\n```\n\nBoth POSTs have the same exact body, but exact identity alone does not make a post-Stop dispatch acceptable: if the first request never admitted, the second creates the work the user withdrew. A later cancel races worker start/provider work.\n\n**Required correction:** latch withdrawal independently from whether one cancel request succeeded; check it before every POST, including already-scheduled recovery. Continue read-only reconciliation of the exact submitted ID and retain its body while admission may still commit. Once the row becomes visible, retry cancellation as needed; terminal wins cancellation. Do not clear unknown custody on a missing cancel response. A missing GET schedules a POST. If that POST gets an active-job refusal naming B, `attachComposerObserver(..., ambiguous)` receives false and discards submitted A instead of moving it into `unresolvedSubmissions`. B's terminal then clears foreground custody too.\n\nMeasured trace:\n\n```\nrestored submitted A (exact body present)\nSTREAM A -> unavailable\nGET A -> operation_missing\nPOST A -> composer_operation_active(B)\nGET B -> completed\nforeground = null\nunresolvedSubmissions = []               # A body has disappeared\n```\n\nThis is the contract's late-SQL-admission race. B's terminal says nothing about A; A can still admit after B settles. The tab can now consider itself free to mint another action while A's custody has been erased.\n\n**Required correction:** restore descriptors conservatively and preserve earlier potentially dispatched submissions independently of the foreground observer. Read-only restoration, with submission requiring an explicit current action/recovery policy, avoids silently reviving prior work. If any restore replay is retained, admission certainty must be represented/proved; absence of in-memory ambiguity is not proof. Only A's own terminal, session disappearance, or a reviewed definitive refusal resolving A may clear it. The observation deadline is only tightened after the stream ends and a durable GET supplies remaining time. A valid stream can therefore keep observation alive beyond the remaining-duration budget; every valid heartbeat refreshes the inactivity watchdog. There is no separate browser absolute subscription timer in this function.\n\nA controlled monotonic-clock probe compared the same remaining duration through the two transports:\n\n```\nGET remaining=0, elapsed=26000:\n  outcome=ComposerObservationDetached, GETs=1, cancels=0, custodyRetained=true\nSSE status remaining=0 + heartbeats at 10s and 20s, elapsed=26000:\n  outcome=pending, GETs=0, cancels=0, custodyRetained=true\n  only outstanding timer: 15s inactivity watchdog, due at 35s\n```\n\nThe zero remaining duration plus the configured 25,000ms grace is deliberately well inside the proposed 120-second server subscription lifetime. This establishes different observation-budget behavior without relying on a broken server lifetime. Continuous valid frames would also defeat a browser-only lifetime bound if the server did not close it; that server fault was not exercised here.\n\n**Required correction:** route admitted status remaining durations through the same monotonic tighten-only deadline while streaming. On expiry detach/close the reader and retain custody, with no cancel POST and no provider replay.
