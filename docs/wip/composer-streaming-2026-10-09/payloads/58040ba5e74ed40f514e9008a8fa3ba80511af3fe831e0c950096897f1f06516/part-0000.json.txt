"# Local nominal guards as a narrower reserve proof alternative\n\nRead-only evaluation; no repository source/test/doc edits, scanner writes, production rename, test run or exemption. Root's canonical gate remains frozen. The preceding complete design and raw live receiver inventory remain authoritative: `transport-reserve-proof-design.md` and `transport-reserve-receivers-live.json`.\n\n## Decision\n\n**Local runtime guards can materially shrink the supplier proof, but carrier guards alone cannot soundly close all reserve collisions.** Recommend a hybrid of genuine integrity-boundary checks and narrowly source-proven exact guard/immutable binding facts. Reject a claim that adding a handful of constructor checks eliminates every caller/dispatch proof. A full guard-only closure would require repetitive guards immediately before each unresolved dispatch, including four coordinator self methods, and either rejecting supported telemetry test subclasses or freezing/checking actual method objects. Those remaining changes are principally scanner-driven or change the adopted nominal telemetry extension semantics; they are not justified by the presently measured runtime gaps.\n\nThe useful smaller implementation boundary is a **reserve-specific local proof** that recognizes (a) an unchanged exact runtime type guard, (b) construction of unchanged RequiredWorkBinding whose post-init exact guard validated the same non-rebound local, and (c) closed guarded carrier writes plus unchanged getter, followed by the unchanged pure method/transitive recipe. No annotation establishes a proof. If a site lacks those facts, it remains red; the proof must not invent an incoming supplier.\n\nHistorical failed canonical diagnostic3 had 29 unknown reserve receiver rows. The subsequent controlled live direct-call registry has **31 production calls = three genuine Landscape calls + 28 Web collisions, of which 27 concern coordinator and one installation**. The earlier extra worker site is absent from the later AST. This document does not rerun the mutation gate or assert its latest violation count. The later measurement recorded no source changes during capture; no new count is inferred from a text search.\n\n## Actual facts already available without new guards\n\n1. `SessionServiceImpl._run_composer_terminal_sql` already rejects non-None values whose exact type is not RequiredWorkCoordinator before its two direct reserve calls (8003/8035). A source recognizer for that dominating exact guard, unchanged class binding and non-rebound parameter would avoid caller traversal for those two calls. A changed None-only/context-only guard must fail the proof.\n2. RequiredWorkBinding.__post_init__ already requires `type(coordinator) is RequiredWorkCoordinator` and is a frozen, final dataclass. ProviderCallCustody.__init__ requires the exact binding type, validates its context, stores it once and returns it through its getter. A narrow exact binding/field/getter recipe can close the two quota calls (162/260), provided every replacement/write to that field/property or binding constructor guard invalidates the recipe. This is a real runtime check, not a type annotation.\n3. `_run_composer_turn` captures `required_work = observation.required_work`, then constructs `provider_binding = RequiredWorkBinding(required_work,...)` at697 **before** its direct title reserve at835. The existing exact post-init guard therefore validates that same local. If local non-rebinding and unchanged constructor/post-init dispatch are proved, an additional type check before title reserve is gratuitous. This fact was not included in the first design's generic unresolved result and is a genuine opportunity to shrink the proof.\n\nThese facts provide local guard/binding evidence for five external sites. They do not by themselves prove all self/property dispatches or all uses of the mutable observation field.\n\n## Genuine runtime integrity gaps and proposed minimal checks\n\n### Lease ownership: genuine boundary checks\n\nCurrent SessionOperationLease.__init__ assigns optional `_required_work` without validating its type or context, and starts a renewal task. adopt checks matching context but calls `required_work.reserve` before constructor validation. bind_required_work checks context and existing equality but does not require an exact coordinator before reading its authority. Thus a first-party corrupted/impostor argument can receive dispatch before a nominal owned coordinator failure is diagnosed. This is an ownership/physical work lifecycle boundary, not merely a scanner collision.\n\nSmall repair candidate:\n- __init__: before any task allocation, require optional value to be None or the exact coordinator and, when present, the context to match the lease. Preserve constructor fail-fast ABI and existing owned authority failure semantics; do not add a rank or wire error.\n- adopt: perform the same exact optional-type check before its first authority/property/reserve access, because this reserve occurs before __init__. Constructor-only validation is insufficient.\n- bind_required_work: require exact coordinator before property access, and compare retained ownership by identity; preserve immutable context checks. Refuse a corrupted previously retained non-None field rather than allowing a custom equality implementation to classify it as equal.\n\nThe scanner may prove a **closed field-write recipe**: the only admitted writes are the validated constructor and validated bind method, and the getter is unchanged. An additional unguarded write, property replacement, subclass overriding the getter, arbitrary alias mutation or unbound foreign carrier invalidates that recipe. Merely trusting `lease: SessionOperationLease` remains forbidden.\n\nThese checks improve runtime diagnosis independently of the gate. They do not solve a caller passing a completely foreign object as `lease` whose `required_work` getter returns another foreign object; worker reserve still needs a validated actual coordinator snapshot or an actual carrier class proof.\n\n### Worker's coordinator snapshots: genuine once-per-job ownership check, conditional scope\n\n`_run_started` already captures `coordinator = lease.required_work` before its setup reserve. Validating that local exact coordinator (or the permitted None arm) before reserve would refuse an invalid supplier even if lease/property origin is unknown, and preserve the job's coordinator identity. This eliminates traversal for that direct site and fits a real required-work entry boundary.\n\n`_run_started_under_lease` repeatedly reads lease.required_work and creates a turn observation. A local **single validated snapshot** used consistently for the producer and observation is preferable to checking one property read and later dispatching a second potentially different read. This is an ownership consistency choice, not a variable rename to evade the scanner. A type guard on one expression cannot protect a later expression with dynamic getter or reassignment behavior. The exact coordinator snapshot must agree with any already retained job coordinator; do not introduce a second coordinator or relax the existing operation/fence contract.\n\nThis change needs review of actual job-frame custody and forwarding, rather than assuming all uses can be substituted safely during a frozen gate. It is a concrete source boundary, not an implemented patch.\n\n### Turn observation: one real entry check; constructor guard alone is insufficient\n\nComposerTurnObservation is a final **mutable** dataclass and its required_work field has no post-init guard. Both turn entry functions accept an already supplied non-None observation coordinator, while absent values are derived from the lease or constructed. The lease bind currently precedes the RequiredWorkBinding exact check. A nominal check after the selected observation coordinator is captured and before bind prevents dispatch on a corrupt supplied coordinator, and is a legitimate required-control entry check.\n\nAdding only __post_init__ would not cover later mutation of that field, so it cannot replace the entry check or carrier-write proof. Adding a repeated check before title reserve is unnecessary once the existing immutable binding has validated the non-rebound local.\n\nThe error helpers receive `observation.required_work` after awaits, rather than the already validated `required_work` local. Forwarding the same validated coordinator used for provider ownership would make the scope stable and avoid trusting a later mutable observation read. This may be a genuine consistency repair, but does not alone prove all callers of the three helpers. Each helper's optional input is also an independently callable required-work boundary: an exact check before its first required reserve is defensible if the function contract explicitly promises nominal custody. Alternatively retain its unknown row until the closed actual caller is proved. Do not add a type check at every private helper just to reduce records while claiming no semantic change.\n\n### Proposal scope: genuine input check\n\n`_settle_pipeline_proposal_under_compose_lock` chooses proposal_work either from a supplied parent/child or a direct constructor. The supplied branch checks proposal/tool identifiers but not the coordinator's actual type, so its first `.authority`/reserve access can dispatch on an impostor. Validate the **selected** proposal_work exact type before any dispatch and preserve existing proposal/context identity checks. This is a business ownership entry seam and covers all eight direct reserve sites using a local checked value, without traversing caller arguments.\n\nThe proof must reject reassignment after the check, a supplied alternate branch not passing the check, a shadowed coordinator class, or changed pure reserve/key/ticket bodies. It must not accept the existing resolver's final constructor binding while ignoring the supplied branch.\n\n## Why a complete guard-only closure is not presently justified\n\n### Seven internal self calls\n\nreserve_pair (two), reserve_audit_work (three), begin_proposal_child (one), prepare_lease_release (one) call `self.reserve`. Lexical self does not prove an exact runtime receiver. A fake object can be supplied in an unbound base-method invocation, and a subclass can override reserve; a guard inside the base reserve does not run when another method is selected.\n\nTo eliminate incoming-self traversal with runtime checks, each of those four calling methods would need an exact self check **before** any lock/other self dispatch and before reserve. Reusing a dynamically selected `self.assert_owner()` would be equally bypassable by the fake and would not establish an exact function. The direct exact checks would be sound against foreign/subclass/unbound calls, but no independently observed legitimate caller presently violates these self method boundaries. Adding these four checks exclusively so the scanner can avoid proving actual dispatch is a scanner-driven production expansion, unlike the concrete incoming coordinator seams above. A constructor exact-self check or @final annotation does not solve an unbound call on an object that never used that constructor.\n\nRecommendation: retain a small source dispatch proof for these self sites (exact constructor roots, unbound call and override/replacement census) or leave them red. Do not silently waive their mandatory negatives.\n\n### Telemetry installation and the supported nominal test domain\n\nOperatorTelemetryCleanupOwner.__init__ deliberately accepts nominal TelemetryInstallation instances through isinstance. Existing reviewed offline controls use OwnedTestTelemetryInstallation subclasses:\n- setter installs the actual provider and then raises the original (custody test221);\n- getter raises the original and leaves unresolved installation (244);\n- finish_cleanup raises and must never publish a witness (287).\nThese are real adopted lifecycle controls, not fake production defaults. Restricting the installation to exact two classes would reject them before the lifecycle behavior under test and would silently change the approved nominal test-factory ABI.\n\nThe installation.reserve method calls both self.assert_process and owner.assert_process. Nominal owner/installation guards alone cannot prove those particular executable methods or stop a subclass overriding reserve before the base body's guard runs. An installation-class check in reserve does not establish the caller's selected method. The owner's installation field is public/mutable; a one-time constructor guard does not make a later changed field safe.\n\nA runtime guard on the actual **bound callable identity**, captured once and checked against unchanged method bodies, could avoid supplier traversal while retaining setter/getter test subclasses. It would have to prove MethodType/function/self identities, inherited process checks and no dynamic-getter switch between check and dispatch. That changes how the caller selects/invokes the method and creates a new dispatch integrity API; it is not the requested minimal concrete-type guard, and introducing bound-callable aliases merely to placate the scanner is prohibited. It therefore remains out of this recommended alternative.\n\nA narrower source subclass/field recipe can accept the production and explicit test-domain classes **only when reserve and process-check dispatch remain inherited and unmodified**, permitting unrelated setter/getter/finish_cleanup overrides. That still needs bounded supplier/override proof; it is not eliminated by the guard proposal. No current production installation corruption was measured that justifies rejecting every nominal subclass.\n\n## Recommended smallest hybrid, and exact limits\n\n1. Implement no changes during the frozen gate. Review the independently useful lease/adopt/bind, selected observation/worker coordinator and selected proposal input integrity checks first, preserving originals, existing ABI and fixed policy categories. No new error mapping, finalizer kind or provider authority.\n2. Add one reserve-specific **local evidence recognizer**, not a generic receiver annotation rule: recognize exact dominating guards and same-local validation through immutable RequiredWorkBinding, with rebinding/mutation/changed-dispatch refusal. Require the same reviewed pure method/transitive source recipes from the first design.\n3. Use only closed source field/write/getter checks where they genuinely prove the carrier; do not infer a property's runtime class from its annotation. Keep the self-dispatch and installation subclass/supplier boundaries unresolved until their small exact recipes are proved.\n4. If root requires all sites green with no supplier traversal, this guard-only proposal is **NO-GO as a complete solution** under the anti-gratuitous-change constraint. It can reduce unresolved work, but cannot honestly eliminate it while retaining every foreign/subclass/unbound/reassignment/modified-dependency negative.\n\nGuard-local evidence is currently available for five external calls (two service, two quota, one turn title) even without new production guards. Selected proposal check would cover eight more; selected worker snapshots two more; adopt checks one more. Three error-helper entries and one renewal carrier still need their actual guards or closed carrier/caller proof. The seven self calls and one installation call remain the irreducible dispatch cases for this alternative. These coverage figures describe the measured direct-call inventory and proposed evidence, not completed scanner tests.\n\n## Negative matrix that must remain red\n\n- Annotated foreign/impostor .reserve, shadowed class imports and overridden coordinator reserve.\n- Unbound reserve_pair/reserve_audit_work/child/release call with foreign self; constructor guard must not falsely admit it.\n- Instance/class reserve replacement, including alias/setattr, and any post-check local or carrier reassignment.\n- Modified real reserve, key maker, ticket/key constructor, installation record or process-check dependency that introduces DML or an unknown callable.\n- Lease constructor/adopt/bind supplied impostor and changed field/getter/write path; incorrect retained identity/context.\n- Mutable observation changed after initialization; validating a different earlier read must not admit the later read.\n- A proposal's supplied branch without the exact guard while its constructor branch remains positive.\n- Installation/owner nominal subclasses with changed reserve/process dispatch must refuse; setter/getter failure subclasses with inherited unchanged reserve must preserve their existing lifecycle positive/negative intent.\n- Guard changed into None-only, isinstance-of-a-structural-Protocol, context-only or annotation-only proof.\n- Bound callable escape/unknown dynamic factory and unresolved caller defaults must not become an exemption.\n- Genuine Landscape reserve calls must stay in normal authority/DML inventory.\n\nNo negative test was run and no new runtime gap is claimed measured by execution. The conclusions above follow directly from complete relevant source methods and the retained controlled AST receiver registry. They distinguish first-party fail-fast ownership improvements from production edits proposed only to make a scanner number smaller.\n"
