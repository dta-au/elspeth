R6 is pending in the reviewed source; its report is a dependency, not a passing-test claim.\n\n## Findings requiring changes\n\n### 1. The proposed monotonic lease bound is not proved by the actual database clock\n\n`coordination/repository.py:4593` chooses PostgreSQL `SELECT clock_timestamp()` or SQLite `SELECT CURRENT_TIMESTAMP`. Acquisition assigns `lease_expires_at=database_now + lease_seconds` at line 4782; renewal uses the same form at line 5095. The returned value is only the immutable context, not an expiry/time receipt. Expiry is checked with strict `lease_expires_at > database_now` at line 4965. Capturing a local monotonic timestamp before submission correctly accounts conservatively for queue and SQL latency **only after** a relation between future database clock readings and local elapsed time has been established.\n\nThe draft specifically discusses backward movement but omits forward steps and clock precision. A forward database step can expire the row before `submission_monotonic + duration`. Even without a clock step, SQLite's whole-second clock admits a counterexample: submit/sample at real time 100.9, record database time 100, and use duration 10. SQL rejects at database time 110 while the proposed bound remains live until local time 110.9. This is a source-derived counterexample, not a runtime measurement. Taking a paired expiry/database observation alone does not eliminate future forward-clock movement.\n\nRequired change: declare and justify the actual clock model, including precision, bounded rate/step assumptions, and a conservative margin; or refuse this retry eligibility where that model is unavailable. If using an expiry/clock return receipt, specify its transaction, commit, context and clock-pairing semantics and review that ABI separately. The receipt must expire during a long successful SQL call when its conservative bound has already elapsed; success cannot reset it to completion time. Reject non-finite/invalid bounds. A lease-time observation must never authorize a business effect, suppress a real renewal failure, infer database expiry, or supersede an authoritative Stop/deadline check.\n\n### 2. Retry needs a cutoff at admission, not merely between attempts\n\n`async_workers.py:503` delegates to `_wait_for_admission`, which waits up to one second; its loop tries admission **before** testing its admission deadline. `_submit_shared` then checks generation availability, but has no caller lease/job cutoff. A watcher retry begun just before its lease/job bound can therefore submit SQL after that bound unless the new bridge explicitly enforces the earlier cutoff. The existing watcher checks deadline and shutdown only after the read (`composer_async_worker.py:723–739`).\n\nRequired change: make the no-submit retry budget interruptible by the exact loss/shutdown latch, and recheck the earliest original job budget and valid lease observation at the point authorizing a new submission. Define the linearization with generation/submission admission. Do not use outer cancellation of an ordinary `run_sync_in_worker` as proof that a potentially submitted read never ran. Once there is an actual Future, use its real observation/join semantics; an expired retry budget cannot erase custody or its original outcome. Never start overlapping read attempts to improve latency.\n\nThe private refusal receipt should be minted only in the actual `_acquire_admission` failure arm of `_submit_shared` (lines 173–181), for the exact timeout instance and unchanged ACTIVE generation/reservation. At that point the reservation is not held, registered or submitted. This is the correct branch; a generic catch around a worker callable is not. Verify the same generation object remains current and available when consuming the receipt, not only its integer/name. An old valid receipt cannot authorize retry after quarantine/replacement/draining. A class, constructor seal, or copied identity fields alone are not issuance evidence. Keep eligibility pinned to the intended observation call site; the carrier is no general write-retry permission.\n\n### 3. Renewal retry is a distinct ABI obligation; do not slide it into read retry\n\nActual source40 renewal reserves a ticket for each predetermined renewal ordinal (`coordination/lifecycle.py:789–795`), executes `run_required_sql_finish_once`, and validates the exact coordinator/ticket/outcome (`:828–866`). `_submit_shared` completes a pre-admission failed ticket with the actual error; `RequiredWorkTicket.complete_without_submission` refuses ticket reuse (`required_work.py:553–560`). R6 addresses retained Unknown/cancellation identity and close error masking; it must remain intact.\n\nThe draft's “renewal retry, if needed” does not yet specify the attempt key, when a new ticket may be reserved, or how original failed attempts participate in existing reduction if a later attempt succeeds. Do not reuse a completed ticket, reset the renewal tick identity, issue a bound from `RequiredSQLRaised`, or turn a recorded operational failure into an unrecorded success. Either explicitly exclude renewal retry from this amendment, or define its precise existing-key mapping and selection behavior and review that small extension. This requires no new source/rank and gives no authority to source51/52.\n\n### 4. Successful acquisition can arrive after sealing; the registry needs an admitted owner before that race\n\nThe real `/execute` route acquires before calling `service.execute` (`execution/routes.py:1034–1047`). Acquisition is an asynchronous submitted SQL operation (`coordination/lifecycle.py:438–451`); cancellation cleanup can release a returned context without ever constructing the lease object (`:224–247`, `:452–467`). Recovery separately acquires EXECUTE leases (`execution/recovery.py:236–244`). Application finalizers are sealed before `begin_shutdown` (`app.py:1038–1043`). Therefore “register at successful acquisition before draining” is not a complete implementable rule: acquisition may already be running when seal/drain wins, then return a valid context.\n\nRequired change: establish ownership of each eligible in-flight EXECUTE acquisition before the seal boundary, with an exact later handoff of its actual successful context to its pre-admitted release obligation; or demonstrate an existing admission barrier that joins all those acquisitions before sealing. Do not admit new acquisition after seal. A pre-admitted completion is not blanket permission to register arbitrary post-seal cleanup. Bind the exact authority object/release callable and actual context, and cover route refusal, cancellation-before-transfer, constructor/handoff failure, recovery and normal pipeline completion. Do not give all `SessionOperationLease` kinds a process-drain bypass. Whether recovery EXECUTE acquisitions belong to this family must be stated explicitly, not inferred from the enum alone.\n\n### 5. Join-all semantics must survive executor-finalizer cancellation/failure\n\n`ExecutionService.shutdown` awaits the executor finalizer at `execution/service.py:1597`, then gathers completion Futures at `:1598–1609`. `run_application_finalizer_in_worker` preserves cancellation and raises it after joining the actual executor Future (`async_workers.py:252–276`). Consequently, a cancellation or failure at that first await exits `shutdown` before the lease-completion loop. The application catches the error and proceeds to shared-worker shutdown (`app.py:1032–1064`), closing the generation needed by remaining release tasks. The proposed release registry alone does not fix that ordering.\n\nRequired change: capture executor-finalizer outcomes, continue physically joining all existing execution completion tasks and their exact lease release obligations, then propagate originals using the established preservation policy. Keep the registry visible to application completion checks even if callback allocation or service completion bookkeeping fails. A release callback completing with SQL failure proves physical completion, not successful release; do not delete its last failure evidence when removing the pending entry. Same-owned completed observation can be idempotent with per-capability terminal state; foreign or replaced ownership must fail integrity checks.\n\nNormal watchdog COMPLETE currently requires no primary lifespan error and no generation-unavailable latch (`app.py:651–654`). Retain that condition and require registry/physical completion as well. No unresolved capability, unknown submission, failed cleanup, or abandoned completion callback may become success. A known pre-submit cleanup refusal may remain a failed cleanup for supervision; do not forge a completion receipt to empty the registry.\n\n## Boundaries that should remain unchanged\n\nThe separate EXECUTE family is preferable to adding generic functions to `ApplicationFinalizerKind`, which currently declares membership drain, membership stop and executor join. Its sole bypass is process draining with the exact same ACTIVE generation. `_submit_shared` must retain actual reservation registration, Future binding, callback installation and gate arming; quarantine, `_GENERATION_UNAVAILABLE`, CLOSED/shared shutdown and unknown submission remain refusals. No new pool, worker, admission slot, business write, renewal or START bypass follows from a release capability.\n\nThe source constants are `MAX_WORKERS=16`, `MAX_QUEUED=16`, `ADMISSION_CAPACITY=MAX_WORKERS+MAX_QUEUED` (`async_workers.py:29–34`). These are inspected configuration, not a live occupancy measurement. `ComposerStreamPermits.acquire` rejects at operation 2, principal 4 or total 8 (`composer_stream.py:43–49`); permit release follows outstanding I/O task completion (`:110–114`). Retain those caps and the existing job/provider limits. A retry carrier cannot free a held physical reservation or subscriber permit.\n\nStop is not identical to lease expiry. `request_cancel` durably records `cancel_requested_at` (`composer_operation_authority.py:453–470`); the watcher observes it (`composer_async_worker.py:731–733`), and mutation authority separately rejects it (`composer_operation_authority.py:812–848`). `/operations/...` cancellation also signals the local worker after its durable operation/readback (`sessions/routes/composer/operations.py:230–234`). A local signal does not replace cross-instance polling. `SessionOperationLease.guard_external_effect` explicitly re-proves authority using CAS and the loss latch (`coordination/lifecycle.py:721–740`); a timing bound is not a replacement.\n\nWhile read admission is refused, the watcher has no fresh evidence that a remote Stop has not committed. The amendment must state that bounded polling delay rather than promise immediate Stop observation. Preserve authoritative pre-effect/mutation checks and fresh stream authorization. Do not retry stream authorization by treating the last observation as continued authorization. Retain terminal/deadline/Stop ordering when observation resumes and the original watcher/renewal failures before final failure selection.\n\nThe physical-custody report documents an actual release-after-drain refusal and the source chain still supports it: `begin_shutdown` sets the draining event, `service.shutdown` joins execution, `_finish_execution_authority` calls `lease.close`, and null-required `_release_current` uses the ordinary stream worker bridge (`lifecycle.py:906–919`).
