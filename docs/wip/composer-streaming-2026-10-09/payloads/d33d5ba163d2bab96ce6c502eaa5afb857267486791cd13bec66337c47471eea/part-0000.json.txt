"# R2: required SQL Future custody — implementable scoped design\n\nPLAN ONLY. The atomic amendment remains HOLD. This document supplies the missing custody boundary; it grants no code clearance. No production edits or tests were performed. Read the complete current 95-line atomic amendment and readiness-baseline/daybreak-atomic-pipeline-rereview.md. The latter's technical NO-GO is retained with its explicit provenance disclaimer: the outer requested model and the report's prose cannot be collapsed into verified model provenance. R1's deterministic reducer remains a separate required amendment.\n\n## Source facts and the exact gap\n\nCurrent async_workers.run_stream_read_in_worker owns the real concurrent.futures.Future returned by the same bounded shared executor. It polls actual done(), retrieves actual result(), joins running work despite repeated task cancellation, and cancels queued work when possible. Pool admission is released by _release_admission_when_finished on the actual concurrent Future, not by an asyncio wrapper. SessionServiceImpl._run_composer_sql delegates to that helper; ingress, intermediate compose/audit/provider writes and terminal SQL already use it where implemented. These are the correct primitives to retain.\n\nThe route _await_with_deferred_cancellation owns only an asyncio Task; it is not an authoritative registry of the underlying Futures. pipeline_commit.bounded uses wait_for(run_sync_in_worker(...)), whose awaiter can finish while its actual thread still runs. SessionOperationLease.create_task tracks asyncio children, and close joins those children before stopping renewal/releasing; it cannot infer actual SQL completion from a prematurely cancelled wrapper. The worker currently selects failure while retaining the live lease, which is the correct placement for a new drain barrier.\n\nMeasured local Python3.13 ThreadPoolExecutor.submit orders operations as: create Future/work item; queue.put(work item); _adjust_thread_count(); return Future. Therefore an exception before a Future is returned is NOT universally proof that nothing was queued. The current generic helpers release admission on any submit exception; the new REQUIRED path must not inherit that inference. This document does not widen the ordinary helper or introduce a replacement executor/pool or SDK adapter.\n\n## Concrete coordinator and explicit API\n\nAdd one owned ComposerRequiredWorkCoordinator for each adopted durable turn. Instantiate it before provider admission or required preparation, attach it to the existing lease as a required-work drain participant, and pass it explicitly through run_composer_turn and settle_pipeline_proposal_under_compose_lock. A manual PROPOSAL settlement gets the same scoped coordinator with no durable-job ID, under its own existing lease. It is an ownership ledger, never a database mutation authority or audit-only permission.\n\nDefine an immutable RequiredSQLStageKey with session UUID, job operation ID or null, claim attempt or null, exact session-operation ID/epoch/kind, transition tool-call ID or null, a closed stage enum, semantic ordinal, and immutable SQL attempt ordinal (initial0, exact retry1). Allocate stage/ordinal from the fixed call graph and input/cohort order, not task scheduling or completion order. Reusing a stage key is an owned lifecycle error. Capture the exact source-boundary origin category for R1; do not derive it by searching SDK causes or exception strings.\n\nThe initial closed stage enum is INGRESS, PROVIDER_ADMISSION, PROVIDER_SETTLEMENT, COMPOSE_CHECKPOINT, PROPOSAL_CREATION, PREPARATION_READ, PREPARATION_VALIDATION, DISPATCH_AUDIT, INTERPRETATION_VALIDATION, PIPELINE_PUBLICATION, TRUST_REVOCATION, REQUIRED_UNWIND_AUDIT, OPERATION_TERMINAL, TERMINAL_WRITER_READ and TERMINAL_FAILURE. Lease renewal/release retain their existing lifecycle owner and joined Future handles; they contribute explicit LEASE_RENEWAL/LEASE_RELEASE observations to the final lifecycle result, rather than pretending to be business SQL tickets. Any added stage requires a named source seam and reviewed cancellation policy.\n\nCoordinator API:\n\n- reserve_sql(key, cancellation_policy) -> exact RequiredSQLTicket: synchronous, before any admission wait; strongly retained by the coordinator.\n- run_required_sql(ticket, func) -> result: acquires existing shared-pool admission, executes the submission protocol below, and joins the actual Future. Only reviewed service/SQL seams use it.\n- note_projection(ticket, exact_result_or_exception): records required pure projection outcome separately from physical Future completion. Projection must not quietly launch unregistered SQL.\n- drain_transition(transition_key): stops that transition's producers, joins its registered work and returns typed immutable observations; it does not close the whole turn or authorize terminal settlement.\n- begin_terminal_drain(): closes ordinary producer admission, joins producer tasks and all required stage observations, then exposes a provisional R1 failure/result candidate. Only the coordinator-owned terminal/fresh-read/failure-audit finalizer stages may be registered afterward.\n- finish_terminal_and_drain(): waits for those finalizer Futures and projections, applies existing committed-terminal/fresh-writer recovery rules, and exposes the final retained observation set.\n- prepare_lease_release(): succeeds only after all participants and registered required work have observed outcomes and no unknown-custody ticket remains. This is a lifetime check; the existing exact DB lease release still supplies authority.\n\nTickets use closed states: RESERVED, WAITING_ADMISSION, ADMITTED, SUBMITTED, OBSERVED_SUCCESS, OBSERVED_FAILURE, CANCELLED_BEFORE_START, NOT_SUBMITTED, SUBMISSION_UNKNOWN; physical queued/running/completed are read from the actual Future where available. A projection-pending flag is separate: actual SQL completion does not prove projection completion. Typed observations retain the original object/result/exception, stage key, cancellation signals and source origin. Records are bounded by the existing turn/tool/cohort/retry bounds and retained until coordinator release; no global mutable history or payload logging.\n\n## Submission and registration, with no cancellation window\n\nExtend the existing joined helper only with an optional exact RequiredSQLTicket owned observer; preserve its default callers and pool/admission limits. SessionServiceImpl._run_composer_sql gains explicit ticket/coordinator plumbing for reviewed required seams. Ordinary run_sync_in_worker, generic SDK dispatch and read-only stream default semantics remain unchanged.\n\nThe ticket and a small invocation gate/witness are reserved before awaiting admission. After admission returns, perform the following entirely synchronously on the event-loop thread: mark admission held; call executor.submit(gated_callable); bind the returned actual Future to the already-retained ticket; install one actual-Future completion observer and exactly one release-admission callback; arm the gate. No await, async callback invocation or user code is allowed between submit, binding, callbacks and arming. A task.cancel() at an injected synchronous seam only schedules cancellation for the next await: registration finishes first. A completed Future is still registered and immediately observed. Registry locks must tolerate a done callback running inline during add_done_callback (use a local RLock or install callbacks outside the held registry lock); never hold the executor admission lock while acquiring the registry lock.\n\nThe gated callable may run before submit returns, but it waits on the preallocated gate. It cannot enter SQL until the ticket is bound and callbacks installed. Gate states are WAITING, ARMED and ABORTED, guarded by an owned lock/event. Arming is not authority: the callable still executes every exact DB fence/Stop/deadline predicate on its actual connection. Gate abort never synthesizes a provider result or zero usage.\n\nA bind/callback setup failure after a Future is returned must retain that Future on the reservation, abort the gate if not armed, record the exact setup error and join/poll the actual Future. Use release-once bookkeeping shared by callback and drain fallback; no double release. The cancellation handler never drops a ticket or its actual Future reference.\n\nSubmission failures have two disjoint arms:\n\n1. A failure before calling submit — admission timeout/cancellation, coordinator closing, executor construction error — has a structurally proved NOT_SUBMITTED ticket. No Future exists, no callable was queued by this invocation, and an acquired unused admission is released exactly once. Preserve the exact original failure; do not fabricate a SQL failure.\n2. submit was called and raised without returning a Future: immediately abort the invocation gate, retain the exact submission exception, mark SUBMISSION_UNKNOWN and KEEP its admission charged. Do not claim not-submitted, rollback, actual-Future done or no queued worker. An already queued late wrapper sees ABORTED and performs no SQL. If this path has no returned Future and no sufficient actual completion witness, terminal selection, lease release and local transition-lock release are forbidden; retain the existing unresolved-completion recovery marker/custody. No cheap global pool shutdown, timer, task.done(), string match or generic retry resolves it. A later actual gate-wrapper completion witness is retained as narrow proof of callable/SQL nonexecution or completion, but it does not invent the absent executor Future: the pool admission is not released by a wrapper-finally event pretending to be that Future's done callback. If exact physical completion remains unprovable, the admission remains held until a separately authorized measured lifecycle recovery; bounded capacity fails closed. This conservative no-return arm is intentional and implementable, not magical knowledge of acceptance.\n\nIf a future can be retained from an owned submission failure API in a later independently reviewed implementation, bind that exact handle and follow the normal drain. Do not reach into private executor queues/work items or weaken this scoped plan to recover a handle. The generic submit implementation and its normal no-return error assumption are not silently changed here.\n\n## Cancellation and status behavior\n\n| Point/status | Required behavior | Admission/lifetime consequence |\n| --- | --- | --- |\n| Cancel before admission or before submit | Record NOT_SUBMITTED; no SQL dispatch. For a phase already owing evidence, coordinator records an unsettled required-child outcome and schedules its sealed recovery, rather than declaring the evidence durable. | No worker slot held; release only an acquired unused slot. |\n| Cancel synchronously between submit and registration | Finish synchronous binding/callback installation/gate decision before the next await. | Actual Future retained; no orphan window. |\n| Queued Future, cancellable preparation/admission stage | cancel() returning true proves CANCELLED_BEFORE_START; inspect actual cancelled() and observe it. | Actual done callback releases slot; no provider attempt/zero-use outcome invented. |\n| Queued Future, finish-once-submitted required audit/settlement stage | Record local cancellation but leave Future queued; required phase retains custody. | Slot and lease/transition custody persist through actual completion. |\n| Running Future | cancel() false is not completion. Join actual done()/result(), even after repeated cancellation. | Slot remains charged until actual Future callback; no terminal/release while SQL can commit. |\n| Actual Future success/error | Capture actual result/original exception once, even if its asyncio awaiter was cancelled; required projection still completes or records its own failure. | Physical admission can release at Future completion; lease remains until required observations/projections/finalizer are drained. |\n| Cancel after SQL completion, before projection | Keep committed result and run/observe required projection; retain local cancel as a separate signal. | No SQL replay merely to reconstruct the lost async return. |\n| No-return submit exception | SUBMISSION_UNKNOWN, gate aborted, original error retained. | No false admission release, terminal, lease/lock release or provider/SQL replay. |\n\nPolicies are closed and assigned by stage, not caller-selected as a business bypass. Preparation reads and initial provider admission are cancel-before-start. Required dispatch/audit settlement after an approved effect, atomic pipeline settlement, revocation evidence, terminal SQL and its immutable recovery/fresh read are finish-once-submitted. Physical Future cancellation on a setup failure is separate from ordinary local cancellation; if it cannot be cancelled, join it. Durable Stop/deadline are reread by DB authority and can refuse business publication; they never substitute for joining submitted SQL.\n\n## Concrete stage ownership and reuse\n\n| Required stage | Registering layer | Existing primitive retained / concrete change |\n| --- | --- | --- |\n| Job ingress, intermediate compose/audit/provider evidence | SessionServiceImpl required public method -> _run_composer_sql(ticket) | Same run_stream_read_in_worker pool; add ticket observer before its first await after submit. |\n| Proposal creation | Service creation method under exact COMPOSE transaction | Replace only this required ordinary _run_sync dispatch with the registered joined bridge; actual normal authority remains. |\n| Pipeline preparation reads/validation and approved executor preparation | pipeline_commit.bounded at the precise owned sync boundary | Pass explicit ticket into the joined bridge; wait_for expiry records budget/cancel signal and coordinator drains actual Future, rather than treating wrapper timeout as SQL completion. Arbitrary provider SDK calls do not enter the registry or become storage failures. |\n| Required dispatch audit | Canonical pipeline coordinator -> service.add_messages_atomic | Existing composer-custody bridge, finish-once-submitted ticket; record exact audit failure at its existing nominal producer seam. |\n| Prepare-only interpretation DB validation and atomic candidate/review/proposal/assistant publication | Service preparation methods and atomic pipeline service method | Explicit stage tickets; one publication Future owns the whole locked transaction and rollback domain, not one independently committable Future per review. |\n| Narrow trust-revocation SQL | New reviewed sealed service authority | One registered finish-once-submitted Future, no general audit-only business capability. |\n| Operation terminal / exact retry / independent writer read | _run_composer_terminal_sql | Retain current actual Future join, witnessed SQL result and closed immutable retry/fresh-writer recovery. Give each physical attempt/read its distinct stable ticket; do not duplicate execution or restart provider. |\n\nPure interpretation preparation creates no Future. It is still a producer task whose failure is observed before terminal drain. Any lower-level service method used in these paths must receive the coordinator explicitly; a hidden contextvar, best-effort registry or wrapper-task inventory is not the concrete custody proof. Manual and durable callers remain distinguishable by existing exact authority; the ledger never grants mutation permission.\n\n## Drain, late outcomes, terminal and lease ordering\n\nComposerAsyncOperationWorker remains the whole-turn owner. It cancels/joins provider and other producer tasks on Stop/deadline/loss/local shutdown, closes ordinary required-stage registration and calls begin_terminal_drain BEFORE choosing a provisional public failure or starting failed-terminal SQL. A producer cannot report cancelled completion while hiding a registered running Future: tickets outlive their awaiters and their actual outcomes are fetched by the drain. Drain uses bounded polling with active event-loop timers, catches repeated cancellation and continues; a timeout records a signal, never completion. No full blocking thread join or sleep on the event loop.\n\nThe canonical pipeline coordinator calls drain_transition before returning its pipeline result or propagating cancellation; this prevents a late preparation/read/audit/publication result from crossing a proposal transition boundary. It cannot consume another transition's stage identity or release the whole lease.\n\nLate Future errors/results are inserted into their preassigned stage ticket, and the preterminal R1 reducer sees the full immutable observation set. It sorts by the reviewed total rank and stable stage key, never callback/ExceptionGroup arrival order. The original cause/group objects are retained as evidence; no generic SDK cause promotion or string classifier. Projection failures and lease-control failures carry their separately owned phase identity. This design supplies observations, not R1's unresolved rank definitions.\n\nOnly after producer tasks and currently registered required Futures/projections have observed outcomes may a provisional terminal candidate be chosen. Its terminal write and independent read are then registered FINALIZER stages; no final response/durable-completion claim or lease release occurs until those stages have actual outcomes. A strict hash-valid already committed operation terminal wins later errors under the existing contract. A failed/unproved terminal follows existing immutable retry versus changed-state failure arms; registry drain is not a retry permit. SUBMISSION_UNKNOWN or any actual Future still running keeps the unresolved marker and forbids competing terminal/provider replay.\n\nLease renewal/control is not a new business authority. Keep existing SessionOperationLease renewal/release joins (currently run_stream_read_in_worker), keep renewal active while required SQL drains when possible, and retain any actual renewal error under its owned lifecycle phase. Before close releases the fence, its attached coordinator must pass prepare_lease_release; then existing lifecycle joins/stops actual renewal work and performs the exact release. Close failure cannot bypass the barrier. If renewal loses authority, the owner still joins submitted work and refuses late competing commits through current locked DB predicates/recovery, rather than interpreting loss as rollback. A current valid terminal can be read after close; a lost lease does not create permission for old publication.\n\nThe shared worker-pool slot and Composer logical concurrency/CRL capacity are different resources. Physical pool admission releases exactly on a known actual Future's done callback (or structurally proved no-submission); Composer/CRL/transition ownership releases only after required producer/Future/projection/finalizer drain plus current lifecycle settlement. SUBMISSION_UNKNOWN retains the physical charge and logical custody. No resource is released because an asyncio Task alone is done.\n\n## Required future implementation controls (not run)\n\nUse deterministic actual executor/thread/transaction gates for: cancellation immediately before admission and submit; synchronous cancel hook after submit/before binding with no await; callback-install failure with retained returned Future; actual queued cancel-before-start versus finish-once required write; running thread/direct child/repeated owner cancellation; SQL committed before projection; late error after awaiter cancellation; submit exception before queueing and after queueing/before Future return with aborted gate/no SQL and charged unresolved admission; failure during drain/fresh read; and no terminal/fence/transition/CRL release until the ticket proves completion. Mutating registration to occur after an await or releasing slots on wrapper cancellation must turn controls red. Existing SQLite/PG cancellation proofs remain evidence for their original source only; they do not certify this planned registry. Add actual PostgreSQL delayed lock/SQL controls and preserved original cause identities, no provider replay or extra provider call. No tests were run for this document.\n\n## Limits\n\nThe design deliberately preserves no-return submission uncertainty instead of claiming universal recoverability. It does not solve a hung thread, process death, missing original reports, denied archive input, model-provenance discrepancy or the unresolved R1 total failure order. Ordinary worker infrastructure semantics remain unchanged outside the explicit required path. Implementation, source review, measured payload sizes, new failure controls, full frozen gates and actual amendment GO are still required.\n"
