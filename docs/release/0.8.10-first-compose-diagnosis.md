# 0.8.10 U-45 — first-Compose retention `TimeoutError`: load-independent diagnosis

Status: diagnosis only (phase 1 of U-45). No production code or test was changed.
Measured against the v152 prototype `897dabeb8`
(`preserve/0.8.10-p4-prototype-v152-20261024`) on 2026-10-24, on a shared host
under load (load average 12–27 on 24 cores throughout). Wall-clock figures below
are therefore hints, not evidence. The verdict rests on counts.

Evidence labels: **M** = measured here (command and raw output given);
**M-soft** = measured, but load can still move it (per-thread CPU time:
frequency scaling, cache and SMT contention); **I** = inferred.

## 1. Verdict

**Case (B), a real inefficiency, is established. Case (A), fixture fragility
under load, is not excluded.** The first-Compose retention stage is CPU-bound
Python work that re-parses and re-verifies the same session source many times
inside one stage. Neither cursor-execute time nor lock waiting explains the
miss. Whether an idle host still exceeds 1.0 s after the waste is removed is for
§9 to measure. The 2026-10-24 review amended this section (§12).

- **M** With the allowance lifted, the stage issues 1,096 SQL statements
  (SQLite and PostgreSQL alike), 11 transactions and 8 worker hops. Counts are
  identical across 3 repeats and across both dialects.
- **M** Exact-key repeats, measured by full statement text plus full parameters
  on the same DB-API connection (§4.1), summed over the 11 transaction windows
  and excluding database-clock reads:
  - SQLite: 689 of 996 SELECTs repeat an earlier SELECT in their own window. 580
    have no intervening write; 109 follow a write in the publication window.
  - PostgreSQL: 646 of 1,007, with 544 having no intervening write.

  For example, 18 distinct chunk rows are read 291 times. **A repeat is not
  proof of redundancy.** Publication writes and then re-reads in the same
  transaction, and admission must be re-evaluated against a fresh clock (§8).
- **M** Per distinct artifact, one stage decodes 5 distinct snapshots 213
  times and re-verifies 11 distinct private chunks 429 times, which is 18.7 MB of
  canonicalization. It also runs 265 credential scans of 23 distinct
  scan contexts (§4.8).
- **M** Cursor-execute time totals 10–14 ms on SQLite. That excludes result
  fetching and row processing, which fall in the CPU figure. Python-side
  session-lock waits total about 2 ms. On SQLite, the stage is about 95%
  worker-thread CPU.
- **M-soft** That CPU is 1.21–1.81 s per first-Compose retention stage, on a
  loaded host with the probe attached, against the fixture's 1.0 s allowance.
  Counts establish the excess work. They do not give a load-independent CPU
  lower bound, so this does not on its own exclude (A).
- **M** Statement count does not grow with chat-history size: it stays at 1,108
  from 0 to 80 extra message pairs, so there is no SQL N+1. CPU does grow
  linearly, from 1.41 s to 2.61 s. The canonical-JSON string-escape regex calls
  rise from 167k to 358k at 40 pairs. The re-read multiplier is applied to work
  proportional to the transcript.
- **M** This is not case (C). With the allowance lifted, the stage completes and
  every later assertion in the test passes, including the original-message wire
  identity and the read-only replay.
- **M, PostgreSQL** The same 1,096 statements cost 565 ms of cursor-execute
  time against a local container (mean 0.52 ms per statement). **I, not
  measured:** ECS-to-RDS or ACA-to-Azure-Database round trips are likely
  slower than a local Docker socket. At about 1 ms per round trip, the statement
  count alone would use the whole 1.0 s allowance before any Python work.

Two **other** red tests are hidden behind this timeout today. They are not
retention defects, and they will surface as soon as retention is fixed. See §6.

## 3. What the retention stage does

The stage is `retain_and_consume` in
`src/elspeth/web/composer/continuation_composition_initialization.py`. It runs as
8 sequential worker hops through `run_required_sql_finish_once` on the shared
16-thread `async-worker` pool. Per-hop figures come from run 4 of the
`[nonpaid-rootless]` case, with the allowance lifted. Each hop is in a
`locked_session_transaction`: `BEGIN IMMEDIATE` on SQLite, or an advisory
transaction lock on PostgreSQL.

| Hop | Statements | SQLite exec | SQLite CPU (M-soft) | PG exec | PG CPU (M-soft) |
|---|---:|---:|---:|---:|---:|
| `publish_composition_initialization` | 309 | 3.9 ms | 447 ms | 119 ms | 485 ms |
| `load_selected_continuation` | 24 | 0.3 ms | 19 ms | 12 ms | 24 ms |
| `materialize_continuation_env_inventory` (two hops) | 13 + 13 | 0.2 ms | 9 ms | 5.5 ms | 11 ms |
| first-runtime `_read_first_sources` | 160 | 2.2 ms | 259 ms | 82 ms | 316 ms |
| first-runtime `_restore_first_graph` (before, rebuild, after) | 325 | 3.6 ms | 647 ms | 227 ms | 796 ms |
| first-runtime `_restore_live` | 79 | 1.4 ms | 236 ms | 35 ms | 261 ms |
| final `_bind_first_state_on_connection` | 173 | 2.0 ms | 191 ms | 83 ms | 233 ms |

Totals, **M**: 1,096 statements, 11 BEGIN, 11 COMMIT, 0 ROLLBACK. Queue wait
before a worker picked a hop up was 0.6–2.8 ms in total, so the 16-thread pool is
not saturated. Poll latency after a hop finished was 28–54 ms in total. That
comes from the 10 ms poll loop across 8 hops, roughly 3–5% of the stage.

The same stage runs three times per test: run 2 is the earlier ready
publication, run 4 is first-Compose publish plus consume, and run 6 is the
read-only replay. Run 4 is the one that fails.

| Run | Statements | Transactions | Hops | Allowance lifted: CPU (M-soft) |
|---|---:|---:|---:|---:|
| 2 (ready) | 166 | 1 | 1 | 36–64 ms |
| 4 (first Compose) | 1,096 | 11 | 8 | 1,211–1,807 ms |
| 6 (replay, consume only) | 787 | 10 | 7 | 928–1,331 ms |

## 4. Measurements

All instruments are pytest plugins passed with `-p`, and none modifies tracked
source. They are committed, marked WIP and not reviewed, on branch
`codex/0.8.10-u45-fix-prototype` (`5932af0e9`, on top of `897dabeb8`) under
`docs/release/u45-fix-prototype/`. The files are `u45probe.py`, `analyze.py`,
`compact.py`, `callcmp.py`, `lockcontrol.py` and `u45liftonly.py`, plus the
later `u45budget.py`, `u45bindctl.py`, `windows.py`, `u45memo.py` and
`firstcpu.py`. The plugin installs SQLAlchemy `Engine` class-level listeners
for `before_cursor_execute`/`after_cursor_execute`, `begin`, `commit`,
`rollback` and `handle_error`. It labels the stage by wrapping
`ContinuationActionClock.run`. It labels sub-steps by wrapping the async callers
and propagating the label into the worker thread. It wraps
`run_required_sql_finish_once` to time each hop's queue, work, poll and
per-thread CPU (`time.thread_time`). It also times the session `RLock` and
`flock` acquisitions in `elspeth.web.sessions.locking`. Optional switches:
`U45_LIFT=1` lifts the retention allowance so the whole stage runs, for counting
only. `U45_PROFILE=1` runs cProfile over the retention stage. `U45_MIN=1` strips
the per-statement recording, to bound probe overhead. `U45_INJECT`, `U45_DELAY`
and `U45_HISTORY` are the controls and the growth knob.

predicates and snapshot or chunk loads. In `require_continuation_mutation`, 5
predicate sites each run 50 times.

### 4.2 Lock wait versus work (M)

SQLite, run 4: there are no `handle_error` events, so no `database is locked`
error happened. The slowest single statement took 0.1 ms. The BEGIN IMMEDIATE
statements, where a busy-timeout wait would show, are all near 0 ms.

```
python-side lock acquisitions in retention: 66; kinds={'rlock': 44, 'flock': 22}; sum wait=2.29ms max=0.10ms
db errors: []
```

PostgreSQL, run 4: 11 `pg_advisory_xact_lock` statements wait 4.9 ms in total
(max 1.49 ms). Statement timings: mean 0.515 ms, median 0.255 ms, p95 1.972 ms,
max 27.81 ms.

Python-side asynchronous contention: queue wait before a worker started is
under 3 ms per stage, so the pool is not saturated. The only other loop-side
cost is the 10 ms poll granularity, about 30–54 ms per stage. **M-soft:** worker
wall time minus worker CPU is about 60 ms per stage on SQLite. So the worker
spends almost all of its time on CPU, not waiting.

## 7. Causal reading

1. **M** The retention allowance is spent on worker-thread CPU, about 95% of
   stage wall time on SQLite. Cursor-execute time is about 1%, lock waits about
   0.2%, and loop polling 3–5%. Result fetching and row processing are inside
   the CPU share.
2. **M** That CPU comes from rebuilding the same values again and again. In one
   stage, the code runs 7 full composition-initialization source reads, 3 full
   first-runtime source reads and 4 turn-evidence reads. It decodes 213
   snapshots, which means 213 embedded policy decodes, and verifies 429 private
   chunks. Each of those canonicalizes JSON with RFC 8785, which is the
   `re.sub` string escape. Those calls cover only 5 distinct snapshots and 11
   distinct chunks (§4.8). The code also runs 265 credential scans of 23
   distinct scan contexts, and rebuilds 60 plugin catalog schemas that the
   catalog had already built at construction.
3. **M** The SQL mirror of the same pattern: 689 of 996 SELECTs on SQLite repeat
   an earlier exact SELECT in their own window. **Not all of them are
   redundant (M, source).**
   - 109 follow a write: publication appends and then re-reads in the same
     transaction
     (`src/elspeth/web/sessions/continuation_composition_initialization.py:686-711`).
   - 313 of the remaining 580 feed admission checks, which are re-evaluated
     against a fresh database clock every time
     (`src/elspeth/web/sessions/continuation.py:148-198`,
     `src/elspeth/web/coordination/database_clock.py:54-70`).
   - That leaves 267 repeats on data tables with no intervening write.
   **I:** on SQLite, a `BEGIN IMMEDIATE` holder excludes other writers, so those
   267 return identical rows. On PostgreSQL (READ COMMITTED) that holds only if
   every writer of those tables takes the session advisory lock.
   `request_cancel` does
   (`src/elspeth/web/coordination/composer_operation_authority.py:1433`). The
   other writers are not proven, and the design rule "Issue no reusable SQL
   capability; independently run on every window" stands
   (`src/elspeth/web/sessions/continuation_first_runtime.py:42`).
4. **M** The work grows linearly with transcript size, because the multiplier
   applies to transcript-proportional encode and scan work.
5. **I** On a loaded host the stage's wall time stretches beyond its CPU time.
   Sol's 4.002 s is one such observation. The excess work is load-independent
   (counts). Whether the remaining work misses 1.0 s on an idle host is not yet
   measured (§9).

**Unreconciled:** the brief records a 4.002 s TimeoutError. Here, natural runs
overshoot to about 1.3–1.4 s wall under a 1.0 s allowance, because the in-flight
hop cannot be cancelled. A 4 s figure would need either much heavier load or a
longer hop in flight when the deadline fired. Neither was reproduced, and the
verdict does not depend on it.

## 8. Fix specification (not implemented)

### 8.2 The changes

- **F1, the shared parse within the stage.** Memoize the pure parse and
  validation helpers on their complete exact input: `decode_continuation_snapshot`
  on the exact text, and `verify_private_chunk`'s strict-parse and canonical
  check on the exact (reference, canonical) pair. Scope the memo to one retention
  stage, owned by the stage and not by `RequiredWorkBinding`. The binding
  validates only fence identity and queries no SQL state
  (`src/elspeth/web/required_work.py:1577-1579`), so it is no currentness
  authority. The SQL reads that produce the text stay per window.
- **F2, chunk verify reuse.** This is the chunk half of F1. It keeps G4's byte
  checks on every read. The old wording, "(chunk key, stored sha256)", is
  withdrawn because it is not fail-closed: §12, review point 2.
- **F3, catalog schemas.** Reuse the construction-time schemas in `_to_summary`
  with copy isolation (G6). This is the lowest-risk change.
- **F4, credential scans.** Memoize the full scan context, as listed in G7.
- **F5, proven-redundant SQL de-duplication.** Optional, and only after proof.
  267 data-table repeats with no intervening write exist (§4.8). These are chunk,
  event, checkpoint and message reads, never admission tables. Reusing them
  within a window needs two things first. It needs a proof that every writer of
  those tables holds the session advisory lock on PG; `request_cancel` does, at
  `composer_operation_authority.py:1433`, and the rest must be enumerated, for
  example from the mutation-fencing inventory in
  `tests/unit/architecture/test_web_landscape_mutation_fencing.py`. It also
  needs an explicit amendment of the `:42` design rule. F1–F4 do not depend on
  F5. F5 is the only change that lowers PG round trips.

Composer invariants: none of these touches the planner path or a tutorial path.
The stage makes 0 provider calls before and after (§4.7). A9 still needs its
per-transition count recorded in the U-45 review record.

- No idle-host wall-clock timing was taken, by design. The CPU seconds are
  M-soft and should come down somewhat on an idle host. Only §9 can say by how
  much.
- PostgreSQL ran against a local container. Production round trips from ECS to
  RDS or from ACA to Azure Database were not measured. The 565 ms is a local
  figure, not a measured production bound (**I**).
- The SQL repeat keys prove exact statement and parameter identity (§4.1). They
  do not prove identical results, because no result rows were hashed.
- The decode, verify and scan budgets (§4.8) were measured on SQLite only. Their
  inputs are the same text on PG, but that was not run.
- The growth knob varies chat history only. Graph size and plugin catalog size
  were not varied. The catalog-schema cost scales with the number of registered
  plugins (**I**).
- §10.3's production-side claims rest on source reading (**I**). No production
  compose turn was driven end to end to read its stored envelope and modality
  back.

## 13. Is 1.0 s the right retention allowance?

This section answers the maintainer rule in `AGENT-BRIEF.md` § Literal
constraints: evaluate the cap, do not only fit under it.

**Recommendation.** Size the U-38 production `session_sql.retention` at
**5.0 s**, not 1.0 s, **and** land the §8 fix. Neither is enough alone. Make
`tests/helpers/continuation_policy.py` derive from the U-38 production policy
constructor instead of literals. Any test that exercises a deadline should
inject its own explicit small allowance. Raising the value loosens no safety or
audit property; the evidence is in §13.2.

### 13.1 Where the 1.0 s comes from (M)

- It is a **test-fixture literal**: `local = ContinuationActionPolicy(preparation=1.0,
  guard=None, quota=None, physical=5.0, retention=1.0)` at
  `tests/helpers/continuation_policy.py:13`. The provider-action policy beside
  it already uses `retention=5.0` (`:12`).
- **No production policy exists** at `897dabeb8`. No module under `src/`
  constructs a `ContinuationAdmissionPolicy`, `ContinuationActionPolicy` or
  `ContinuationSegmentPolicy`, and no setting supplies one
  (`git grep` over `src/`, run 2026-10-24). Nothing in `src/` calls
  `initialize_continuation_composition` yet; U-37 and U-45 wire it. So 1.0 s
  is neither a REPO POLICY nor a MAINTAINER RULING, nor a platform limit. Sol's
  "never pad the fixture" was task-local (§2).

### 13.2 What the retention allowance protects (M, source)

- **The segment deadline.** It does this through admission accounting. An action
  is admitted only while the segment's hard remaining time covers its whole
  `total` (preparation + guard + quota + physical + retention) plus the
  segment `reserve` (`src/elspeth/web/composer/continuation_clock.py:39-43,
  47-63`). A fresh segment is sized as `max(nominal, total + reserve +
  watermark)` (`:21`, used at `src/elspeth/web/sessions/continuation.py:688-689`).
  The stage clock then enforces each stage's slice, and a post-join check
  refuses a late result (`continuation_clock.py:160-165`). Retention is the
  slice of that budget for making the action's result durable. Its job is to
  ensure an admitted action can finish, and leave the reserve for settlement,
  before the segment's database-time hard deadline.
- **Not user wait (I).** Users wait on the whole compose loop. That is bounded
  by `composer_timeout_seconds` (`src/elspeth/web/config.py:371`; the fixture
  service logs 85 s) and by 300 s segments (`nominal=300.0`,
  `tests/helpers/continuation_policy.py:15`). A larger retention slice changes
  no user-visible latency unless it is the difference between finishing and a
  `TimeoutError`. Today that error is the user-visible failure.
- **Not the lease (M, I).** The compose session lease defaults to 30 s
  (`src/elspeth/web/sessions/service.py:781`) and the async claim lease to 30 s
  (`config.py:403`). Lease validity is checked fresh at every mutation
  (`sessions/continuation.py:148-158`, G2). The allowance cannot bound an
  in-flight hop, because cancellation is deferred until the hop finishes. A
  natural run overshot the 1.0 s deadline to about 1.4 s (§2). Lease safety
  therefore rests on renewal and the fence checks, not on this number. Lease
  renewal was not traced (I).
- **No content, custody or audit property.** The policy module states it plainly:
  "These values retain timing allowances, never content clearance or live
  execution custody. Current security and capability admission still run at
  every use." (`src/elspeth/web/composer/continuation_policy.py:3-4`).

**Platform ceiling (M, deploy files).** An admitted action's `total` should fit
inside the shutdown drain window, so an in-flight action can make its result
durable before the container is killed. ECS runs
`--timeout-graceful-shutdown 30`
(`deploy/aws-ecs/terraform/modules/scenario/ecs.tf:113`), and ECS `stopTimeout`
is not set, so the platform default applies (**I:** 30 s). ACA uses
`terminationGracePeriodSeconds = 60`
(`deploy/azure-container-apps/workload.bicep:78`,
`workload.production.bicepparam:23`). With `retention=5.0`, the
`session_sql` total is 1 + 5 + 5 = 11 s, inside both windows.

### 13.3 What retention would cost after the §8 fix (M-soft, plus I for production)

`u45memo.py` is a lane-local **prototype** of F1–F4, used to estimate cost and
not for merging. It memoizes the four pure functions on their complete exact
input at every binding, scoped to one retention stage, and memoizes successes
only. It reuses copy-isolated construction-time catalog schemas. It does not
change SQL; F5 is not prototyped. Its correctness check, on the whole file at
`-n 0` with the lift: `2 failed, 24 passed`. That is the same set as without it,
and both failures are the masked reds (§10). Without the lift, it took the file
from 6 passing to 18 passing at load average about 20. The remaining 6 were
still retention `TimeoutError`s, not behaviour breaks.

Interleaved A/B runs: first-Compose retention stage, `U45_MIN=1`, allowance
lifted, two repetitions, load average 19–25. Absolute CPU is inflated by load,
so the **ratio** is the robust figure.

| Case | Extra history pairs | CPU without fix | CPU with prototype | Ratio |
|---|---:|---:|---:|---:|
| `[nonpaid-base]` (SQLite) | 0 | 1,786 / 1,955 ms | 818 / 787 ms | 0.42–0.46 |
| `[nonpaid-base]` (SQLite) | 40 | 2,860 / 3,012 ms | 1,428 / 1,432 ms | 0.48–0.50 |
| `[nonpaid-base]` (SQLite) | 80 | 3,910 / 4,497 ms | 1,753 / 2,171 ms | 0.45–0.48 |
| `[paid-accepted]` (SQLite) | 0 / 40 / 80 (knob inert: no seeded base) | 2,314–2,482 ms | 1,094–1,121 ms | 0.45–0.47 |
| `[nonpaid-rootless]` (PG, one run each) | 0 | 2,182 ms CPU, 2,611 ms wall | 985 ms CPU, **1,446 ms wall** | 0.45 |

On PG, cursor-execute time is unchanged at 432 and 452 ms for 1,096 statements,
because F1–F4 leave SQL alone. After the fix, PG wall time is about one-third
round trips and two-thirds CPU.

Post-fix growth on SQLite is about 12–17 ms of CPU per history pair at this
load. Without the fix it was about 29 ms per pair under the same conditions, and
15 ms per pair at the lower load in §4.5.

**Production estimate (I).** Take the PG post-fix wall time of 1.45 s, loaded.
Assume idle-host CPU is about 0.6–0.7 of the loaded figure; that is unmeasured,
and §9 owes it. Add 1,096 statements times the production round trip, assumed
0.3–1 ms for ECS to RDS or ACA to Azure Database in the same zone, which was
not measured. Add 12–17 ms per history pair. That gives roughly **0.9–1.9 s at
an empty history** and **1.5–2.7 s at 50 prior pairs**. Even after the fix, a
1.0 s cap would fail in production at ordinary history sizes. It would fail
first on PG, the dialect production uses.

### 13.4 The recommended value and its cost

| Option | Fits post-fix estimate? | Segment cost | Drain fit (ECS 30 s / ACA 60 s) | Verdict |
|---|---|---|---|---|
| 1.0 s (today's fixture) | No: 0.9–2.7 s estimated | admission needs 32 s remaining | 7 s total: yes | **mis-sized** |
| 2.5 s | Marginal at 50 pairs, no p95 headroom | 33.5 s | yes | too tight |
| **5.0 s** | Yes: about 1.9× over the 2.7 s high estimate | 36 s, about 1.3% of a 300 s segment | 11 s: yes | **recommended** |
| 15 s | Yes | 46 s | 21 s: yes for ECS, but erodes drain margin | unnecessary |

Reasons for 5.0 s:

- It is the smallest round value that covers the post-fix production estimate
  at moderate history, with about 2× headroom for p95.
- It matches the provider actions' existing `retention=5.0`
  (`tests/helpers/continuation_policy.py:12`).
- Its only cost is 4 s less admissible time per segment.
- It keeps every action well inside the ECS drain window.

**5.0 s is still a ceiling on growth.** At 12–17 ms per pair, a first-Compose
retention reaches about 5 s at roughly 200 to 300 prior pairs (**I**). Long
sessions therefore still need the work to become sublinear: F5, or an
incremental source comparison. The cap must not keep growing. §9 confirms the
number: if the idle post-fix p95 at 50 pairs is above 2.5 s on PG, re-size it
before U-38 freezes the policy.

### 13.5 Should the fixture derive from the policy? Yes

- `minimal_continuation_policy()` should call the U-38 production policy
  constructor, whatever U-38 names it, instead of restating numbers. Tests then
  run the deployed allowances, and a production re-size cannot leave the tests
  certifying a different number.
- Tests whose subject **is** a deadline should construct an explicit small policy
  for themselves. Several already do, for example
  `tests/unit/web/composer/test_continuation_action_admission.py:256, 302, 331`
  with `physical=0.05`, `0.02` and `0.01`. They should not depend on a shared
  literal that happens to be tight.
- Deadline enforcement stays proven by the §9.4 deadline-crossing control and
  those explicit-allowance tests, not by a production-path test that misses by
  coincidence.
- Interaction with §8: under the derived 5.0 s, the existing first-Compose test
  would likely pass even without F1–F4 at low history (§13.3). The §8.3 count
  budgets, B1–B6, are therefore what keeps the inefficiency from coming back.
  Land them with the fix and do not rely on the timed test.
