## Confidence Assessment

**High confidence in source-confirmed added work and production callers. Moderate confidence in measurement priority. Runtime cost and deployed frequency remain unmeasured.** The six findings below are candidates, not a severity-ranked defect inventory.

### 1. PostgreSQL deadline setup adds an execution before each qualifying statement

**Before/after:** The base session transaction helper did not install the new per-statement listener. `src/elspeth/web/sessions/locking.py:507-552` now installs `before_cursor_execute`; it recomputes remaining time and calls the raw DBAPI cursor to set transaction-local `lock_timeout` and `statement_timeout` before each application statement (`:543-546`). It applies only to PostgreSQL when an explicit deadline or continuation deadline owner exists (`:513-515`).

**Actual production reach:** Required SQL callbacks install deadline ownership in `web/async_workers.py:819-860`; `locked_session_transaction` enters this connection scope before acquiring the session lock (`sessions/locking.py:556-564`). Deadline-bearing authority reads also enter it (`coordination/composer_operation_authority.py:730-734`). This is not a claim that every query on every backend pays it.

**Cost model:** For `Q` qualifying statements, source implies `Q` setup executions, each with driver/server work and potentially a network round trip. This is an added linear multiplier. The raw setup deliberately bypasses SQLAlchemy event recursion, so existing cursor observations may omit it or fold its duration into another interval depending on listener ordering.

**Small measurement:** Root can count actual DBAPI executions by setup/application category for 1/2/4 otherwise equivalent PostgreSQL statements at fixed data size and topology. Measure setup wall time separately. Use SQLite and untimed PostgreSQL transactions as negative controls.

**Safe direction:** Reduce avoidable statement multiplicity or setup allocation if material. Setting the timeout only once per transaction would leave later statements with stale allowances and is not equivalent. Any batching must preserve shrinking absolute bounds, lock behavior, transaction-local restoration and failure ordering.

### 2. Quiet live GET/SSE observation now pays a parent/segment/parent consistency read

**Before/after:** The previous GET/stream paths called `get_with_database_now` once. Current routes call `read_projection_inputs` (`sessions/routes/composer/operations.py:280,431-439`). The added projection reads parent/time, current segment, then parent/time and compares revision/generation, retrying a bounded number of times (`sessions/composer_operation_projection.py:99-122`). Parent and segment reads open their own connection contexts (`coordination/composer_operation_authority.py:723-728`; `composer_operation_projection.py:66-75`).

**Frequency mechanism:** The live stream performs these reads before checking whether `status_revision` changed (`operations.py:431-445`). Quiet streams therefore still pay the read cohort even when no status frame is emitted. The loop sleeps one second; actual observed rate depends on work duration and stream control, and was not measured. Missing/terminal parents take a shorter branch.

**Cost model:** Approximately `live streams × polls × consistency attempts × cohort cost`. Bounded retries can amplify concurrent transitions; this is not evidence of unbounded or quadratic behavior. Counterevidence: unchanged status/progress frames avoid some serialization, so added reads do not by themselves prove a net regression.

**Small measurement:** One/two/four quiet streams over a short fixed window; count projection attempts, connection checkouts, parent/segment reads, frames and worker CPU. Add one controlled revision transition. Keep authorization/progress reads separately attributed.

**Safe direction:** Explore one coherent query/transaction that returns the same validated parent, segment and database-time cohort, with concurrent-transition controls. Do not cache authority or remove current ownership checks. Changing consistency boundaries requires explicit review.

### 3. Catalog cache hits now deep-copy complete schema records inside policy fan-out

**Before/after:** `web/catalog/service.py:241-253` changed a direct cached-record return to `model_copy(deep=True)`. This fixes mutable schema/secret-requirement aliasing. The work occurs on a hit, before callers decide which fields they need.

**Actual callers:** `web/plugin_policy/availability.py:100-149` walks authorized plugins and calls `catalog.get_schema` at `:145` to inspect secret readiness. `web/catalog/policy_view.py:96-115` calls it for each visible profiled summary. Composition validation also obtains the full schema (`web/plugin_policy/validation.py:802`). Thus a policy acquisition/listing can copy many schemas although its immediate decision uses a smaller subset.

**Cost model:** Roughly `policy acquisitions × selected plugins × schema graph size`, with additional profiled-listing calls. A dictionary cache hit is O(1); the returned deep copy is not. Actual frequencies and schema-size distribution are unmeasured.

**Counterevidence:** The same catalog change removes per-listing `get_config_schema` regeneration and uses the construction-time schema (`catalog/service.py:404-412`), which may outweigh added copying. Report the net listing result, not just the new copy cost.

**Small measurement:** Existing policy/listing calls over 1/2/4 representative plugin sets, measuring `get_schema` calls, copied schema nodes and CPU separately from schema generation. Preserve actual secret-ready and unavailable branches without exposing credentials.

**Safe direction:** A private immutable metadata projection for internal readiness checks may avoid copying unrelated schema fields while leaving public schema returns detached. It must not expose the mutable cache or reuse principal authority. Measure before changing the interface.

### 4. Replay LLM reconstruction now refreezes an already detached raw response

**Introduction:** Commit `cd62a3a94` explicitly removes the unsafe `MappingProxyType` skip from three freeze guards. In `plugins/infrastructure/clients/llm.py:65-71`, every non-null raw response now passes through `deep_freeze`. A generic mapping proxy is a view over potentially mutable backing data, so the old skip was unsound.

**Concrete added-work caller:** Replay builds `LLMCallResponse` at `llm.py:624-632`; that DTO freezes `raw_response` (`contracts/call_data.py:240-246`). It then passes the DTO's already-frozen raw response to `LLMResponse` (`llm.py:633-639`), which now recursively freezes it again. `contracts/freeze.py:55-73` rebuilds proxy dictionaries and traverses tuples. This is a confirmed extra traversal for this path, not merely a hypothetical proxy argument.

**Cost model:** `replayed responses × raw-response container nodes`; nested immutable scalar strings are returned unchanged, so this is not automatically proportional to string bytes copied. It could matter for high-throughput local replay where network latency is absent. No replay throughput loss was measured.

**Counterevidence:** Normal `ValidationSuccess` receives a freshly parsed dict (`plugins/transforms/llm/validation.py:171-189`), and the replay cache stores thawed dict data (`clients/replayer.py:247-274`); those normal inputs already traversed the old freeze path. Do not count all three edited guards as three demonstrated regressions.

**Small measurement:** Reconstruct replay responses with 1/2/4 container-node counts at fixed scalar sizes; count full freeze traversals, allocation and CPU. Retain mutation-of-backing-proxy negative controls.

**Safe direction:** Investigate eliminating the intermediate representation or an explicitly owned immutable constructor path. Never restore a generic `isinstance(MappingProxyType)` bypass. New ownership contracts require review; this report authorizes no interface change.

### 5. Prepared-provider verification adds repeated full checks around ordinary physical calls

**Before/after:** The base gateway detached messages and validated forwarded partitions; the new `PreparedProviderInput` adds bounded preparation, an original content/provenance binding, consumption and verification. This applies through the shared provider gateway, not only the known current-evidence restore.

**Actual sequence:** `prepare_provider_input` measures borrowed input then constructs a DTO (`web/composer/prepared_provider_input.py:503-559`); the constructor measures again and binds it (`:343-364`). `consume` verifies then copies (`:450-472`). The gateway verifies original and dispatch copies after guard and after quota, and the timed branch again at physical entry (`provider_gateway.py:627,644-658,718,746,775`). `verify` loops over candidate copies, measures complete wire, validates provenance and recomputes its binding (`prepared_provider_input.py:407-448`). These counts are source branch structure, not observed call counts for every request.

A separate fixed-cost addition rebuilds the logical guard-policy dictionary, sorts rule inventories, JSON encodes and hashes it (`composer/prompt_guard.py:79-115`) at construction, verification and actual enforcement. The physical adapter's `policy_fingerprint` property merely returns a field (`prompt_guard_clients.py:122-123`); it should not be confused with the reconstructing logical-policy helper.

**Cost model:** `physical attempts × verification count × request/provenance size`, plus `fingerprint calls × rule inventory size`. Fixed verification multiplicity alone is not quadratic. Retained history growth across repeated attempts can compound total work; measure bytes per attempt separately.

**Small measurement:** Use an existing non-continuation gateway case with 1/2/4 message bytes and fixed message count, plus fixed bytes/more messages. Count constructor/verify calls and distinguish size/provenance checks, copying and policy-fingerprint CPU. Preserve no-timer/timed and refused-input branches.

**Safe direction:** Optimize pure traversal/allocation within a check. Do not remove post-await mutation detection. A policy-generation mechanism could avoid repeated static inventory assembly only if it still detects every supported live-rule change; caching a prior hash unconditionally is not equivalent. This is a new measurement target, not a recommendation to reopen the already-known serializer repair.

### 6. Deadline-aware progress SQL observes completion by 10 ms polling

**Before/after and callers:** Deadline-bearing progress begin/bind/heartbeat/publish now use `ProgressSQLInvocation` and `run_progress_sql_in_worker`, rather than directly awaiting the generic worker (`coordination/composer_progress_authority.py:563-575,645-674`). The driver/progress owner supplies finite cutoffs. `async_workers.py:1152-1186` repeatedly checks the future/cutoff and sleeps `min(0.01, remaining)`; cleanup has a similar loop.

**Cost model:** Wakeups grow with outstanding invocation duration and concurrent invocations. Completion just after a check may wait until another tick; this is not a measured 10 ms penalty on every call. Long provider waits alone do not imply polling—these loops run while progress SQL is pending. No-deadline calls retain the prior path. This is lower priority until volume is established.

**Small measurement/safe direction:** Count iterations and completion-to-observation lag for 1/2/4 concurrent short controlled SQL workers using existing deadline tests. If material, consider completion notification plus an absolute-deadline wakeup, retaining native outcome custody, cancellation races, quarantine and late cleanup. A naive cancelling await is not equivalent.

## Risk Assessment

Deadline, consistency, ownership and mutation checks protect real correctness boundaries. Treat their removal as high risk regardless of code size. Pure implementation improvements are more reversible, but still need negative controls for changed bytes, policy, backing stores, deadlines and concurrent state. No candidate is approved for adjacent code changes.

## Caveats & Required Follow-ups

Prioritize PostgreSQL setup and quiet-stream reads for operational measurements, then catalog copying and replay refreezing where relevant workloads exist. Measure ordinary provider preparation separately from continuation reconstruction. Use existing fixtures and narrow counters with known-positive/negative calibration, not a new generic profiling framework. For scaling tests, distinguish fixed overhead, O(n) traversal repeated k times, n×m fan-out and threshold-driven cache behavior; do not declare quadratic complexity from three timings alone. Root retains control of all measurements and integration.
