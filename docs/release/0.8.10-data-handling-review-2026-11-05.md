## Scope and method

Finding IDs are stable. Unless stated otherwise, disposition is **open recommendation, unimplemented, not natively reproduced by this review**. Timing work does not close unrelated findings. Qualified and rejected candidates remain recorded below.

The comparison starts at `3b28d537be98234da8135c418bf185a998c18b68`, the verified `origin/main`/merge base with version 0.8.9, and includes current working source and Git-inventoried untracked 0.8.10 implementation. The published review-start HEAD was `a6990ffb72bd8b49e8298fbb4b152d586ce683a5`. This is deliberately broader than comparison against the old assembly ancestor. Unrelated 0.8.11 planning documents are excluded and preserved.

The review asks who owns each value, who can actually change it, what each check proves, and whether that proof is repeated without a new intervention. Persisted application data still has application-owned invariants: corruption must fail loudly. Parsing it is not permission to reinterpret corruption as ordinary user error. Conversely, arbitrary same-process monkeypatching of installed classes is not a useful substitute for an actual external or concurrent writer.

**Threat-model qualifications (TM1–TM5):** users, including authenticated users, are outsiders. Operators and application/plugin developers are trusted in intent; their accidents remain in scope. Plugin code is trusted, but outsider data passing through it still needs boundary admission. Checks are not justified by malicious-insider scenarios, lint/whitelist compliance or metric counts. Apply these qualifications to the findings below:

- **TM1 — installed code versus changing data (O3/O25, S4/S7):** accidental schema or binding changes warrant construction/startup validation and meaningful regression controls. They do not establish an actor changing private globals between successive runtime uses.
- **TM2 — actual internal error paths (O2/O10/O15, Q9/Q13):** supported validation-skipping updates and exposed mutable aliases can produce accidental invalid state. Validate at that transition or detach at the ownership boundary; preserve causal SDK/audit distinctions without making owned objects unforgeable against developers.
- **TM3 — persistence and concurrency (O1/O4/O5/O14/O18/O19/O21/O22):** wrong-operation joins, interrupted writes, accidental writer/schema errors and replacement-worker races justify their specific source, history and fence checks. Reuse already admitted immutable data only across intervals with no relevant intervention; retain independent cold and current locked proof. D0 needs only an ordinary failure and a user's valid concurrent Stop.
- **TM4 — support tooling (S1–S3/S6):** a permitted local client or candidate source is not automatically hostile. Resource bounds, no-import handling and input binding need an actual accidental large input, module side effect, concurrent build or outsider-data boundary; the support findings below qualify their necessity accordingly. Operator-key custody policy is unchanged.
- **TM5 — exposure claims (D2/D3/D7, O6/O7):** growing outsider input/history and accidental malformed producer output can justify bounds without insider hostility. D7's remote reachability remains unproved. Neither a corruption fixture nor a private-helper monkeypatch alone establishes an external exploit.

Eight bounded reviewers inspect production changes, their callers and meaningful test bodies. No native tests, benchmarks, database mutations, implementation changes, deployments, Git mutations, branches or worktrees are performed by this review. Root owns testing and integration. Per-file hashes, review times, detailed findings and coverage notes live under `.claude/lanes/codex-takeover-20261101/data-care-audit/`; these are ordinary working notes, not a sealed package.
