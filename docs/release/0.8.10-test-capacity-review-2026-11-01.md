## Verdict

**ENDORSE SUBSTANTIALLY SAME.**

The proposal is the right shape: the serial `-n 0` requirement is a
container-sharing constraint of the acceptance conftest, not a database
resource requirement, so the database container's quota is a separate
knob from the pytest worker count; the canonical helper is the only honest
place to put that knob because the architecture gate already pins it as the
sole `PostgresContainer` construction site; per-run assignment after a live
look at the host is the only policy consistent with readings that moved by
more than an order of magnitude within one hour (table below); and no
default change without evidence is correct because the throttling I measured
on the capped containers is real but small.

The endorsement carries one **blocking condition** that must be decided
before implementation, plus validation items. The condition is a parameter of
the same seam, not a different solution, so the solution remains
substantially the same within the meaning of the user's instruction.

**Blocking condition (decide before code):** the proposal says an assignment
"overrides fixture mem_limit/nano_cpus". It does not say what happens to the
callers that pass no limits today. Measured from source with
`grep -rn "postgres_test_target(" tests/` excluding the helper itself:
64 call lines in 61 files. 58 lines pass no `mem_limit` or `nano_cpus`
(including the two `tests/integration/web/` callers at
`test_blobs_ready_hash_postgres.py:70` and
`test_compose_loop_concurrent_sessions.py:56`). 6 lines pass limits: 5 at
`mem_limit="256m", nano_cpus=500_000_000`
(`test_composer_operations_postgres.py:300`,
`test_continuation_memo_accounting_postgres.py:55`,
`test_content_publication_postgres.py:44`,
`test_add_message_transcript_postgres.py:42`,
`test_reviewed_plural_authority_postgres.py:31`) and 1 at
`nano_cpus=1_000_000_000` as a labelled profile
(`tests/testcontainer/mcp/test_sql_policy_postgres.py:51`). Separately, 63
files reference the name `operation_postgres_target`; three of them define
their own fixture at the same 256m/0.5 limits and the rest import it. So a
"replace declared limits" assignment touches the composer cohort only, while
an "apply to every Docker container in the run" assignment newly caps 58
call lines that have never been limited. Either is defensible; they are
different behaviours. Root must state which one is implemented, the pure
helper tests must pin it, and Root's per-run budget must account for it
(under "apply to all", the session-scoped TLS container in
`tests/testcontainer/web/conftest.py:42` and a module-scoped container can be
alive at once, so the budget is at least two containers' worth). My
recommendation: replace declared limits only, with "cap all" available as an
explicit second value, because that preserves current behaviour for the 58
and matches "preserve caller behaviour with no assignment".

magnitude on CPU and by a factor of two on available memory. That is the
strongest evidence for the proposal's point 1: a stored default, including
the gate's 12-or-8 rule, cannot be right for this host. The I/O pressure
figure is the one a CPU/RAM assignment cannot address and the one a
PostgreSQL proof is most sensitive to (fsync, checkpoint, WAL). Point 1 names
I/O; the measurement shows that word must carry weight. Note also that the
one-minute load average (34, then 22) overstated the measured busy CPUs
(about 12) by two to three times; that is expected when I/O pressure is
high, because Linux load counts uninterruptible I/O waiters. Pressure stall
files, not load average, are the instrument for the pre-run look.

## Assessment of each point

1. **Root measures and assigns.** Endorsed. Required content of the
   measurement, from today's readings: CPU busy over a multi-second delta,
   MemAvailable and swap in use, all three PSI files, the CI shard inventory
   from argv (cwd will be unreadable), and the running testcontainer set with
   its effective limits. One broad suite at a time stands. Do not derive a
   worker count from load average; it overstated busy CPUs by two to three
   times during my sample for the reason given above.
2. **Per-run assignment at the seam.** Endorsed with the blocking condition
   above. Validation must be exact: a CPU quantity converted to `nano_cpus`
   without rounding, a positive integer memory quantity, both-or-neither if
   paired. Docker rejects `NanoCpus` outside 0.01 to `nproc`; let that error
   surface rather than clamping. State whether `memswap_limit` is set
   alongside `mem_limit` or left at Docker's 2x default; either is fine,
   silence is not. The provisioned branch must say the assignment is
   inapplicable and must not write it into the `testcontainer-run` receipt as
   if applied.
3. **Read back and observe.** Endorsed. The fields I read are the right
   ones: `HostConfig.NanoCpus/CpuQuota/CpuPeriod/Memory/MemorySwap/ShmSize`
   and cgroup `cpu.max`, `cpu.stat` throttled deltas, `memory.max/peak/
   events`. Add `io.stat` for the container and host I/O PSI, because that
   is where today's pressure is. Keep the inspect format restricted to those
   fields; never `.Config.Env`.
4. **Tests and one real cohort.** Endorsed. The architecture gate's textual
   count means the read-back must use the container handle the helper
   already has, not a second construction. Add a negative control to the pure
   tests: with the assignment set and the provisioned URL set, the kwargs
   must not reach anything.

## Controller decision after endorsement

The maintainer authorized adoption if this independent Fable review endorsed a substantially similar solution. The verdict meets that condition. Root chooses **replace existing caps only, independently for each field**: an already capped CPU field may receive the run assignment without adding a memory cap, and vice versa; absent, null or unlimited fields stay unchanged. There is no cap-all mode in this repair. Explicit caller swap configuration and every unrelated argument remain unchanged; otherwise Docker retains its normal swap behavior, whose effective value is measured rather than assumed. No permanent numeric default is adopted.

The detached gate already copies the complete environment (`os.environ.copy()`), so exported assignments are inherited; the remaining gate change is validation and an explicit receipt, not a second propagation mechanism. The reviewer's textual source-match counts above are diagnostic matches, not a runtime registry inventory. The implementation decision does not depend on those counts.

Requested and effective limits, live CPU/RAM/I/O pressure, active owners and supervisor cleanup remain separate measurements. CI runs for the earlier release checkpoints were cancelled under the current controller; old PostgreSQL containers and all source/evidence backups remain untouched. Native helper, architecture and real serial PostgreSQL qualification are still owed.
