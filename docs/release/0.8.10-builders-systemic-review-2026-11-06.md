# Continuous Composer: independent structural review and remediation plan

**Review date:** 2026-11-06. **Target:** 0.8.10 Continuous Composer. **Evidence:** current saved source on `release/0.8.10-assembly`, observed HEAD `cfa979308f29d49ffa6784cf7aa25a9fab22f362`, meaningful test bodies, and the existing R103 safe failure trace. Significant changes were uncommitted; this is a source review, not qualification of that commit or a frozen tree. Implementation status must be reported separately.

The shared defect is a mismatch between helper contracts and their effects. Capture and validation helpers can acquire SQL authority, reconstruct complete history, and perform expensive work without exposing those obligations to callers. Tests construct genuine inner owners but sometimes supply a different outer stage protocol. Consequently, individually plausible helpers and repairs can compose into unsupported transactions, timing behavior or publication paths.

The objective remains usable Composer under unchanged five-second preparation, 1 MiB private-document/evidence and 16 MiB retained-history limits. Users and providers are hostile outsiders; operators and application/plugin developers are trusted in intent, with accidental mistakes in scope. This review recommends no provider bypass, tutorial-specific behavior, larger limits, malicious-internal-code controls or new framework.

### F1 — Capture hides authority SQL and executes on the event loop in END

**P1; High confidence in source structure; runtime impact unmeasured.** `_capture_owners` rebuilds policy, serializes evidence and calls `composition_scope_for_operation` ([runtime:774](../../src/elspeth/web/composer/continuation_runtime.py#L774)). That function invokes authority CAS ([content_scope:36](../../src/elspeth/web/composer/content_scope.py#L36)); the repository opens a transaction and updates the fence row (`coordination/repository.py:6028–6032,6123–6124,6291`). This is a liveness no-op update, not business publication or lease renewal.

EARLY holds an outer session transaction while calling capture (`continuation_checkpoint_projection.py:243–251`), explaining the nested-writer mechanism identified in R102. The related END problem is different: complete-repair calls capture synchronously between awaited cold reads ([complete_repair:182–195](../../src/elspeth/web/composer/continuation_checkpoint_end_complete_repair.py#L182)). Cold-repair, complete-review and cold-review use the same structure. Their SQL and encoding execute on the coroutine's event-loop thread.

Authority still exists, but the registered worker installs the SQL deadline scope inside its callback (`async_workers.py:832–860`); a preceding awaited callback does not install it in the caller. PostgreSQL deadline handling depends on that scope or an explicit deadline (`sessions/locking.py:558`). Exact scheduling delays and database behavior require measurement.

**Correction and control:** place before-read, unlocked capture and after-read inside the existing registered callback, closing each read transaction before capture. Preserve final writer checks. Exercise genuine warm/cold END and EARLY with a competing writer, responsive heartbeat/cancellation task, actual worker/deadline observation and changed-head/fence opponents. Warm complete-review overflow currently returns before its second read (`:130–139`); explicitly define and test overflow plus final-read-failure handling rather than assuming all branches already match.
