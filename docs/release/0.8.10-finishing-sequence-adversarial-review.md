# Independent adversarial review of the 0.8.10 finishing sequence

Reviewed 2026-10-26 AEDT by a separate Astra review context. Subject:
`docs/release/0.8.10-finishing-and-landing-sequence.md`, complete lines 1–558,
whose stated evidence snapshot is `50d5d16c17930083a3d183a168df43177580950f`.

**Verdict: ready with a narrow sequencing correction and qualification
clarifications.** I found no source-grounded reason to stop the authorized
bounded landings, reject the main dependency chain, or revive the old
GREEN-before-all-other-landings hold. The sequence is not implementation or
release clearance. Its most consequential strength is that it does not treat
emptying the fifteen-branch queue as completing Continuation.

**Resolution:** the sequence now incorporates the accepted U-45/U-38 timing
split, immutable-main A4/A8 comparators, and local versus operator-cloud
acceptance boundary. The findings below retain the original reviewed wording
and evidence. Later implementation and validation progress belongs in the
current delivery report; this review does not confer runtime clearance.

## 1. Correction: keep the policy timing result off U-45's landing gate

**Priority P2; concrete ordering defect.** Sequence P4, lines 272–276, lists
idle-host timing and the 50-pair PostgreSQL p95 threshold among that package's
exit requirements. This combines two acceptance boundaries that the accepted
correction deliberately separated.

The source is explicit:
`0.8.10-handover/lanes/u45-officer-gate.md:419–425` assigns the result to
U-38's production policy, says a result above 2.5 seconds requires policy
resizing before the release merge, and states: “U-45 lands on its
deterministic gate either way.” Lines 405–417 retain the full deterministic
B1–B6, refusal/mutation, and root-cause requirements. This is not permission
to drop the optimization or weaken its controls.

**Consequence:** an executor using the package's stated exit can hold a
completed U-45 unit behind an idle-host measurement or policy change that
does not belong to that landing. That is contrary to both the accepted
correction and the sequence's own lines 546–550, which call for prompt
landing of completed receiving-verified units.

**Smallest correction:** split P4's exit paragraph. Keep U-45's deterministic
checks, affected receiving comparisons, review, keyless diff and A9 there.
Assign the idle-host result and any justified policy resize explicitly to
U-38/release qualification in P14, where the timing run is already required.
Say that this measurement does not hold an otherwise qualified U-45
landing. No new approval step is needed.

**Counterevidence:** the sequence retains the threshold and requires policy
analysis rather than hiding elapsed work. This is an ownership/ordering
error, not an attempt to remove the performance requirement.

## 2. Clarification: pin the final release comparator to main

**Priority P2; acceptance ambiguity, not a demonstrated bad scan.** P11
lines 414–418 and P14 lines 507–508 call for a reviewed “base/tip” finding
set. Throughout the document, `base` also means the current receiving base,
frequently post-50d. Original master-plan A4 (`0.8.10-master-plan.md:49`)
instead requires the release-wide keyless comparison between `main` and the
final assembly. The custody mandate repeats that comparator under §5
Gates. A8's compatibility comparison is also against `main`
(`0.8.10-master-plan.md:53`), whereas P14 line 515 only names “V1 failure-set
parity.”

**Consequence:** a final post-50d-to-tip comparison can omit changes already
present in the large overlay and earlier carries. Correct per-unit receiving
comparisons do not, by themselves, constitute the explicitly required final
release comparison. Conversely, a release-wide comparison does not replace
the no-passing-to-red rule at each landing.

**Smallest correction:** name both roles in P14: per-unit comparisons use
their actual receiving parent; final A4 and A8 use the recorded immutable
`main` release base and the final assembly tip. Bind the finding sets and
test identities to those revisions and explain any later movement of main.
Retain the existing signing suspension, no-zero-corpus criterion, and actual
exit handling. This is ordinary validation provenance, not a document seal.

**Counterevidence:** P14 expressly invokes A8, P13 requires checking the
original acceptance mapping, and the opening states that this is not a new
scope proposal. Reading those references strictly preserves the original
comparators. The requested edit removes an executable ambiguity; it is not
evidence that the author intended to replace A4 or A8.

## 3. Uncertainty to preserve: local process proof is not cloud acceptance

P12 lines 462–470 correctly requires genuine signals and separate ECS/ACA
process shapes; it does not confuse deterministic lease expiry with process
death. Runtime-design §6 defines those shapes as one or two local
`elspeth web` subprocesses against testcontainer PostgreSQL
(`0.8.10-continuation-runtime-design.md:1243–1255`). These can be prepared
and run in the coordinator's local test slot.

The protocol design separately states that reconnect across **real ACA
replicas and ECS tasks** is operator acceptance outside CI
(`0.8.10-continuation-protocol-design.md:886–888`). P14's “ECS/ACA
process/reconnect proofs” does not explicitly distinguish that remaining
environment-dependent evidence from the local PROC cases.

**Smallest clarification:** state which evidence closes local qualification,
which CI result belongs to the actual merged SHA, and which real-platform
acceptance remains operator-owned. Preserve the latter as unmeasured until
performed; do not let local P-5, a browser mock, or green CI stand in for it.
The current authorization does not permit deployment, remote push or merge
to main. This is not a request to delay authorized local work or seek fresh
permission now. No claim about actual cloud availability was verified here.

## 4. Findings I challenged but did not sustain

### Scope and dependency closure

- The branch inventory is expressly bounded, not a release completeness
  claim (sequence lines 107–145, 420–460, 553–558). P12 retains U-38c,
  U-37, U-39, U-36, real Stop, C6/Advisor follow-through and phase-owner
  wiring. P10 retains U-24. P4 retains U-45 part 2. P5 retains T5f and the
  `_StrictResponse` disposition. P8 retains the uncanonicalizable MCP-key
  audit defect. These are concrete counterexamples to an allegation that
  all work outside the fifteen branches was forgotten.
- The carve's cross-unit cycles are real reasons not to restore numeric
  order or cherry-pick whole obsolete stacks: carve-partition §3a–3d and
  §6 (`:164–250`, `:400–450`) identify the C1a, TITLE and larger overlay
  dependencies. The sequence acknowledges the already-landed overlay and
  distinguishes source presence from runtime reachability. It does not
  propose splitting those original cycles into independently ready features.
- U-35b before worker integration is supported by runtime-design §3 and
  §7; U-38 policy is already in the snapshot, while U-38c addresses a
  distinct repeated-admission cost. The runtime report's evidence-read
  diagnosis explicitly says U-45 part 2 does not cover that read. The
  sequence correctly retains both pieces of work.
- Protocol can land as a partial slice before real Stop. Its candidate
  explicitly refuses lifecycle-2 Stop, and P3 labels that incomplete release
  behavior. P12 assigns the real marker/settlement path and the named PG
  cases before completion. Treating that refusal as completed Stop would
  be wrong, but the sequence does not do so.

### Source ownership, carried work and commit grouping

- P1 preserves the exact distinction between old reserve re-pins and the
  uncompleted DATA/application proof. It carries the compose binding with
  extracted-reader coverage, retains newer supplier/import proof, avoids
  duplicating the recipe files, and forces one coherent required/defaulted
  attachment API choice. These match the immutable-object reconciliation
  in `.claude/lanes/task0-fixpoint-review/unlanded-carve-reconciliation.md`.
- P2/P4 correctly retain 2ef's stronger physical SDK/original-audit controls
  while separately carrying the absent validated history extension, both
  guarded-thaw boundaries, quota fixture correction and real paid-family
  producer joins. The source is
  `.claude/lanes/task0-broader-performance/unlanded-producer-sdk-fixes.md`.
  Neither the 69/52 historical families nor the single successful probe is
  represented as current qualification.
- P4 anticipates the schema-cache/copy-isolation intermediate problem;
  P8 identifies the issue327 red-first folds; P10 keeps U-30 collection
  repairs together and U-22 cap/evidence settlement together. P7 uses the
  reviewed U-35b squash. The generic rule additionally requires every newly

- The U-35b and residue additions of
  `tests/helpers/continuation_budgets.py` are the same blob (evidence below).
  The shared-file receiving reconciliation must still happen, but this is
  not evidence of two conflicting budget implementations.
- The current parent-owned afaedad/435f candidate is staged, not durable

  The sequence's final paragraph already allows a coherent reserve unit
  to precede its timestamped envelope candidate. No contradiction is proved

### Acceptance, authority and compatibility

- P12 incorporates the complete named runtime §6 and protocol §5 acceptance

  settlement, required-work ownership, released/expired fence recovery,

  P4, P10, P12 and P14; K-7 is specifically named. The controls distinguish
  an actual provider-authored transition from notes or an unexecuted
  Advisor prescription. No server-authored successor fallback is proposed.
- P4 uses the accepted fresh-Context memo mechanism, not the superseded

  isolation and `_SESSION_WRITE_LOCK_HELD` requirements agree with officer

- P5 does not silently authorize epoch 80 or a store reset. It identifies

- Signing remains suspended. S1–S3 remain open for post-release protected

- The coordinator owns the integration index and runtime queue. Shared
