# 0.8.10 approved integration and completion strategy

John approved this recommendation on 26 October 2026 and requested its written
handoff to Emmy and the implementation agent. The approval follows the independent
review in chat `01a176e7-b9f8-7123-8b31-b342174e9bed`.

**Decision: integrate dependency batches, finish the missing continuation behavior
on the common assembled base, then qualify and land 0.8.10 once.**

This supersedes the strategy-deferred status and the assumption that every private
branch must finish independently before integration. It does not declare any
candidate qualified, waive a test or integrity obligation, authorize destructive
store operations, enable signing, or grant final publication approval. Existing
controller ownership and operational access boundaries remain in force.

## Ownership and governing requirements

- Emmy retains coordination and operator-facing decisions. The existing Nyx
  controller, `ELSPETH 0.8.10 - Implementation`
  (`01a16f44-9d3e-72e2-924a-073cd1ef9df6`), retains receiving-branch and test-capacity
  ownership. Use its existing workers; do not create a duplicate controller.
- Ship all Continuation scope. Preserve provider-authored transitions, the normal
  tutorial path, V1 behavior with V2 admission default-off, epoch-79 preserve/refuse
  contracts, durable evidence/accounting, and ECS/ACA operation.
- Signing remains suspended. Use keyless finding-set comparisons, never signature
  clearance claims. No agent holds the operator HMAC key.
- Retain one final main merge, required protected CI on the actual merged SHA, and
  the maintainer's final publication decision. Deployed acceptance remains an
  independently reported operator activity.

## Approved execution sequence

1. **Restore dependable validation capacity.** Reconcile the active controller and
   existing worker. Complete the `40babb9a` review, explicit-capacity and finite-data
   automatic-mode controls, and real owned-process cleanup. Never retry prohibited
   general host-process discovery. Tooling qualification is not product completion.

2. **Create the first durable integration checkpoint.** Reconcile T5e `17ba`, the
   kernel/launcher and owner-fixture closure on the controlled receiver. T5f fits
   the schema boundary if its DB checks clear; it need not hold an otherwise
   qualified T5e repair indefinitely. Run the union of relevant controls against
   the combined source. Test-infrastructure and whole-tree-analysis changes justify
   a receiving full gate. A completed red run can support an explicitly monotonic
   repair landing, not closure of unfulfilled proof obligations.

3. **Receive prepared Composer work in dependency batches.** Reconcile
   SG/SDK/U-45 part 1/codec residue, preserving stronger current behavior. Receive
   U-35b and protocol coherently, and U-30 with metadata fixtures and live-provider
   controls. Use one integration review and affected-test union per coherent batch;
   fold red-first/WIP history into independently landable units. Do not require the
   stronger SG positive merely to qualify the separate fail-closed kernel, or waive
   SG's eventual release obligation.

4. **Finish the product on the assembled interfaces.** Critical runtime chain:
   U-35b → U-38c → worker/recovery/cold restore, joined with real Stop/C6 and owner
   wiring. PromptShield chain: U-30 → U-22 → U-24. Complete U-45 part 2, exception
   evidence preservation and issue327 defects against those interfaces. Parallelize
   only disjoint ownership; serialize shared service/gateway and proof-helper edits.

5. **Freeze and qualify the complete release.** Run the canonical six stages,
   including serial PostgreSQL, with no hang-file exclusions; complete
   frontend/browser/gateway, real process SIGTERM/SIGKILL/reconnect/stale-owner,
   A8 V1/default-off and A9 per-transition provider checks. Run the specified
   PostgreSQL timing measurement. Compare keyless finding sets against immutable
   main, not zero. Preserve approved xfails while inspecting their underlying
   evidence. Distinguish receiving GREEN, release qualification and deployment.

6. **Prepare the single protected publication decision.** Finish version, upgrade,
   security/runbook consistency and independent assembled-release review. Present
   the concrete candidate for maintainer publication approval; then verify required
   CI on the actual merged SHA. Deployed ECS/ACA reconnect acceptance remains
   separately operator-owned.

## Validation, stopping and custody rules

Run discriminating regression controls and affected checks when their inputs
change. Reuse unchanged source-bound reviews/results with their actual limits.
Run broad gates at justified batch boundaries and on the final assembled tree,
not after every fixture or pin correction. Never infer regression safety from
equal failure counts: compare test-ID/failure-signature pairs and require every
introduced test to pass at its landing commit. Retain real negative controls,
authority boundaries and required PostgreSQL coverage.

Stop the affected batch for an unexplained passing-to-red result, failed positive
prerequisite, stale proof binding, lost denial, integrity defect, unsupported access
requirement or source drift. Surface a process deviation when the procedure cannot
produce valid evidence or produces prepared work faster than it can be integrated.
Branch counts alone are not a useful trigger. Report the concrete blocker and next
decision rather than adding another approval or evidence ceremony.

Checkpoint with ordinary commits and preserved candidate refs. Do not disturb the
shared staged candidate or foreign work. Preserve failed candidates for diagnosis;
do not reset, stash or clean other owners' state. Code rollback does not downgrade
epoch-79 stores: preserve old stores and keep data cutover operator-owned.

Maintain one authoritative current status record. Refresh stale pause/next-action
instructions rather than creating parallel status authorities. Resolve the
[toolchain guide](../maintainer/toolchain.md)'s old `codex-cli` recommendation
against [AGENTS](../../AGENTS.md)'s current disabled-transport rule during release
closure. Do not introduce signed plans, new manifests, approval chains or duplicate
controllers. This ordinary release document may be updated or retired as work
progresses.
