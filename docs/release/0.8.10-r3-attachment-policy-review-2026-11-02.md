## P1: committed attachment refresh enters the native tool issue reader

`src/elspeth/web/composer/continuation_live_phases.py:762` runs the attachment result owner, reloads the resulting selected checkpoint, then calls `self.current(selected)` at line 775. The published attachment checkpoint is `ToolBatchFrame(effect_reconciling, composer.tool-batch.v1)` with its committed `attachment:<response>:<index>` read result.

`src/elspeth/web/sessions/continuation_runtime.py:105` routes this shape unconditionally to `require_issued_tool_runtime_on_connection`. That reader, in `src/elspeth/web/composer/continuation_phase_transitions.py:551`, constructs and requires a **native** `tool:<response>:<index>` issue. The new `attachment_prepared` transition intentionally creates no such native issue. Consequently the normal live path can inspect and commit the attachment but cannot refresh its runtime to apply history. The new cold published-result route reaches the same reader before it can consume the committed attachment result. The new positive/cold tests should expose this when Root executes them; they were not run by this reviewer.

Smallest repair: distinguish the actual attachment result owner in the runtime source reader and prove its exact committed result, prepared source, current selected root and receipt through the existing SQL attachment reader. Preserve native issue proof for native dispatch. Do not remove the check for this frame family or admit an attachment read from its shape. Add an opposing case that substitutes a missing/uncommitted attachment result or a native issue into this branch.

## P2: post-attachment multi-call batch receives the wrong next action allowance

`src/elspeth/web/composer/continuation_next_action.py:858–880` returns `policy.actions.session_sql` for the coupled `tool_ready` cut whose latest settled effect is an attachment. Thus after the first attachment in a multi-tool response, a subsequent attachment/blob/external call can be selected under a SQL-only budget. This is an existing selector branch newly exposed by connecting ordinary PRIMARY attachment reads to this lifecycle. The structural comment promising that no subsequent business action is admitted is inconsistent with the phase consumer.

Smallest repair: prove/discriminate the completed-prefix DATA and retain the appropriate existing next-call allowance when another original call remains; use SQL-only sizing for the actual completed batch/application suffix. Preserve the current SQL source admission and original SDK call identity. Add a real two-call response with attachment first and another original tool second, asserting the driver's installed action clock/fit allowance and no replay of the attachment. A standalone phase invocation does not prove this boundary.

## Prepared-only cut: availability gap, not demonstrated read-authority escalation

`attachment_prepared` retains the original SDK preparation, audit DATA, provider response and creator before a new read. Its writer rejects V3 and active semantic actions, checks the current predecessor and completed prefix, and validates the complete newly stored evidence graph before commit. The live path retains its actual context/audit owner and proceeds directly to the existing attachment owner. It does not create a synthetic semantic Read grant.

If interrupted after this new durable checkpoint but before the attachment owner starts, cold continuation fails closed: `continuation_next_action.py:816` refuses this unpublished prepared cut, and `continuation_live_phases.py:759–761` requires original live preparation to initiate a read. A fresh actor cannot simply reuse the old prepared creator. This is a genuine recovery/availability limitation of the new persisted boundary, rather than a demonstrated authorization bypass.

`ContinuationFrameStack.is_handoff_safe` (`composer/continuation.py:254`) still returns true for this `tool_ready` shape. That classification is broader than recoverability. However, the actual yield transaction (`sessions/continuation.py:1978–2013`) derives the successor action through `_retained_successor_action` after appending the candidate handoff, within the same transaction. The selector refusal prevents a committed successor grant and rolls back the yield. Do not describe this as a safe recoverable prepared handoff; equally, no unsafe committed read allowance was demonstrated. Any recovery repair needs explicit original-preparation/creator/current-actor ownership or a durable refusal disposition, never a frame-only allowance.
