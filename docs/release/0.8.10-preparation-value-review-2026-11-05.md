# EARLY preparation: what the elapsed time buys

Independent Astra high review, 2026-11-05. Scope: preparation of the original EARLY checkpoint Advisor action, before its original five-second preparation clock finishes. This is an assessment of work and its purpose, not release qualification or permission to weaken a boundary.

**Operator-specified threat model:** users, including authenticated users, are outsiders. Operators, application developers and plugin developers are insiders whose intent is trusted; their accidents remain in scope. Plugin implementation is trusted internal code, while user/provider data flowing through it remains outsider-sourced. Validation protects against hostile outsiders and accidental human error inside the implementation, not hostile insiders. Deliberately replacing a private pure builder with code that uses a captured SQL connection is therefore not a legitimate production adversary. A mistaken assignment, incorrect serializer change, unchecked model copy or unintended mutable alias can still require a check. The question is what mistake the check detects at this precise point and whether a cheaper check preserves that protection.

**Operator-specified justification rule:** validation performed merely to avoid a whitelist or allowlist entry is inappropriate. No recommendation in this review treats scanner friction, signature churn or the desire for a clean lint report as a runtime boundary. Keep code that protects a concrete boundary; handle an honest justified scanner finding separately.

The original EARLY action reviews the transition from an empty to a nonempty composition. Its content task is to build the current graph summary, contracts and visible transcript, render the configured Advisor instructions, prepare the exact provider request, and bind the actual provider, recorder, work and clock owners. The provider performs the review.

The request is built and `prepare_provider_input` returns in [advisor_checkpoint.py](../../src/elspeth/web/composer/advisor_checkpoint.py), lines 636–684. It prevents prospective application from mutating the original graph, recorder, transcript, batch dictionaries and disclosure tracker. Simply deleting it or moving all reconstruction after the provider is not a safe remedy.

## Findings, ranked for action

### PV1 — Stored evidence is decoded, then sent through the fresh-encoding pipeline again

**High confidence; local implementation risk medium; current seconds saved unknown.**

`AdmittedTurnEvidence.__init__` receives a `PrivateChunk`, verifies its codec, complete byte bound and content binding, strictly decodes `TurnEvidenceSnapshot`, and compares the canonical projection with the incoming bytes ([continuation_evidence.py](../../src/elspeth/web/composer/continuation_evidence.py), lines 390–405). It then unconditionally calls `_encode_turn_evidence_source` at line 412.

That helper performs retained-model validation at line 559 through its field-admission call, transcript integrity admission at line 614, canonical encoding at line 644, another whole-snapshot strict decode at line 647, another canonical encoding at line 650, and private-chunk encoding at line 654. The source snapshot just decoded inside the constructor has not escaped to a caller between these steps. There is no intervening SQL/provider/plugin actor changing it.

**Smallest correct replacement:** separate admission of stored bytes from encoding a fresh or caller-supplied snapshot. The stored path should strictly decode once, retain the verified original bytes and reference, and perform the actual field, graph, recorder, transcript, credential and evidence-pair checks once. It should not feed the same local object through an encoder whose job is to make and then read back new bytes. Preserve the public fresh-snapshot path's defense against unchecked `model_copy`/`model_construct` and mutable input.

Do not remove semantic checks merely because Pydantic accepted the schema. Do not trust supplied byte length without checking actual bytes. Do not treat an admitted graph as current authority. The opportunity is to remove repeated representation work while keeping those distinctions.

The test currently pins this repetition: [test_continuation_evidence_graph.py](../../tests/unit/web/composer/test_continuation_evidence_graph.py), lines 179–186, expects two writer calls for capture and three more for decode. Lines 195–224 deliberately corrupt the internal writer on its `self_roundtrip` call. That particular control protects against a substituted implementation, not an external source. Tests for malformed stored fields, credentials in a supplied copied model, unchecked model construction and mutation after the admitted object escapes remain materially different and must survive.

An accidentally broken serializer is a real internal-human-error concern. In this stored path, however, the initial strict decode and canonical equality already bind the just-created model to the incoming complete bytes. Retaining those original bytes avoids invoking the serializer again and then validating its newly introduced output. The recommendation removes the unnecessary transformation and its consequent failure opportunity; it does not assert that internal implementation errors are impossible.

### PV2 — Message-family reconstruction performs a second complete read inside the same lock

**High confidence in duplication; medium confidence in replacement scope; current seconds saved unknown.**

`CurrentContinuationMessageFamilies._restore_cohort` enters one `locked_session_transaction`, obtains `_read_current_sources`, rebuilds messages, obtains `_read_current_sources` again, compares the results, then repeats per-recipe proofs ([continuation_message_families.py](../../src/elspeth/web/composer/continuation_message_families.py), lines 1085–1170). Normal cooperating session writers cannot change these sources inside that lock. The production builders are pure reconstruction functions and receive no SQL connection.

The test opponent at [test_continuation_family_cohort.py](../../tests/unit/web/sessions/test_continuation_family_cohort.py), lines 122–161, monkeypatches a builder and uses a captured connection to write cancellation inside the same transaction. This demonstrates refusal under altered implementation behavior; it does not establish a normal concurrent actor between those two reads.

**Smallest correct replacement:** perform the full historical/source admission once for this transaction, rebuild from that admitted data, preserve exact reconstructed-wire equality, and retain the necessary inexpensive current/deadline/Stop check. Do not repeat full graph decoding and historical reconstruction merely to defend arbitrary SQL injected into an owned pure builder. An accidental legitimate writer bypassing the session lock is a different internal-error case; exact raw-source/relational comparison can retain detection if that case is promised. The review does not introduce a malicious database administrator as an assumed actor. Session locks alone do not exclude direct writes under PostgreSQL READ COMMITTED.

This is distinct from the outer current-evidence pre/post reads that span separate callbacks or transactions. Those cannot be removed on the same reasoning.

### PV3 — Detached preparation uses a full cold restore followed immediately by a full recapture

**High confidence in work performed; medium confidence in replacement design; implementation risk high.**

[continuation_checkpoint_end_detached.py](../../src/elspeth/web/composer/continuation_checkpoint_end_detached.py), lines 134–171, reloads selected durable state, re-materializes the environment inventory, restores the runtime, checks mutable-owner separation, captures the restored runtime again and independently builds the expected capture. `_restore_runtime` separately reads runtime sources, builds current message producers, restores the evidence graph and constructs live owners ([continuation_runtime.py](../../src/elspeth/web/composer/continuation_runtime.py), lines 471–510).

The final expected capture is itself work: `expected_prepared_end_capture` recaptures cache history and rebuilds policy validation because capture appends cache history and restoration refreshes validation (`end_detached.py:83–131`). The comparison therefore proves a transformation performed by ELSPETH's own restoration, not simple identity with the original retained bytes. The new detached graph has not been exposed to a provider or user callback before this immediate proof.

**Replacement direction:** construct the independent mutable owners once from freshly admitted capture data; retain fresh durable-byte and relational consistency checks and current policy/environment admission. Prove constructor equivalence and mutable isolation with meaningful tests. This avoids routing a warm, already owned source through every cold recovery entrypoint and immediately replaying it again to certify the construction.

This is the largest structural opportunity in the current spans: the full restore is 10.853841 seconds, with its immediate recapture 3.189074 seconds. It is not an immediate deletion and has no measured speedup. Capturing a graph once and constructing independent mutable owners may still be substantial work. All cache/validation transformations and the post-response use must be accounted for. A blanket `deepcopy`, a nominal-type check alone, or head/fence equality alone does not establish the required properties.

The existing recapture can catch accidental wrong-field assignments, missing retained content or wrong cache/validation transformation in the restore implementation. Those are legitimate concerns under the operator's threat model. A replacement must make the construction explicit and check the actual field/content correspondence and owner separation; “the constructor is ours” is insufficient. What is not established is that detecting these mistakes requires rerunning the entire cold source-admission pipeline and independently rebuilding policy/cache state. PV3 remains a design opportunity until the cheaper correspondence checks are specified and verified.

**Bounded PV3 next step, design only: source-review GO for conditional generic reuse.** Retain cold restoration, mutable-owner separation, the actual `_capture_owners` serialization, the independent expected-capture calculation and their complete equality comparison. In the existing generic capture worker, when `runtime.source.selected is selected` and `runtime.source.evidence_env_ref_names == inventory.names`, obtain a fresh `authority.read_continuation_env_selection`, require equality with `inventory.selection`, and use the actual `runtime.source`. Otherwise perform the existing full initial runtime-source read. Keep the full final read and existing refusal path unchanged. This can cover both initial and detached captures; it needs no checkpoint-only wrapper, caller-supplied proof, skip-validation flag, global cache or new authority token. Minimal production scope is the existing `capture_scoped` body in `continuation_runtime.py`.

The fallback matters. [test_continuation_runtime.py](../../tests/unit/web/sessions/test_continuation_runtime.py), lines 321–359, advances real attachment history and then captures an older live runtime against the newer selection/inventory. Blindly using `runtime.source` would build against the old selected root; a final check that the new selection is valid would not repair that lost history. Exact carrier identity is a conservative qualification: equivalent but separately constructed selections can continue through the full reader. For the same carrier and credential binding, the reused fields consumed by capture are owned frozen snapshots, scalar/tuple values, immutable private bytes and JSON strings. No supported mutation of those source fields was found. The admitted source's graph can be exposed, but the capture uses the actual `runtime.live`/`runtime.graph`, not that graph as a substitute. Live changes remain subject to the actual capture's semantic checks.

The narrow facade still checks current running ownership/Stop/lease, snapshot CAS and complete root equality (`continuation_env_inventory.py:40–58`). The retained final full reader checks the actual private SQL chunk cohort against `selected.chunks`, historical relationships and current inventory (`sessions/continuation_runtime.py:174–176` and its enclosing reader). It runs before a capture returns, on success and on the existing `ComposerContextUnsupported` refusal path, preserving refusal aggregation and attached evidence. Thus an outsider-originated or accidentally corrupted same-head document still refuses before provider admission. The changed behavior is when deep corruption is discovered: after capture instead of before it. No provider or user-visible result is produced in between. A transient corrupt database value repaired before the final check may go unobserved, but the capture used the previously admitted DATA, not that transient value; this is not a new authority or an atomic-history guarantee.

Two independent source readings found no lost successful-acceptance guarantee for this conditional generic design. It is not implemented or tested by this review. Preserve the real changed-state-version and alias controls; exercise actual Stop/lease/selection and same-head SQL corruption before and during capture, including refusal, required-work completion, changed credential binding and the advanced-selection fallback. The R29 detached-capture wrapper's 2.596 seconds outside `_capture_owners` includes both full source reads and other overhead; removing one read does **not** establish a 2.596-second saving.

Do not instead reuse the original pre-restore capture as the expected post-restore capture. Capture appends cache history and restore refreshes validation. Nor should the detached object's own cache/validation outputs become their independent expected values: that would conceal wrong constructor assignments. The shared expected-cache computation remains in the bounded proposal.

**Why retain the comparisons in this bounded change?** This is change isolation, not a claim that installed code can defend against malicious installed code. The ownership comparison catches ordinary accidental mutable sharing cheaply and belongs at the construction boundary. The selected-root/retained-byte comparison binds actual durable input and remains a real data-boundary check. Immediate full capture versus independent expected capture detects wrong scalar assignments, dropped recorder/transcript content and wrong cache/validation transformations in the constructor; no new outsider acts on the private fresh object between those calls. Those regression checks could be replaced by a clearly typed constructor, direct correspondence invariants and meaningful constructor tests. A complete cheaper replacement for that correspondence has not been established here, so it is a separate potential removal, not a reason to retain the current round trip permanently. The later post-response comparison additionally spans time and mutable-owner exposure and is unchanged by this design. None is justified merely by a test that maliciously replaces a private implementation.

### PV4 — Fresh owned P4 and other internal values are repeatedly re-admitted

**High confidence in source pattern; medium implementation risk; current savings unknown.**

`prepared_p4_members` serializes and strictly decodes an already nominal `PreparedP4Value` specifically to guard `model_construct`/`model_copy` inputs ([continuation_prepared_p4.py](../../src/elspeth/web/composer/continuation_prepared_p4.py), lines 221–226). That is appropriate for an independently supplied value. Fresh capture calls it immediately after constructing a value; encoding and semantic projection call it again (lines 523–581).

Use a private construction/admission result carrying the actual value and its checked members through adjacent internal calls. Keep strict admission at public or stored-input boundaries. The current `_decode_prepared_p4_with_members` is already an example of this narrower pattern; the review does not propose a global proof registry or unbounded cache. Historical call counts cannot quantify how much repetition remains after the current working changes.

There is also an explicit repeated content-view admission in the Advisor argument builder (`advisor_checkpoint.py:1238–1264`), retained for error precedence. Passing an admitted view to the later pure producer could preserve that order. The historical argument-builder timings were only milliseconds; this is not the priority for recovering seconds.

### PV5 — Ordinary runtime reads discard and repeat adjacent admissions

**High confidence in duplication; low-to-medium implementation risk; current savings unknown.**

The ordinary runtime path obtains current inputs through an evidence reader that already invokes the P4 application-journal verifier ([continuation_evidence_restore.py](../../src/elspeth/web/composer/continuation_evidence_restore.py), lines 85–88). Runtime assembly then invokes that verifier for the same selected state and evidence on the same connection ([sessions/continuation_runtime.py](../../src/elspeth/web/sessions/continuation_runtime.py), lines 173–178).

The current-input assembler also decodes the selected iteration and retains only its producer inputs ([continuation_prompt_producers.py](../../src/elspeth/web/composer/continuation_prompt_producers.py), line 280); runtime assembly decodes that same iteration again at `sessions/continuation_runtime.py:191`.

Carry the actual admitted iteration and journal result through the adjacent internal calls. Preserve separate owed-work entry paths, which do not necessarily perform the first ordinary-reader admission. The intended result is one explicit proof per applicable path, not an “already checked” boolean supplied by a caller or a general-purpose proof cache.

This table applies the operator's threat model to the recommendations. “No trust-changing event” does not imply that arbitrary unchecked values are safe; it identifies where the exact result of a completed admission can be used instead of independently recomputed.

## Checks that should remain, and hypotheses rejected

- Historical tool-result graph proof is not redundant merely because the ordinary request builder does not inspect it. It independently binds transcript, recorder, frontier, base, creator and attachment history. Current-head checks do not establish those relationships.
- A final head/fence-only check is insufficient. Actual durable chunk payloads can change under the same head. A cheaper consistency check must compare the exact relevant bytes and all relational dependencies against a prior complete admission, or re-admit changed inputs.
- Stop, lease ownership, original clock and paid-result accounting remain real requirements. A pure memo result cannot grant authority.
- Fresh local construction differs from public copied models and later mutable alias escape. Removing local self-round-trips must not make externally supplied unchecked objects trusted.
- cProfile function counts can locate repetition, but its heavy tracing overhead makes the old traced self-times unsuitable for current percentages. R18 covers one selected worker, not the whole preparation.
- The R23 cross-thread elapsed aggregation is not a CPU breakdown. GIL gaps and overlapping intervals overcount. Approximate phase alignment is not sufficient for a precise current attribution.
- Large-string/category memo improvements are observed changes, but they do not prove that more caching is the best next action. Cache hit/key/accounting machinery is itself work; the semantic source admission still repeats on hits.
- More CPU workers cannot automatically parallelize this sequential dependency chain. This review did not establish host contention as the cause of the measured delay.

## Risk Assessment

Local separation of fresh encoding and stored admission has **medium** risk and is readily reversible in code.
