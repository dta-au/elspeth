# R4 retained-capacity design — independent review

The fixed policy is coherent: preserve every mandatory paid-result byte, refuse before dispatch without a proved complete bound, and retain the existing 1 MiB private/evidence limits. The design correctly distinguishes aggregate retained payload from individual-document limits and producer envelopes. **Its immediate implementation sequence needs narrowing: do not activate V3 or disable fresh default composition as part of the integrity repair.** No new user policy choice is needed to make that separation.

## Activation is a product behavior change

[WebSettings](../../src/elspeth/web/config.py#L452) defaults the retained allowance to `None`; [the live app](../../src/elspeth/web/app.py#L2324) currently supplies the V2 builder. [The V3 builder](../../src/elspeth/web/composer/continuation_policy_settings.py#L102) returns `None` for that default. Therefore design step 2's unconditional app switch would refuse every fresh operation on a default installation, while preserving only exact existing-id replay. Supplying an explicit aggregate allowance does not restore paid usability: current V3 PRIMARY/TITLE/semantic guards refuse before their unbounded producers. This is a hard-disable consequence, even without adding a numeric default.

The statement “no production default ... proposed” does not make that wiring compatibility-neutral. Keep app activation and public HTTP status/code selection as a separate, explicit deployment/product slice. Do not silently fall back to V2 while advertising V3 guarantees, and do not silently reinterpret absent configuration as a newly authorized shutdown. Existing V2 behavior remaining in place means R4 remains incomplete; it must not be relabeled compliant with the fixed predispatch-bound policy.

## Implementable integrity work

The parent-policy gap is confirmed: [_composer_operation_transition_condition](../../src/elspeth/web/sessions/models.py#L4017) omits policy version, policy hash and retained allowance from its immutable tuple. The [bounded-read contract](../../src/elspeth/web/sessions/continuation_retained_capacity.py#L43) subsequently relies on those parent fields. Adding them to both dialects' trigger condition is a concrete independent integrity repair; no provider contract or app activation is needed. Coordinate the supported schema version/upgrade inspection so installed schemas cannot retain the weaker trigger unnoticed. Preserve normal claim/status changes and historical V1/V2 records; do not migrate or reset a running store as part of this source task.

Safest next scope: tests first for direct mutations of each parent policy field (including V3 downgrade and allowance increase), unchanged-value updates, ordinary claim/status transitions and historical policy read/resume; then the narrow trigger/schema compatibility implementation and affected SQLite/PostgreSQL validation under Root. A separately injected `None`-policy authority test can specify typed unconfigured refusal and exact authenticated replay without rewiring production defaults. Refusal must precede operation insertion, quota debit and irreversible work, but must not promise absence of all SQL writes: [quota.prepare](../../src/elspeth/web/coordination/composer_operation_authority.py#L551) invokes [cleanup](../../src/elspeth/web/coordination/rate_limit_authority.py#L105) before replay/config classification. Preserve lock ordering if changing that sequence.

## Actual refusal scope and remaining producer constraint

Current PRIMARY and TITLE entry guards do precede physical preparation; semantic refusal precedes action preparation. The tool guard occurs before tool preparation/issue, with a second V3 refusal at the SQL transition for `tool_issued`/`attachment_prepared`. These are useful defenses but not proof that every later cut can durably settle through the generic refusal owner.

[refuse_v3_retained_tail_before_paid_on_connection](../../src/elspeth/web/sessions/continuation.py#L1773) explicitly rejects any effect frontier, pending owner/settlement, off-frontier effect or physical attempt. It proves a **wholly unpaid operation** refusal. A historical V3 END/iteration/tool state with a prior paid source cannot use it as a general successful terminal-refusal path. The design's later-cut controls should distinguish no-dispatch integrity refusal from an actually retained terminal receipt, preserving prior paid results and unresolved custody. A fresh app V3 test usually stops at the first producer guard and cannot qualify those later paths.

No inspected code contract proves a finite bound for the complete external response and all required encoded forms. Requested token limits are not a bound on arbitrary response metadata, tool identifiers/arguments, reasoning, escaping or audit duplication. Schema parsing and post-return byte checks are also insufficient. Do not solve this with truncation, an over-limit transport abort, widened document limits or a made-up bound. Establish an enforceable producer envelope first; otherwise honest predispatch refusal remains required for that producer. This review does not research or assert an external provider guarantee.

A future persisted paid-tail hold is reasonable only after that envelope exists. It must cover every representation and outcome, stay tied to original effect/policy/source custody, survive unknown outcomes and prevent unrelated writes consuming reserved capacity. The current prospective unpaid terminal allowance is not such a hold. Usable R4 paid composition remains externally constrained and unproved; shipping the independent parent-integrity fix does not complete it.
