The relevant stocks are retained immutable text proofs in the preparation parent; fresh decoded values and compound keys in SQL-local children; temporary encodings, token arrays and parsed trees during misses; and independently retained application owners. A structural feedback risk is: additional repeated validation motivates another cache family; that family consumes the shared budget; displacement causes old work to recur; pressure motivates another cache or larger budget. This is a source-supported possible mechanism, not a measured causal attribution to every historical revision. Another possible loop is slower preparation increasing the number of overlapping requests at a fixed arrival rate, which increases memory and contention, further slowing preparation. Arrival rate and live-parent count have not been measured, so no numerical concurrency prediction follows.

## Findings and candidate dispositions

### CS1 — Parent scopes pay for compound memo keys that cannot hit

**Confirmed mechanism; qualified optimization; high source confidence.** `credential_guard.py:295–309` builds `_credential_scan_key` whenever a memo exists. That walks the complete eligible input, encodes each spelling to measure UTF-8, creates typed tokens and freezes policy (`108–232`). `RetentionStageMemo.credential` and `state_credentials` explicitly call the producer without retaining the result when the memo itself is a V4 or legacy parent (`continuation_retention_memo.py:863–881`). That producer reconstructs the tree from tokens before scanning (`credential_guard.py:235–278`). The same work occurs in the owned-options route (`331–347`).

In a parent-only scope, tokenization and reconstruction therefore cannot buy a compound-cache hit. The existing category memo can still accelerate a fresh traversal. First candidate: choose direct fresh traversal with `_find_with_credential_text_memo` before constructing compound keys when compound caching is unavailable. Preserve the existing detector fallback, policy, field handling, traversal order and actual category cache. This avoids extending mutable object lifetime or reusing a clearance across SQL cuts. Measure parent versus child invocation frequency before promising a latency reduction. In child scopes, compare the current full compound key against fresh traversal plus category reuse; do not assume the compound cache is profitable merely because it hits.

**R27 implementation follow-up, source review only:** Root implemented this candidate during the review. `RetentionStageMemo.caches_credential_inputs` mirrors the existing parent-versus-child compound retention decision. Both guard routes now choose fresh category-assisted traversal before key creation only for parent scopes with the original detector. The changed-classifier branch remains earlier, and foreign/custom detector routes remain unchanged. Independently inspected hashes are `6010908a61dc7a1e182a940b6e9de1484e03a71570cd4b84a52f05cbb712be95` for the memo and `55cba4b0b576bba41fbcd928fa49cff70839e4a578ba9e3e2e92409a3c588272` for the guard. These supersede the initial hashes only for this follow-up.

Verdict: suitable for the diagnostic run; no lost meaningful detachment identified in the narrow delta. Direct traversal returns only a value-free finding and retains only immutable text/category, while current policy, limits, secret-field/reference handling and finding location are still evaluated. The eligible exact builtin tree path has no await or supplied callback between visits. Generic proxies already fell back to direct scanning, and constructor-owned options have detached backing. Arbitrarily concurrent mutation of a mutable alias is not thereby made atomic: the old token-building walk was also non-atomic. Do not broaden this verdict into a guarantee about all nominal objects or reuse whole mutable values. Child compound caching and fresh SQL boundaries are unchanged. R27 was reported running when this paragraph was written; no timing or native-test result is asserted.

### CS2 — A hit does not mean the expensive input work disappeared

**Confirmed mechanism; qualified optimization; high source confidence.** Every compound lookup pays token construction, UTF-8 encoding and tuple/dataclass hashing before `memo.credential`. Even a category hit is reached only after fresh `utf8_size` in `_find` (`credential_material.py:262–265`, mapping keys at `280–282`). Canonical chunk encoding measures UTF-8 before consulting the proof (`continuation_codec.py:124–143`); a miss measures again in `_private_chunk_canonical_text_bytes`, parses/re-renders, and then the memo compares against another UTF-8 encoding (`175–183`; memo `471–473`). Block-hash miss accounting encodes the complete text again (`memo:614`).

Retaining an exact string's pure UTF-8 size alongside its category or canonical bytes is potentially useful. Reuse the measured number, but still compare it with the current traversal/document limit at every visit. Do not cache a whole traversal-limit outcome without its shape and policy. Avoid adding a separate large cache before examining whether the existing text entry already contains the needed derivation. Python string hash caching helps repeated use of the same object; independently decoded equal strings still need their initial hash and equality comparison. Digest-keying all inputs would also perform a full scan and would add collision/binding obligations; it is not an automatic improvement.

### CS3 — The policy is not a global LRU, and full proofs receive different treatment

**Confirmed policy; performance consequence unmeasured.** Each family moves hits to its own ordered tail. Canonical-verification, block-hash, request and category insertion evict their own family first while the aggregate is full (`memo:571–594`, `622–645`, `713–736`, `835–858`). Old entries in other families can remain while a currently active family repeatedly evicts itself.

Full-proof insertion differs: it first enforces its own budget, then evicts other families under aggregate pressure (`500–523`). This gives full proofs a practical cross-family preference. There is no single recency order, reuse-distance estimate or saved-work-per-byte policy. A global LRU is a candidate, not an established cure; a short scan can also evict expensive hot entries under ordinary LRU. Capture the actual sequence and replay the current policy versus global recency or explicit family shares before choosing. Keep replacement policy independent from semantic admissibility.

### CS4 — The advertised retained-byte number is an accounting budget, not an exact heap cap

**Confirmed accounting mismatch; high confidence.** Full proofs charge twice encoded length plus digest/reference spellings (`memo:483`), block proofs charge UTF-8 strings (`614`), requests charge UTF-8 components (`691–707`), and categories charge UTF-8 plus tuple/entry shallow sizes (`823–826`). This does not uniformly count Python Unicode storage, ordered-dictionary nodes, key objects, integers, allocator overhead or temporary computation. It also charges some shared strings repeatedly. Consequently neither a fixed multiplier nor summing all shallow values establishes actual incremental resident memory.

The supplied prior fixture observation of a roughly 449 kB UTF-8 string with roughly 899 kB Python resident size is plausible input-specific context, not independently measured here. Do not assume every string uses four-byte representation. Distinguish logical cache charge, reachable Python object bytes deduplicated by object identity, incremental allocations, and process RSS. The latter includes unrelated and allocator-retained memory.

Compound `_snapshots`, `_chunks`, `_credentials` and `_states` dictionaries are outside the shared text counter (`memo:294–326`, `371–381`). Their scopes close, but this class has no aggregate byte or entry cap for these families. This is not proof of an unbounded accepted workload: enclosing operation/shape limits may bound them. It does mean the 32 MiB number is not a bound on all memory reachable from a preparation. Measure child peak and temporary peak as separate quantities.

### CS5 — Individual proof eligibility and aggregate capacity are different constraints

**Confirmed behavior; high confidence.** The aggregate constant is now `32 * 1_048_576`, while individual proof retention still compares against `CONTINUATION_PRIVATE_DOCUMENT_MAX_UTF8_BYTES` (`continuation_limits.py:14–21`; memo `492`, `564`, `616`, `691`, `828`). A valid near-1 MiB document cannot enter the full-proof family because that family's charge includes text and encoded bytes. The canonical-only fallback remains live in `verify_private_chunk` (`continuation_codec.py:190–211`). Enlarging aggregate RAM cannot change this eligibility cliff.

Do not delete the canonical-verification family on the assumption that removal of the failed parser integration made the entire family dead. Conversely, do not enlarge the product's document limit to make a cache entry fit. If workload measurements justify changing the per-entry memo policy, give it a separate internal constant and account for its real retained representation. That is distinct from permitting larger persisted documents.

### CS6 — Scope placement intentionally sacrifices compound reuse; text lifecycle is sound in the inspected path

**Confirmed source structure; no runtime clearance.** EARLY opens the parent before source capture (`continuation_checkpoint_early_physical.py:90–123`), and closes it in a `finally` around original preparation finish (`393–398`). The parent context manager closes again on lexical exit; child context managers close their own dictionaries and restore context (`memo:916–954`). Late computations check `_closed` before publication. SQL callable capture transfers only the memo through a fresh Context (`1027–1052`).

`test_continuation_retention_memo.py:480–549` contains meaningful nested-error, close-during-compute and independent-concurrent-scope checks; `860–944` checks that separate SQL children share text while compound proofs are fresh. These bodies were read, not run. The latter currently pins the historical 6 MiB constant at line 934, so adopting the 32 MiB experiment needs an intentional test update and focused verification.

Do not extend compound caches across current SQL boundaries merely to increase hit rate. Instead identify pure sub-results or pass the actual fresh admitted value within the one owner where no callback or mutable alias can intervene. A larger text budget increases each live parent's potential footprint. No global admission/concurrency bound was established in this review.

### CS7 — Repeated local construction is a stronger removal opportunity than caching all its outputs

**Confirmed example; broader reach and timing qualified.** `MaterializedCompleteValue.from_value` canonicalizes, encodes and hashes a local input, then its constructor encodes, validates JSON, canonicalizes and hashes the just-produced text again (`contracts/composer_content.py:311–333`; `_canonical_value:106–114`). No external actor intervenes inside that synchronous sequence. The constructor must still reject independently supplied bad text, and `to_value` must still return detached mutable data. A private admitted construction path can retain the same proof once without creating global identity machinery. Parent review O1/O2 identify additional candidates, but they must be individually traced rather than accepted by citation alone.

The current-evidence change already demonstrates this principle: a fresh initial complete read feeds reconstruction, while the independent final read remains (`continuation_current_evidence.py:60–95`). Preserve that final boundary because policy callbacks run inside the reconstruction. The useful question is which actor or alias can intervene between two checks, not whether two functions have different names.

### CS8 — A separate rooted lifetime defect must not be mistaken for cache churn

**Confirmed EARLY reference graph; timing unproven.** The EARLY global weak-key registry stores `_OriginalEarlySource`, which stores custody (`continuation_checkpoint_early_physical.py:67–87`, `390`). Its finalizers close over `source` through `require_admission` (`516–568`). This corroborates data-review D5's EARLY root path when custody retains those callbacks. It concerns completed-owner retention, not the explicitly cleared text dictionaries. Fix the ownership lifecycle independently; no evidence here attributes the present preparation delay to garbage collection or that leak. END and all terminal paths were not independently re-audited in this review.

## Minimum measurement and intervention plan

1. **Remove demonstrably unrewarded parent compound-key work first, if Root admits the patch.** Count parent-only versus child calls and key bytes once. Validate identical secret-field/env-reference, location, shape-limit, corruption and changed-input behavior; then run the unchanged original case. Expected benefit is plausible but currently unmeasured. This is the narrowest subtraction candidate and does not need wider cache scope.
2. **Observe the current five families once, with bounded accounting and known controls.** Extend the existing four-family observer to category calls, all five occupancy counters and closure. Record admissions rejected by per-entry size separately from eviction misses; distinguish first-seen from seen-but-unretained. Record input bytes and elapsed key construction separately from classifier/producer work, and parent/child scope. Do not print private text. A single bounded synthetic control should exercise hit, changed-input miss, over-entry refusal, cross-family pressure and close-during-miss. Deliberately omit one family's charge in the control to establish that the aggregate check detects it. Observe current source identity and report observer overhead; use a separate inclusive-only run for latency.
3. **Measure representation and working set only as far as needed for the decision.** Current `EndTextMemoObservation` names only four families (`tests/helpers/continuation_end_profile.py:32,62–75`) and estimates identities via Python hashes (`84–85`, `188–196`). It cannot qualify current five-family occupancy. Prefer exact per-run ordinals assigned from the actual exact-key table for replay; keep that instrumentation bounded and report drops. Do not preserve payloads merely to improve accounting. Capture family weights and reuse distances, plus parent/child peak reachable bytes at selected boundaries. The old 8,162,015-byte estimate is neither a proven current minimum nor an exact heap footprint.
4. **Choose the next change from the remaining cost.** If eviction recomputation dominates, compare replacement policies and a small capacity sweep with fixed document/history limits. If hits dominate but time remains high, remove key construction and duplicate local admission, or carry pure size/category/encoding within the existing owner. If misses are per-entry refusals, more aggregate RAM is irrelevant. If fresh SQL/current evidence dominates, narrow repeated work only within a proven transaction/ownership interval, preserving independent reads and accounting.
5. **Qualify memory at actual concurrency before treating a RAM budget as deployable.** Measure the peak number and age of live parents and escaped workers, normal/failure closure, and total memory at representative concurrency. A 24-core host is not a 24-parent bound. The dispatch's 61 GiB total / 43 GiB available supports a controlled single-action experiment, not an unrestricted production concurrency claim. A real overload response or existing admission limit must own aggregate demand if demand is otherwise unconstrained.

Avoid a broad new proof framework. The observer needs enough controlled evidence to choose between repeated work, replacement pressure and admission cliffs. The timing test itself remains the acceptance instrument; profile sample counts, trace elapsed sums and observer launcher status cannot replace its terminal result.

## Risk Assessment

**Implementation Risk: Medium. Reversibility: Easy for internal RAM/replacement changes; Moderate for admission-path subtraction.** The main correctness risk is accidentally reusing policy, mutable values or current authority instead of a pure derivation. The main performance risk is replacing useful compound hits with repeated traversal in children, or solving one family's churn by displacing another. The memory risk is interpreting UTF-8 charge as resident bytes and multiplying per-parent allocation by an unmeasured concurrency. Preserve exact boundary/corruption/alias controls and compare terminal timing on the unchanged case.
