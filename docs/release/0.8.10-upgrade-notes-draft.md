## Composer authoring and boot descriptions

Composer uses the common provider tool loop for empty and existing graphs. The
old planner-only `emit_pipeline_proposal` route and escape hatch are removed;
the provider authors complete replacements through `set_pipeline`. Its web
wire schema now advertises the runtime node, connection and sink naming rules.
Both supported short and full pending interpretation-review forms remain
accepted; resolver-owned resolved metadata remains refused.

The `composer_tool_contract_resolved` event no longer includes
`hatch_transport`, `hatch_dialect` or `hatch_diagnostic`. Update consumers of
those removed fields. The common loop's existing `planner_*` resolution fields
and loop tool counts remain.

Boot request descriptions now cover `loop_tools` and `advisor`. The retired
`planner_tools` and `hatch_terminal` descriptions and the hatch's nonfatal
configuration-rejection exception are removed; configuration rejections on
either retained surface are fatal. Sessionless boot still skips physical
provider calls because it has no durable guard-audit custody, so those
descriptions do not qualify a remote provider. The loop description's 16-token
cap does not exercise Anthropic/Bedrock extended thinking; removing the larger
planner description removes that former description coverage.

The configured legacy planner repair budget is still checked by the common
provider-cost policy for an initially empty logical request. The supported
value remains `2`; removing the old route does not make other values valid.

## Public attachment-root authoring and reapplication

The provider can author a complete replacement with one default `source` or
named `sources`, selecting `blob_id` or ordered `blob_ids` for each root. The
provider must choose the source plugin explicitly. Plural selection requires
`plugin:"blob_rows"`, even for a one-member list; the server does not infer a
plugin or invent a root or route to make the request pass. The public list
contains 1–512 IDs. The separate private/plugin storage limit of 1,000 entries
does not enlarge that public request bound. Duplicate identity or content
within one list is refused; separate roots can reuse an attachment. Plural
selection retains original user-upload provenance rather than admitting
LLM-authored document content.

Binding uses current session-owned READY blob records; the original-upload
restriction above belongs to plural selection, while scalar selection retains
its supported authored/review flows. Every selected root must be admitted
before an applied replacement publishes, so a refusal leaves the previous
candidate intact and an applied replacement advances the graph version once.
With explicit approval, `APPROVAL_REQUIRED` is a proposal and leaves the saved
graph unchanged until accepted. Reusing persisted private plural authority
revalidates every member against its current user/session ownership and exact
stored metadata facts.
It neither refreshes those facts silently nor reads file bytes to establish
byte integrity.

`get_pipeline_state(component="set_pipeline_arguments")` projects scalar IDs
or ordered plural IDs, ordinary/review options and public output names while
stripping matching private custody. Public reapplication uses the strict
authoring contract and resolves current metadata; the projection grants no
private reviewed authority or prior inspection clearance. Malformed or
contradictory custody is refused rather than dropped, and raw and owned
response paths enforce the public shape. The full canonical saved-review echo
keeps its existing contract.

Use the maintained [attachment selection and projection reference](../reference/composer-tools.md#set_pipeline)
for selector/null/ambiguity channels and the
[versioned call contracts](../reference/composer-tool-contracts-0.8.10.md)
for the separate source and receiving boundaries. These changes preserve
provider-authored structure and the ordinary backend for tutorial sessions;
they do not establish live-provider delivery or completion of the full scripted
tutorial.

## Session schema epoch 78 → 79 (hard cut)

0.8.10 moves the Sessions schema from epoch 78 to **79**. Continuation adds seven
tables and alters `composer_operations`. The Landscape schema stays at
**epoch 50**.

This is a hard cut. 0.8.10 does not open, migrate, restamp or repair an
epoch-78 Sessions store:

- **An existing epoch-78 store is refused.** Its table set differs from the
  epoch-79 model, so the schema probe classifies it `STALE`
  (`src/elspeth/web/schema_probe.py`, `probe_session_schema`). Schema
  initialization reports the drift and refuses to convert it
  (`init_session_schema` → `explain_non_current_schema`). `doctor` therefore
  fails, and startup refuses the store. "`STALE` is a stop, not a migration"
  ([ACA cold install](../runbooks/azure-container-apps-cold-install.md) §6; the
  ECS operating skill, rule 5).
- **An empty target is classified `MISSING`.** `doctor … --init-schema` creates
  and stamps it at epoch 79. Only an object-free, unstamped target is eligible
  ([session store compatibility runbook](../runbooks/staging-session-db-recreation.md),
  "Current Cutover").
- **The existing store is preserved.** Upgrading means allocating a **new**
  Sessions database for 0.8.10. Leave the epoch-78 database in place, unchanged.
  Its sessions, drafts and identity rows are not readable by 0.8.10.
- **Landscape is not cut.** The existing epoch-50 Landscape database may be
  reused only if `doctor` reports `landscape_schema` OK. If it does not, stop and
  allocate a new Landscape database as well. Do not repair the old one.
- **Users must be admitted again.** Identities live in the Sessions store, so
  the new store starts with no administrator. Every user lands `pending` until an
  administrator activates them. Bootstrap the first administrator as described
  per platform below.

Blob and payload storage (EFS on ECS, Azure Files on ACA) holds no database and
is not cut. Objects referenced only by the preserved epoch-78 store stay on disk
and are not reachable from 0.8.10.

## Composition-state pipeline metadata

Composition-state pipeline metadata is required in 0.8.10. Callers constructing `CompositionStateData` must supply `metadata_` as a keyword argument; omission and explicit `None` are refused. Stored-record construction, state reconstruction and the state-writing boundaries require metadata to be present, and historical P4 checkpoint payloads require a metadata dictionary. There is no new production default or automatic metadata backfill. Genuinely nullable fields, including the separate operational `composer_meta` and nullable graph columns, retain their own contracts. The `composition_states.metadata_` JSON column is now SQL `NOT NULL`. SQL NULL and JSON null are distinct: the database constraint excludes SQL NULL, while a metadata value decoded as `None`, including a versioned envelope whose `data` is null, is refused by the record guard. This presence rule is not comprehensive validation of every arbitrary non-None metadata value. The session schema epoch remains **79**. An earlier epoch-79 store whose metadata column is still declared nullable fails schema-shape validation without being changed, even if its current rows contain metadata; the epoch number alone does not establish compatibility. This does not mean every epoch-79 store is invalid or that historical metadata-less checkpoints never existed. Preserve an incompatible store and prior access to it, and use the established ECS/ACA fresh-session-store procedure for the new deployment. T5e does not migrate, restamp or reset existing stores, automatically advance the epoch to 80, or modify the Landscape store or blob storage. T5f's terminal-run database CHECKs and the `_StrictResponse` audit are separate work and are not included in this metadata change.

## AWS ECS: provision a new session database

The tracked Terraform package is
[`deploy/aws-ecs/terraform`](../../deploy/aws-ecs/terraform/README.md). The
procedure changes the **Sessions database name**, never the existing database.

1. **Schedule downtime and stop the service.** The service already deploys with
   zero overlap (`deployment_minimum_healthy_percent = 0`,
   `deployment_maximum_percent = 100`, `modules/scenario/ecs.tf:583–584`).
   - Set desired count to `0` and wait for zero running tasks.
   - Record the current service task definition as `PREVIOUS_TASK_DEFINITION`
     and the current `session_database_name`.

   The Terraform step below rewrites the runtime secret's `session_url`. Any
   0.8.9 task started after that would read the new, empty database and refuse it.

2. **Set the new inputs.** In the scenario's tfvars, set:
   - `session_database_name` to a new identifier, for example
     `elspeth_session_v079`. It must be a safe PostgreSQL identifier distinct from
     `landscape_database_name` (`modules/scenario/variables.tf:349–368`). Keep
     `landscape_database_name` unchanged;
   - `candidate_image` (with its candidate SHA inputs) to the 0.8.10 ECR digest.

3. **Plan, review, apply.** Use the same identity checks and plan/show/apply
   sequence as
   [cold install §7](../runbooks/aws-ecs-cold-install.md#7-plan-and-create-the-stack).
   Expected changes:
   - new versions of the runtime and schema Secrets Manager secrets. Both
     `session_url` values name the new database (`storage_identity.tf:97,119`);
   - a new `database_bootstrap` task definition. Its environment carries
     `ELSPETH_DB_SESSION_DATABASE`, and its ARN is a `triggers_replace` input of
     `terraform_data.database_bootstrap` (`database_bootstrap.tf:149,183–189`).
     The bootstrap re-runs and issues `CREATE DATABASE … OWNER <schema role>`
     only for a database that does not exist, then re-applies grants and default
     privileges;
   - new candidate web, schema-init doctor and runtime doctor task definitions.

   **Stop** if the plan replaces or destroys `aws_rds_cluster` or an
   `aws_rds_cluster_instance`, or touches the old database in any other way.

4. **Initialize the new schema as the schema owner.** EFS directories already
   exist on an installed stack, so `provision-storage` is not needed. Run the
   `schema_init_doctor` task, which runs `doctor aws-ecs --init-schema --json`
   with the schema-owner secrets (`ecs.tf:190–203`). Use `run_doctor_task` and the
   Terraform outputs exactly as in
   [cold install §8](../runbooks/aws-ecs-cold-install.md#8-initialize-schemas-then-prove-runtime-credentials).
   Require exit `0`:
   - `session_schema` must be OK. The new database was `MISSING` and is now
     epoch 79;
   - `landscape_schema` must be OK. If it is not, the existing Landscape store is
     not compatible: stop, and repeat steps 2–4 with a new
     `landscape_database_name` as well.

5. **Prove runtime credentials.** Run the `runtime_doctor` task, which runs
   `doctor aws-ecs --json` with the runtime secrets. Require exit `0`, with
   `rds_trust_root`, `session_tls`, `landscape_tls`, `session_schema` and
   `landscape_schema` green.

6. **Enable the service.** Print and run
   `terraform output -raw service_enable_command`. It updates the service to the
   Terraform `candidate_web` task definition with desired count 1. The service
   ignores Terraform changes to `task_definition`, so this explicit command is
   the deployment (`ecs.tf:615`). If the live service ran a hand-registered
   revision with settings that are not in tfvars, reconcile them into tfvars
   before step 3. Then verify the rollout and probes as in
   [cold install §9](../runbooks/aws-ecs-cold-install.md#9-enable-and-verify-the-service).

7. **Bootstrap the first administrator.** The new Sessions store has none, and
   this package does not export the SSO admin-seed setting. Run the command
   inside the running web task, whose environment carries the runtime
   `ELSPETH_WEB__SESSION_DB_URL` and `ELSPETH_WEB__LANDSCAPE_URL`:

   ```bash
   aws ecs execute-command --cluster "$ECS_CLUSTER" --task "$TASK_ARN" \
     --container elspeth-web --interactive \
     --command "elspeth composer users bootstrap-admin oidc <cognito-sub> --note 'first administrator after 0.8.10 epoch-79 cut'"
   ```

   `<cognito-sub>` is the user's `sub` claim
   ([full ECS runbook](../runbooks/aws-ecs-deployment.md), "first administrator").
   ECS Exec is enabled on the service (`ecs.tf:581`). It needs the Session
   Manager plugin, and the task's command agent must be `RUNNING`. Then activate
   other users through the administrator UI or API. `bootstrap-admin` grants no
   workload role.

**Rollback.** 0.8.9 cannot read the epoch-79 store. To return to 0.8.9:
- restore the previous `session_database_name` **and** the previous
  `candidate_image`/SHA inputs, then apply. The preserved epoch-78 database is
  unchanged. Without the image revert, the doctor task definitions keep the
  0.8.10 image;
- redeploy `PREVIOUS_TASK_DEFINITION`.

Sessions created on 0.8.10 are not visible to 0.8.9. 0.8.9's compatibility with
Landscape rows written by 0.8.10 has not been established, so prefer
fix-forward. This matches the ECS skill's rule that a schema-changing candidate
is not assumed rollback-safe.

## Azure Container Apps: new stores only

The ACA deployment hold stays in force. The current candidate supports only
fresh stores, and an existing-store transition is unsupported
([existing-service runbook](../runbooks/azure-container-apps-existing-service-redeploy.md),
"Temporary deployment hold"):

- **Do not** roll 0.8.10 onto an existing ACA app or point it at an existing
  deployment's databases. Leave the existing deployment and all its stores
  unchanged.
- Install 0.8.10 as a **separate, genuinely fresh deployment** with
  [ACA cold install](../runbooks/azure-container-apps-cold-install.md), from step 1,
  with fresh Sessions and Landscape databases. Old and new deployments must not
  share either store
  ([session store compatibility runbook](../runbooks/staging-session-db-recreation.md)).

The Job order is fixed. Each step is a stop condition, using
`deploy/azure-container-apps/scripts/run-job.sh`:

1. Deploy `environment.bicep`. Publish the 0.8.10 image by digest. Store
   secrets in Key Vault. Resolve the workload parameters and create the Jobs with
   `deployWebApp=false` (cold install §1–§4).
2. Run `provision-storage` (§5).
3. Run `doctor-schema-init` (`workload.bicep:539–541`). It runs
   `elspeth doctor deployment --init-schema --json` with the schema-owner
   identity and URLs from the dedicated vault. Both schemas must be `MISSING`
   and are created: Sessions at epoch 79, Landscape at epoch 50. `STALE` is a
   stop: the targets are not fresh (§6).
4. Run `doctor-runtime` (`workload.bicep:579–581`). It runs
   `elspeth doctor deployment --json` with the runtime URLs. Every check must be
   OK, including `session_tls` and `landscape_tls` (§7).
5. Deploy `workload.bicep` in the production shape, then prove the rollout and
   probes (§8–§9).
6. Admit the first administrator. Either list their exact IdP subject in
   `ELSPETH_WEB__SSO_ADMIN_SUBJECTS`, which seeds at first login while no active
   human administrator exists, or run `elspeth composer users bootstrap-admin
   PROVIDER SUBJECT --username USERNAME --note TEXT` in a configured runtime
   container after schema initialization (cold install §4,
   "first administrator"). Neither grants a workload role.

## Graceful shutdown with non-snapshot sources

Programmatic `Orchestrator.run()` calls that omit `settings` or pass
`settings=None` now withhold executable processing from an undecided source row
ingested after shutdown was requested. Previously those calls could process
that row; CLI calls and calls with settings already withheld processing but
recorded a row failure. If the interrupted non-snapshot source makes the run
non-resumable, finalization records the unstarted row as undecided
`(outcome=NULL, path=ABANDONED, completed=False)`, with its source payload
retained for inspection. Resume is refused with `IncompleteSourceResumeError`;
start a fresh run. Already-started claims and source-complete resumable work
retain their existing contracts
([ADR-038](../architecture/adr/038-non-terminal-abandoned-path.md)).

## Other upgrade notes from landed units

These items come from units already landed on `release/0.8.10-assembly`. Each
is also recorded in `CHANGELOG.md` under `## 0.8.10 - 2026-10-31`.

### Engine: changed `exception_type` values and conservative replay

- **Retry shutdown has its own exception type.** Framework retry-shutdown
  diagnostics now use `RetryShutdownRequestedError`, an `InterruptedError`
  subtype. Persisted pre-attempt `exception_type` values change from
  `InterruptedError` to `RetryShutdownRequestedError`; the shutdown reason and
  message are unchanged. Audit queries or dashboards that match the old value
  must also match the new one. A plugin raising an ordinary
  `InterruptedError` keeps its existing failure behaviour.
- **Replay stays conservative; history is not rewritten.**
  - Previously recorded Azure/Bedrock blank-text `SUCCESS` calls keep their
    recorded outcome when copied, then fail text admission.
  - Newly recorded unusable SDK `ERROR` responses refuse replay instead of
    dispatching a provider request.
  - Gateway replay of historical null or blank responses, or of newly rejected
    required usage, can refuse with `AuditIntegrityError` where the corrected
    result differs from the recorded call.
- **Some Python 3.12 lint identities need reinspection.** Existing Python 3.13
  AST identities stay compatible with the canonical form. Older Python 3.12
  identities need reinspection where they differ, and moved lint bindings need
  operator review. Signatures are not refreshed (signing is suspended).

### Composer: `composition_content_hash` and mixed-version probes

- **The key is always present.** `/state` responses carry a required
  `composition_content_hash`, which is null when the state has no metadata
  (`web/sessions/schemas.py:383`; see
  [Composer graph checksum](../reference/composer-graph-checksum.md)). Clients
  that enforce a closed response shape must admit it.
- **Mixed versions during a rollout or an acceptance run.** The ACA acceptance
  probe now reads only the state identity from `/state`, so a 0.8.10 probe
  accepts a 0.8.9 server's body (no key) and a 0.8.10 body (a non-null hash).
  Other strict readers of `/state` across that boundary need the same
  treatment.
- **New refusal codes.** `complete_value_unavailable` and
  `complete_value_unsupported` report a complete-value reference that cannot be
  resolved, or a value outside the supported size envelope (from the
  PromptShield bounded-view change).

### Composer worker: committed terminal handoff

The worker retains the actual nominal terminal receipt returned by the owned
turn before timeout and watcher cleanup can fail. A later cleanup fault or
cancellation therefore keeps the receipt available to the existing exact
running-authority and database-readback path instead of losing the known
committed return. Existing uncertain-completion refusals remain in force. The
original late fault and its cause remain observable, and required-work checks
are not bypassed or completed synthetically. This is the normal-return/late-cleanup
handoff repair, not a claim that every recovery or shutdown path is qualified.

### Composer MCP server (#327): safe names and argument evidence

The MCP saved-content and argument-admission repairs use the existing
credential-material refusal rather than adding a new refusal vocabulary.
Operator-visible behaviour:
- **A failed `load_session` keeps the previous diff baseline.**
- **Saved session content is admitted for credential material.** This happens
  before `load_session` adopts it or `list_sessions` returns it, through the
  existing credential-material refusal. Listing is admitted per entry.
- **Unregistered caller names have a safe identity.** Registered tool names
  remain unchanged; other names are represented by a SHA-256 identity in the
  audit, and unknown-tool errors do not echo the caller's name. The SDK's
  cache-miss and unlisted-tool diagnostic records replace only their tool-name
  argument with that same identity. Records and unrelated SDK logging remain
  intact; this is not a general log scrubber or suppression policy.
- **Argument evidence is admitted as a complete pair.** Captured canonical
  input and its hash remain private until credential admission succeeds.
  Credential refusal retains priority over a capture defect, and refused
  arguments are replaced by a value-free `{"_arguments_withheld": …}` stand-in.
  Unexpected capture or credential-admission faults that propagate before
  input evidence is admitted, and faults while preparing safe refusal
  evidence, leave the audit with the complete matching
  `{"_arguments_unavailable": "evidence_not_completed"}` evidence pair.
  Such owned faults record `PLUGIN_CRASH` once and propagate with their
  original failure/context; they are not successful calls or ordinary argument
  refusals. A later tool failure retains the already admitted canonical input
  and its hash. Audit-sidecar readers must accept the withheld and unavailable
  shapes without treating either as caller content or clearance.

The [versioned MCP outcome contract](../reference/composer-tool-contracts-0.8.10.md#tc-020--local-mcp-call-outcomes-preserve-safe-evidence)
records the bounded evidence separately from final joined acceptance and any
external-host transport guarantee.

### Judge and signing: `codex-cli` refuses

- **The Codex judge transport is disabled.**
  `elspeth-lints … --judge-transport codex-cli` now refuses with "the codex-cli
  judge transport is disabled"; use `--judge-transport agent`.
  - The MCP `stage_preview` tool and the sign command it renders already use
    `agent`.
  - Every judge call needs the installed judge supervisor and refuses without
    it.
- **Key-bearing verbs refuse from an editable checkout.** They exit 2 with
  `Operator runtime unavailable`.
- **Signing is suspended** until the protected runtime is installed after the
  on-prem migration
  ([ADR-052](../architecture/adr/052-key-bearing-lint-operations-run-only-in-a-protected-operator-runtime.md)).
  The signer findings S1–S3 stay OPEN until then.

## Composer V2 attachment inspection limit

`composer_attachment_inspection_max_bytes` configures the complete-original
inspection limit for each fresh current V2 attachment read, including reads
that return only a page through `get_blob_content`. The default is 262,144
bytes. Supported values are integers from 1 through 262,144; operators can
tighten the existing ceiling with
`ELSPETH_WEB__COMPOSER_ATTACHMENT_INSPECTION_MAX_BYTES`. Invalid types and
out-of-range values refuse startup configuration; the value is never clamped.
An original whose recorded size exceeds the configured limit is refused
before its file is opened. UTF-8 bytes determine the limit.

This setting controls inspection of the complete original. The independent
response, credential, provider and retention budgets still apply, so an
original admitted for inspection can still have its complete serialized
response refused. V1 and direct-tool attachment paths keep their existing
limits. Continuation remains default-off, and requests without
`Composer-Operation-Version` still use V1.

Each fresh V2 read uses the current setting and current environment-reference
names. Its retained inspection fingerprint identifies that inspection's
policy. Earlier receipts remain historical data when the setting changes;
they do not clear a later read under the current policy. This addition changes
no persisted timing-policy shape or database format and requires no migration, reset or
replay of earlier inspections.
