# Independent evaluation: Continuation retained-storage policy

Reviewer: Astra, independent read-only review for John via Root. No cap is approved by this report. No tests, imports of project code, benchmarks, database/provider access, Git mutations or source edits were performed. Source and immutable Git blobs were read; the implementation proposal was treated as background rather than authority.

**Recommendation: implement and verify a configurable, immutable per-logical-operation admission policy, but do not select 128 MiB—or a different numeric production default—from the evidence currently available.** Preserve the existing 1 MiB private-document and evidence/recorder-pair policies. If aggregate enforcement is required for every new operation before release, require an explicit operator-selected limit until the bounded workload measurements below support a default. An omitted value must not silently mean approved unlimited storage or an implicit 128 MiB.

## What must be bounded

The resource is a logical operation's retained history, not its latest selected root and not a segment. `sessions/continuation.py::put_chunk` preserves immutable `(session_id, operation_id, chunk_key)` rows. Reusing an existing identical key adds no payload; different keys each occupy a row even when their bytes match. Collision validation checks actual bytes, digest, recorded length and codec before reuse. `append_complete_snapshot` writes event payload keys and a uniquely keyed root snapshot in addition to private documents retained elsewhere. Old prefixes remain stored.

A sound payload measure at commit t is:

    O(t) = sum(actual payload bytes for every retained chunk key of this logical operation)
    O(next) = O(t) + sum(bytes of genuinely new keys in the transaction)

This includes historical roots/events/private prefixes, including rows outside the current selected dependency closure. It does not include every byte in checkpoints/events/effects/provider-ordinal/attempt tables, their indexes, chat audit rows, blob files, database pages, WAL or backups. Calling this “total storage” without that qualification would be incorrect.

A payload-only cap also does not bound row/index overhead by itself: the generic put_chunk contract accepts exact bytes without a positive minimum length. Many distinct tiny rows can have very low charged payload and substantial key/index/transaction overhead. Actual production transitions have nonzero structures, but that is not an enforced universal row bound. Record row count and key/metadata costs alongside payload; do not claim the new payload ceiling alone solves physical disk exhaustion. A separate row/transition ceiling or a conservative per-row accounting charge is a possible further policy, requiring its own scope and measurement—not an excuse to silently change byte semantics.

`continuation_handoff.roll_slice_for_successor` resets only technical composition/discovery slice counters. Request totals and logical identity survive. Aggregate usage must likewise survive successor sequences, recovery generations, retries, cancellation and restart. A same-key retry is zero additional payload only after exact immutable equality; a new snapshot/event key costs its actual bytes. Failed SQL transactions must roll back both storage and any accounting change.

## Why local codec bounds cannot determine the operation default

Current `continuation_limits.py` sets both private-document and combined evidence/recorder size to 1,048,576 UTF-8 bytes. The pair is a SUM bound, not two independently spendable MiB. An individually valid retained provider context near 1 MiB may therefore fail once recorder wrappers/evidence are included. Existing contract is bounded refusal, not a promise that every allowed input completes.

`continuation_audit_buffer.py` v2 stores a block dictionary plus a complete recorder projection. Deduplication is within that document. Every changed recorder prefix may be a new SQL chunk. Even if one document grows linearly with newly distinct message content, retaining each successive prefix adds a sum of prefix sizes; a simple linear prefix-growth scenario has quadratic cumulative storage. Stable shared prefixes, changing Advisor tools/prompts, many short messages and differing PRIMARY contexts have different curves. There is no justified “largest prompt plus fixed header per call” estimate.

Every recorder channel matters: invocations, llm_calls, planner_attempts, withheld_replies, visible_tool_events, private_candidates, private_authorings and drain cursors. TITLE's initialization/response storage must be included separately from the Compose recorder. The codec preserves non-capture-format retained contexts verbatim, so their nested-string escaping costs must be measured as stored canonical UTF-8. Unsupported/unavailable contexts have explicit receipts; changing their disposition or dropping original content to fit a cap is not permitted.

The actual `ContinuationProviderCostPolicy` supports only `not_applicable` for lifecycle 2. Compose totals have lower bounds but no useful request-wide upper bound in that model. Neither a proposed 75-call policy nor a count of codec variants bounds actual history. A future paid-call cap still would not independently bound recovery attempts, no-SDK transitions, stored roots or every audit channel.

Decode memory is another independent dimension. `_restore_request` reconstructs each call's full canonical request from shared blocks, and decode subsequently serializes/validates the reconstructed recorder and re-encodes it. Shared stored blocks can expand repeatedly in memory; a compact recorder limit is not a decoded-heap limit. Encoding also constructs projections before final private-document enforcement. Increasing the document bound would directly change these risks, whereas increasing only the operation cap mostly changes historical retention and SQL accounting work. Keep those decisions separate.

## Fundamental invariants versus policy choices

Necessary safety properties:

- Exact positive integer configuration, explicit policy version/meaning, immutable capture at admission, and no per-segment reset. Reject bool, nonfinite/nonnumeric/negative values and unsupported policy shapes at the appropriate boundary.
- Accounting and storage admission in the SAME original fenced transaction, serialized with competing writers and the selected-root CAS. Compare against actual stored lengths; don't trust corrupt byte_length metadata. A cached counter needs independently verified correspondence and rollback semantics.
- Validate an existing immutable key before zero-delta treatment. Validate complete source/owner/link/credential/Unicode/codec integrity before classifying ordinary fresh size overflow. Invalid owned data must not become a convenient user-capacity error.
- Saturating size measurement must bound allocation/work without skipping semantic validation or masking original errors. Fresh valid overflow is a declared unsupported-capacity outcome; corrupt persisted accounting or codec remains integrity refusal.
- Preserve paid-effect custody. A cap-hit cannot erase the original native exception, claim a result/audit was retained when it was not, replay paid work or silently start a new logical budget. Existing required-finish/error grouping must retain the actual original objects and secondary retention failure.
- Enough capacity must remain for the allowed owed retention/terminal path BEFORE irreversible physical work is admitted. Exact preflight of a known transaction is straightforward; reserving for an unknown provider/tool result requires an actual enforced upper bound plus its whole tail. The current 1 MiB pair alone does not prove that tail bound because roots, extra documents and other rows remain. If a bounded reservation cannot be established, refuse before physical work or explicitly keep qualification open; do not promise that a post-effect cap check guarantees complete audit retention.
- Preserve current stored-data refusal semantics and original admitted policies. Extending the frozen v1 policy shape requires a new policy version or an equally explicit existing-contract mechanism. Do not retrofit old roots with a new smaller allowance or delete history to make them conform.

Policy choices requiring workload/host evidence: the operation limit, row/transition overhead allowance, emergency-retention reservation, and any enlarged document/pair or decode bound. Cryptographic digest length and exact-identity/CAS checks are not discretionary performance caps.

## Alternatives and sensitivity

| Alternative | Benefit | Cost / reason not sufficient alone |
|---|---|---|
| Keep only current document/pair limits | No new admission compatibility change | No aggregate historical storage bound; cannot claim aggregate protection |
| Explicit configured operation cap, no default yet | Implementable and testable without inventing capacity evidence | Operator must size it; new admissions must fail clearly if policy requires a value |
| Smaller candidate such as 32 or 64 MiB | Lower maximum retained payload per operation | May reject legitimate multi-stage histories; not justified merely because local documents fit |
| 128 MiB candidate | More room for retained histories | No source-derived completion guarantee or measured justification; larger disk/WAL/accounting exposure |
| 256 MiB or larger candidate | Reduces some history-size refusals | Does not improve local 1 MiB failures; amplifies storage exposure and may prolong pathological work |

These numbers are comparison points for a controlled sensitivity sweep, not proposed defaults. For illustration only, 1,000 fully occupied retained operations would contain 31.25 GiB at 32 MiB each, 125 GiB at 128 MiB each, or 250 GiB at 256 MiB each, BEFORE indexes/WAL/other tables. This is arithmetic, not a forecast of normal usage. Retention lifetime and admitted operation volume dominate fleet disk use; worker concurrency bounds simultaneous execution, not accumulated completed history.

For an operator decision use measured amplification and retention assumptions:

    safe payload allowance <= available durable storage budget /
                              (simultaneously retained operations × measured physical amplification)

Reserve explicit disk headroom for active WAL, checkpoints, other products and backups rather than spending total filesystem free bytes. For memory, measure concurrent live capture/restore peaks and account for workers plus HTTP/process overhead; don't divide current free RAM by the encoded operation cap. Current workstation capacity is not a deployment sizing contract.

Identity/container/session blob quota formulas in `coordination/quota_authority.py` count blobs and excess output reservations. They do not count Continuation chunk history. Preserve their configuration and refusal precedence; do not treat those quotas as an existing reserve for this new policy, nor claim that the aggregate operation cap enforces a global retained-history disk quota.

## Other relevant numeric choices in this scope

Immutable comparison with common branch base `8cc2d5cfc0f591c1daaef3c22f0f83c236c67628` found `continuation_settings.py`, `continuation_limits.py` and `bounded_json.py` unchanged. `continuation_controls.py` changes its applicability description, not its 500-byte notes bound. `continuation_policy_settings.py` removes the enabled/None branch, making policy mandatory. These are not newly introduced numeric constants in the integration, but their newly universal applicability deserves workload qualification.

- 1 MiB private-document/pair and provider-context limits; JSON depth64/items10000/leaf65536/aggregate-text limits: retain current preserve/refuse behavior. Raising only one is incoherent and could move a failure to a different boundary. None is a derivation of 128 MiB.
- 500 UTF-8 byte continuation notes: small bounded model hint, not a progress certificate or storage reserve. No new numeric change found; do not expand its semantics to carry missing history.
- Segment nominal420 s, watermark120 s, quantum180 s, reserve25 s; primary physical240 s, title30 s, local read10 s/session-SQL5 s/blob and external30 s; preparation5 s, quota10 s, retention5 s and guard timeout+5 s. These are operational allowances, not universal resource guarantees. `size_segment` can exceed nominal to fit the complete next action; 420 s is not a hard request-runtime ceiling. The new aggregate-accounting workload must fit relevant SQL/retention allowances, especially near its limit. The comment citing historical 1.45/2.7 s PostgreSQL retention is not a current measurement of aggregate-history accounting or recorder v2 restoration.
- One-day stage/segment settings ceilings are conservative policy limits; finiteness/representable derived deadlines are necessary, but 86,400 is not mathematically the only representable value. No numeric change was found, so no unrelated timeout redesign is recommended.
- Shutdown allowance validation is now unconditional alongside Continuation. Larger retained histories or slower aggregate checks must not be assumed to fit the existing drain/reserve merely because a size cap passes.

Any proposed new aggregate-byte default, row surcharge/ceiling, reserved tail size, prospective-recorder cap or maximum configuration value requires the same explicit policy/evidence separation. I did not find a newly installed aggregate numeric cap in the inspected source. This was a bounded review of the relevant Continuation owners, not a census of every constant in 0.8.10.

## Root-owned bounded measurement plan

No new harness or real paid provider is needed for the first pass. Extend the actual retained-source tests with deterministic provider responses and real write/restore owners. Store test databases only in the assigned project-local pytest area; notes/results may go to this lane. Root must bind the frozen source, own host/test admission and record terminal exit/cleanup. Suggested sequence:

1. **Control accounting before sizing.** Use exact tiny explicit limits. Read the actual operation's chunk rows via `composer_continuation_chunks_table` filtered by session/operation. On SQLite use LENGTH(payload); on PostgreSQL use OCTET_LENGTH(payload). Reconcile actual lengths per row with recorded byte_length, and separately count chunk/checkpoint/event/effect/attempt rows. Establish a positive new-key delta, identical-key zero delta, same bytes under different keys charged twice, collision refusal, failed-transaction rollback, and actual predecessor/successor no-reset. Plant latest-root-only accounting and metadata-understatement mutants and require failure. Do not rely on a counter checking its own sum.
2. **Codec matrix.** Reuse `tests/unit/web/composer/test_continuation_audit_buffer_blocks.py::_calls/_snapshot` and actual `encode_recorder_snapshot`/`decode_recorder_snapshot`. Compare stable shared prefix, distinct message content, changing tool lists/roles, many short repeated messages, verbatim non-capture fallback, escaped/control/multibyte text, unavailable receipts and all recorder channels. Step through small histories and then stop at actual current document/pair refusal. Record encoded bytes, decoded request text bytes, peak RSS/allocation and encode/decode time. Treat this as codec evidence, not operation evidence.
3. **Real complete-history matrix.** Extend `tests/unit/web/sessions/test_continuation_runtime_provider_history.py`: `prepared_runtime`, `publish`, `append_actual_native_and_capture`, `select_next_primary_input`, and its actual fresh-claim/no-new-SDK test. Retain the original paid-input identity rather than manufacturing equal snapshots. Include TITLE/bootstrap, ordinary PRIMARY, Advisor/tool prefix, attachments/application history, failure/P4 and both productive successor and same-sequence recovery. Measure all historical chunk keys after each committed boundary, not only selected chunks. Use existing runtime/phase fixtures for graph-bearing histories; do not counterfeit a live publication with bare generated chunk inserts.
4. **Candidate-policy sensitivity.** Replay the same deterministic successful histories under explicit 32/64/128/256 MiB candidate ceilings without changing local document/pair limits. Also replay exact measured aggregate ceilings and +1 boundaries. Report which policy fails first, semantic stage, whether physical work had occurred, owed tail size and actual retained history at refusal. Do not force histories beyond the existing 1 MiB boundary by weakening it; that would measure a different policy.
5. **Database and concurrency cost.** Start single-worker native SQLite measurements, then established-capacity modest concurrent distinct operations. Use existing serial PostgreSQL wrappers `tests/testcontainer/web/test_continuation_private_document_postgres.py` and `test_continuation_runtime_provider_history_postgres.py` for actual transaction/concurrency qualification. Measure accounting query and retention transaction latency as historical row count and payload grow; test competing same-operation writers and stale CAS. Record database/relation size and WAL deltas separately from payload after controlled commit/checkpoint phases. Do not interpret filesystem size mid-WAL as pure logical data size.
6. **Memory and tail safety.** Measure peak RSS for capture plus cold restore of high-sharing and low-sharing recorder cases, including all live owners, not merely `len(encoded)`. Exercise refusal with an original handler/provider exception, cancellation and Stop during retention. Verify original identities/required receipts, no new SDK call, no false-success disposition and no cleared historical accounting. Use the existing private-document exact-boundary/SQL corruption tests in `tests/unit/web/sessions/test_continuation_private_document.py` unchanged as controls.

Record per-case semantic transitions, actual source identities, bytes by chunk family, distinct keys/rows, peak selected-closure bytes, total retained bytes, candidate cap, refusal reason/stage, physical attempts, peak memory, SQL/capture/restore timing and terminal cleanup. Keep successful workload percentiles separate from adversarial maxima and censored histories that already hit a local limit. A small deterministic matrix characterizes sensitivity; it cannot establish production percentiles. An approved default needs an explicit supported workload and deployment retention/concurrency assumption in addition to these results.

## Decision and confidence

High confidence in the separate resource domains, immutable-history accounting requirement, inactive V2 call-count premise, codec expansion risk and preserved/refused boundary. Moderate confidence in which workloads dominate real storage; no current whole-operation distribution, physical amplification, decoded-memory peak or aggregate-accounting PostgreSQL timing has been measured in this review.

I reject using “128 pair units” or an assumed 75 calls as sufficient justification for 128 MiB. I do not reject 128 MiB as a candidate to measure. The smallest honest next step is exact enforcement with explicit test/operator budgets, controlled whole-history measurements and a separate default decision. Until that decision and tail-safety evidence exist, aggregate capacity remains unqualified.
