The original five-second preparation check remains red. A valid R11 function

## Independent review

Four independent Astra medium reviewers covered databases, systems thinking,
concurrency and Python runtime behavior. The attempted external Claude Fable
reviews did not complete: three returned account-limit HTTP 429 responses; the
fourth was stopped after the shared cap was established. No Claude endorsement
is claimed. All 21 source files supplied to the independent review remained
unchanged during it.

The four reviewers independently identified the same selection defect. The
physical test deliberately rejects substituted messages and model before its
real binder invocation. The observer treated each binder attempt's exit as the
end of the original preparation. Its later scope selector therefore excluded
the legitimate worker. Empty selected-worker and profile lists were failed
measurement, not evidence that the production route did not execute.

The repair records binder attempts separately. Eligibility requires the
original observed clock, its live V4 memo owner and no actual preparation-finish
attempt. An actual successful finish, an actual timeout with an empty stage
set, and a closed parent remain negative controls. Root's R11 calibration
completed with exit 0: **29 passed in 7.48 seconds**, using four workers. The
genuine R11 rerun completed with exit 1 and the original preparation timeout
after 306.57 seconds of whole-test time. Its selected profile is valid, covers
one original witness/worker within the original preparation window, and has no
observer errors, unfinished spans or unpaired submissions. Profiling overhead
is included; this is attribution evidence, not an unprofiled speed measurement.

The selected scope made **36,558 public canonical serializer calls**. RFC
string escaping invoked its replacement callback **15,864,001 times**.
`continuation_tool_batch._read_json_value` accounts for 6,934 serializer calls
and `_dump_owned` for 2,358. The four currentness guards caused four complete
current-input reads; their descendants include six P4 journal reads and 254
calls to `prepared_p4_members`. These are actual function/caller counts, not
counts inferred from source text. They establish a multiplier worth repairing;
they do not establish quadratic scaling.

All production and test file hashes and HEAD were unchanged over R11. The full
working fingerprint changed only because the tracker, handover and this review
were edited. Consequently R11 is diagnostic evidence with stable code inputs,
not a frozen whole-tree acceptance run. The actual warm classifier control also
completed: **1 passed in 95.63 seconds** through its original metadata/P4/driver
owners.

## What the completed observation establishes

R10 recorded one worker at 9.459896 seconds elapsed and 9.447889 seconds native
thread CPU, with a 76.8 microsecond queue interval. Another took 5.560402 seconds
elapsed and 5.550250 seconds CPU. These inclusive observations disfavor blocking
as the dominant cost inside those workers. They do not clear other workers,
production contention or SQL-associated Python processing.

The original preparation reached finish at approximately 31.618 seconds and
raised its original timeout. Cursor observations exclude query construction,
row materialization and transaction setup; a small cursor-time sum cannot clear
the whole persistence path. Nested span times must not be added together.

The same observation recorded 5,588 full-proof requests, 6,391 block-proof
requests and 913 request-proof requests. Recomputations were respectively 169,
1,113 and 39. Those are measured events, not CPU attribution. The 6 MiB transient
memo stayed within budget and closed empty. Its fingerprint-based retained-key
estimate is not exact memory usage or a demonstrated required capacity.
