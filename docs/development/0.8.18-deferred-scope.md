# 0.8.18 deferred scope

**Renumbered 2026-11-23 (naming only).** The hotfix after 0.8.16 is 0.8.17; this line, first
called 0.8.17, is now 0.8.18. Version numbers below use the new names, including for rulings made
before the renumbering; A1 and B10 also give the old name.

This is the durable list of work pushed out of 0.8.16 into 0.8.18, plus the work already queued
for 0.8.18. It exists so that nothing deferred during the 0.8.16 release is lost. Update it as
items land, change status or move release; do not delete an entry without recording why.

Started 2026-11-22 on the 0.8.18 integration branch, cut from the 0.8.16 candidate `3e22cc124`.
The branch moves forward to the green 0.8.16 tip by fast-forward or merge, never by a rebase of
pushed commits. Landed so far (2026-11-24): K9 and K10 (section K), a PostgreSQL recovery-sweep
test, and agent tooling; the rest of this list is unbuilt or queued.

**0.8.16 scope is locked** (ruled 2026-11-23, 01:43 AEDT): anything found from then on belongs to
0.8.18, unless it is a fast fix for something the 0.8.16 work itself broke. A pre-existing defect
found now is 0.8.18 work even if serious; a serious one is raised with the maintainer.

**Compatibility in 0.8.18** (ruled 2026-11-23): no backwards compatibility. The engine, and the
engine's audit database schema, may change in this release. A store the release cannot read is
refused, never reinterpreted; every such break, and what an operator must do about it, is stated
plainly in the upgrade notes. A session schema epoch or database CHECK constraint change goes ahead
when the work requires it, under ordinary review (ruled 2026-11-23); no separate approval is needed.
No migration, reset, wipe or downgrade of any store without the maintainer.

## How to read an entry

Each entry gives what the item is, why it was deferred, its status, an evidence pointer and, where
one exists, a revisit trigger.

- **Status.** *Ruled*: the maintainer decided it belongs in 0.8.18. *Integrator's call*: placed in
  0.8.18 by the release integrator without a maintainer ruling. *Pending*: a question is open with
  the maintainer, and the item may still land in 0.8.16. When a pending item lands in 0.8.16,
  update its entry here.
- **Provenance.** *Measured* (from a run), *read* (from the code at the cited lines), *relayed*
  (reported during the release and not re-checked when this list was written), *inferred*.
- **Line numbers** refer to the 0.8.16 candidate unless stated, and drift. Re-locate by symbol
  before building.
- **Evidence** marked "working notes" is held in the integrators' untracked notes under the same
  entry id. Anything a builder needs from those notes is copied into the handoff for that item.
- Every item here still needs the normal release process before it lands: a red test on the exported
  base, every static step of `.github/workflows/ci.yaml`, an independent review, and the whole-tree
  gates in `CONTRIBUTING.md`.

## A. No-op edits, version writes and required-control staging

- **A1. Where required-control staging is triggered.** Ruled 2026-11-22: pushed to this
  release (0.8.17 before the renumbering). Today all three staging sites run only when the
  version advances: the freeform preview and the post-mutation finaliser in
  `web/composer/tool_batch.py` (~2324 and ~900), and proposal accept in
  `web/sessions/routes/composer/proposals.py` (~578). Read, not probed. Question: if an identical
  call stops writing a version, what triggers staging instead (session open or graph
  load, every turn independent of a write, or only at run admission, which must refuse in every
  case)? The integrator's unbuilt preference is per turn, independent of a write, at a cost that
  does not grow with graph size, with review-card timing and the tutorial path checked (no
  tutorial-only branch). Must be answered before A2 can change.
- **A2. Should an identical call write a version at all, across all tools.** Ruled with A1.

  controls; a no-op call in freeform and in approval mode; what is staged, what accept returns).
- **A4. Sibling tools: identical calls reported as fresh success, receipts that do not say what
  changed.** Integrator's call. Measured by calling each tool twice: `set_output`

## B. Context budget and shedding

- **B1. Estimate overshoot.** Ruled 2026-11-21: slipped for now, but it must not be lost; if it
  later becomes a potential issue, it is revisited. The byte arm's rate can only get denser
  (`web/composer/context_budget.py:272-274`); the anchored arm charges one token per
  non-shared byte (`:280-286`); history is never shared (`:254`), so the byte arm wins on 181 of
  182 records. Measured on a live 62-edit session: the first shed estimated 172,875 tokens against
  the provider's 115,258 (1.48x), so history is dropped at a real ~58% of the cap and falls to
  ~43%. Fix candidates: let a plausible anchor move the rate both ways inside the existing
  plausibility band; or price only the non-shared delta at the anchor's density. Risk: content
  denser than the anchor is under-counted; it changes what `refuse` callers refuse, so the
  handoff must list every one. A naive two-way rate under-counts after shedding. Unlanded tests
  from an archived working tree assert that a measured ratio may not lower the admission bound,
  the opposite of the first candidate; reconcile them. Take early, after the 0.8.16
  shed-history-only and retry commits are on main. **Revisit trigger:** an edit that fails, or a
  guess presented as fact, on a turn where the provider's real count was well under the cap.
- **B2. Default request byte ceiling against larger model windows.** Ruled 2026-11-21, in a
  two-part answer: yes to the first part, delay the second. `composer_planner_max_request_bytes`
  defaults to 960 KiB (`web/config.py:397`; confirm which setting the compose loop uses).
  Computed at 4.33 bytes/token, it refuses requests a model would take once the window is above
  ~227k tokens; it does not bite on a 200k-token model. It conflicts in principle with "if it
  fits, it goes". Fix: derive the ceiling from the declared window, or raise the default; keep the
  operator override, and keep any value an operator set explicitly. Size defaults are judged
  against the four direct provider routes. Take with B1.
- **B3. Exhaustive review of the context-budget code, then a review of that review.** Ruled
  2026-11-21: when there is capacity, a more exhaustive review of that code, after which a second

  before starting; the other reading is the lease code): `web/composer/context_budget.py`,
  `context_budget_apply.py`, the compose-loop and planner shedding call sites (`service.py`,
  `pipeline_planner.py`), advisor age shaping and pricing (`advisor_checkpoint.py`,
  `advisor_transcript.py`), and the refusal and retry paths. Read-only and exhaustive: all three
  seats; estimate against provider counts; marks, order and hysteresis; every accounting guard;
  both growth patterns (work redone over the whole history each turn; pairwise work inside one
  call); what each `on_over_estimate` mode does; the claim that no accounting guard can fire on
  legitimate inputs. Inputs: the compaction design and overshoot notes and the 182 recorded budget
  decisions (working notes). The second review confirms or rejects every finding against the code
  and ranks the survivors; findings are claims until confirmed. Run after the 0.8.16 shedding and

- **B4. Retry once with all history shed after a provider context-length rejection.** Exists only

- **C12. Growth sweep.** Proposed, not started: a read-only sweep for both growth patterns,
  growth-ratio tests at two sizes, and server time per edit against edit number in the battery
  report.
- **C14. Token quota refusals between users.** Pre-existing; no deployment sets a quota today, but
  assume one is coming (ruled 2026-11-23). With a daily quota or container ceiling configured, one
  user's call in flight makes the day's total unknown for other users, run starts included, and
  they are refused with "Ask an administrator to reconcile token accounting", for a condition that
  clears in seconds. Work: treat an unsettled attempt as unknown only when its operation is no
  longer live (existing columns; no schema change), changing the status view's mirror of the same
  measure in the same commit; check whether an attempt cut off mid-call is ever settled without an
  administrator, since otherwise it holds the day unknown until UTC midnight; correct the refusal
  text. Calls in flight settle as they already do within one run (ruled 2026-11-23). Detail:
  `docs/development/concurrent-execution-research-2026-11-23.md` §1.2 and §8.7.
- **C13. Work abandoned at a deadline keeps running (priority).** Ruled 2026-11-22: these land on the
  0.8.18 branch as a priority. Same class as the late lease loss fixed in 4251a5c59. Each fix comes
  with a test that is red on its base.
  1. The run-status bridge stops waiting after 30 s without cancelling the work, so late run
     status, event, file and token writes can land after failure handling. **Pending, may land in
     0.8.16** on its own fix branch; the maintainer decides after seeing the fix. If not, 0.8.18.
  2. Pipeline commit preparation runs under a timeout; on timeout the user is told to retry while
     the preparation may still store prepared prompt files, leaving orphan or duplicate files and
     quota use. State itself is committed later by the caller.
  3. Test race: `test_runtime_preflight_blob_reuse.py::test_an_evidence_read_that_outlasts_the_budget_raises_the_timeout`
     must wait for outstanding admissions to reach zero after opening its gate.
  4. To settle, not a known defect: late row-level errors from an evicted batch attempt.
- **C15. Shutdown can report a false lifecycle failure.** Pre-existing in 0.8.16. Shutdown sets the
  instance to draining before it asks the execution service's run-loss watcher to close. A watcher
  tick in that gap reads a run, the read is refused because the instance is draining, and the
  watcher dies with an unhandled error, so shutdown reports "Application lifecycle obligations
  failed". No data loss or false record was found: the held terminal write still lands once and the
  stored status matches it. Reproduced by widening the gap. Root fix: request the watcher's close
  before draining begins; a minimal guard is for the watcher to end quietly on that refusal while
  draining. Seen as a failure of
  `test_execute_terminal_write_held.py::test_shutting_down_while_the_terminal_write_is_held_waits_for_it_and_no_longer`.

- **I13. Research: concurrent pipeline runs. HIGH PRIORITY** (maintainer, 2026-11-23). Pencilled
  in for 0.8.18, 0.8.19 at the latest; research and a recommendation, no build until the maintainer
  rules. Research delivered 2026-11-23:
  `docs/development/concurrent-execution-research-2026-11-23.md` (recommendation: a server-owned
  bounded run pool with fair per-user admission, default 1; three couplings to fix before raising
  it; a long-life-save sink contract; rulings needed are listed in its §8.6). Ruled 2026-11-23: the
  default run-worker count is 1, as policy; operators raise it. Also ruled 2026-11-23: 0.8.18 may
  ship the concurrent path built but not seriously tested, to be examined later; the default-1 path
  must keep working unchanged, and the operator documentation must say that values above 1 are not
  yet validated. The other four §8.6 items are under
  technical review before any goes to the maintainer; outcome in the research document §8.7 (quota
  in-flight settlement and fair-admission caps default off, both ruled 2026-11-23). The web server runs every
  pipeline on one thread (`ThreadPoolExecutor(max_workers=1)`, `web/execution/service.py:1286`,
  since the first execution layer, not configurable, server-wide), so one slow run queues every
  other user's run. The scope is wider than running two pipelines at once; three concerns collide
  and must be designed together: (a) across runs, users and runs progress independently (per-run
  or per-user executors, and how many); (b) inside a run, multi-worker execution must not pile up
  behind the slowest sink or transform (back-pressure); (c) durability, a row is not done until its
  sink write has landed, with no early acknowledgement or buffering, so completion, audit, run
  accounting and recovery hold for sink calls lasting minutes, against today's fixed bounds (the
  run-status bridge give-up, the 30 s lease and its heartbeat, the 30 s pool checkout). Also: does
  the composer, or the server on its behalf, start executors (execution capacity, not authoring;
  the composer invariants hold). Extended 2026-11-23 to the multi-container deployments (AWS
  ECS/Fargate, Azure Container Apps): (d) what is per-process today and breaks or duplicates across
  replicas, the database as the only cross-replica coordinator, shared file storage, and what
  happens to a long sink call when a container is stopped, replaced or scaled in. Assume concurrent composer users and concurrent runs as normal, and a
  multi-worker executor that will still saturate behind slow transforms (LLM calls) and long-lived,
  irreversible sinks (a row is not done until it is sunk, and one send may take minutes). Answer:
  what assumes one run at a time and what is already safe (audit writes and their coordination
  tokens, run leases and fences, progress broadcast, the run-status bridge, shutdown's executor
  join and lease-release registry, file and output finalisation, token accounting, the async
  worker pool); per-session versus server-wide concurrency; the resource model on a 4-vCPU host
  (CPU, database pool and its 30 s checkout timeout, memory per run); behaviour at saturation
  (admission, queueing, what a waiting user sees, fairness, starvation); durable per-row in-flight
  state for long sends, resume that reconciles instead of resending, and leases renewed through
  multi-minute sends; a recommended shape and bound, the operator setting, and how to test it,
  PostgreSQL included.

## M. Found in the review of the 0.8.16 patch (2026-11-23)

Ruled 2026-11-23: 0.8.16 ships as is; each finding goes either into a hotfix after 0.8.16 (now
0.8.17) or to the next release (now 0.8.18). The 0.8.17 hotfix includes M1 and M2; the rest are
0.8.18.

- **M1. (0.8.17 hotfix)** `get_pipeline_state` refuses `field_path` and `since_start` pages once the
  validation block alone exceeds the page budget, so the planner cannot read exact state on a
  large invalid graph.
- **M2. (0.8.17 hotfix)** Saving a node with several prompt files in the editor re-reads custody
  once per file per file under the session lock; read it once, as the card writer already does.
- **M3. Explicit-approval teaching contradicts the code.** The skill says a change that leaves
  errors is still recorded as a proposal, but the explicit-approval path requires a valid pipeline
  and refuses with no card, so the planner loops.
- **M4. A refused direct `set_pipeline` leaves a stored copy of an inline source**, one per retry.
  Confirm first.
- **M5. After a context-rejection retry, later turns re-send the refused history** and pay one
  rejected call per turn when the configured limit exceeds the real one.
- **M6. A failed first build reads as "The pipeline is now empty".** A successful `set_metadata`
  plus a failed `set_pipeline` on an empty session reports an empty pipeline instead of the failed
  build.
- **M7. A routing-only rewire shows as a no-op row in the proposal diff**, and a test pins it.
- **M8. Editor line endings.** The prompt editor normalises CRLF and drops a BOM, so its dirty state
  cannot clear. Confirm with a browser test.
- **M9. One upload or delete refusal disables every "Edit file" in the Files table** with a false
  "File names are unavailable", because the table reads the shared error instead of the list's own
  load state.
- **M10. Every terminal turn pages the whole session and file lists**, with no tie-breaker in the
  ordering. Growth; low in practice.
- **M11. A provider-rejection record does not enforce its own pairing rule** (a context-length
  reason source with the matching code). Only reachable through a corrupt store or a future writer
  bug.
- **M12. Investigate:** the row reorder buffer's shutdown moves pending rows to evicted, so a lease
  loss after shutdown is discarded. Pre-existing.
- **M13. Follow-up review items.** A loop-side cancel of a bridged call is not treated as unsettled
  (pre-existing, no trigger found); not yet reviewed: lifespan shutdown order against the pipeline
  thread, and a non-list review field before the new check in the tool batch and pipeline planner.
- **Open with the maintainer, not to be built yet:** whether the planner should retry with less
