# 0.8.10 test feedback and structural leverage review

The immediate improvement is to establish whether each proof's positive prerequisite is valid **before scheduling its mutation expansion**, while running independent functional controls separately. R160 demonstrates wasted feedback capacity, not inadequate worker allocation. The broader improvement is to stop repeatedly reconstructing or re-proving a prerequisite whose ownership and validity can be established once at the right boundary. Neither conclusion permits blindly changing proof pins, bypassing provider calls, or removing current data-integrity checks.

This is an independent source/receipt review for `release/0.8.10-assembly`, 6 November 2026. Root owns execution, Git, integration and acceptance. I ran no tests, profiles, product imports, containers, database operations, or Git operations. The source is concurrently receiving repairs; line references identify the inspected implementation, not a claim that every finding survives subsequent edits. This document proposes changes; it does not implement or qualify them.

## Boundary and observations

The decision is how to shorten the interval from a source change to a trustworthy next repair without reducing failure detection. The boundary includes scope selection, collection, proof prerequisites, runtime receiving, failure triage, source repair, proof rebinding, commit/push, shared-host CI and final acceptance. The useful horizon is the remaining 0.8.10 repair/acceptance cycle, with larger structural changes separately bounded.

## Findings, in priority order

### 1. A failed prerequisite fans out into mutation failures before the run returns useful repair feedback

The [reviewed reserve fixture](../../tests/unit/architecture/test_web_reserve_reviewed_contracts.py#L1918) reparses the production inventory, asserts recipe acceptance, then constructs the full positive reserve proof. Tests using it can fail at setup before any mutation. Other tests repeat their own positive proof before applying a parameterized mutation. R160's `test_reserve_v4_no_sdk_closure_refuses_foreign_originals_even_with_rebound_template` failed at its initial `failures == []` assertion, naming the classifier's `_finish_v4_no_sdk`; its planted counterexample had not been evaluated. Repetition of that failure does not add corresponding independent evidence about the mutations.

The [recipe dispatcher](../../tests/unit/architecture/test_web_landscape_mutation_fencing.py#L6190) also returns at the first failing category: full-source seals, cancellation route, cancellation consumers, transitive recipes, then writers. Repairing the first refusal can therefore reveal the next only on a later attempt. This sequential masking is source-demonstrated; the exact number and runtime share of hidden roots are not measured here.

**Smallest intervention:** introduce a cheap, explicit positive-prerequisite receiving selection for each affected proof family. Report all independently checkable prerequisite failures in one diagnostic invocation, while retaining the fail-closed acceptance path. If a positive prerequisite fails, do not launch that family's mutation matrix. Mark its receipt as blocked/unexecuted and keep the aggregate non-green; continue independent functional families. Once a prerequisite passes, run its relevant mutations and then the required complete acceptance selection. A blanket `--maxfail=1` is a useful emergency bound but insufficient as the permanent design: it can conceal independent functional defects behind the first stale seal.

**Safeguards:** do not remove the initial positive assertion; do not count blocked mutations as passes; do not cache mutable ASTs across mutations; keep proof coverage and selection accounting. Prove the new prerequisite check catches a deliberately invalid baseline and that a valid baseline still dispatches the original mutation set. Compare unchanged mutation outcomes, not just test totals.

### 2. “Focused” is currently a file-selection intention, not an execution budget

The selected architecture file calls itself “Fast prerequisites and adversarial controls for the expensive reserve proof” at [line 1](../../tests/unit/architecture/test_web_reserve_reviewed_contracts.py#L1), but contains both prerequisites and broad parameterized semantic controls. R160's collected cardinality demonstrates that selecting a handful of modules is not enough to bound work. The [pytest defaults](../../pyproject.toml#L484) supply 12 workers but no early failure limit. The [canonical runner](../../scripts/full-suite-gate.sh#L434) launches its default `tests/` selection and appends optional arguments; it does not establish proof prerequisite readiness. These defaults are understandable for acceptance and poorly matched to diagnosis.

**Smallest intervention:** centralize two named modes in the existing runner/selection mechanism: diagnostic receiving, with an explicit selected manifest and prerequisite phase; and acceptance, retaining complete required selection. Display actual collected node IDs/count and historical duration estimate when available before a large diagnostic launch. Collection has a cost and imports test modules, so perform it under the same supervision and freeze/provenance conditions; do not add a second unowned collection process. Missing duration history means unknown cost, not zero cost. Avoid a new universal count threshold: one test may spawn expensive descendants, while many scalar cases may be cheap.

The present file-level choice should be corrected centrally, not with another hand-maintained command in every handover. Falsification: if a bounded prerequisite-first selection still spends comparable CPU time before identifying the first actionable root on unchanged input, the assumed leverage is wrong and collection/setup or the positive proof itself needs measurement.

### 3. Exact-source protection mixes a legitimate proof assumption with an overly broad maintenance obligation

The [cancellation supplier and full-source guards](../../tests/unit/architecture/test_web_landscape_mutation_fencing.py#L6138) hash whole source strings; the [writer recipe comparison](../../tests/unit/architecture/test_web_landscape_mutation_fencing.py#L6212) compares AST forms. Such binding can be a valid assumption of a static proof: a proof about one implementation must refuse another. It does not follow that every source spelling change is a product integrity defect, or that the entire product should be reshaped to preserve that spelling.

The same reviewed-contracts file tests `__code__` replacement, reflected attribute replacement and namespace substitution. Under the stated model, external users/provider output are hostile; installed developers/operators/plugin authors have trusted intent, while accidental mistakes remain in scope. A repository test cannot enforce a security boundary against an actor who controls both code and tests. Some mutations still represent realistic accidental bypasses and protect real audit obligations. Their value must be assessed by the invariant and reachable failure they expose, not by how adversarial the syntax looks.

**Smallest intervention:** retain the current gate while classifying each changed binding as (a) product behavior or external-data boundary; (b) necessary static-proof assumption; or (c) unsupported hostile installed-code scenario. Replace broad body seals with narrow semantic obligations only where the same unwanted behavior remains rejected. There is already a useful [below-seal semantic control pattern](../../tests/unit/architecture/test_web_reserve_reviewed_contracts.py#L8049): it tests a precise refusal without allowing a stale recipe to masquerade as mutation detection, then rechecks the positive. Apply that pattern deliberately rather than blindly regenerating templates.

Do not remove all static checks or assume trusted intent implies correct code. In particular, keep provider-per-transition requirements, authority/transaction ownership, cancellation handoffs, external JSON parsing, SQL constraints, audit completeness and no-write-after-refusal controls. Signing is suspended and is not a dependency of this intervention. Pre-1.0 policy also supplies no reason to preserve retired interfaces solely to satisfy old fixtures.

### 4. Small cache optimizations can leave the dominant prerequisite reconstruction intact

The [recorder decoder](../../src/elspeth/web/composer/continuation_audit_buffer.py#L275) verifies the chunk, parses/restores the block document, constructs an owned model, validates links/cursors and re-encodes for exact canonical equality. The [memo's snapshot API](../../src/elspeth/web/continuation_retention_memo.py#L383) concerns `ContinuationFrameStack`, and V4 ownership recomputes it; its [canonical proof API](../../src/elspeth/web/continuation_retention_memo.py#L436) retains bytes/digest, not the decoded recorder. A cache hit on bytes therefore does not establish that repeated decode/model/roundtrip work disappeared. This is a source-backed mechanism, not a measurement that it dominates end-to-end latency.

The decision should be made at the expensive dependency's owner: can exact immutable admitted recorder data be reused within a bounded lifetime while fresh authority, reference and credential checks still run? The [encoder](../../src/elspeth/web/composer/continuation_codec.py#L114) includes credential admission, so caching the entire public decode indiscriminately would skip meaningful current behavior. Expanded recorder data can also exceed its compressed source size; an uncharged decoded-object cache is not an acceptable shortcut.

The smallest feasible current-family optimization may remain the proposed request reverse lookup. Treat it as a bounded hypothesis: measure actual eligible hits and removed enclosing work, then the unchanged original workflow. Do not infer value from forward-hit rate or a lower leaf-call count. The larger ownership/pure-data split deserves consideration once centrally because it can remove repeated prerequisites across callers; it needs explicit memory accounting and preserved cold/corrupt/error-order behavior. No speedup figure is justified by this review.

### 5. Publication triggers a competing work queue whose policy conflicts with local receiving

The [CI concurrency policy](../../.github/workflows/ci.yaml#L28) intentionally keeps active release runs instead of cancelling them on newer work. The [matrix budget](../../.github/workflows/ci.yaml#L389) is explicitly a per-run ceiling, not reserved host capacity. The local runner's [sibling heuristic](../../scripts/full-suite-gate.sh#L356) observes pytest processes and adjusts workers; observation does not reserve capacity against jobs starting later. Thus “commit/push to preserve progress” can create competing receiving work even when the local preflight was correct.

The [receiving handover](../release/0.8.10-consolidation-handover-2026-11-02.md#L41) records actual CI cancellation and an overlapped R137 failure followed by R138 progress after draining CI. That chronology is evidence of coordination friction, not a controlled estimate of contention's contribution: workflow stages and later failure boundaries differ. R160's CPU use independently shows that CI contention is not required to explain its waste.

**Smallest intervention:** give local acceptance and CI a single capacity policy, using an existing host scheduler/lease if available, and make release-run supersession intent explicit. Separate preservation pushes from qualification requests operationally without bypassing hooks or suppressing final required CI. Inspect job-level activity, since queued run-level state can coexist with active jobs. Any change to cancellation/shared-runner policy needs its existing operator authority; this review performs none. The test is whether an authorized local reservation prevents newly dispatched CI from overlapping, and whether final merged-SHA CI still executes every required job.

## End-to-end repair loop

| Transition | Current failure mode | Central improvement and retained obligation |
|---|---|---|
| Decision → selection → collection | Module scope understates expanded work | Select by affected invariant/family; show actual manifest and uncertainty |
| Collection → baseline → mutations | Invalid positive feeds many dependent cases | Gate dependent expansion; keep non-green blocked status and independent functional checks |
| Failures → triage | Repeated wrappers look like many roots; first seal masks later roots | Group by exact first failing prerequisite and assertion location, retain every original node ID/error |
| Triage → source repair → rebinding | Risk of repairing source to satisfy historical spelling | Repair current behavior first; review proof assumptions and rebind semantic controls honestly |
| Receiving → commit/push | Static success mistaken for runtime readiness | Keep static, functional, proof and workflow receipts distinct; preserve coherent WIP through normal hooks |
| Push → CI/local receiving | New queue competes with active local work | Shared capacity/supersession policy with job-level visibility |
| Receiving → acceptance | Earlier or partial success promoted beyond its workload | Run required default, PostgreSQL, runtime/recovery/browser and merged-SHA gates on the actual receiving tree |

The reinforcing mechanism is plausible and partially observed: source changes invalidate proof assumptions; large dependent selections amplify the diagnostic backlog; delayed feedback permits more unresolved changes; later receiving must disentangle both. The relevant stocks are unresolved root defects, stale proof assumptions and queued execution work. Failures per run are not the defect stock. Flows are repairs, new invalidations, completed receiving and new CI submissions. Capacity is CPU/process slots plus reviewer attention; wall delay includes collection, execution, queueing and triage. Parameter products and shared prerequisite fan-out make work grow nonlinearly with apparently small scope expansion. A smaller worker count alters service rate, not arrival rate or fan-out.

An alternative explanation is several independent product/fixture defects with no persistent reinforcing loop. R160 supports that possibility too. The discriminating observation is whether prerequisite-first receiving reduces repeated failure work and time to the next correctly identified root across comparable repair cycles. This review does not establish long-run growth rates or quantify reviewer time.

## Intervention comparison and limits

| Option | Expected effect | Principal risk / falsifiable check |
|---|---|---|
| No change | Same invalid baseline can repeatedly consume a broad selection | Reproduce unchanged input: repeated pre-mutation failures should recur; no projected completion time |
| Fewer workers only | Lower instantaneous demand, potentially longer feedback | Does not reduce CPU work; compare CPU seconds as well as wall time |
| Prerequisite-first receiving | Avoids uninformative dependent mutations; exposes independent roots | Must remain non-green when blocked and later dispatch original mutation coverage |
| Narrow semantic contracts | Reduces irrelevant rebinding while preserving actual obligations | Plant meaningful ownership/data-boundary faults and harmless refactors; harmful must fail, harmless must pass |
| Reuse at expensive data owner | Can remove repeated construction across callers | Exact bytes, fresh authority/credentials, memory bounds, cold behavior and end-to-end clocks must survive |
| Shared capacity policy | Reduces accidental local/CI interference | Reservation must cover startup and descendants; required final CI must remain complete |

Start with prerequisite-first receiving and honest failure classification. They directly address the demonstrated R160 loss and need no speculative product redesign. Then use enclosing measurements to decide whether cache ownership or proof-contract redesign repays its complexity. Do not add sealed plans, approval sidecars, new parallel broad suites, or an extra release gate. No current source fix, performance improvement, proof equivalence or release acceptance is certified here.
