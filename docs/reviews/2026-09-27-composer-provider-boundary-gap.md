# Composer provider failure boundary: gap analysis

Date: 2026-09-27
Target: `release/0.8.1` at `b97549096d4ad3967311f2b862b15d609f621a5a`
Method: read-only source and installed LiteLLM inspection. The reported staging sessions were not queried, and no deployment logs or live gateway responses were available.

## Incidents and limits of attribution

The operator reported three Composer attempts in session `a1914bf9-9b4f-45b9-bdad-316a628362a5` that received gateway HTTP 502 `upstream_response_invalid` and reached LiteLLM as `BadGatewayError`. The message route produced an unhandled server failure. The operator also reported that the second Sonnet planning call in tutorial session `59c85fd9-7ae5-4453-91a6-6ad69ca65edb` received gateway HTTP 503 after about 29 seconds. Quota settlement raised `AuditIntegrityError`, leaving one admitted provider attempt pending and masking the provider error. These are incident inputs, not independently verified database or gateway measurements.

The installed LiteLLM classes `BadGatewayError` and `ServiceUnavailableError` both inherit `openai.APIStatusError`; `litellm.exceptions.APIError` instead inherits `openai.APIError` (`.venv/lib/python3.13/site-packages/litellm/exceptions.py:661,709,806`). Catching `LiteLLMAPIError` alone therefore does not catch the concrete 502 or 503 classes.

The same class seam includes LiteLLM `Timeout`, which inherits `openai.APITimeoutError` rather than builtin `TimeoutError` (`litellm/exceptions.py:355`). A broad SDK fallback that labels every remaining `OpenAIError` as a generic API outage would also misclassify provider timeouts. The remediation must recognize that typed timeout explicitly and preserve the existing timeout audit/outcome semantics.

The gateway's `upstream_response_invalid` is a closed HTTP 502 with `retryable=false` (`gateway/src/elspeth_llm_gateway/core/errors.py:41-89`). It is produced for invalid success JSON, adapter parse/validation failure, redirects, and the reference adapter's unknown or malformed non-2xx fault (`core/transport.py:108-125,185-213`; `core/service.py:213-228`; `reference/adapter.py:306-315`). The code does not prove which of those happened in Tom's calls. HTTP 503 may be `oauth_token_unavailable` or `upstream_unavailable`; elapsed time alone does not identify the source. Gateway `request_id` and `error_code` are logged and returned in its safe error envelope (`core/app.py:367-377`; `core/errors.py:109-119`). The observed AWS-side cause still requires matching gateway records.

## Application path and demonstrated source defect

1. `_litellm_acompletion` admits a quota attempt before physical dispatch (`src/elspeth/web/composer/service.py:928-945`). The pending row is durable (`src/elspeth/web/coordination/quota_authority.py:136-179`).
2. The ordinary Composer call has a catch-all that records an `API_ERROR` call with a class-only error value and attaches buffered calls to the exception (`service.py:9403-9545`). The `send_message` route catches LiteLLM authentication and API errors, but not `BadGatewayError` (`src/elspeth/web/sessions/routes/messages.py:345-346,407-494`). Its generic finalizer can drain attached audit calls (`messages.py:723-745`); it cannot turn an unhandled exception into a failed progress event and sanitized 502. `recompose` independently duplicates this exception taxonomy (`routes/composer/compose.py:194-195,242-315`).
3. Planner `call_model` is enclosed by `quota_provider_calls` (`src/elspeth/web/composer/pipeline_planner.py:3964`). Its catches record `CANCELLED`, `TIMEOUT`, `AUTH_ERROR`, `BAD_REQUEST_ERROR`, or `API_ERROR` only for the named classes (`pipeline_planner.py:4107-4189`). `ServiceUnavailableError` bypasses all of them, so `record_provider_failure` is not called.
4. The quota wrapper's finalizer requires a bound `ComposerLLMCall`; without it, `_settle` raises `AuditIntegrityError` and deliberately preserves the pending attempt (`src/elspeth/web/composer/provider_quota.py:52-95`). This secondary exception replaces the original provider exception. The integrity refusal is correct: an admitted dispatch must not be recorded as complete without terminal evidence.
5. On a normal planner provider error, `PipelinePlannerError(code="PROVIDER_ERROR")` is translated to a failed progress snapshot and a safe HTTP 503 with retry guidance (`messages.py:642-682`; `routes/_helpers.py:2893-2900,2970-3061`). The 503 incident never reaches that path because the pending-attempt failure supersedes it.

## Why this is a systemic boundary gap

The gateway has a closed status/code/retryability contract, but Composer repeats provider exception enumerations at planner, ordinary call, advisor, boot probe, guided chat, and two HTTP routes. Their coverage differs. `advisor_provider_failure_types` includes the broader `OpenAIError` family (`service.py:623-651`), while planner and routes enumerate `LiteLLMAPIError`. The normal call has a terminal-audit catch-all; planner does not. A gateway status class absent from one enumeration can therefore change both the HTTP outcome and whether an admitted call is settled.

This is a stock-and-flow hazard, not merely presentation. A pending `quota_provider_attempts` row causes daily token measurement to return unknown (`src/elspeth/web/coordination/quota_authority.py:261-291`), and admission returns `TOKEN_ACCOUNTING_UNAVAILABLE` where an identity or container quota applies (`src/elspeth/web/coordination/chargeable_admission_authority.py:100-128`). `tests/unit/web/composer/test_provider_quota_end_to_end.py:157-178` confirms a fresh operation is refused after an unsettled attempt. A previous cancellation review identified the same missing-terminal-evidence shape (historical note, not proof that its current reproduction is identical); the cancellation paths must be audited after the repair.

Terminal evidence fixes the pending-attempt integrity defect but does not establish token usage. A settled failed call with NULL token counts still makes daily quota usage unknown (`quota_authority.py:293-316`), and the next retry or fresh operation can be refused before dispatch (`chargeable_admission_authority.py:102-128`). `tests/unit/web/composer/test_provider_quota_end_to_end.py:132-154` already proves this for a settled timeout. The UI needs a separate safe accounting-unavailable outcome when a retry is refused; it must not claim a third provider failure or imply that immediate retry can succeed. Reconciliation of unknown usage is a distinct operational problem requiring real provider evidence.

There is also semantic loss. The gateway marks `upstream_response_invalid` nonretryable and `upstream_unavailable` retryable, but LiteLLM class-only handling does not preserve the gateway code or request ID in Composer's audit. The route helper optionally exposes scrubbed `str(exc)` in staging debug mode (`src/elspeth/web/sessions/routes/_helpers.py:758-807`); this is unsuitable for a promise that the upstream body never reaches the client. Safe retry guidance must distinguish a transient 503 from a persistent invalid-response 502 without printing provider text.

## Coverage gap

`tests/integration/web/composer/test_freeform_planner_failure_translation.py:182-193,548-627` manufactures `APIError(status_code=503)` and therefore exercises the existing catch, not the actual `ServiceUnavailableError`. `tests/unit/web/composer/test_pipeline_planner.py:5790-5811` does the same. `tests/integration/web/composer/test_composer_against_gateway.py:616-653` proves a real gateway 503 becomes `ServiceUnavailableError`, but stops at the service exception and does not assert HTTP translation or quota settlement. Route redaction tests in `tests/unit/web/sessions/test_routes.py:6269-6560` cover authentication, `APIError`, and bad request, but no `BadGatewayError`.

## Required repair contract

- For every *admitted physical provider dispatch*, produce exactly one terminal `ComposerLLMCall` with actual attempt identity, class-only failure metadata, and unknown token counts when the provider did not return usage. Settle it atomically with the ledger. Admission failure before dispatch must not fabricate a call.
- Classify known third-party provider status/transport failures at a shared boundary. Preserve `CancelledError` and first-party `AuditIntegrityError` as distinct outcomes. Do not broaden a route catch to arbitrary `Exception` or turn an internal bug into a provider outage.
- Map a gateway 503 to the planner's existing `PROVIDER_ERROR` safe 503 and failed progress when retries exhaust; map ordinary 502/503 provider failures to a sanitized response and failed progress on both `send_message` and `recompose`. If quota refuses a subsequent retry because usage is unknown, keep that authoritative refusal distinct, with safe accounting-unavailable HTTP 503 and failed progress. The route must not reveal the upstream body even when provider debug exposure is enabled.
- Keep retry behavior bounded by the existing attempt and deadline limits and subject to fresh quota admission. Do not blindly retry `upstream_response_invalid`, which the gateway marks nonretryable. If the gateway code is unavailable through LiteLLM, use a conservative class-based policy and document that loss.
- Test the concrete LiteLLM classes through provider dispatch, audit settlement, and HTTP surfaces. In particular, fail the *second* planning call with `ServiceUnavailableError`; under quota assert the first and second call audits, zero pending attempts, unknown usage retained, third dispatch refused, failed accounting progress, safe HTTP response, no pipeline run, and no upstream-content leak. Without quota assert bounded provider retry exhaustion and its safe provider response. Assert a fresh quota-governed operation also remains fail-closed on settled unknown usage.
- Audit every other cancellation path after implementation for `admit -> dispatch -> terminal record -> settlement` ordering, preservation of the primary cancellation, and sidecar persistence under deferred cancellation. Report residual findings separately from the provider exception repair.

The implementation-stage cancellation trace also identified two quota custody races and a recompose route asymmetry. In `provider_quota._settle`, a child settlement failure can replace a prior cancellation; in `admit_provider_attempt`, the synchronous admission worker can commit after its async waiter is cancelled, leaving the wrapper without the new attempt ID. `recompose` suppresses repeated cancellation while shielded sidecar writes continue, then can release its lease before joining those writes. These are source-backed and have deterministic repro targets in the cancellation audit; their final verdict belongs in the post-repair audit report.
