**Direct answer for John:** Some saved work will be waiting; a finished answer is not guaranteed. The latest composer still uses a buffered, long-running HTTP POST. On an origin-visible disconnect it cancels the provider loop. Completed tool/state/audit writes survive, an in-flight protected tool finishes and commits its completed prefix, and a post-provider protected settlement can finish and save the final reply despite the lost connection. Reopening reads these durable records; it does not restart or resume the interrupted provider loop. Blind automatic retry cannot make the original request complete or recover its exact final response.

**Real lifecycle**

1. The browser allocates a client_request_id UUID and optimistic message, retains that UUID and requested state for a local retry, starts progress/message polling, and POSTs /api/sessions/{id}/messages. A per-session browser owner prevents overlapping local sends. The client abort guard is the configured backend composer budget plus 25 seconds (boot fallback 295 seconds; readiness gates entry). [browser ingress](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/stores/sessionStore.ts#L1539); [POST wire](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/api/client.ts#L952); [abort budget](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/config/composer.ts#L1).
2. The API authenticates, rate-limits, takes the compose lock and fenced session operation lease, checks the ingress receipt, then commits the user message and its transcript snapshot together. Ingress is an owned, shielded child; cancellation cannot split that committed write from inspection of its outcome. [API admission/ingress](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L169).
3. The composer loop runs inline in the request task. The http.disconnect watcher starts around this provider-engaged block, not at initial admission or while waiting for the compose lock. A queue-time disconnect can therefore still be followed by ingress before the watcher sees abandonment. There is no 202 return and no response heartbeat/stream on this route; progress polling is a separate GET surface, not bytes in this POST response. [inline provider and watcher](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L578); [watcher implementation](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/_helpers.py#L2362).
4. Each completed tool-turn publication persists its assistant tool-call envelope, tool results, composition-state advances and associated audit records. An interrupted request is not an all-or-nothing transaction. The protected dispatch+persist section finishes only the current in-flight tool, publishes its completed prefix, starts no further tools, and then restores cancellation before another model turn. An already running advisor call in that section can also finish. [protected tool section](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/service.py#L160); [per-turn publication](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/service.py#L2206); [cancel restored](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/service.py#L2441); [atomic turn persistence](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/turn_audit.py#L393).
5. Once composer.compose returns, a distinct lease-owned continuation settles pipeline intent/state, saves the final assistant reply, persists remaining audit, builds the response, and publishes complete progress. It is shielded and joined despite repeated request cancellation. If that succeeds, the route records completed even if the disconnected HTTP response is locally converted to 499 and discarded. Protected settlement is not protection against process death, lease loss, storage failure or an invariant failure. [settlement persistence](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L503); [owned continuation](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L613); [shielded join](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/_helpers.py#L1466); [completed versus cancelled](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L952).
6. If the provider loop is cancelled earlier, route cleanup saves attached LLM-call audit and cancelled progress. It does not create a synthetic final answer or roll back completed tool turns. Cancelling the local provider request also does not prove a remote model provider stopped processing or charging; no remote result-retrieval/resume protocol is used here.
7. Browser AbortError/timeouts and fetch TypeError/NetworkError/status0 use read-only reconciliation. It polls inflight_requests until zero, then GETs messages/state/proposals and refreshes related blobs/reviews. Progress-read failure ends the wait best-effort, so this is not an unconditional settlement guarantee. Periodic readers stop when handling finishes. A plain HTTP504 or HTTP524 is excluded from the ambiguous-network classifier and skips this dedicated reconciliation path. [classifier](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/stores/sessionStore.ts#L244); [settlement/read-only recovery](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/stores/sessionStore.ts#L528); [send catch and teardown](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/stores/sessionStore.ts#L1778).
8. Reopening/selecting a session GETs stored messages/current state/proposals/preferences and loads blobs/reviews. There is no composer task reattachment/resumption. A completed saved answer is normally returned, subject to authorization/retention and pagination. The default messages GET returns the FIRST 100 conversational rows; the frontend supplies no limit/offset. Thus a final reply beyond row 100 can persist yet remain missing from the ordinary reopened transcript. [session reload](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/stores/sessionStore.ts#L1413); [unpaginated browser GET](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/api/client.ts#L807); [default route limit](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L1051); [ascending filtered pagination](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L1119); [DB ordering](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/service.py#L4744).

**Failure-point matrix**

The current first-turn path also matters: an empty pipeline with an explicit mutation request selects the full-pipeline planner, awaited under the same disconnect watcher. The planner does not progressively commit an authored pipeline like the ordinary tool loop. On provider cancellation its physical/semantic planner audit is saved, without a final pipeline result. If cancellation races the shielded proposal-create write, that write finishes; review-required trust leaves a pending proposal, while auto-commit trust rejects it with reason request_cancelled and commits no state. This happens BEFORE composer.compose returns, so it is separate from the route's protected post-provider final settlement. [authoring-path selection](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/service.py#L981); [planner cancellation audit](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/planning_application.py#L792); [proposal cancellation custody](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/planning_application.py#L581).

| Failure point | Does original work continue? | Durable result on return/reopen | Retry effect |
|---|---|---|---|
| Before origin admission | No composer started | No user/result unless admission actually happened | Same key can admit once if genuinely unseen |
| Waiting for lock / protected ingress | Disconnect not yet watched; ingress may still land | Accepted user row/receipt can survive | Same-key duplicate is serialized and/or lease-refused, then 409 once accepted; no final-response replay |
| Origin sees disconnect during provider I/O | Inline loop cancels; no remaining model/tool turns | User and prior committed tool/state/audit; no promised final answer | Reconcile first; a later recompose is a fresh turn if its guard admits it |
| Disconnect during protected tool dispatch/publication | In-flight tool/persist drains; subsequent tools stop | Completed prefix, assistant tool-call row, state, artifacts and audit persist | Recompose may 409 because latest conversational row is assistant, even without a final reply |
| Disconnect after provider returns, during protected final settlement | Continuation joins to settlement despite request cancellation | Final reply/state can be saved; HTTP response can be lost | GET retrieves saved records; same send key returns409 |
| Browser/proxy gives up but origin gets no disconnect | Loop can continue until another cancellation, deadline or failure | May later produce full result | Browser timeout alone proves neither success nor failure |
| Composer budget/provider/auth/audit failure | Terminal application outcome, distinct from transport loss | Saved user, prior commits and any explicit partial/failure state; not a successful result | Follow structured outcome; backend provider retry already handles selected transient failures |
| Process/owner/storage fails | No guaranteed detached composer completion | Only successfully committed durable records | No composer resume-job endpoint; reconcile then explicit new work |
| Already admitted pipeline run loses WebSocket | Background execution continues absent explicit cancel/owner failure | Run status/events/output metadata are durable and replayable | Reconnect/read the same run_id; repeating execute is not result retrieval |

**Retry semantics and gaps**

- Same client_request_id + exact original message/state is deduplicated at ingress and returns409 message_already_accepted plus canonical user_message_id; different semantics return409 message_idempotency_conflict. This is input acceptance idempotency, not response replay, resumed execution or guaranteed exactly-once completed composition. [409 receipt semantics](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/messages.py#L113).
- The browser's accepted-send branch reconciles with GET only. An accepted local retry can remain refresh-only if reconciliation fails. After quiescence and no genuine reply it may deliberately offer retry on the canonical user message. [accepted-send reconciliation](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/stores/sessionStore.ts#L763).
- A new send generates a new UUID and can duplicate the user intent after a lost response. A local failed-message retry preserves the UUID and requested state. After reload these local optimistic descriptors are not a durable composer operation queue.
- Canonical retry POSTs /recompose with expected_user_message_id. It uses current persisted state/history and invokes composer again; it is not instruction-pointer resume or old-response lookup. It requires the latest conversational record to be the specified user. A persisted assistant narration/tool-call row after mid-tool cancellation violates that guard. Frontend genuine-reply detection deliberately distinguishes narration, so recovery can offer a retry the API rejects. [browser retry paths](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/frontend/src/stores/sessionStore.ts#L2233); [backend recompose guard](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/composer/compose.py#L140); [assistant survives conversation filter](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/sessions/routes/_helpers.py#L1767).
- The composer already retries selected transient provider failures with bounded exponential delay inside the same deadline; provider timeout and bad request take terminal paths. That is a separate seam from retrying the browser POST. [provider retries](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/service.py#L2640).

**Pipeline runs are different**

POST /execute returns202 with run_id after admission, transfers the operation lease, and submits the actual pipeline to a background executor. WebSocket disconnect only closes the observer/poller; explicit POST /runs/{id}/cancel and ownership/failure controls govern execution. Reconnect uses persisted sequence-cursor events and authoritative status, with REST results/outputs endpoints. Repeating execute while active is guarded; repeating after terminal can create another run, not retrieve the previous one. This separation is a useful composer design precedent, not proof composer already behaves this way. [execute202](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/execution/routes.py#L1011); [background submit](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/execution/service.py#L1648); [durable event replay](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/execution/routes.py#L1752); [observer disconnect](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/execution/routes.py#L1836).

**ALB versus other middleboxes**

The planner gets the full configured composer timeout and starts its own deadline, rather than receiving the service's earlier absolute deadline. Preparation, later planner audit, runtime preflight/proposal staging, and route settlement extend the actual HTTP lifecycle beyond that planner deadline. Its multiple provider/discovery/repair attempts have separate bounds. Together with protected synchronous-tool drains, this is why the declared30-second transport headroom is not a hard whole-request proof. [planner timeout handoff](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/planning_application.py#L731); [planner own deadline](https://github.com/dta-au/elspeth/blob/edc844699a350a90a624089e12a5a1e75b7b2dde/src/elspeth/web/composer/pipeline_planner.py#L3186).

**Minimum reliable remediation, without implementation**

For safe recovery now, automatically retry READS/reconciliation after ambiguous transport outcomes (including unstructured gateway504/524), preserve the original request identity, wait for server settlement, and show saved progress/final result. Do not automatically call recompose or create a new send on every failure. Address the incomplete-tool-turn retry guard and transcript pagination so recovery is usable. None of this guarantees the first disconnected turn finishes.

For John's stronger requirement that a finished result be waiting after connection loss, remove long execution from the HTTP response: idempotent short admission returning202 with a stable operation ID; server-owned execution independent of browser disconnect; durable status/outcome linked to that ID; polling/reconnect reads; explicit cancellation; bounded failure/lease semantics. Preserve current atomic tool/audit settlement. If completion must also survive worker replacement, add durable claimed work/recovery rather than only a detached in-memory task. Reusing existing progress GETs is possible, but a saved operation outcome is needed to distinguish accepted/running/completed/failed/cancelled reliably. Larger timeouts/heartbeats alone cannot make arbitrary client proxies reliable.
