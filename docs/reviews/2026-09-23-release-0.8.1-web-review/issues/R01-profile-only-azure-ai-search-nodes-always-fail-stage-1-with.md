## Finding

- **Status and severity:** confirmed, **high**. be-19#1 was rated high by both refuters. seam-04-plugin-policy#1 was rated medium.
- **Location:**
  - `src/elspeth/web/plugin_policy/profiles.py:1515`: the plugin joins the profiled roster.
  - `src/elspeth/plugins/transforms/azure/ai_search.py:88,92`: the plugin is `passes_through_input=True` and `OPERATOR_PROFILED`.
  - `src/elspeth/web/composer/_validation_probe.py:66`: an inert stub exists only for `plugin == "llm"`.
  - `src/elspeth/web/composer/state.py:4984-5049`: `_effective_producer_vote_uncached`.
- **What is wrong:** d3dba8a9b made every web-authored `azure_ai_search` node carry only `profile` and `index`. The public schema hides the binding options and sets `additionalProperties: false`. Composer Stage 1 builds the plugin from the authored options. Only `llm` gets a probe stub, so construction fails with `endpoint: Field required; profile: Extra inputs are not permitted`. Because the plugin is a known pass-through, the producer vote fails closed to `(True, frozenset())`.
- **Failure scenario:**
  - The pipeline is csv (`guaranteed_fields=[question]`), then `azure_ai_search{profile, index, query_field: question, output_prefix: policy}`, then `llm{required_input_fields: [question, policy__rag_context]}`. `state.validate()` returns `is_valid=False`, with `schema_contract_violation ... Producer (azure_ai_search) guarantees: [(none)]`.
  - The same pipeline with a raw endpoint binding validates, but a web author cannot produce that shape.
  - `current_source_data_contract_demand` returns `()` on the authored state and `('question',)` on the lowered state. The source_data_contract card is therefore never offered, and `request_interpretation_review(user_term='source_data_contract')` is refused.
  - The cheap Stage-1 gate at `composer/service.py:3733` also pays for a full runtime preflight on every prose turn.
- **Evidence:** Both reviewers ran read-only scratch probes against the worktree, with `elspeth.__file__` checked to be inside the worktree. The probes gave `is_valid: False` for the profiled node against `is_valid: True` for the raw-endpoint control. The lowered options construct and guarantee `{policy__rag_context, policy__rag_score, policy__rag_count, policy__rag_sources}`.
  - `llm/base.py:611` makes omitting `required_input_fields` an error when the template reads row fields, so the downstream `llm` is almost always a required-fields consumer.
  - recent-code-hints.md:1590-1606 records the `llm` fix. It says a stub for another profiled plugin needs proof of provider independence first. That is an unfinished obligation, not a ruling to ship broken.
  - Tracked class: elspeth-bc527113e7, which predates `azure_ai_search` becoming profiled.
- **Suggested fix:** Add an `azure_ai_search` arm to `prepare_validation_probe_options`. When `profile` is present and no `AZURE_AI_SEARCH_PRIVATE_BINDING_OPTION_NAMES` option is, drop `profile` and inject an inert `https://validation-probe.search.windows.net` endpoint plus a placeholder credential or `use_managed_identity=True`. The output contract depends only on `output_prefix` and schema (`rag/core.py:174`). The endpoint is used only in `on_start`. Also add a Stage-1 regression test and add the plugin to the elspeth-bc527113e7 roster.
- **Sources:** be-19#1, seam-04-plugin-policy#1.
- **Verifier notes:** Both lenses reproduced it. "The planner cannot repair it" is slightly overstated: `required_input_fields: []` would get past the check, but only by accepting runtime risk.

### be-19#1: Profile-only azure_ai_search nodes always fail Stage 1 with false guarantees: [(none)]

- **Reported at:** `src/elspeth/web/plugin_policy/profiles.py:1515`; reviewer severity high; category correctness; diff-anchored True.
- **Summary:** d3dba8a9b makes every web-authored azure_ai_search node carry only profile+index. Composer Stage 1 builds the plugin from those authored options; only the llm plugin gets an inert probe stub (_validation_probe.py:66). Construction fails, and because azure_ai_search is passes_through_input=True (ai_search.py:88), _effective_producer_vote reports that the node guarantees no fields, so every downstream required-fields consumer is rejected and the planner cannot repair it.
- **Failure scenario:** csv source (guaranteed_fields=[question]) -> azure_ai_search{profile: search-prod, index: docs, query_field: question, output_prefix: policy} -> llm{profile, required_input_fields: [question, policy__rag_context]}: state.validate() is_valid=False with schema_contract_violation 'Producer (azure_ai_search) guarantees: [(none)]'. The identical pipeline with a raw endpoint/api_key binding is_valid=True. This is the exact RAG shape the plugin's own composer_hints teach.
- **Evidence:** Scratch run against the worktree (elspeth.__file__ in worktree, PYTHONDONTWRITEBYTECODE=1, worktree status clean after): '== profile-bound search -> profiled llm is_valid: False / ERR schema_contract_violation ... Producer (azure_ai_search) guarantees: [(none)]. Missing fields: [policy__rag_context, question]' vs '== raw search (control) -> profiled llm is_valid: True'. A field_mapper consumer fails the same way. recent-code-hints.md:1590-1606 records the llm fix and requires proving provider independence before stubbing another profiled plugin; legacy issue tracker elspeth-bc527113e7 (P1, triage) tracks the roster but predates azure_ai_search becoming profiled.
- **Suggested fix:** In web/composer/_validation_probe.py, add an azure_ai_search arm that mirrors the llm arm: when 'profile' is present and none of AZURE_AI_SEARCH_PRIVATE_BINDING_OPTION_NAMES is present, drop 'profile' and set an inert endpoint (https://validation-probe.search.windows.net) and a placeholder api_key. The output contract depends only on output_prefix/schema (rag/core.py:174); the endpoint feeds only the limiter name and the searcher, which is built in on_start. Add a Stage-1 regression test and add the plugin to the elspeth-bc527113e7 roster.
- **Verifier (trace):** upheld, confidence high, severity high. The finding holds. I reproduced it at the pinned commit. A profile-only azure_ai_search node (profile plus index, no endpoint) cannot be built by the Stage 1 probe. Because the plugin is a known pass-through plugin, `_effective_producer_vote` returns (True, frozenset()) for it, so any downstream consumer that declares required fields is rejected with 'guarantees: [(none)]'. The identical pipeline with a raw endpoint/api_key binding passes. Nothing earlier guards this: Stage 1 runs on the authored state before lowering, and `prepare_validation_probe_options` stubs only plugin == "llm". The recorded ruling in recent-code-hints does not make this deliberate. It names this exact defect class for llm, and it says another operator-profiled plugin must first be proved provider-independent before it gets a stub. That is an unfinished obligation, not a decision to let azure_ai_search fail.
- **Verifier (impact):** upheld, confidence high, severity high. I could not refute this. I reproduced the defect myself at the pinned worktree. There is no recorded ruling that makes the failure intended: recent-code-hints.md:1590-1606 only says to prove the output contract is provider-independent before adding a stub for another profiled plugin. It does not say to leave profiled plugins unstubbed, and nothing downstream repairs the vote. On the web every azure_ai_search node is profile-only, because the plugin declares WebConfigAuthority.OPERATOR_PROFILED and lowering refuses authored private options. So the raw-endpoint control that validates is not a shape a web author can produce. Every web RAG pipeline that feeds a required-fields consumer is falsely rejected. The downstream llm will almost always be one, because llm/base.py:611 makes omitting required_input_fields an error when the template reads row fields, and a RAG prompt reads {prefix}__rag_context. One part of the claim is overstated: "the planner cannot repair it" is not strictly true. The llm opt-out `required_input_fields: []` (base.py:606-609) would get past the check, but only by accepting runtime risk. Even so, this blocks the plugin's own taught pairing (composer_hints: "pair it with an llm transform that reads {output_prefix}__rag_context"), so high severity stands.
