### seam-01-wire#4: Shared readiness decoder does not check the new note field; an absent key renders an empty labelled reviewer note

- **Reported at:** `src/elspeth/web/frontend/src/components/chat/DecisionPanel.tsx:230`; reviewer severity low; category decoder-looser-than-producer; diff-anchored True.
- **Summary:** 6a34007fb made ValidationReadinessBlocker.note required (string | null) in both pydantic and TypeScript. The shared admission check in validationReadiness.ts:15-21, used by validatePipeline and the audit-readiness decoder, never checks note. DecisionPanel.tsx:230 renders the block when row.note !== null, and undefined passes that test.
- **Failure scenario:** A readiness payload without note (or with a non-string note) passes isValidationReadiness. The decision panel then shows the "Reviewer's note (the advisor's own words — not verified by ELSPETH):" label with an empty body, or unvalidated content, instead of rejecting the shape. The backend always sends note today, so this is latent.
- **Evidence:** validationReadiness.ts:15-21 checks code, component_id, component_type, detail and suggestion only. types/index.ts:611 has `note: string | null`. decisionPanelRows.ts:164 sets note: blocker.note.
- **Suggested fix:** Add `(typeof blocker.note === "string" || blocker.note === null)` to isValidationReadiness.
- **Verifier (trace):** upheld, confidence high, severity low. Confirmed at 74c0ce0db, and I could not refute it. The shared decoder isValidationReadiness never checks blocker.note. Both routes that feed executionStore.validationResult go through this decoder. The first is validatePipeline in client.ts:1391. The second is the audit-readiness snapshot, which goes through isValidationResult in auditReadiness.ts:133 and then setValidationResult in useAuditReadinessSync.ts:42. No other check guards note before it is rendered. DecisionPanel.tsx:230 tests `row.note !== null`, and undefined passes that test, so the labelled reviewer-note block renders with an empty body. A non-string note, such as an object, would also get through the decoder. React would then throw when it tries to render that object as a child. This is a real case of the decoder accepting less than the producer and the wire type promise. It stays latent, and low severity is right: the backend's ValidationReadinessBlocker (schemas.py:262) is a strict pydantic model with a required `note: str | None` and no exclude_none, so the server always serialises note. docs/agents/recent-code-hints.md records no ruling that makes this decoder deliberately loose.

DecisionPanel.tsx:230 has `row.note !== null &&`. 6a34007fb added `note: null` to the fixtures in api/auditReadiness.test.ts and api/client.execution.test.ts but did not change the guard.
- **Suggested fix:** Add `(typeof blocker.note === "string" || blocker.note === null)` to the blockers `every(...)` predicate in api/validationReadiness.ts, following the suggestion clause.
- **Verifier (trace):** upheld, confidence high, severity low. The window added the field (6a34007fb) but never touched the guard: `git log 7c986dc97..74c0ce0db -- api/validationReadiness.ts` returns no commits. It is a real half-wired admission.
