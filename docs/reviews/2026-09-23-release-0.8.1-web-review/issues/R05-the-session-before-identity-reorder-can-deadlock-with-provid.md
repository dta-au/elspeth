## Finding

- **Status and severity:** confirmed, **medium**. Raised as high; the trace refuter kept it high and the impact refuter rated it medium.
- **Location:**
  - `src/elspeth/web/coordination/websocket_ticket_authority.py:47-55,105-113`.
  - `src/elspeth/web/coordination/composer_progress_authority.py:135-138,252-255,288-291,323-326`.
  - The other side of the cycle: `chargeable_admission_authority.py:36-43`, `quota_authority.py:163-177` and `sessions/service.py:10501-10512`.
- **What is wrong:** 89444b793 made ticket issue and consume, and the progress writers (heartbeat, bind, publish, begin, replay, clear), lock `sessions` FOR UPDATE and then the identity FOR UPDATE. `begin_provider_attempt` takes only the session advisory lock, which those writers never take. It then locks `identities` FOR UPDATE, and its `INSERT INTO quota_provider_attempts` takes FOR KEY SHARE on the session row through the immediate foreign key. That gives a lock cycle that did not exist before the window.
- **Failure scenario:** A run's LLM call holds identity X in admission. A websocket ticket issue or reconnect, or the 15 s compose heartbeat, takes session S FOR UPDATE and waits on X. Admission's INSERT then waits on S, and PostgreSQL raises 40P01.
  - The victim is normally the session-first side (ticket, consume or heartbeat), which recovers: the client reconnects, and `_helpers.py:2546-2552` retries the heartbeat.
  - Admission stalls for about `deadlock_timeout`, which defaults to 1 s.
  - The ReviewAuthority request, cancel and attest paths have a similar pre-existing ordering. The `settle_provider_attempt` leg depends on foreign-key trigger order and was not measured.
- **Evidence:** No handler for 40P01 or `DeadlockDetected` exists under `src/elspeth/web`. The new `tests/testcontainer/web/test_composer_progress_quota_lock_order_postgres.py:103-110` pre-locks the session and never exercises `begin_provider_attempt`.
- **Suggested fix:** Lock the session row first in admission and settlement: add `.with_for_update()` to the session reads in `RepositoryChargeableAdmissionAuthority.assess` and `settle_provider_attempt_on_connection`, or route both through `session_operation_authority.mutate`. Add testcontainer cases for admission against ticket issue and admission against heartbeat. Correct the progress docstring that claims the writes "match token accounting".
- **Sources:** seam-06-locks#1.
- **Verifier notes:** Victim selection follows PostgreSQL's documented behaviour and was not measured. The run-side failure (the audited LLM call failing) is possible but is not the expected victim.


## Source findings and verification

### seam-06-locks#1: Session-before-identity reorder deadlocks against provider-attempt admission (identity FOR UPDATE, then session FK KEY SHARE)

- **Reported at:** `src/elspeth/web/coordination/websocket_ticket_authority.py:47`; reviewer severity high; category lock-order; diff-anchored True.
- **Summary:** 89444b793 reordered progress writes and ticket issue/consume to lock the session row FOR UPDATE before the identity FOR UPDATE. SessionServiceImpl.begin_provider_attempt still does it the other way round. It takes only the session advisory lock, then assess locks identities FOR UPDATE (chargeable_admission_authority.py:39-43) while the session row stays unlocked, and then the quota_provider_attempts INSERT takes FOR KEY SHARE on the sessions row through its session_id FK (quota_authority.py:165, models.py:4039). The two orders form a cycle that did not exist before the window. The same pattern exists before the window in ReviewAuthority request/cancel/attest (engine.begin with no advisory lock, then session FOR UPDATE, then owner identity FOR UPDATE). settle_provider_attempt (ledger INSERT with identity and session FKs, no session row lock) probably forms the same cycle, depending on FK trigger order, which was not measured.
- **Failure scenario:** PostgreSQL deployment, run executing LLM calls on session S owned by X. Each call runs _admit_run_llm_call, then begin_provider_attempt: advisory(S), then identities X FOR UPDATE. The user opens or reconnects the run websocket, and ticket issue takes sessions S FOR UPDATE (free, because admission holds only the advisory lock) and then waits on X. The admission's INSERT INTO quota_provider_attempts needs FOR KEY SHARE on S, which conflicts with the ticket's FOR UPDATE. PostgreSQL raises 40P01 and aborts one side. Either the websocket ticket fails, or the audited run LLM call's before_call raises OperationalError and the call fails for an infrastructure reason. The same cycle occurs between the compose heartbeat (heartbeat_request every 15 s: session, then identity) and admit_provider_attempt for the same compose turn, which can fail the turn.
- **Evidence:** composer_progress_authority.py:135-138,252-255,288-291,323-326 now take session FOR UPDATE, then identity FOR UPDATE (git show 89444b793). websocket_ticket_authority.py:47-55 and :105-113 take session FOR UPDATE, then identity FOR UPDATE. sessions/service.py:10501-10512: _session_process_locked_begin + _session_write_lock (advisory only, service.py:4801-4822) + _require_session_operation_context_on_connection (plain fence SELECT, :4931-4964), then begin_provider_attempt_on_connection. chargeable_admission_authority.py:36-43: unlocked session SELECT, then identities FOR UPDATE. quota_authority.py:163-177: unlocked session SELECT, then INSERT quota_provider_attempts (session_id FK to sessions.id). Callers: composer/provider_quota.py:110, sessions/_auto_title.py:343, execution/service.py:4358-4367 (LLMCallGovernance.before_call). The new test tests/testcontainer/web/test_composer_progress_quota_lock_order_postgres.py:103-110 covers only settlement, and its settle() pre-locks sessions FOR UPDATE. Before the window, progress and ticket took identity first, waited on admission's X while holding nothing admission needed, so there was no cycle.
- **Suggested fix:** Lock the session row before any identity lock in admission and settlement: add .with_for_update() to the session read in RepositoryChargeableAdmissionAuthority.assess (chargeable_admission_authority.py:36-38) and to settle_provider_attempt_on_connection's session read (quota_authority.py:189). Alternatively, route begin_provider_attempt and settle_provider_attempt through session_operation_authority.mutate, which locks the session row first. Add testcontainer cases for admission versus ticket issue and admission versus heartbeat. Update the progress docstring claim that writes 'match token accounting'.
- **Verifier (trace):** upheld, confidence high, severity high. I could not refute this. On PostgreSQL the claimed lock cycle can be reached with exactly the inputs the finding describes, and nothing earlier in either path guards against it. begin_provider_attempt holds only the session advisory lock, which the ticket and progress writers never take, so the sessions row stays unlocked. It then locks the owner identity FOR UPDATE and afterwards inserts a quota_provider_attempts row. That insert has an immediate (non-deferrable) foreign key to sessions.id, so it needs FOR KEY SHARE on the session row. Since 89444b793, ticket issue/consume and the progress writers (heartbeat_request, bind_request, publish, begin_request, replay, clear) lock sessions FOR UPDATE first and identity second. FOR UPDATE conflicts with FOR KEY SHARE, so the waits form a cycle: the ticket side holds S and waits for X, while admission holds X and waits for S. PostgreSQL then raises 40P01. Before the commit the ticket and progress writers locked identity first, so they never held S while waiting for X, and no cycle was possible. The new tests do not cover this path. The ticket test's session-fenced writer is modelled as a holder that locks sessions FOR UPDATE first, and admission never does that. The progress test uses record_token_usage_on_connection after pre-locking the session. Neither exercises begin_provider_attempt. docs/agents/recent-code-hints.md has no ruling on lock order or provider attempts. Severity stays high because a deadlock on the run side sends the database error out of LLMCallGovernance.before_call and into the provider call. I did not trace the retry path in full, and the timing window (from the identity lock to the INSERT) is narrow, so frequency is low but real. I did not confirm the settlement leg, which the finding itself marks as unmeasured, because it depends on which foreign-key trigger fires first.
- **Verifier (impact):** upheld, confidence high, severity medium. I could not refute the lock cycle. I traced it at 74c0ce0db and it is real, and 89444b793, inside the window, introduced it. No recorded ruling covers it. The commit says it reorders progress, ticket and approval locks 'session before identity to match token-ledger settlement'. That is true for settlement, but provider-attempt admission still locks the identity row first and only then touches the session row, through the INSERT's foreign-key check. Nothing serializes the two sides. Admission holds only the session advisory lock, which ticket issue/consume and progress heartbeat/publish never take. No code under src/elspeth/web handles 40P01 or DeadlockDetected, and no testcontainer test puts begin_provider_attempt against ticket issue or heartbeat.

I am lowering the severity from high to medium. In this cycle the session-first transaction (ticket, consume or heartbeat) always starts waiting first, because it blocks on identity X, which admission already holds. PostgreSQL's deadlock check runs in the waiter whose deadlock_timeout expires first, so that side is normally the one aborted. Every one of those victims recovers. A ticket-issue 500 reaches websocket.ts:132-148, which calls scheduleReconnect with backoff. A consume error before accept fails the handshake, which the client treats as 1006 and reconnects. A heartbeat OperationalError is retried at _helpers.py:2546-2552. The admission itself stalls for about deadlock_timeout (1 s by default) and then goes ahead. The finding's worse outcome, the audited run LLM call failing, is not the expected victim. This victim selection comes from PostgreSQL's documented behaviour and was not measured, because running tests was out of scope. What remains is a real regression: spurious 40P01 errors, websocket reconnect churn and roughly 1 s admission stalls, all likely under load because admission transactions on a busy run follow each other almost continuously. It is not a failure path for audited calls.
