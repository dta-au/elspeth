### be-26#2: Recompose planner-failure progress event lacks the COST_UNAVAILABLE branch added to send_message

- **Reported at:** `src/elspeth/web/sessions/routes/composer/compose.py:434`; reviewer severity medium; category half-wired-change; diff-anchored False.
- **Summary:** 101824e7d gave the send_message route (messages.py:659-668) and the guided route COST_UNAVAILABLE-specific progress wording. The recompose mirror still reports 'model did not return a usable pipeline plan' / 'Retry...check the composer provider' with a hardcoded reason='provider_unavailable', despite its own comment that the two routes must translate PipelinePlannerError identically.
- **Failure scenario:** Model pricing is not configured. Send returns 503 cost_unavailable with the correct advice to ask an administrator. The user clicks Retry and /recompose hits COST_UNAVAILABLE again. The progress snapshot now blames the provider and says to retry, though retrying cannot fix a pricing-configuration error. The HTTP 503 body is still correct because _handle_planner_failure is shared.
- **Evidence:** compose.py:423-425 comment: 'must translate PipelinePlannerError identically or the two routes drift on failure UX'. compose.py:434-436 is unchanged (blame 251879d05). messages.py:661/666 has the conditional wording and uses freeform_planner_progress_reason, which maps COST_UNAVAILABLE to service_setup_failed (_helpers.py:2954).
- **Suggested fix:** Copy the COST_UNAVAILABLE conditional evidence/likely_next into compose.py and replace the hardcoded reason with freeform_planner_progress_reason(exc.code).
- **Verifier (trace):** upheld, confidence high, severity low. I confirmed the drift at 74c0ce0db. The recompose route calls the same `composer.compose` as send_message (compose.py:202). Its `except PipelinePlannerError` arm (compose.py:421-448) still publishes the generic progress event: evidence "The composer model did not return a usable pipeline plan.", likely_next "Retry the request; ... check the composer provider." and a hardcoded reason="provider_unavailable" (compose.py:434-436, blamed to 251879d059 on 2026-07-20). Commit 101824e7d, inside the window, added COST_UNAVAILABLE-specific wording only to messages.py:659-668 and the guided route. It also added the COST_UNAVAILABLE -> service_setup_failed entry to the `_FREEFORM_PLANNER_PROGRESS_REASONS` table (_helpers.py:2954), but only messages.py:672 calls `freeform_planner_progress_reason`, so recompose never uses that mapping. COST_UNAVAILABLE is reachable: pipeline_planner.py:4066 raises it whenever the provider call carries no cost (call.provider_cost is None). I found no guard, normaliser or recorded ruling that excludes recompose. The comment at compose.py:423-425 says the two routes must translate this identically, and the progress event is where they now differ. I lowered the severity to low. The HTTP outcome is correct on both routes: `_handle_planner_failure` is shared and returns 503 cost_unavailable with the "ask an administrator to configure pricing" detail (_helpers.py:2908-2911, 2997-2998), and the durable disposition row carries the right code. Only the progress snapshot's evidence, likely_next and reason are wrong: they blame the provider and tell the user to retry. The hardcoded reason is older than the window; it is the same drift left behind when elspeth-ad5628ecda fixed the reason on the send path only. That older gap makes the drift wider, not a reason to dismiss the finding.

### be-23#3: COST_UNAVAILABLE progress mapping not consumed by the recompose route

- **Reported at:** `src/elspeth/web/sessions/routes/_helpers.py:2954`; reviewer severity low; category half-wired; diff-anchored True.
- **Summary:** 101824e7d added COST_UNAVAILABLE->service_setup_failed and a 503 'ask an administrator' mapping, and wired send_message to use them. The recompose PipelinePlannerError arm (compose.py:429-437) still hardcodes reason='provider_unavailable' and 'Retry the request'. The comment above _FREEFORM_PLANNER_PROGRESS_REASONS ('only codes whose ACTOR is the planner') no longer describes this entry, whose actor is deployment pricing configuration.
- **Failure scenario:** Pricing for the composer model is missing and the user retries via recompose. The progress stream says the composer model returned an unusable plan and invites a retry, blaming the provider. At the same time the HTTP 503 body says retrying won't help until an admin fixes pricing. Telemetry attributes the failure to provider_unavailable.
- **Evidence:** messages.py:655-672 branches on COST_UNAVAILABLE and calls freeform_planner_progress_reason(exc.code). compose.py:429-437 publishes reason='provider_unavailable' with fixed retry copy; git log -L shows that block last changed 2026-08-03.
- **Suggested fix:** Make the recompose arm mirror messages.py:655-672 using freeform_planner_progress_reason(exc.code) and the COST_UNAVAILABLE evidence/likely_next copy, and amend the map's comment.
- **Verifier (trace):** upheld, confidence high, severity low. Confirmed at 74c0ce0db. 101824e7d changed four places: it added COST_UNAVAILABLE->"service_setup_failed" to the progress map (_helpers.py:2954), added the cost_unavailable 503 "Ask an administrator..." HTTP entry (_helpers.py:2894-2897), added the failure-code branch (_helpers.py:2983-2984), and added COST_UNAVAILABLE-specific evidence and likely_next copy in send_message (messages.py:655-672). The recompose PipelinePlannerError arm (composer/compose.py:421-445) was left out of that commit. It still publishes reason="provider_unavailable" with the evidence "The composer model did not return a usable pipeline plan." and "Retry the request...". That arm's own comment (compose.py:423-426) says it must translate the error "identically or the two routes drift on failure UX". The path is reachable. Recompose (compose.py:86-90) calls composer.compose (line 202), which goes through service._plan_and_stage_empty_pipeline (service.py:4099). There the planner raises PipelinePlannerError(code="COST_UNAVAILABLE") whenever provider_cost is None (pipeline_planner.py:4063-4066). No guard catches it before the recompose arm. The same arm then calls the shared _handle_planner_failure, so the HTTP body is 503 cost_unavailable with the admin copy while the progress event blames the provider and invites a retry. One refinement: the durable disposition row and the HTTP failure_code both correctly say cost_unavailable. Only the progress-event reason says provider_unavailable, so the finding's claim that telemetry attributes the failure to provider_unavailable is true of the progress reason only. The drift also covers other codes: the recompose arm never adopted freeform_planner_progress_reason for any code, and that part predates the window. The window made it worse by adding a code whose correct handling is 'do not retry'. The comment on the map ('only codes whose ACTOR is the planner') is mildly stale for a pricing-configuration fault. The effect is limited to wrong progress-stream copy and reason on one route. The HTTP response is correct, so low severity stands.
