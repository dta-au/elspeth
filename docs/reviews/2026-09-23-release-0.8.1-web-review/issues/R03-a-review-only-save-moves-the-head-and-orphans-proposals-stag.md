## Finding

- **Status and severity:** confirmed, **medium**. seam-01-wire#1 was raised as high.
- **Location:**
  - `src/elspeth/web/sessions/routes/messages.py:845-847` and `src/elspeth/web/sessions/routes/composer/compose.py:591-593`, where the new predicate `result.state.version != state.version or completion_gate_decision_changes(...)` is checked.
  - The save itself is at `compose.py:675-682`. Its comment at `677-679` still says "after the LLM composer returns a newer state version".
- **What is wrong:** When only the advisor outcome changed, the routes now call `save_composition_state`, which mints a new row id (`sessions/service.py:6562`). Freeform proposals bind to the pre-turn row: `tool_batch.py:1647` sets `base_state_id=current_state_id`, and `set_pipeline` uses `PresentBase.state_id`. Only guided proposals are ever rebased (`sessions/service.py:2991`). The END gate has no exemption for turns that staged proposals (`composer/service.py:6672-6720`).
- **Failure scenario:**
  1. A session in `trust_mode` `explicit_approve` has head S0 with a non-empty graph and no prior fact.
  2. The model stages proposal P with base S0 and ends the turn without a tool call.
  3. The END advisor blocks the unchanged graph, so the route saves S1.
  4. The SPA's `proposalBaseChanged` (`actionableProposals.ts:12-19`) marks P obsolete. Accept returns 409 `proposal_base_state_changed` (`routes/composer/proposals.py:367-381`), and `set_pipeline` auto-rejects on `BASE_CONFLICT` (`pipeline_commit.py:402-404`).
  5. The same save retires open workflow approvals through `supersede_open_approvals` (`sessions/service.py:6583-6588`) and sets `lastComposeChangedPipeline`, so the SPA shows "Pipeline updated".
  6. For retryable causes (unavailable, malformed, message_rejected), advisor wording that varies between runs can re-save and orphan the next proposal as well.
- **Evidence:** recent-code-hints.md (as changed by 41aeaeac0) sanctions the review-only snapshot but never mentions pending proposals. `test_advisor_recovery_routes.py` has no mention of proposals.
- **Suggested fix:** Pick one of these:
  - Skip the review-only snapshot when the turn left a pending proposal on `pre_send_state_id`, and let the next row carry the fact.
  - Rebase pending proposals whose `composition_content_hash` is unchanged onto the new row in the same save.
  - Persist the review outcome without minting a new head row.
  In every case, derive "pipeline changed" in the SPA from the graph, not the version number. Add a route test that stages a proposal in a turn whose outcome flips and then accepts it.
- **Sources:** seam-01-wire#1, be-20#1.
- **Verifier notes:** Severity was lowered because only `explicit_approve` sessions stage ordinary proposals, and `auto_commit` is the default (`models.py:489,523`). Nothing is lost, and the 409 text tells the user to ask for a rebase. A `graph_rejected` block does not repeat on the rebase turn.
  - Refinement from be-20#1's trace: with no prior fact, `AdvisorGatePassed` does not save. Only three transitions save: blocked with no prior fact, a transient block turning clean, and clean turning blocked.


## Source findings and verification

### seam-01-wire#1: Review-only save (advisor decision changed, graph unchanged) moves the head and orphans proposals staged in the same turn

- **Reported at:** `src/elspeth/web/sessions/routes/messages.py:845`; reviewer severity high; category regression; diff-anchored True.
- **Summary:** Since 41aeaeac0 the send route (messages.py:845) and recompose route (compose.py:591) take the save branch when completion_gate_decision_changes() is true, even when state.version did not change. save_composition_state gives the new row version max+1 (sessions/service.py:6562), so the head row id changes. Freeform proposals are staged with base_state_id set to the pre-turn row (tool_batch.py:1647). Only guided proposals are ever re-based. accept_composition_proposal then returns a 409 proposal_base_state_changed (proposals.py:371-379), and the SPA marks the proposal stale.
- **Failure scenario:** The session is in trust_mode explicit_approve and head row S0 has a non-empty graph and a clean envelope. The user asks for a change, so the model stages proposal P with base S0 and ends the turn without a tool call. The END advisor reviews the unchanged S0 graph and blocks it. The decision differs from the prior fact, so the route saves S1 with the same graph and a new id. The user clicks Accept on P and gets a 409 saying the session state changed after the proposal was created, although they changed nothing. The same save also sets lastComposeChangedPipeline (sessionStore.ts:2216/2259), so the badge says 'Pipeline updated' and validation is cleared. For block causes other than graph_rejected (unavailable, malformed, message_rejected), the gate reviews again on the unchanged graph. Advisor detail and note text varies between runs, so a re-block with different wording saves another row and the next proposal gets the 409 too.
- **Evidence:** At 74c0ce0db: messages.py:845 and compose.py:591 read `elif result.state.version != state.version or completion_gate_decision_changes(...)`. sessions/service.py:6562 computes next_version as max+1. tool_batch.py:1647 stages proposals with base_state_id=UUID(current_state_id). The only proposal.rebased writer is guided (sessions/service.py:2991, guided_proposal_rebase.py). proposals.py:371-379 is the base check. _evaluate_terminal_no_tool_advisor_gate (composer/service.py:6672+) has no exemption for turns that staged proposals. AdvisorBlockCause members are listed at advisor_decision.py:7-11. The recent-code-hints ruling allows the review-only save but does not address how pending proposals are bound to a base state.
- **Suggested fix:** On a save that only changes the review outcome, either carry pending freeform proposals' base forward (append a rebase hop), or compare the graph fingerprint rather than the row id in the accept base check. Alternatively, persist the review outcome without minting a new head row. Also have the SPA derive 'pipeline changed' from a graph change rather than from the version number.
- **Verifier (trace):** upheld, confidence high, severity medium. I traced the whole path at 74c0ce0db and could not refute it. When a turn changes only the review outcome, the route saves a new head row. Freeform proposals are bound to the old head row id. Nothing in the freeform lane re-bases them, so accepting one returns a 409 even though the graph did not change. Two things in the finding go too far. First, the recent-code-hints ruling asks for a new row on a review-only save, but it says nothing about proposals that are still pending. Second, when the cause is graph_rejected there is a workaround. On the next turn, advisor_block_covers_unchanged_graph skips the gate for the unchanged graph, so no new row is saved and a re-staged proposal can be accepted. That is why I lowered the severity from high to medium. For the causes that can be retried (unavailable, malformed, message_rejected), the gate reviews the graph again, so the proposal can be orphaned again.
- **Verifier (impact):** upheld, confidence high, severity medium. I could not refute the finding; the failure path holds at 74c0ce0db. Before the window (7c986dc97, messages.py:830) the route saved only on `result.state.version != state.version`. Commit 41aeaeac0 added `or completion_gate_decision_changes(...)` at messages.py:845 and compose.py:591. A turn that only changes the review outcome now inserts a new head row with a fresh UUID (sessions/service.py:6562-6567). Both accept paths compare the base by row id. Generic proposals return 409 `proposal_base_state_changed` (routes/composer/proposals.py:369-379). `set_pipeline` proposals fail with BASE_CONFLICT on `current_state_id != base.state_id` (pipeline_commit.py:402-404), even when the content hash matches. The END gate has no exemption for turns that staged proposals. `last_mutation_was_pending_proposal` is only an unused alias in service.py:444 and is not consulted in `_evaluate_terminal_no_tool_advisor_gate` (service.py:6672-6720). The skip applies only to a prior `graph_rejected` fact on the same graph. The advisor sees the user's message but not the pending proposals (service.py:8391-8411). So when a user asks for a change that is staged but not applied, a block on the unchanged graph is a realistic outcome, not a corner case. The recorded ruling in recent-code-hints.md (changed by 41aeaeac0) intends the new snapshot on an unchanged graph. It does not mention pending proposals, so it does not cover this effect. The test file added with the change (test_advisor_recovery_routes.py) never mentions proposals. I am lowering severity from high to medium because the impact is narrower than claimed. (1) Only explicit_approve sessions stage ordinary proposals, and the default is auto_commit (models.py:489,523). In auto_commit, `set_pipeline` settles through `route_settlement` before this branch. (2) Nothing is lost or corrupted. The SPA marks the proposal stale (sessionStore.ts:593-597), and the 409 text tells the user to ask ELSPETH to rebase, which re-stages it on the new head. That follow-up turn is usually safe: a `graph_rejected` fact on the unchanged graph makes the gate skip (`advisor_block_covers_unchanged_graph`), so there is no second save. It repeats only for unavailable, malformed or message_rejected blocks whose wording differs between runs. The finding also omits a side effect: the same review-only save runs `supersede_open_approvals` (sessions/service.py:6583-6588). That retires open workflow approvals on a head change that did not change the graph.

### be-20#1: Saving a review-only outcome makes proposals staged in the same turn stale

- **Reported at:** `src/elspeth/web/sessions/routes/composer/compose.py:591`; reviewer severity medium; category ux-regression; diff-anchored True.
- **Summary:** The new persist condition `result.state.version != state.version or completion_gate_decision_changes(...)` writes a new composition_states row through save_composition_state when only the advisor outcome changed. Pending proposals bind to the previous row id (tool_batch.py:1647 base_state_id; the set_pipeline PresentBase.state_id), so a proposal staged in the same turn is stale as soon as the response lands.
- **Failure scenario:** The session uses manual approval and holds a non-empty graph G at row S1 with no prior gate fact. The composer stages approval-required proposal P (base S1) and ends with no tool call. The END gate flags G and returns AdvisorGateBlocked, so completion_gate_decision_changes(None, Blocked, G) is True and the route saves S2. The SPA's proposalBaseChanged (actionableProposals.ts:12-19) marks P obsolete. Accept returns 409 proposal_base_state_changed (proposals.py:367-381); for set_pipeline, BASE_CONFLICT (pipeline_commit.py:403-404) auto-rejects P. The same thing happens when a prior transient block flips to CLEAN, or CLEAN flips to transient. The user must ask ELSPETH to rebase a proposal it just produced.
- **Evidence:** compose.py:591-593 elif predicate; compose.py:675-682 save_composition_state (comment at 677-679 still says 'after the LLM composer returns a newer state version'); service.py:6672 END gate runs on any non-empty state, skipping only on a prior graph_rejected fact for the same graph; service.py:6980-6982 AdvisorGatePassed; tool_batch.py:1647 base_state_id=current_state_id; pipeline_settlement.py:304-331 rejects on BASE_CONFLICT; test_advisor_recovery_routes.py has 0 'proposal' hits. The sibling defect is at messages.py:845-872. Before the window an unchanged-version freeform turn never saved a row (the guided-transition arm at compose.py:686-711 is the only earlier exception).
- **Suggested fix:** Skip the review-only snapshot when the turn left a pending proposal based on pre_send_state_id (e.g. last_mutation_was_pending_proposal) and let the next row carry the fact, or rebase pending proposals whose composition_content_hash is unchanged onto the new row in the same save. Add a route test that stages a proposal in a turn whose advisor outcome flips, then accepts it.
- **Verifier (trace):** upheld, confidence high, severity medium. I could not refute this. I traced the path at 74c0ce0db and it is reachable with no guard in the way. When a proposal is staged, the turn's version does not change: tool_batch.py returns `updated_state=state`. The END gate has no check for pending proposals. It runs on any non-empty state and skips only when the stored fact is a graph_rejected for the same graph (service.py:6746-6760). The window's new `elif` in compose.py:591-593 then saves a new composition_states row with save_composition_state. Nothing in append_state (coordination/repository.py:829-900) moves pending proposals onto that new row. Accepting the proposal then compares its stored base state id against the current row id, so the proposal is stale. The recorded ruling in recent-code-hints ("Both routes save changed review outcomes in a new fenced snapshot even when the graph is unchanged") approves the save itself. Neither that ruling nor the plan docs/plans/2026-09-22-advisor-transient-failure-recovery.md mentions proposals (grep finds 0 hits), so the side effect was not decided on purpose. One detail to tighten: with no prior fact, an AdvisorGatePassed result does NOT cause a save. resolve_completion_gate_facts gives CompletionGateFacts(None), which equals the default previous value (completion_gates.py:238-248). Only three triggers cause a save: blocked with no prior fact, a transient block that turns CLEAN, and a CLEAN result that turns into a block. The reviewer's scenario uses Blocked and is correct.
