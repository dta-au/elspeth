- **Location:**
  - `src/elspeth/web/execution/completion_gates.py:273-276`: the check that `schema_version` must be 2.
  - `completion_gates.py:309-316`: `cause` is required.
  - `src/elspeth/web/sessions/schema.py:36-40`: `_COORDINATION_HARD_CUT_EPOCH = 65`. Its comment still says epoch 65 exists only for the note key.
  - `src/elspeth/web/sessions/models.py:358`: `SESSION_SCHEMA_EPOCH = 65`.

- **What is wrong:** 539121b17 bumped the epoch from 64 to 65 for the required `note` key, because "the strict parser refuses an envelope without it". The writers at that epoch stored `{}` on every clean compose save and blocked facts without `cause`. 41aeaeac0 then made both of those shapes Tier-1 errors and left the epoch at 65. Startup's exact-epoch check (`schema.py:327`) therefore accepts stores it can no longer read.
- **Failure scenario:** A session DB is stamped 65 by a build between 539121b17 and 41aeaeac0^ and then upgraded to `74c0ce0db`. Startup passes. Every session whose head row has `completion_gates == {}` then fails as follows:

  - execute and validate raise `CompletionGateIntegrityError`.
  - audit readiness, shareable reviews and the recovery handlers' `_durable_completion_gates` also fail. The recovery handlers catch only `SQLAlchemyError`.
  - The session cannot compose a new row to recover.
- **Evidence:**
  - `git show 41aeaeac0^:src/elspeth/web/execution/completion_gates.py` has `return {}` at lines 199/202/234 and no `schema_version`.
  - `git log -S` shows only 101824e7d (63 to 64) and 539121b17 (64 to 65) touching the epoch constants in the window.
  - Commit timeline (measured): 539121b17 at 09-22 14:38 on its branch. 5bcd983c9 merged it into the `release/0.8.1` first parent at 09-22 22:55. 41aeaeac0 and its merge 23185f55a landed at 09-23 00:55.
  - The epoch-62 comment (`models.py:346-348`) records the convention: "reject earlier stores at startup before an old blocked envelope can fail during session reload".
  - The ruling ("no old-format compatibility is provided"; plan `docs/plans/2026-09-22-advisor-transient-failure-recovery.md:17,111,260`) forbids dual-read. It does not address the epoch fence.
  - The `74c0ce0db` CHANGELOG says startup accepts "an existing database matching the exact current schema epoch (session 65)". That is false for early-65 stores.
- **Suggested fix:** Bump `SESSION_SCHEMA_EPOCH` and `_COORDINATION_HARD_CUT_EPOCH` together to 66 and name the v2 envelope in both comments. Move the coupled literal sites: the tripwire tests, the tests in `tests/unit/web/sessions`, `tests/unit/docs`, `tests/unit/architecture` and `tests/unit/website`, the README, the CHANGELOG cutoff line, the runbooks and `website/get-started.html`. Add no compatibility code. The alternative is an explicit ruling plus CHANGELOG and runbook text saying that early-65 stores must be recreated.
- **Sources:** be-23#1, be-04#1, be-26#1, seam-01-wire#2, be-17#1, seam-08-execution#1.
- **Verifier notes:** Every trace refuter confirmed the mechanism. The only disagreement is about exposure (§3).
  - be-26#1's claim that `messages.py:216` "was added" is wrong: the parse call already existed. What 41aeaeac0 changed is the grammar the parser enforces.

### be-04#1: Completion-gates schema v2 and required cause shipped without a session epoch bump

- **Summary:** Commit 41aeaeac0 added the required AdvisorSignoffGateFact.cause (advisor_decision.py:22). parse_completion_gates now rejects any completion_gates value that lacks schema_version==2 or a valid cause, including an empty mapping. SESSION_SCHEMA_EPOCH and _COORDINATION_HARD_CUT_EPOCH stayed at 65, the value set by 539121b17, whose writers produced exactly those now-rejected shapes.
- **Failure scenario:** 1. A session store is created at epoch 65 by any build from 539121b17 to 41aeaeac0^ (the epoch-65 deploy note required a DB rename, so this is the expected operator state). 2. Build 74c0ce0db is deployed; the epoch check passes (65 == 65). 3. Every session that ever finished a compose turn has composer_meta.completion_gates == {} or a block without a cause. 4. The next message/compose/validate/execute request on that session, and the audit-readiness and shareable-review reads (messages.py:216, compose.py:135, _helpers.py:998/2760, execution/service.py:1272/1800/2794, execution/routes.py:1003, audit_readiness/service.py:564, shareable_reviews/service.py:434), raises ValueError('Tier 1: completion_gates.schema_version must be 2'). The result is a crash on each request for every existing session, where the project convention is a clean refusal at startup.
- **Evidence:** git show 539121b17:src/elspeth/web/execution/completion_gates.py lines 185-238: the writers return {} or {advisor_signoff:{status,detail,suggestion,for_graph,note}} with no version or cause. At HEAD, completion_gates.py:273-276 requires version 2 and :309-315 requires cause. sessions/models.py:358 and schema.py:40 were last changed in 539121b17, whose message says a required note key 'cannot be read forward. Pre-1.0 policy: the store is recreated'. HEAD writers (completion_gates_meta_from_facts :185, called from _helpers.py:997/998/2763) always emit schema_version 2, so only rows written before 41aeaeac0 are affected. Recorded ruling (docs/plans/2026-09-22-advisor-transient-failure-recovery.md:17,111,260): old-format envelopes must fail validation. Rejecting them is deliberate; leaving out the epoch fence is the disputed part.
- **Suggested fix:** Bump SESSION_SCHEMA_EPOCH and _COORDINATION_HARD_CUT_EPOCH to 66, update the epoch literal sites (tripwire tests, docs, website/get-started.html), and record it in the hints appendix. Old stores are then refused once at startup with the recreate instruction.
- **Verifier (trace):** upheld, confidence high, severity medium. I traced the path at 74c0ce0db and could not refute it. 41aeaeac0 removed completion_gates_meta_value, which wrote {} on every clean turn and a cause-less {advisor_signoff:{status,detail,suggestion,for_graph,note}} on a block. At HEAD, parse_completion_gates (completion_gates.py:273-276) rejects any envelope without schema_version==2, including {}, and :309-315 rejects any block without a valid cause. The epoch stayed at 65 (models.py:358, schema.py:40). No commit after 41aeaeac0 in the window (23185f55a merge, 74c0ce0db CHANGELOG) bumps it.

The codebase's own convention is to fence exactly this class of change at startup. The epoch-62 comment at models.py:346-348 reads: "Semantic-only JSON grammar cut: reject earlier stores at startup before an old blocked envelope can fail during session reload." The 539121b17 message bumped to 65 for a required JSON key because such a store "cannot be read forward".

The recorded ruling does not cover the missing fence. It says "no backwards compatibility; old-format envelopes must fail validation" and "do not add migrations, compatibility branches or reset existing data" (plan :17, :111, :260; hints entry). An epoch bump is none of those things. It is the project's fail-closed refusal of a stale store, not compatibility code, and the ruling is silent on it. 74c0ce0db makes the gap visible in the docs: the CHANGELOG now says startup accepts "an existing database matching the exact current schema epoch (session 65)". An epoch-65 store written before 41aeaeac0 passes that check, then every existing session fails with ValueError on each of the uncaught parse sites.

Limits: the only stores affected are epoch-65 stores that builds between 539121b17 (09-22 14:38) and 41aeaeac0 (09-23 00:55) wrote into, which means dev or staging stores on the unreleased branch. Upgrades from 0.8.0 are still refused at startup because their epoch is below 65. The failure is loud (a Tier 1 ValueError giving HTTP 500), not silent. It bricks every existing session in an affected store with no startup message pointing to the recreate step, and that is the outcome the convention exists to prevent. Medium is fair, with low arguable given how narrow the window is.
