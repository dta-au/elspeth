## Finding

- **Location:** `src/elspeth/web/frontend/src/components/workspace/ApprovalsView.tsx:18-22`, `inspector/GraphApprovals.tsx:5-37`, `ArtifactWorkspace.tsx:601-611` and `workspace.css:313-321`.
- **Wrong:** The tab has no focusable content, and its scrolling tabpanel has no `tabIndex`. This conflicts with the house WCAG 2.1.1 idiom (`chat.css:1113-1120`, `GraphOutputs.tsx:113`). **Scenario:** a keyboard-only Safari user cannot scroll to approval rows below the fold.
- **Fix:** Wrap the table in a labelled `tabIndex={0}` group, or make the panel focusable.
- **Sources:** fe-06#2, fe-10#2.
- **Verifier notes:** The Approvals tab never had the scroller. 040b89986 removed the Workflow disclosure, which was the only surface with one. Chromium 130+ and Firefox auto-focus scrollers.


## Source findings and verification

### fe-06#2: Approvals history lost its keyboard-focusable scroller; the Approvals tabpanel is not focusable

- **Reported at:** `src/elspeth/web/frontend/src/components/inspector/GraphApprovals.tsx:7`; reviewer severity low; category accessibility; diff-anchored True.
- **Summary:** 040b89986 removed the `graph-detail-table-scroll tabIndex=0 role=group` wrapper along with the Workflow-tab disclosure. ApprovalsView renders the bare table inside the `.artifact-workspace-panel` tabpanel, which has overflow: auto and no tabIndex, and the table has no focusable content. That conflicts with the project's recorded WCAG 2.1.1 ruling that scroll containers without controls must be focusable.
- **Failure scenario:** A session with several approved full prompts (pre-wrapped values) overflows the Approvals panel. A keyboard-only Safari user (or one on older Chromium) opens the Approvals tab. Tab moves past the panel and arrow keys switch tabs, so rows below the fold can't be scrolled into view. Before the window the same rows sat in a tabIndex=0 scroller on the Workflow tab.
- **Evidence:** GraphApprovals.tsx:5-37 (table only). ApprovalsView.tsx:19-20. ArtifactWorkspace.tsx:603-611 (tabpanel, no tabIndex). workspace.css:314-322 (overflow: auto). Ruling precedent: chat.css:1113-1116, ChatPanel.tsx:3397, GraphOutputs.tsx:113. Chromium 130+ and Firefox auto-focus scrollers, so the impact is mainly Safari. recent-code-hints.md has no contrary ruling.
- **Suggested fix:** Give the Approvals tabpanel tabIndex={0} (the WAI-ARIA tabs pattern for a panel with no focusable content), or wrap ApprovalsTable in ApprovalsView in a focusable, labelled role=group container like GraphOutputs.tsx:113.
- **Verifier (trace):** upheld, confidence high, severity low. I traced the code path and it holds. At 74c0ce0db the Approvals artifact tab renders ApprovalsView. ApprovalsView puts the bare ApprovalsTable in a plain div with no tabIndex (ApprovalsView.tsx:18-22). The table contains only th/td/code/span/time elements, none of them focusable (GraphApprovals.tsx:5-37), and ApprovalsView adds no controls of its own (ApprovalsView.tsx:34-54). The element that actually scrolls is the tabpanel `.artifact-workspace-panel` (workspace.css:313-321: flex 1 1 auto, min-height 0, overflow auto). That tabpanel has role/id/aria/hidden/inert attributes but no tabIndex (ArtifactWorkspace.tsx:601-636). The only tabIndex in the file is the roving tabindex on the tab buttons (ArtifactWorkspace.tsx:518). No custom keyboard-scroll handler exists: grep for PageDown/scrollBy finds none, and --scroll-owner is a CSS naming contract only. So a keyboard-only user in a browser that does not auto-focus scroll containers cannot reach approval rows below the fold. That conflicts with the project's own WCAG 2.1.1 idiom for content-only scrollers (chat.css:1113-1119, and the removed graph-detail-table-scroll tabIndex=0 role=group wrapper). recent-code-hints.md has no ruling on approvals or scrollers. One correction to the attribution: the Approvals tab never had a focusable scroller. It was added in the window by 6a50bab15, and 543ed1d68 swapped its list for the table 'given the whole panel instead of a 12rem scroller'. What 040b89986 did was remove the Workflow-tab disclosure, which was the only remaining keyboard-reachable scroller for the same rows. All three commits are in 7c986dc97..74c0ce0db, so the defect is diff-anchored either way. The severity stays low: the impact falls mainly on Safari, since recent Chromium and Firefox make scrollers keyboard-focusable, and nothing is lost or corrupted.

### fe-10#2: Approvals tab dropped the keyboard-focusable scroll region the removed disclosure had

- **Reported at:** `src/elspeth/web/frontend/src/components/workspace/ApprovalsView.tsx:19`; reviewer severity low; category accessibility; diff-anchored True.
- **Summary:** 040b89986 removed GraphApprovals' `<div className="graph-detail-table-scroll" tabIndex={0} role="group" aria-label="Approvals table">`, which existed under the house WCAG 2.1.1 ruling. The new tab renders a bare text-only table inside a tabpanel scroller (.artifact-workspace-panel, overflow:auto) that has no tabIndex and no focusable descendants.
- **Failure scenario:** A session with several prompt-template approvals, each rendering the full system and user prompt with pre-wrap, overflows the pane. A keyboard-only user in a browser without automatic focusable scrollers (Safari) presses Tab from the Approvals tab button, focus leaves the panel, and the rows below the fold cannot be scrolled into view.
- **Evidence:** ApprovalsView.tsx:19-21; GraphApprovals.tsx ApprovalsTable has no interactive content; ArtifactWorkspace.tsx:601-611 tabpanel has no tabIndex; workspace.css:314-321 overflow:auto; ruling precedent at chat.css:1116 and ChatPanel.tsx:3397. The Spec and YAML panels share the tabIndex-less tabpanel pattern, so the regression is specifically the dropped explicit scroll group.
- **Suggested fix:** Wrap the table in a labelled tabIndex={0} scroll group, as before, or set tabIndex={0} on the tabpanel when its content has no focusable descendant.
- **Verifier (trace):** upheld, confidence medium, severity low. The finding's framing is slightly off, but the defect is real. The Approvals tab never had the tabIndex scroll group. `ApprovalsView.tsx` is new in this window (6a50bab15, then 543ed1d68, 040b89986 and 29f9af13b), and none of its versions carried a tabIndex. The `<div className="graph-detail-table-scroll" tabIndex={0} role="group" aria-label="Approvals table">` that 040b89986 removed lived in the Workflow tab's `<details>` disclosure (GraphApprovals, rendered by GraphView). So the Approvals tab did not "drop" anything. What did change is where a keyboard user can reach the approvals. Before 040b89986, the approval rows could be read through the Workflow disclosure's focusable 12rem scroller. After it, the only place they appear is the Approvals tab, and nothing there can take focus. Tracing the render: ApprovalsView.tsx:19-21 is a plain `div.graph-detail-table` holding the ApprovalsTable. The table (GraphApprovals.tsx:5-37) contains only th/td/code/span/time, with no links, buttons or tabIndex. The header (ApprovalsView.tsx:37-46) is text only. The scroller is the tabpanel (ArtifactWorkspace.tsx:603-611), which has no tabIndex. Its CSS at workspace.css:314-321 sets overflow:auto. The only tabIndex in ArtifactWorkspace is on the tab buttons (line 518). Neither .checks-view nor .audit-readiness adds a scroller of its own. .audit-readiness is overflow:hidden, so the panel is what scrolls. The rows show the full approved prompt text (approvalRows.ts:94 `value: event.accepted_value`, and inspector.css:405-407 sets `white-space: pre-wrap` on `.graph-approvals-value`), so overflow is plausible once there are several prompt approvals. The house WCAG 2.1.1 ruling at chat.css:1113-1120 requires exactly this idiom, and GraphOutputs.tsx:113 still follows it. No recorded ruling exempts this panel. The failure path holds only in browsers that do not make scrollers focusable automatically, mainly Safari. Chrome/Edge 130+ and Firefox let the keyboard reach the overflowing panel, which keeps the severity low.
