## Finding

- **Status and severity:** confirmed, **medium**. be-09#1 was lowered to low; seam-02-advisor#2 and be-06#1 stayed medium.
- **Location:**
  - `src/elspeth/web/composer/no_tool_policy.py:157-172`: the comment and `_ADVISOR_SIGNOFF_UNVERIFIED_PUBLISHED_NOTICE`.
  - `composer/service.py:8621-8627` (flagged reasons mapped to `GRAPH_REJECTED`), `:8683-8698` (the ABSENT arm), `:10956` and `:11388` (the contradicting suggestion).
  - `execution/completion_gates.py:381-398`: `advisor_block_covers_unchanged_graph`.
- **What is wrong:** The comment's premise, "A fact persists only with a new state row, which only a mutating turn writes … Such a block persists nothing", was made false by 41aeaeac0. A `flagged_final_pass` or `flagged_no_repair` block with `runtime_preflight` None now persists as GRAPH_REJECTED, and the next unchanged message skips the review with `unchanged_graph_already_blocked`. The copy is still chosen by preflight shape, not by cause. 41aeaeac0 removed the matching premise from recent-code-hints.md and rewrote the ruling to "graph rejection requires a pipeline change". It left this comment, the notice and the test pin in place.
- **Failure scenario:** On an unchanged, Stage-1-valid, blob-free graph, the user asks a question. The advisor flags twice. The chat and the in-turn blocker say the review runs again on the next message, while the same blocker's suggestion says "after your next pipeline change". The user resends and no review runs. Only a pipeline edit clears the block.
- **Evidence:** `tests/unit/web/composer/test_no_tool_policy_segments.py:857-892` still pins the notice in the "unchanged turn" family (`_NOTICES_FOR_AN_UNCHANGED_TURN_BLOCK`). Plan Task 5 step 1 says graph-rejection notices keep their pipeline-change guidance.
- **Suggested fix:** Split the ABSENT family by cause, as the GREEN and RED families already are. The flagged / graph-rejected unverified notice should say "after your next pipeline change" and keep its not-re-verified clause. The outage and message-rejected variants keep "next message". Rewrite the `:160-167` comment and move the constant to `_NOTICES_FOR_A_PERSISTED_BLOCK` in the segments test.
- **Sources:** seam-02-advisor#2, be-06#1, be-09#1.
- **Verifier notes:** On later skipped turns the durable fact's detail uses the PENDING notice, which says "after your next pipeline change". The false promise therefore appears on the blocking turn, not on every later turn as the original finding said.

### be-06#1: ABSENT-preflight flagged notice promises a re-review 'on your next message' that the END gate now skips

- **Reported at:** `src/elspeth/web/composer/no_tool_policy.py:168`; reviewer severity medium; category stale-copy/regression; diff-anchored True.
- **Summary:** _ADVISOR_SIGNOFF_UNVERIFIED_PUBLISHED_NOTICE (no_tool_policy.py:168-172) and the comment at :160-167 assume a block on an unchanged turn persists nothing. Since 41aeaeac0, messages.py:845-847 and compose.py:591-593 save a new state row whenever completion_gate_decision_changes() is true, even on an unchanged graph. A flagged_final_pass or flagged_no_repair block with runtime_preflight None (cause GRAPH_REJECTED) is therefore saved, and advisor_block_covers_unchanged_graph skips the review on the next unchanged message. The copy is still chosen by preflight shape, not by cause, which contradicts the rewritten hints entry and Task 5 of the plan ('graph-rejection notices should retain their pipeline-change guidance').
- **Failure scenario:** Wired, Stage-1-valid pipeline; the prior row has no fact or a PASSED/UNAVAILABLE fact. The user asks a prose-only question and the model does not mutate, so the preflight is None. The advisor flags twice, so the turn blocks as flagged_final_pass with the ABSENT shape. Chat says 'validation and the advisory review run again on your next message', and the route saves a graph_rejected fact. The user resends without editing the pipeline: the gate logs composer_advisor_end_gate_skipped, no review runs, and completion stays withheld. The saved blocker's detail (which embeds the UNVERIFIED notice) says 'next message' while its suggestion (service.py:11388) says 'after your next pipeline change', and merge_completion_gates shows that detail again on every later turn.
- **Evidence:** completion_gates.py:381-398 skips on an unchanged version, GRAPH_REJECTED and a matching fingerprint; service.py:3707 returns a None preflight only when the version did not move; service.py:8621-8627 maps the flagged reasons to GRAPH_REJECTED; messages.py:845-847 saves a row on a decision change; tests/unit/web/sessions/test_advisor_recovery_routes.py:123 saves a first block on an unchanged graph; test_no_tool_policy_segments.py:858-891 still pins this notice in the 'unchanged turn' family with the old premise in its comment; docs/plans/2026-09-22-advisor-transient-failure-recovery.md Task 5 step 1.
- **Suggested fix:** Reword _ADVISOR_SIGNOFF_UNVERIFIED_PUBLISHED_NOTICE to '...run again after your next pipeline change.', keeping the not-re-verified clause. Rewrite the :160-167 comment to state the cause-keyed rule. Move the constant to _NOTICES_FOR_A_PERSISTED_BLOCK in the segments test and fix that test's comment. The withheld twin and the finalize suffix are derived from it and follow automatically.
- **Verifier (trace):** upheld, confidence high, severity medium. I could not refute this finding. I traced the whole path at 74c0ce0db and every step is reachable. The comment at no_tool_policy.py:160-167 rests on the claim that "a fact persists only with a new state row, which only a mutating turn writes". Commit 41aeaeac0, which is in the window, made that claim false. Both routes now save a new row when the review decision changes, even if the version did not move. So an ABSENT-preflight block caused by a flag is saved as GRAPH_REJECTED, and the END gate then skips the review on the next unchanged turn. Only the flagged_final_pass and flagged_no_repair arms, which map to GRAPH_REJECTED, are wrong. Completion stays withheld, which is the intended behaviour, so the harm is misleading instructions that send the user round a resend loop with no fresh review. Medium severity stands.
