## Finding

- **Status and severity:** confirmed, **medium** (be-03#1 raised as high).
- **Location:**
  - `src/elspeth/web/auth/admin_routes.py:235`: the only guard is against self-deletion.
  - `admin_routes.py:123-131,140-141`: `is_dev_admin` matches on username.
- **What is wrong:** `is_dev_admin` grants credential administration by username alone. ce3602aed lets any active human admin reach DELETE, where before only the dev admin could, and the dev admin cannot delete itself. `delete_user` frees the username by design (`local.py:645-648`). Open registration is the default (`config.py:224`), it activates new users immediately (`app.py:1116-1119`), and it has no reserved-name check. `LastActiveAdminProtected` does not apply, because the dev-admin grant does not depend on a role.
- **Failure scenario:** With `dev_admin_user=devadmin` and `registration_mode=open`, admin A deletes `devadmin`. An anonymous user registers as `devadmin` and is active at once. They reset A's password (unaudited, see R08), sign in as A and hold identity-admin authority. The delete dialog (`SignInSection.tsx:132`) promises that a later account with that name "starts fresh", which is false for this name.
- **Evidence:** No ruling in recent-code-hints.md covers this. `WebSettings._validate_auth_fields` (`config.py:1084-1088`) does not forbid combining `dev_admin_user` with open registration.
- **Suggested fix:** Refuse DELETE for `settings.dev_admin_user` on the web route, and reserve that name at registration. Binding the grant to an identity id rather than a username would also close the older exposure.
- **Sources:** be-03#1, seam-05-people-auth#2.
- **Verifier notes:** The name was already claimable before the window whenever no account held it, for example before the operator created it or after a CLI removal. The window added an ordinary-admin HTTP path into that state. Exploiting it also requires open registration and winning the re-registration race.


## Source findings and verification

### be-03#1: Deleting the dev-admin account lets the next registrant of that username inherit the credential grant

- **Reported at:** `src/elspeth/web/auth/admin_routes.py:235`; reviewer severity high; category security; diff-anchored True.
- **Summary:** is_dev_admin grants credential administration by username. delete_user deliberately frees the username for re-registration. ce3602aed lets any live admin reach DELETE, and the only guard is self-deletion. Open registration (the default) activates a newcomer immediately and does not reserve dev_admin_user.
- **Failure scenario:** Settings: dev_admin_user=devadmin, registration_mode=open. Admin A deletes the 'devadmin' account (204; R5 does not protect it because it holds no admin role). An anonymous user POSTs /api/auth/register with username devadmin and gets an active identity, so is_dev_admin is true. They POST /api/auth/admin/users/<A>/reset-password, receive A's new password, sign in as A and gain full identity-admin.
- **Evidence:** admin_routes.py:131 (username comparison), :139-140, :235-240 (only a self-delete guard); local.py delete_user docstring ('a later registration of the same username gets a FRESH identity'); app.py:1116-1119 (activate when registration_mode == 'open'); config.py:224 (default 'open'); routes.py register has no reserved-name check. Before the window only the dev admin could reach DELETE, and it cannot delete itself.
- **Suggested fix:** Refuse deletion of settings.dev_admin_user on this route, as self-deletion is refused. Also reserve that name at registration and/or bind the grant to the identity first admitted under it.
- **Verifier (impact):** upheld, confidence high, severity medium. I could not refute it. I traced the whole path at 74c0ce0db and it holds. is_dev_admin grants credential administration by username alone (admin_routes.py:131). ce3602aed swapped `_require_dev_admin` for `_require_local_account_admin` (admin_routes.py:145-157), so any live human admin can now reach DELETE. The only name guard on that route stops an admin deleting their own account (admin_routes.py:235-237). Nothing protects the account named by settings.dev_admin_user. R5 (LastActiveAdminProtected) only covers the last active human admin role holder, and a plain dev_admin account holds no role. By design, delete_user retires the identity and its natural key so that 'a later registration of the same username gets a FRESH identity' (local.py:645-648). Registration mode defaults to 'open' (config.py:224). Under open mode _admit_identity activates newcomers at once (app.py:1116-1119). The register route checks only registration_mode and has no reserved-name check. A newcomer who registers that username passes is_dev_admin and can call reset-password on any account, including admin A, since set_password has no target guard. That takes over identity administration. No recorded ruling covers this. The config comment, the reference docs and identity-providers.md:47 all describe the grant as belonging to 'the one local user' by that name, which is exactly the weakness. I am lowering severity from high to medium for three reasons. (1) The attack needs a legitimate admin to delete the dev-admin account while leaving dev_admin_user configured, on a deployment that has both open registration and the short-term dev grant enabled. (2) The root weakness is older than the window: the grant was already bound to a username that could be claimed. Under open registration anyone can take the name whenever no account holds it (for example before the operator creates it, or after an out-of-band removal), and register has never reserved it. The window adds one new API path to that state, but it did not create the class of bug. (3) The attacker also has to win the race to re-register the freed name. The suggested fix is correct: refuse DELETE on settings.dev_admin_user and reserve the name at registration. Binding the grant to an identity would also fix the older exposure.
- **Verifier (trace):** upheld, confidence high, severity high. I traced every step of the path at 74c0ce0db and nothing guards it. (1) After ce3602aed, `_require_local_account_admin` lets any active human admin reach DELETE /api/auth/admin/users/{user_id} (admin_routes.py:146-159). Before the change only `is_dev_admin` could reach it. (2) The only guard in delete_user is `user_id == admin.username` (admin_routes.py:235). No check refers to settings.dev_admin_user. The dev_admin_user setting is read in only three places: config.py, admin_routes.py:120/131 and routes.py:796. (3) The retirer refuses only for R5 (last active human admin). A dev-admin account that holds no admin role passes, and `retire_identity` rewrites the natural key so the name is free for a fresh identity (identity_authority.py:2124-2131; local.py:645-648). (4) registration_mode defaults to "open" (config.py:224). `register` has no reserved-name check (routes.py:78-110, 355-428), and `_admit_identity` passes `activate=settings.registration_mode == "open"` (app.py:1116-1119), so the newcomer is active right away. (5) `_authenticate_sync` builds UserIdentity with `username=claims.username`, the local username (local.py:1313-1315). For the newcomer, `is_dev_admin` compares that against dev_admin_user and returns True (admin_routes.py:131). (6) `reset_password` accepts any local username and returns the new password (admin_routes.py:207-222), so the attacker can take over admin A's account. No recorded ruling in docs/agents/recent-code-hints.md covers the dev admin. The new test file has no case for deleting the dev-admin account and re-registering the name. Two caveats, neither of which refutes the finding. First, the name was already unreserved before the window: if the dev-admin account had never been registered, the first open registrant could claim it. The window adds the new step, which is that an ordinary admin can free an established dev-admin name over HTTP. Second, the exploit needs registration_mode=open, which is the default. In email_verified mode the identity is left pending (activate=False). I keep the severity at high because the payoff is an anonymous user gaining credential administration over every local account, including the admins.

### seam-05-people-auth#2: Deleting the configured dev admin's account frees a username that still grants credential administration

- **Reported at:** `src/elspeth/web/auth/admin_routes.py:235`; reviewer severity medium; category authz; diff-anchored True.
- **Summary:** is_dev_admin grants local-account admin by username match. Since ce3602aed, any local admin may DELETE the dev admin's account; the only guard stops self-deletion. Nothing reserves the name. Under open registration (the default) a stranger can re-register it and inherit the grant. The UI's delete dialog promises that a later account with that name 'starts fresh'.
- **Failure scenario:** Settings: auth_provider=local, dev_admin_user=devadmin, registration_mode=open. Admin alice deletes 'devadmin'; the identity is retired and the name freed. An anonymous user POSTs /api/auth/register as 'devadmin' and is activated immediately (app.py:1118). is_dev_admin is now true, so they list every account, reset an administrator's password (unaudited, F1), sign in as that administrator and gain identity-admin authority.
- **Evidence:** admin_routes.py:123-131 compares by username. admin_routes.py:235 blocks only user_id == admin.username. config.py:224 defaults registration_mode to 'open'. app.py:1118 activates on open registration. routes.py register has no reserved-name check. SignInSection.tsx:132 says 'A later account named X starts fresh. It does not receive this person's roles...'
- **Suggested fix:** Refuse deletion of the configured dev_admin_user account on the web surface, or bind the dev-admin grant to an identity_id rather than a reusable username. Reject registration of the configured dev_admin_user name.
- **Verifier (trace):** upheld, confidence high, severity medium. I could not refute this. I traced every step at 74c0ce0db and found no guard on the path.

1. The dev-admin grant is decided only by comparing the username with `dev_admin_user` (admin_routes.py:131). `can_manage_local_accounts` returns True on that match before it looks at any role (admin_routes.py:140-141).
2. Since ce3602aed, any active human admin passes `_require_local_account_admin`. Before that commit, only the dev admin did, and it could not delete itself. The web DELETE surface could therefore never remove the dev-admin account; now it can.
3. `delete_user` refuses only self-deletion (admin_routes.py:235) and `LastActiveAdminProtected`. The dev-admin grant does not depend on a role, so the dev-admin account need not be an administrator, and the last-admin rule does not protect it.
4. `LocalAuthProvider.delete_user` deletes the credential row. It retires the identity together with its natural key, so the next registration of that username gets a new identity (local.py:631-677).
5. Registration defaults to open (config.py:224). Open registration is refused only under `closed` (routes.py:371). It inserts the username with no reserved-name check (local.py:515-520). `_admit_identity` activates the new identity when `registration_mode == "open"` (app.py:1118).
6. The token's username is the local account name (local.py:1102, 1243). So `is_dev_admin` is true again for whoever registers the name, and they can list, create, delete and reset passwords for every local account. `reset_password` writes only a structlog line (admin_routes.py:217).
7. Nothing in `WebSettings._validate_auth_fields` (config.py:1084-1088) forbids combining `dev_admin_user` with open registration. docs/agents/recent-code-hints.md records no ruling on this.

Mitigating factors:
- An administrator has to act first by deleting that account.
- The same weakness already existed before the window: a configured `dev_admin_user` that was never created, or one removed with the CLI, can be claimed by anyone under open registration.
- The finding's severity (medium) stands. The new part is that an ordinary admin can now open the gap from the web UI, whose delete dialog (SignInSection.tsx:132) says a later account with that name 'starts fresh'. For the configured dev-admin name that is not true: it gets the credential-administration grant back.
