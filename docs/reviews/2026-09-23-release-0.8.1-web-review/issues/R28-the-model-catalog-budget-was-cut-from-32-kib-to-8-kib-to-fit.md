## Source findings and verification

### be-08#1: Model-catalog budget cut 32 KiB to 8 KiB to fit a test ratchet; the shipped catalog carries 3 of 503 slugs

- **Reported at:** `src/elspeth/web/composer/planner_authoring_aids.py:1184`; reviewer severity medium; category regression; diff-anchored True.
- **Summary:** b08fe591d set _MODEL_CATALOG_MAX_CANONICAL_BYTES to 8 KiB. Its own comment says this sizes the aid to fit the 119,398-byte 'initial-scaffold gate', which is the test-side _FIXED_SCAFFOLDING_MAX_CANONICAL_BYTES ratchet (106 KiB x 1.10). That ratchet's comment says it moves only by operator ruling and must not absorb growth by trimming load-bearing aids. After the LiteLLM 1.102 bump, the catalog now drops both azure and openrouter.
- **Failure scenario:** A deployment has no usable llm operator profile, and the user asks for an Azure or OpenRouter model. Before the window the slug was carried in the aid and bound with no discovery turn, which is the function's stated purpose. Now models_omitted lists azure and openrouter, model.catalog becomes discoverable, and the planner spends an extra list_models provider turn (re-sending the ~112 KB request) before it can bind. The per-turn saving is about 6.4 KB, so one added turn outweighs roughly 17 turns of savings.
- **Evidence:** Measured at the pinned tree (PYTHONPATH=<worktree>/src; elspeth.__file__ confirmed inside the worktree). At the 8 KiB cap the catalog is 1,846 B and carries bedrock only, with azure (232) and openrouter (268) omitted. At 9 KiB it is 8,289 B and carries azure and bedrock. Uncapped it is 15,212 B. Leaving out only openrouter gives 8,295 B, 103 B over the cap. The ratchet baseline stayed at 106 KiB (test_pipeline_planner.py:158/193). litellm went from >=1.83.10 to >=1.102.0 in this window (6e377bdc4). recent-code-hints.md:1667 still lists _MODEL_CATALOG as 32K, and no ruling for 8 KiB exists.
- **Suggested fix:** Put this to the operator as a ratchet decision. Either raise _FIXED_SCAFFOLDING_BASELINE_BYTES for the LiteLLM 1.102 inventory and restore a cap that carries azure, or record a ruling that profile-less deployments pay the discovery turn. Then update the recent-code-hints ceiling inventory and the stale docstrings (F1).
- **Verifier (trace):** upheld, confidence medium, severity low. I could not refute the finding. The behaviour change is real and reachable, and I found no recorded ruling for it. Before the window the cap was 32 KiB with whole-lists-or-none. At the pinned tree the uncapped catalog is 21,665 B, so the old code would have carried azure, bedrock and openrouter. b08fe591d set the cap to 8 KiB and defers the largest lists first. Azure alone is 7,650 B canonical, which cannot fit under 8,192 B once the base catalog is added. pyproject.toml now requires litellm>=1.102.0, so every deployment on this tree drops azure, whatever size its openrouter snapshot is. The ratchet comment (test_pipeline_planner.py:141-146) says growth is never "absorbed by ... trimming load-bearing teaching text to fit". recent-code-hints.md:1667 still says 32K. I found no ruling in the commit's own docs changes, recent-code-hints or CHANGELOG. Two things argue against the finding, and together they lower the severity.
