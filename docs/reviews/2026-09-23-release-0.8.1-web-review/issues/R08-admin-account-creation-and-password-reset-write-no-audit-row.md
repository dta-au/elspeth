## Finding

- **Status and severity:** confirmed, **medium** (be-03#2 raised as high).
- **Location:** `src/elspeth/web/auth/admin_routes.py:203` (create) and `:220` (reset), which only call `_slog.info`. The docstring at `admin_routes.py:1-10` was rewritten.
- **What is wrong:** The base docstring justified structlog-only records because the surface was "off in any deployment whose audit trail matters". ce3602aed widened the surface to every active human admin and deleted that justification, but added no `auth_events` row. `AuthAuditEventType` (`contracts/auth.py:100-128`) has no credential-created or password-reset event. Open self-registration, by contrast, is audited through `register_open_user_with_audit` (`local.py:483-510`).
- **Failure scenario:** Admin A resets admin B's password, receives it, signs in as B and grants roles that the Landscape attributes to B. The Landscape has no row for the reset or for who did it.
- **Evidence:** The 2026-08-07 change-password spec accepts this gap for the CLI only, and the SSO spec (`docs/specs/2026-09-02-pluggable-sso-design.md:969`) accepts it only for the dev-only gate.
- **Suggested fix:** Before returning the password, record auth-audit events for create and reset: the actor identity id, the target username, request provenance and no secret material. Fail closed if the write fails. The alternative is an explicit operator ruling that accepts the gap.
- **Sources:** be-03#2, seam-05-people-auth#1.
- **Verifier notes:** Structlog-only reset existed before the window for the dev admin, so the window widened an existing gap. The original finding's claim that B's JWTs survive a reset describes documented, deliberate behaviour (`local.py:720-725`), not part of this defect.

### be-03#2: Admin password reset and account creation write no audit row now that every administrator can use them

- **Reported at:** `src/elspeth/web/auth/admin_routes.py:220`; reviewer severity high; category audit-integrity; diff-anchored True.
- **Summary:** The base docstring justified structlog-only mutations because the surface was 'off in any deployment whose audit trail matters'. ce3602aed enabled it for every local-auth administrator and rewrote the docstring to say the routes 'retain their operational log events', but added no auth_events row. AuthAuditEventType has no credential-reset or credential-created event. The 2026-08-07 spec accepts this gap only for the CLI. No ruling in recent-code-hints covers it.
- **Failure scenario:** Admin A POSTs /api/auth/admin/users/B/reset-password on admin B, receives B's password, signs in as B, and performs role grants that the Landscape attributes to B. The Landscape has no event for the reset or its actor; only a dev_admin_password_reset structlog line exists. set_password (local.py:720-727) also leaves B's outstanding JWTs valid.
- **Evidence:** Base docstring at 7c986dc97, lines 10-13, vs HEAD admin_routes.py:7-9; :203 and :220 call _slog.info only; contracts/auth.py:100-128 event vocabulary; audit.py:1365-1398 shows that administrative disable records actor_identity_id; spec docs/specs/2026-08-07-change-password-panel-design.md § Audit accepts the gap for the CLI only.
- **Suggested fix:** Record an auth_events row, with the acting identity and request provenance, for create and reset before responding, and fail closed. Or record an explicit operator ruling that accepts the gap for local-auth deployments.
- **Verifier (trace):** upheld, confidence high, severity high. I could not refute it. The code path is reachable as described, no guard writes an auth_events row, and I found no recorded ruling that accepts the gap for the widened surface. Before this window, the audit gap was justified only because the surface was limited to one configured dev account and was 'off in any deployment whose audit trail matters'. ce3602aed opened the same routes to every live local-auth administrator, deleted that justification, and added no audit record. The finding also says outstanding JWTs survive a reset, and that is correct: set_password only updates the hash. I kept the severity at high. The actor must already be an administrator, but these routes also let one administrator reset another administrator's password and then act under that person's name in the Landscape without trace. That attribution gap is exactly what an audit-grade product has to close.
- **Verifier (impact):** upheld, confidence high, severity medium. The core defect holds at 74c0ce0db. ce3602aed ("let local administrators manage local accounts", Fixes elspeth-3031873251) widened the credential surface from the single configured dev admin to every active human administrator on a local-auth deployment. It kept structlog as the only record of credential creation and reset. I found no ruling that accepts this: recent-code-hints has no entry for it, the commit message says nothing about audit, and the one accepted gap in the change-password spec covers only the CLI. The window rewrote the docstring and dropped the base's justification ("off in any deployment whose audit trail matters") instead of addressing the gap. The reset-then-impersonate path is concrete: A resets B, signs in as B, and the Landscape has no row for the reset or its actor. I am lowering severity to medium for three reasons. (1) The same structlog-only reset already existed before the window for the dev admin on any local deployment, so the window widened an existing gap rather than creating one. (2) The claim that B's outstanding JWTs stay valid is documented, deliberate behaviour, not a defect: the local.py:720-725 docstring says so, and the people-access plan says the UI must not promise sign-out. (3) The creation half matters less. A new credential grants no authority until identity admission, which the docstring says runs on the existing audited paths. The remaining gap is attribution of an administrator-initiated credential takeover. That is real in an audit-grade product, but the actor is already a fully trusted, deployment-wide administrator.

### seam-05-people-auth#1: Administrator account creation and password reset have no Landscape audit row; the surface now reaches every local-auth administrator

- **Reported at:** `src/elspeth/web/auth/admin_routes.py:220`; reviewer severity medium; category audit-integrity; diff-anchored True.
- **Summary:** ce3602aed removed the docstring that justified structlog-only records ('this surface is off in any deployment whose audit trail matters'). It also enabled create_user and reset_password for every active human admin on local-auth deployments. Both still emit only _slog.info, and the auth audit recorder has no event for either.
- **Failure scenario:** On a local-auth deployment, admin A POSTs /api/auth/admin/users/B/reset-password, receives B's new password and signs in as B. The Landscape auth audit shows only B's login. No durable row records that A reset B's credential, so the evidence exists only in ephemeral logs, which the audit-primacy policy forbids for probative events.
- **Evidence:** admin_routes.py:1-10 docstring rewritten in ce3602aed. admin_routes.py:203 and :220 are _slog.info only. local.py:451 create_user and :720 set_password write no audit. web/auth/audit.py record_* has no credential-created or password-reset event. Deletion is audited through local_identity_retirer. No ruling in recent-code-hints.md or the people-access plan docs.
- **Suggested fix:** Add auth-audit events for administrator credential creation and reset (actor identity_id, target username, no secret material), recorded before the password is returned. Otherwise restore the gating that justified structlog-only records.
- **Verifier (trace):** upheld, confidence high, severity medium. I could not refute this finding; the path is reachable exactly as described. At the pinned commit, `_require_local_account_admin` (admin_routes.py:145-157) admits any caller on a local-auth deployment whose identity_id is in `RepositoryIdentityAuthority.active_human_admin_ids()` (identity_authority.py:1471-1482), or the configured dev_admin_user. Before ce3602aed only the dev_admin_user could get in. Once admitted, `create_user` (admin_routes.py:184-205) and `reset_password` (admin_routes.py:207-222) write to auth.db through `LocalAuthProvider.create_user` (local.py:451-481) and `set_password` (local.py:720-735). Neither method writes an audit row, and the routes emit only `_slog.info` (lines 203 and 220). The Web auth recorder (web/auth/audit.py) has record_* methods for login, token, identity admitted/retired/rebound/enabled/disabled/activated, role, relationship, quota, approval, review and library events, but none for credential creation or password reset. There is no guard that stops one admin resetting another admin's password. Only two commits in the window touch admin_routes.py and audit.py (ce3602aed and 793d0f95a), and neither adds an audit event. The 'structlog-only' choice was a recorded design decision only while the surface was dev-only. The SSO spec (docs/specs/2026-09-02-pluggable-sso-design.md:969) says 'the existing dev-admin gate is local-only and structlog-only by design', and the old docstring and the old config.py comment both said the surface was for short-term dev deployments and off wherever the audit trail matters. ce3602aed removed both premises and widened the surface to every local-auth administrator. The new docstring line 'Credential creation and reset retain their operational log events' states what the code does but is not a ruling. I found nothing in recent-code-hints.md or the people-access plan or review docs that re-justifies structlog-only records for the wider population. The codebase itself treats local credential events as audit-worthy: open registration goes through `register_open_user_with_audit` with a durable intent and compensating deletion (local.py:483-510), while admin-driven creation and reset of the same credentials go unaudited. Medium severity is right: this is a missing durable audit row, not an authorization bypass, because only administrators are admitted and they are already trusted.
