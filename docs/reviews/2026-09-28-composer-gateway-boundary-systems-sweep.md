# Composer and gateway boundary systems sweep — 2026-09-28

Scope: read-only review of the Composer provider/tool loop and the local gateway at baseline commit `4a55af499`. The agency Bedrock adapter is in a separate secure enclave and was not inspected. The implementation worktree changed while this review ran; the probes and source locations below describe the baseline unless noted otherwise.

## System pattern

The critical invariant is **closure under continuation**: a gateway response that Composer admits and puts into its next provider transcript must itself satisfy the gateway's inbound contract. The original empty-text failure crossed that boundary after a successful tool call. A stricter gateway alone does not establish closure: Composer can keep a rejected provider tool-call envelope in the transcript after returning a tool error. That converts one malformed model result into a later gateway 400; a retry of the unchanged transcript cannot repair it.

The highest leverage checks are at the two crossing points: validate or safely project the provider tool call before Composer appends it, and validate the gateway's canonical response against its own next-turn request contract before rendering HTTP 200. The latter response finding is already recorded in the separate gateway implementation review and is not duplicated here.

## Confirmed findings

### C1 — Composer admits tool calls that make its continuation invalid (P1)

- **Source and trigger:** `src/elspeth/web/composer/tool_batch.py:268-294` validates call IDs, but only checks that `function.name` and `function.arguments` are strings. Empty or whitespace-only names and syntactically invalid JSON arguments are admitted. `tool_batch.py:845-862` appends the raw function fields to `llm_messages`. Invalid JSON is reported as an `ARG_ERROR` at `tool_batch.py:950-1023`, with a tool result appended; ordinary syntax errors do not take the `JsonBoundaryError` branch that replaces the raw arguments at lines 967-979.
- **Consumer mismatch:** `gateway/src/elspeth_llm_gateway/core/contract.py:68-101` rejects blank names and requires strict JSON arguments. `ChatRequest` validates the whole transcript on the next call. The gateway's `core/app.py:273-290` maps that to `invalid_request`/HTTP 400 before an upstream call. This also explains why a model-side repair attempt cannot run once the bad assistant call remains in the transcript.
- **Controlled read-only probe:** `_admit_tool_batch` admitted `lookup/{}` and `ChatRequest` accepted its completed assistant/tool transcript. The same Composer admission accepted `""/{}` and `lookup/{broken`, while `ChatRequest.model_validate` rejected those transcripts at `messages[1].tool_calls[0].function.name` and `.function` respectively. Probe process exit: 0. The repair path is conditional on a later provider call; a turn that terminates without continuing will not hit this gateway rejection.
- **Fix and regression:** Preserve truthful audit of malformed model output, but ensure any assistant tool-call envelope retained for a later provider request is gateway-valid. For invalid arguments, use a bounded, explicit valid-JSON error sentinel in the provider transcript while keeping the original attempted bytes only in the appropriate audit custody; for blank function names, reject or project before the assistant message is appended. Cover both malformed-name and malformed-JSON tool turns through the next actual provider request, including an ordinary valid-call control and the persisted audit result. Do not loosen the gateway's inbound validation.
- **Sibling planner path:** `src/elspeth/web/composer/pipeline_planner.py:1589` checks `not name`, admitting a whitespace-only function name. `_assistant_tool_calls_message` at lines 1722-1741 preserves that name for the next request. A read-only probe accepted both `lookup` and `" "` in `_parse_response_tool_calls`; the valid name passed `ChatRequest`, while `" "` was rejected. The planner also needs the gateway-compatible nonblank-name rule and a continuation regression.

### C2 — Oversized integer literal escapes strict JSON classification (P2; repair in progress)

- **Source and trigger at baseline:** `gateway/src/elspeth_llm_gateway/core/parsing.py:105-110` caught `StrictJsonError` and `JSONDecodeError` from `json.loads`, but CPython raises a plain `ValueError` for an integer literal exceeding its configured decimal digit limit. `core/app.py:273-283` catches only `StrictJsonError`; `core/transport.py:108-115` has the same parser on upstream success bodies. An inbound body or upstream 2xx body with such a literal could therefore become `internal_error`/HTTP 500 through `core/app.py:107-116`, rather than `invalid_request` or `upstream_response_invalid`.
- **Controlled read-only probe before edit:** `parse_strict_json` accepted a 30-digit integer and raised `ValueError` for a 5,000-digit integer inside a small JSON object; process exit 0. The integer fits the gateway's default 1 MiB body cap. During this review, the implementation owner added a `ValueError` to `StrictJsonError` translation at `parsing.py:111-114`; a subsequent local ASGI control returned `400 invalid_request` for both a 30-digit unknown `n` field and the 5,000-digit version. This is evidence of an active uncommitted repair, not merged-release status.
- **Fix and regression:** Keep the parser translation and test the parser, inbound ASGI route (HTTP 400), and 2xx upstream-body path (`upstream_response_invalid`/HTTP 502), with a normal finite integer control. Freeze the tree for any final gate.

### C3 — Response validation omits configured argument-length bound (P2; active repair still incomplete at observation)

- **Source and trigger:** `gateway/src/elspeth_llm_gateway/core/service.py:156-166` in the active worktree validates returned tool-call syntax and IDs but does not apply the configured `Bounds.max_string_chars` to returned arguments. The next inbound turn does apply it at `gateway/src/elspeth_llm_gateway/core/contract.py:373-397`. A model can therefore return a long, valid JSON tool argument in an HTTP 200 response that becomes an HTTP 400 `invalid_request` when the client sends back the completed tool result.
- **Controlled read-only probe:** With `max_string_chars=40`, a 5-character JSON argument value passed both `_validate_canonical_response` and the rendered continuation's `bounds_check`. A 100-character JSON argument value passed response validation but the continuation failed `bounds_check` with `invalid_request`; process exit 0. The probe used the current uncommitted response validator, so this is a live repair-gap observation, not a claim about the secure adapter.
- **Fix and regression:** Validate returned tool arguments against the same configured bound before rendering success, with exactly-at/over-limit response-to-continuation controls. Consider response prose if the client might replay a mixed prose/tool message. The configured bound needs to be passed to the response validator; checking strict JSON alone is insufficient.

## Related contract gaps with conditional provider impact

### G1 — Historical tool protocol bypasses the TOOLS capability check

`gateway/src/elspeth_llm_gateway/core/service.py:121-122` tests only `request.tools`. The inbound contract accepts completed historical assistant tool calls and tool results with no currently declared tools (`core/contract.py:104-139,269-287`). A read-only probe built that valid transcript with `tools=None` and `_check_capabilities` accepted it for an adapter declaring only `Capability.TEXT`; process exit 0. An adapter lacking tool-history translation then receives canonical tool messages despite not declaring TOOLS. Actual upstream failure is adapter-dependent and was not tested. Either reject any transcript using the tool protocol when TOOLS is absent, or explicitly define/test the narrower capability meaning; add a conformance case with historical calls and no current tool declaration.

### G2 — The configured string bound does not cover protocol identifiers or tool metadata

`gateway/src/elspeth_llm_gateway/core/contract.py:373-405` applies `max_string_chars` to message content and call arguments only. It omits `tool_call_id`, call IDs, function names, tool names, descriptions, and schema names. A read-only probe with `max_string_chars=3` accepted 20-character tool-call IDs, tool names, and tool descriptions; process exit 0. The raw body cap still bounds total bytes, and no agency adapter rejection was measured, so this is a contract-limit gap rather than a proven Bedrock failure. Decide which fields the bound promises to cover, enforce those consistently, and test just-above/at-limit controls alongside the existing body cap.
