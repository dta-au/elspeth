## Freeform Section 4a: ingress contract and continuation review

**NO-GO for the complete Section 4a extension until its ingress contract is adopted concretely. GO for the proposed whole post-provider continuation architecture, with the completion/transport distinction below included in its acceptance tests.** This verdict is limited to the new freeform extension and does not revoke earlier guided approvals. Reviewed the design note, live routes, service/schema and frontend; obtained an independent ingress design cross-check. No production edits or new tests were run.

### Blocking contract gap

Section 4a currently defers ingress identity to a later design decision. The defect is real in the source: `sessions/schemas.py:145-160` accepts content and optional state only; `routes/messages.py:241-248` inserts a user row without retry identity. `sessions/service.py:9614-9650` allocates a fresh sequence and message for each invocation. The frontend generates an optimistic local UUID but does not transmit it (`frontend/src/stores/sessionStore.ts:2199-2225`, `frontend/src/api/client.ts:899-915`). Joining this write protects worker custody but cannot distinguish exact transport retry from a deliberate second identical message.

Recovery is also not bound to a specific turn: `retryMessage(messageId)` locates that message in frontend state, then calls bodyless `/recompose` (`sessionStore.ts:2830-2863`). The server selects whichever conversational user row is last (`routes/composer/compose.py:140-160`). A navigation/cross-tab update can therefore turn recovery of one accepted message into recomposition of another. A concrete ingress contract must cover this handoff as well as duplicate insertion.

### Recommended minimal contract

1. Require a UUID `client_request_id` on `/messages`. Generate it once per intentional send; retain the original validated content and original nullable `state_id` for transport retries. Omitted and explicit null state are equivalent. Distinct intentional sends get different keys even for identical text. Do not derive identity from content, the current state head, or a request task.

2. Add a small immutable `message_ingress_receipts` table with composite primary key `(session_id, client_request_id)`, canonical `user_message_id`, and original nullable `requested_state_id`. Bind the message with a same-session composite FK and uniqueness constraint; bind an explicit requested state to the same session. The existing message row supplies exact immutable content, so a duplicated body or request hash is unnecessary. Verify its user role and `route_user_message` principal. Keep receipt lookup behind authenticated session ownership and expose no cross-session identifiers. Forked transcript history must not copy these acceptance identities into the fork.

3. Introduce a dedicated typed ingress result: freshly accepted message plus same-transaction transcript, already accepted receipt, or conflicting request. In the existing fenced session write transaction, check the receipt before allocating a sequence. Exact content plus original nullable requested state returns `already_accepted`; same key/different payload conflicts. Fresh acceptance atomically inserts both user row and receipt, then reads the transcript as today. Preserve the fresh transcript's maximum-sequence assertion (`service.py:9588-9606`); never pretend an old accepted row is the last row of a replay transcript. Do not resolve an omitted state against today's head and then compare it with yesterday's resolved provenance. The receipt must retain the original optional input.

4. Keep the ingress worker owned and joined through commit/rollback before lease release. If cancellation arrives after accepted ingress but before provider dispatch, finish the acceptance write and stop; do not start a provider because cleanup suppressed cancellation. Preserve actual writer/integrity failure. The database transaction and uniqueness constraints establish cross-process duplicate safety; a local compose lock or blanket `IntegrityError` catch does not.

5. Return structured HTTP 409 for an exact accepted duplicate, with `error_type="message_already_accepted"`, `client_request_id`, and `user_message_id`. This is an acceptance receipt, not a claim that composition completed. Return a distinct `message_idempotency_conflict` for changed payload. Neither duplicate starts a provider, inserts another message, or publishes a fictitious starting/complete progress event. Existing busy/lease responses may apply while the first owner is active; the same key remains safe to retry afterward. Full `MessageWithStateResponse` replay is unnecessary and currently lacks a durable whole-turn receipt.

6. Make frontend recovery use identity. An uncertain optimistic send retries POST with its retained key/payload. An `already_accepted` response maps that intent to its canonical message ID and refreshes transcript/state/proposals/progress under the existing generation fence. Refresh failure stays saved-but-unreconciled; it must not allocate a fresh send key. Expose a nullable acceptance key on applicable message projections, or an equivalent exact mapping, so polling can associate the accepted row without content matching. A deliberate user retry after reconciliation invokes `/recompose` with required `expected_user_message_id`; under the compose lock, require that exact ID to be the last conversational user row. Otherwise return a reconciliation conflict with no provider dispatch. Do not automatically recompose merely on an acceptance receipt. Scope reload persistence explicitly: preserving pending intents across reload requires storing their original key/payload before dispatch; absence of such storage is not permission to silently resend them with a new identity.

7. Treat this as a session schema/wire contract change: update the session epoch and exact-schema inventory/validation, service protocol and nominal result types, request/response schemas, API client and store tests. Add PostgreSQL contention evidence alongside SQLite. No data reset is implicitly authorized by this review; a local stale-schema blocker must be reported through the existing operating rules.

Required ingress controls: cancellation before/after actual commit with lease retention; rollback then same-key retry; simultaneous same-key requests through independent service instances; exact duplicate after state head advance with originally null state; content/state mismatch; identical text with different keys; no duplicate sequence, user row or provider on replay; frontend uncertain-local retry and reconciliation failure; cross-session isolation; explicit recompose ID mismatch. Preserve first-party transcript verification failure even when ingress has already committed.
