## Findings

### R1 — P1: Required settings are absent from every runtime environment

At [workload.bicep:213](../../deploy/azure-container-apps/workload.bicep#L213),
`contractEnvironment` omits these required runtime inputs:

```text
ELSPETH_WEB__COMPOSER_MAX_COMPOSITION_TURNS
ELSPETH_WEB__COMPOSER_MAX_DISCOVERY_TURNS
ELSPETH_WEB__COMPOSER_TIMEOUT_SECONDS
ELSPETH_WEB__COMPOSER_RATE_LIMIT_PER_MINUTE
```

The requirement comes from `WebSettings` in
[config.py:307](../../src/elspeth/web/config.py#L307) and line 339. The current
Dockerfile does not supply defaults. The parameter resolver and example
parameters do not supply them either.

Both `doctor-schema-init` and `doctor-runtime` fail before inspecting their
databases. Adding the settings to `extraEnvironment` fixes only the web
environment: [workload.bicep:299](../../deploy/azure-container-apps/workload.bicep#L299)
does not append it to either doctor environment.

The published image was exercised with networking disabled and synthetic
credentials. Its actual CLI returned exit 1:

```json
[{"name":"settings_load","ok":false,"detail":"web settings could not be loaded (ValidationError)"}]
```

Controlled configuration probes reported exactly four missing-field errors.
Supplying all four made configuration loading pass. Review values were only
test inputs, not selected operational limits.

**Correction:** introduce explicit bundle parameters, materialize them in the
resolver, and place them in the shared contract environment. Set the timeout
below the selected transport ceiling minus the runtime's required headroom.
Verify the exact resulting environments with the image before running Jobs.

### R2 — P1: The documented endpoint-key path is invalid; model setup is incomplete

[Cold-install step 4](../runbooks/azure-container-apps-cold-install.md#L284)
instructs the operator to set `COMPOSER_ENDPOINT_SECRET_NAME`. The resolver
and Bicep then inject `ELSPETH_WEB__COMPOSER_ENDPOINT_API_KEY`, but neither
supplies nor instructs setting its required paired
`ELSPETH_WEB__COMPOSER_ENDPOINT_BASE_URL`.

The runtime [pairing validator](../../src/elspeth/web/config.py#L1262)
rejects a key without a URL. A controlled probe confirmed key-only failure
and key-plus-URL success. This fails web startup even after R1 is repaired.

The advisor has independent model/endpoint credentials. Pipeline LLM
transforms also need operator profiles and a standard default profile for
the tutorial. The cold-install procedure does not cover those inputs, and
its status projection omits `composer_available`, `composer_missing_keys`
and `tutorial_ready`.

**Correction:** document and configure both model roles and their credential
paths, plus `ELSPETH_WEB__LLM_PROFILES` and the selected standard profile.
Supply the primary URL through explicit configuration. Distinct advisor,
provider or SSO secrets need actual ACA secret definitions: the current
`extraEnvironment` parameter alone does not create a referenced secret.
See the maintained [LLM configuration reference](../reference/environment-variables.md#L302).
Require a real Composer call and a small pipeline execution after startup.

### R3 — P1: Default authentication creates SQLite state on the NFS mount

The bundle sets `/mnt/elspeth/data` as `data_dir`, mounts it on 2–4 replicas,
and leaves authentication settings unspecified. The live settings defaults
are `auth_provider=local` and `registration_mode=open`
([config.py:189](../../src/elspeth/web/config.py#L189), line 220).

[app.py:1137](../../src/elspeth/web/app.py#L1137) creates the local provider
at `settings.data_dir / "auth.db"`; the provider uses `sqlite3.connect`.
Selecting external PostgreSQL for sessions and Landscape does not override
that credential store. This puts `auth.db` on NFS, contradicting the stated
ACA storage contract that shared NFS holds files, never SQLite. Corruption
was not reproduced; the deployed storage shape is the confirmed finding.

The runbook also omits the first administrator bootstrap and authenticated
first-use procedure. An anonymous readiness check does not establish that
an administrator or admitted workload user exists. The auth-mode check
accepts local configuration without inspecting users.

**Correction:** configure the intended production identity provider, its
redirect origin and Key Vault credentials, and explicitly select registration
policy. Prepare the first administrator's provider/subject and the
`elspeth composer users bootstrap-admin` procedure. Admin bootstrap does not
itself grant a workload role; verify the intended user's author/run access.
If local authentication is desired, resolve its shared-SQLite deployment
contract explicitly rather than treating the current default as qualified.

### R4 — P1: The stated Azure permissions are insufficient

[Prerequisites:96](../runbooks/azure-container-apps-cold-install.md#L96)
ask for Contributor on the target resource group plus authority to assign
`AcrPull` on the registry. The environment also creates Key Vault and Blob
role assignments in the target group, and step 2 grants the operator Secrets
Officer there. Contributor does not grant role-assignment authority.

The registry role modules execute nested deployments at the registry's
resource-group scope, which requires deployment rights there as well as
role-assignment rights on the registry. The operator also needs image push
permission for the GHCR-to-ACR copy. The runbook's `az group create` needs
the corresponding outer-scope permission if the group does not exist.

**Correction:** enumerate resource deployment, role assignment and image push
rights at their actual scopes before the window. Contributor plus suitably
scoped RBAC Administrator is one possible arrangement; subscription-wide
Owner is not inherently required. These are missing prerequisites, not a
claim that the actual operator lacks permissions.

Sources: [Contributor capabilities](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/privileged#contributor)
and [Bicep deployment permissions](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/deploy-cli#required-permissions).

### R5 — P2, conditional: Existing-registry prerequisites are incomplete

The registry check at [cold-install:135](../runbooks/azure-container-apps-cold-install.md#L135)
reads only its name/login server. The bundle always grants legacy `AcrPull`.
An ACR using RBAC plus ABAC repository permissions ignores that role.
Both runtime and schema-owner identities then fail image pulls despite
successful role-assignment deployment. ACA managed-identity pulls also
require ARM audience tokens to be enabled.

Inspect the existing registry before rollout:

```bash
az acr show --ids "$ACR_RESOURCE_ID" --query roleAssignmentMode --output tsv
az acr config authentication-as-arm show -r "${ACR_LOGIN_SERVER%%.*}"
```

**Correction:** document the supported registry mode, or support the proper
repository-reader role for ABAC. Verify ARM-token authentication and the
network path from the fresh ACA VNet. The bundle does not create an ACR
private endpoint or DNS connection to an existing isolated registry.
Changing an existing shared registry is a separate operator action.

Sources: [ACR authorization modes](https://learn.microsoft.com/en-us/azure/container-registry/container-registry-rbac-abac-repository-permissions)
and [ACA managed-identity image-pull prerequisites](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity-image-pull).

### R6 — P2: Cold-install and redeploy disagree about image provenance

Cold install assumes publication by `build-push.yaml`, lists `cosign`, but
never verifies a signature. The existing-service procedure
[requires a GitHub Actions OIDC signature](../runbooks/azure-container-apps-existing-service-redeploy.md#L173).
The selected image was published locally with provenance and SBOM
attestations; it has no such CI signature.

Copying the OCI index by digest does not establish that separate Cosign
signature artifacts are present at the ACR reference. The CI workflow
explicitly signs ACR after copying the image.

**Correction:** make the intended verification path consistent with how this
candidate was built. If the GitHub Actions signature is required, use the
configured CI publication/signing path and verify the deployed registry
reference. A local image smoke test is not CI release verification.

### R7 — P2: The TLS acceptance instructions do not match the doctor

[Cold-install:342](../runbooks/azure-container-apps-cold-install.md#L342)
requires `session_tls` and `landscape_tls` checks. The ACA doctor collector
does not emit them: those checks are gated on its AWS-specific path. A
controlled collector probe found neither check for ACA; the AWS positive
control emitted both. Do not report a successful ACA doctor as evidence
that those named checks ran.

The [skill troubleshooting reference](../../.agents/skills/operating-azure-container-apps/references/test-and-triage.md#L52)
also recommends changing `verify-full` to `verify-ca`. With the documented
`sslrootcert=system`, the driver rejects this combination before connecting:

```text
OperationalError: connection is bad: weak sslmode "verify-ca" may not be used
with sslrootcert=system (use "verify-full")
```

**Correction:** retain `verify-full` and fix server FQDN/private DNS/certificate
matching. State the doctor's actual coverage and add an explicit TLS proof
if needed. Implementing shared TLS checks would be a runtime change requiring
its own validation and a new image.

### R8 — P2: The resolver reselects latest secrets instead of using captured versions

Step 4 saves uploaded secret version IDs into `<secret>.version` files.
Step 5 says it uses those versions, but
[resolve-workload-parameters.sh:32](../../deploy/azure-container-apps/scripts/resolve-workload-parameters.sh#L32)
queries each name without a version and freezes whatever is latest then.
A rotation between those steps can select a password different from the
one used during role bootstrap.

**Correction:** consume the captured version IDs, or explicitly document and
verify reselection of the latest version against the provisioned credentials.
The stored values remain secret; this is an ID-selection issue.

### R9 — P2: Replica preflight accepts types that the template rejects

[validate-workload-parameters.jq:28](../../deploy/azure-container-apps/scripts/validate-workload-parameters.jq#L28)
uses relational comparisons without checking types or integrality. Controlled
probes with otherwise valid parameters returned:

```text
known-valid:       exit=0, true
bad image:         exit=1, false
string replicas:  exit=0, true
fraction replicas:exit=0, true
```

`minReplicas="two"` and fractional counts pass this preflight but cannot
satisfy Bicep's integer parameters. Generated defaults are unaffected.
**Correction:** require integer-valued numbers before comparing the bounds.

### R10 — Fixed during review: Build guide lost its named builder

The newly written build guide created a named Buildx builder before changing
`DOCKER_CONFIG`. Builder definitions live under that configuration directory,
so the later build could not find the builder. The failure was reproduced:
`ERROR: no builder ... found`, exit 1.

The [guide](../../.agents/skills/operating-azure-container-apps/references/build-and-push-ghcr.md)
now sets the private Docker configuration before creating the builder and
retains it through cleanup. A disposable builder created and inspected under
the corrected sequence returned exit 0. No image rebuild was needed.

## Remaining operator preparation

The actual subscription, region and credentials were not supplied for live
inspection. No Azure validation/what-if, PostgreSQL role bootstrap or live
application flow was executed. `az` and `psql` were absent from this host's
PATH during review; the repaired runbook lists both prerequisites.

Before the window, have the following ready:

1. A host with Azure CLI, PostgreSQL client, private-network routing and DNS
   to PostgreSQL and both vaults, or deliberate temporary bootstrap allowlists.
   The bundle does not create a workstation VPN or a bootstrap host.
2. Confirmed registry mode, image-pull network access, operator RBAC and image
   push rights; subscription provider registration, region/SKU availability,
   quotas and policy constraints checked using the actual principal.
3. Corrected concrete workload parameters, selected model budgets/providers,
   versioned secrets, production authentication settings and initial admin
   identity. Export required variables before invoking child scripts.
4. An ARM what-if for those actual parameters, then storage provisioning,
   schema-init doctor and runtime doctor in that order.
5. After rollout, both public probes, candidate revision/digest verification,
   an authenticated administrator login, an admitted user's Composer call and
   a small run with output/audit inspection. Anonymous HTTP 200 alone does
   not establish a usable installation.

The principal startup corrections are in configuration, Bicep and operator
instructions and can use the already published image. Any chosen runtime
repair, such as changing authentication storage or adding doctor TLS checks,
would require rebuilding and publishing a new image.
