## User-visible behaviour

**Steps 1 and 2 (source, output).** The docked chat box is the one primary input. After one Send the learner sees ONE card — the existing "Review sources" / "Review outputs" card, now carrying per component: the humanised name (`componentDisplayName`, raw name in `title=`) and plugin display name, the settings summary rows (the same `<dl>` the schema form's summary view shows, including its "Advanced settings (N)" fold), the observed columns (source) or the pinned fields / "All source fields pass through" line (output), a per-item **Edit {name}**, and one primary **Continue** (the existing `finish` action, relabelled). "Continue → Looks right → Finish sources" and "Continue → Let source decide → Finish outputs" each collapse to "Continue". The chip picker ("Which data source…?" / "What format…?") is still derived and emitted but renders collapsed behind a `<details>` whose summary is the server-posed question plus "— choose from a list instead"; it opens automatically only when the assistant replied without advancing the turn (a plain reply, or a synthetic failure whose copy does not invite Retry) or when the user opens it. Schema forms, the column-confirm card and the fields picker are never visited on the default chat walk. They appear only via Edit, via the list path, or when the chain could not complete the resolution — in which case the walk stops on that form, OPEN, with the assistant's own reply plus a server constant saying what still needs a value (never a rejection that throws the user back to the picker).

A second chat message on the review card ("actually make it JSON") is honoured when the stage holds exactly one reviewed component of that kind and no pending intents: the assistant's fresh resolution REPLACES that component in place (same stable id, name and position; new plugin and options) and the chain lands back on the card. For a source this re-decide runs against the session's existing blob: a resolution whose plugin the existing blob cannot be inspected as stops on the open form rather than failing the turn. Any other shape (several components, a pending intent) stays advisory with the existing withheld copy.

**Steps 3 and 4 (proposal, wiring).** One card each, unchanged in count. Rows read `{committed name} · {plugin display name} · node-N` — "Scrape Page · Fetch · node-1", "Cleanup · Field Mapper · node-3", "JSON Output · JSON · output-1" — the ordinal rendered as muted secondary text because the step-3/4 assistant still speaks in ordinals (chat_solver.py:2007 `alias = f"{kind}-{index}"`, names listed under "omitted") and the learner must be able to map its "node-3" to a row. No transform is ever suffixed "Output". The constant "Transforms each incoming item." gloss is gone; a transform row shows the deployment catalog's one-line plugin description when the catalog is loaded (the card triggers the load) and otherwise only the plugin name + the existing `node_options_summary` pairs — never a fallback constant. The routes list renders once per stage as a closed `<details>` "Routes as text (N)" (the accessible alternative to the 1.1 graph pane); the wire card keeps its status roll-up line visible and folds WireReviewList and the raw `<pre>` dump into that disclosure. The step-3 "Revise a component" fieldset and the step-4 correction form sit behind disclosures; the chat box remains the prose-revision composer at step 3 exactly as today.

**Names at commit.** GraphView's committed node label goes through the same humaniser (one line in lane 1.1's file, coordinated), so the name reviewed is the name on the committed graph.

## Mechanism

### Backend — chained chat resolution (2.3)

In `guided_chat_atomic.py`, add `_prepare_chat_resolution_chain(...)`, invoked from the `transition_body is not None` branch (:1649) INSIDE the existing degrade `try/except`, replacing the single `_schema8_answer_and_project_next` call:

1. **Arriving hop.** Call `guided_route._schema8_answer_and_project_next` for the ARRIVING turn with `transition_body` exactly as today (`source_inspection_facts` / `sink_prefill_*` applied here; a rejection here propagates to the existing `SinkAdmissionRejectedError` / `(PluginConfigError, InvariantError, TypeError, ValueError)` handlers and yields today's not-applied synthetic reply with state untouched). It returns `(state_1, planned_response_1, next_turn_1, prepared_next_1)`; `next_turn_1` is already appended as the unanswered TurnRecord (guided.py:2668-2680), so the chain never calls `_prepare_server_turn_occurrence` itself (that would raise "Cannot append a guided turn while an unanswered occurrence remains", guided.py:710-711).
2. **Loop, bounded ≤ 4 hops.** While `next_turn_k` is not `None` and not `review_components`, compose the answer body for `next_turn_k`:
   - **step-1 `schema_form`** (plugin_options intent emitted by this settlement): echo the form's own prefill via `_step_1_uploaded_bind_form_options(next_turn_k)` (the upload-bind precedent, :717), then merge the resolution's contract OVER it: `schema` from `source_resolution.options["schema"]` when present, and `on_validation_failure` from `source_resolution.on_validation_failure`. Custody still matches: `_schema8_server_options` treats only blob-bearing keys and `blob:` paths as server-held (guided.py:2217-2222), and `_require_inspection_custody_match` compares blob ids only (stage_transitions.py:260-271). This closes the model-facing seam where `resolve_source` teaches `guaranteed_fields` as IMPORTANT (chat_solver.py:481-495) while the chat path discarded `resolution.options` and `on_validation_failure` entirely (zero reads in guided_chat_atomic.py; selection stores `options=None`, stage_transitions.py:890-895).
   - **step-1 `inspect_and_confirm`**: answer with `next_turn_k["payload"]["observed"]["columns"]` — the server-inspected headers, exactly what the manual "Looks right" resubmits (InspectAndConfirmTurn.tsx:51-52). The LLM's `observed_columns` are NOT used: `transition_source_inspection_review` stores submitted columns verbatim with no comparison to the facts (stage_transitions.py:1057-1082), so answering from the model would make the graph pane's "fact" a model claim and would raise on an empty list.
   - **step-2 `schema_form`** and **step-2 `multi_select_with_custom`**: the bodies the UNCHANGED `_transition_request` SCHEMA_FORM / MULTI_SELECT arms build (options + `on_write_failure`; `required_fields` split into chosen/custom, or `PASSTHROUGH` when empty). Sink admission runs inside `_schema8_answer_and_project_next` at this hop as it does for a manual form POST.
   - If no body can be composed, stop with `next_turn_k` as the current turn.
   Each completed hop k>1 records an `_IntermediateOccurrence(step, turn=next_turn_{k-1}, payload=prepared_next_{k-1}, response=planned_response_k)` — the tuple `_prepare_step_1_uploaded_source_bind` already records for its form hop (:851-865). Summaries are server constants: "Source settings resolved through guided chat.", "Source columns confirmed from guided chat resolution.", "Output settings resolved through guided chat.", "Output fields resolved through guided chat."
3. **Longest successful prefix.** A rejection at hop k>1 (`PluginConfigError`, `InvariantError`, `TypeError`, `ValueError`, `SinkAdmissionRejectedError`) stops the chain with `state_{k-1}` (which already holds `next_turn_k` appended, unanswered), `next_turn = next_turn_k`, the intermediates completed so far, and the assistant message = the LLM's reply + the server constant "I filled in what I could; a required setting on the form below still needs a value." (admission: + the admission detail, as the existing handler already surfaces). This is required because a resolution whose facts cannot prefill the chosen plugin lands today on an open form (docstring :895-899; prefill without matching facts is only `{schema:{mode:observed}}`, emitters.py:155-162), and an all-or-nothing chain would have turned that documented fallback into a not-applied reply on the picker. Only a FIRST-hop rejection maps to today's synthetic reply.
4. Assign `resulting_state` / `planned_response` / `next_turn` / `prepared_next` / `intermediate_occurrences` from the chain's result. The user chat turn's `turn_token` stays `body.turn_token` (:1731) — the token of the turn the message was sent on.

Occurrence counts: source with facts = 2 intermediates (schema_form, inspect_and_confirm); source without facts = 1 (schema_form; the form resolves directly, stage_transitions.py:1006-1039); sink = 2 (schema_form, multi_select_with_custom). Each intermediate is one `guided_turn_emitted`/`guided_turn_answered` audit pair in the same cohort. If lane 1.4-r2 later stops emitting the fields turn, the bounded loop simply reaches the card one hop earlier — no change to this design.

**Review-card re-decide (A2, after A1).** `_transition_request` returns `None` whenever an active edit target is set (:566-567) and both edit-mode schema_form transitions pin the plugin to the reviewed one (stage_transitions.py:974-975, :1181), and `remove_reviewed_component` refuses the last component (:801-802) — so neither `begin_component_edit` nor remove+add can honour a plugin change. Instead add one pure transition in `stage_transitions.py`: `replace_reviewed_component(session, target, *, plugin, inspection_facts=None, prefill_options=None)` — deletes the reviewed entry for `target.stable_id` (even if it is the last), keeps `source_order`/`output_order` and the name, and stages a `plugin_options` intent under the SAME stable id (source: `SourceIntent(name, "plugin_options", plugin, options=None, inspection_facts=facts, ...)`; sink: `SinkIntent(name, "plugin_options", plugin, options=prefill_options)`), legal only on a `review_components` turn of the same kind with no pending intents and exactly one reviewed component. The chat route enters it when the arriving turn is `review_components`, the resolution kind matches, and that shape holds: it answers the review turn (response payload `{"component_action": {"action": "replace", ...}}` — a new `ComponentReviewAction` literal `"replace"`, SERVER-emitted only, never in `allowed_actions`, so the client cannot send it) and enters the loop at the derived schema_form. For a source, `_step_1_inline_source_inspection_facts` is widened to fire on a `review_components` arrival too (:1436-1439 today gates on `SINGLE_SELECT`); its "newest ready session blob stays authoritative" rule means the re-decide inspects the EXISTING blob — a plugin the blob does not match yields `facts=None` and the chain stops on the open form (rule 3). `_transition_request` is not edited; `begin_component_edit` and the user's Edit path are untouched.

Zero provider calls are added by A1 or A2: every hop is answered from the LLM's own tool result or server-held facts. `chat_solver.py`, `planning.py`'s binders/planner path, `plan_guided_pipeline`, `_transition_request` and the skills' contracts are unchanged; the one skill TEXT change is below.

`emitters.build_component_review_turn(guided, component_kind, *, catalog)` gains the catalog parameter (both callers are in `_build_get_guided_turn`, guided.py:399/443, which holds `catalog`; fork hydration reaches the same builder through `_build_get_guided_turn`, service.py:1305-1430) and fills each item's `form` by calling `build_step_1_schema_form_turn_from_resolved(reviewed, catalog)["payload"]` / `build_step_2_schema_form_turn_from_resolved(SinkResolved(outputs=(reviewed,)), catalog)["payload"]` — same `blob:<ref>` masking, same decorated boundaries, no new parsing site — plus `observed_columns` (source) or `required_fields` (output; empty = pass-through).

### Protocol (all three surfaces; no new TurnType, endpoint, control signal or error code)
