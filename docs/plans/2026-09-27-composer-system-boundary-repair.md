# Composer boundary ownership and failure classification repair

Date: 2026-09-27. Target: local `release/0.8.1`, base `1f14d49995f6ad66c75da25f78ad1a846347f0f6`. Implementation branch: `fix/composer-system-boundaries-20260927`. This plan is subject to independent Astra review before production edits.

## Problem and system model

The previous provider boundary repair closed the observed Sonnet 502 and planner 503 gaps. A wider Composer inspection found the same *ownership* defect at other interfaces. Admission, provider dispatch, durable settlement, HTTP acknowledgement, and frontend publication can be owned by different tasks. A local catch or session-ID check can report success while another owner is still working, or let an older owner publish after the current one.

For chargeable calls, the measurable stock is admitted provider attempts awaiting a terminal quota result. For guided operations and proposal decisions, it is admitted operations awaiting an authoritative durable outcome. Cancellation and exceptions should not reduce either stock by merely ending a request task. For frontend state, each request or stream read has a generation and a monotonic terminal result; a completed older request must not reclaim current state. Misleading retry copy creates a reinforcing loop: unchanged credentials or bad request produce another doomed attempt and additional quota pressure.

The leverage points are: classify failures at the physical provider call; retain and join every task that can write durable outcome after its caller is cancelled; make terminal outcomes and exact retries observable; and require generation and terminal precedence before frontend publication. These are behavioral contracts, not a target count of catches, tests, or lint findings. Honest signature churn is acceptable. Do not synthesize a Composer graph or add a tutorial-only path.
