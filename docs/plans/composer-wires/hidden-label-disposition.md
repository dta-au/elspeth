## Distinguish three cases

1. **Owned fixed field absent from an admitted shape or audit disclosure.** These are separate decisions. An unexpected field violating the owned response contract is producer drift and should fail precise admission. A field intentionally withheld by audit policy is not a contract defect merely because it has a fixed name. Add a field to audit output only when its disclosure has separately been approved; precise response admission does not grant that approval. Never paper over either case with a stable hidden-key hash. The baseline preview report is a concrete example of deliberate D4 audit withholding: data/runtime_preflight coalesce into the top-level unknown marker while the provider receives the original response. It does NOT establish an unauthorized omission or authorize exposing preview verdict/proof data. This top-level aggregate mechanism is also distinct from numbered nested labels.
2. **Legitimate dynamic keys inside an admitted response field.** Plugin schema property names, user-authored option names, and nested external mappings can remain arbitrary even after the envelope is precisely modeled. Their identities are not automatically disclosure-safe. Precise response admission must summarize or structurally redact these keys at the designated field boundary; it does not eliminate their legitimate occurrence. A dict[str, T] model constrains values, not key vocabulary/privacy. In particular, do not route arbitrary-key mappings blindly through `_project_validated_response_scalars`, whose current comment assumes model-validated keys are schema vocabulary.
3. **Malformed/unknown defensive diagnostic input.** Retain safe shape-only handling if the redaction boundary is deliberately invoked on external malformed content. Do not let that defensive path turn an internally malformed successful ToolResult into an apparently admitted success. Strict owned response admission should reject the owned contract violation before normal successful serialization.

Therefore planned precise response admission can remove normal occurrences caused by fixed internal fields, but cannot honestly promise that all unknown-key labels become defensive-only. Dynamic nested key carriers require their own explicit disposition. This is the acceptance question for the model work, not an inferred accomplishment of that unfinished patch.

## What current numbering guarantees

`_project_untrusted_response_structure` in redaction.py:483-521 iterates each mapping in input order. It preserves keys in `_SAFE_UNTRUSTED_RESPONSE_STRUCTURE_KEYS`; only unknown keys increment hidden_index, starting at 1. The counter restarts for every nested mapping. Lists and tuples preserve their order. Each opaque label is a position in this one projected mapping, not a semantic source-field identifier across rows, tool versions, or sibling mappings.

Stable row-local ordering is achievable by retaining that iteration contract and requiring internally owned producers to construct their known output in a stable order. Test the consumer-visible mapping, not only the set of labels. Inserting or moving a known safe key should not renumber hidden siblings; swapping two unknown input entries should swap the corresponding projected child shapes while labels remain 1,2. This is transparent positional behavior.

Do not sort by raw key: ordering would depend on secret names, would still not create semantic identity, and would change historical projection bytes. Sorting by already-redacted child shape avoids raw-key disclosure but cannot distinguish equal shapes, destroys source order, and adds no needed identity guarantee. Neither is the smallest repair. No generic key hash or correlation token is justified.
