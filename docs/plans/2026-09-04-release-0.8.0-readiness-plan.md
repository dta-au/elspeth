# Release 0.8.0 readiness plan — from `landing/multi-replica` to `main`

Written 2026-09-04. Tracker milestone: `elspeth-b63124d973` (each phase below
is a child ticket; dependency edges are recorded there and are the authority
on ordering). Operator direction that produced this plan (John, 2026-09-04):
a concrete plan to get **all** of the code onto `release/0.8.0` and ready for
merge to `main` as 0.8.0 — "merge and then fix all the bugs" is acceptable as
long as it is written down and tracked. Two further rulings the same day:
release 0.7.2 was folded into 0.8.0 when its scope sprawled (so the two
tickets still titled 0.7.2 are this release's work); an Azure Container Apps
equivalent of the AWS ECS deployment is in scope and was the reason the
multi-replica program existed; and the WS6 collector remediation tail of
the barrier-scopes campaign is folded in too, because **0.8.0 is the last
release before users and schema management constrain what can change**. The
pre-1.0 break posture (barrier-scopes spec ruling 22) is the licence for every
narrowing taken here; none of them is available again after launch. Phase
order: 1 → {2, 3, 4, 4b} → 5 → {6 ∥ 6b} → 7.

## Two bars, deliberately different

| bar | applies to | definition |
|---|---|---|
| **Landing bar** | Phase 1 only | the merged tree's failing pytest node-id set is a **subset** of the 402 failures already present on the platform parent `a2176dfe2`. Compared by node id, never by count — the branches collect differently (1,573 nodes added, 144 removed). |
| **Release bar** | Phase 7 | full `pytest tests/` with **zero** failures and a summary line; ruff, ruff-format, mypy clean; trust-tier judge-signature gate green with the operator key; CI `CI Success` + `composer-redaction-gate` + `enforce-allowlist-judge-gates` green; live trial and ECS/Azure acceptance receipts recorded. |

The 402 are the platform branch's own debt (`feature/deferred-platform-recovery`,
74 commits off `7cd2fc6db`), scoped out of the landing and into the release.
"Platform" and "mainline" are the integration method's names for the two
merge parents: `a2176dfe2` (multi-replica) and `b21f17a0a` (`release/0.8.0`).

### Phase 4b — WS6 collector remediation and the unified-lineage tail · P0

Ruling (John, 2026-09-04): "fold it all in, 0.8.0 is our last release before we
have to deal with users and schema management, so let's run this window hard."
The barrier-scopes / unified-lineage campaign (spec
`docs/specs/2026-08-21-barrier-scopes-full-nesting-spec.md`, rev 3.2) is not a
branch to land: `feature/unified-lineage` is 0 commits ahead of `release/0.8.0`
and WS1 through WS5 are already in the tree. What remains gates the merge to
main:

- the WS6 collector remediation epic `elspeth-3da1474353` — 19 open children
  plus 2 with expired codex claims; read each child's falsification comment
  first, since the epic records three severity collapses and two proposed fixes
  that would have made things worse. Two P0s are unreachable-today guards with
  a recorded reactivation trigger: do not build them. Must not ship past 0.8.0:
  the shareable-review strict models that 500 on any pipeline with a description
  (`elspeth-989d369d82`), the unsatisfiable deferred-intent demand that 409s the
  wire with no planner recovery (`elspeth-3d392c04ca`), and the collector
  `on_error` that is accepted and inert (`elspeth-239a31daeb`, which needs a
  spec ruling: wire it, or make it inexpressible like `trigger`);
- the WS3+WS4 integration item `elspeth-512206ca33`, whose claim expired on
  08-26 while the branch it describes was fully merged: reconcile and close or
  re-scope honestly;
- the two spec-level engine defects, silent single-member convergence
  (`elspeth-76e936568e`) and rule 4's false universal (`elspeth-46825d0055`).

Lanes start after Phase 1 lands and rebase onto it. Their file surface
(composer state, guided deferred-intents, frontend, config and builder, MCP

Every fix derives from an existing authority; guard-versus-guard drift is the
epic's root pattern. This phase settles before Phase 5: the spec's §11 says a
staged signing bundle is invalidated by exactly this churn.

### Phase 5 — trust-tier judge-signature gate green · `elspeth-0bc8af7054`

The `trust_tier.tier_model` rule runs inside CI's static-analysis job, which
feeds the required `CI Success` check, so `main` cannot merge until the signed
allowlist is green. Re-signing is deferred on OpenAI quota (capacity, not

agents never hold, verify with the key, CI green. Corpus home:
`elspeth-13f0cc04fb` (titled 0.7.2; now 0.8.0's).

### Phase 6b — Azure Container Apps, the program's goal · `elspeth-f23854fed7` (P0)

Ruling (John, 2026-09-04): the whole multi-replica program was a
prerequisite for Azure containerisation. The tracker already encodes this —
`elspeth-3bbf9a9731` (Bicep bundle + live provider acceptance) is blocked by
the multi-replica feature `elspeth-b5d7aa5655`, which Phase 1 unblocks. So
this phase runs in **parallel** with the ECS acceptance off the staging
trial, not behind it; the ECS acceptance package is the reference
implementation to mirror, not a gate.

Today `azure-container-apps` is a reserved target value, the reference doc
declares Container Apps unsupported, and `deploy/` has no Azure bundle.
Mirror the ECS side surface by surface: `deploy/azure-container-apps/`
Bicep; an `_azure_container_apps_acceptance` package sharing **one** receipt
schema with ECS; three runbooks and a skill; ACR publication in CI; the same
four replica>1 probes with live, unmocked evidence; flip the support matrix
and the reserved-value wording. Blocks Phase 7.
