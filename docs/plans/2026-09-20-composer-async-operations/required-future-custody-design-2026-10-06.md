## Scope and concrete owner

`ComposerRequiredWorkCoordinator` owns one adopted durable COMPOSE turn, manual PROPOSAL settlement, or retained synchronous COMPOSE scope. For a durable turn it is created immediately after atomic START supplies the exact running job/fence/attempt and BEFORE lease adoption or any required preamble, so adoption is observed at LEASE_RENEWAL/SQL_INITIAL. Pre-START claim/START SQL remains owned by the shared gated infrastructure and existing actual-Future joined helper; no coordinator fabrication of a running scope or capacity release on unresolved START is permitted. Manual/synchronous coordinators are created from their exact acquired authority before owned producers. It registers explicit producer tasks, SQL tickets and projections, and participates in lease close. `RequiredSQLTicket` is allocated before awaiting shared-pool admission. `run_required_sql(ticket, callable)` extends the existing joined bridge with explicit ticket observation; it uses the existing executor and limits. `_run_composer_sql` and `_run_composer_terminal_sql` retain their actual-Future joins and immutable recovery rules. No generic SDK adapter, cause promotion or audit-only business permission is authorized. Normal ACTIVE ordinary-helper result/cancellation semantics remain unchanged; the shared generation gated-submission and rare-anomaly quarantine behavior below deliberately applies to ordinary and required bridges. No parallel executor pool is allowed; sequential generation replacement using existing configuration is explicitly included after measured old-generation shutdown.

A separate process-local `RequiredExecutorGenerationCustodian` owns rare no-return submission recovery for the existing shared executor generation. It has an exact executor reference, monotonic generation ID, generation submission lock, release-once admission reservations, quarantine state and one control-thread drain. It is not a DB writer. Every ordinary and required submission must consult this generation's ACTIVE/QUARANTINED/CLOSED state at the existing shared executor admission/submit boundary; normal behavior in ACTIVE is unchanged. This narrow quarantine interlock is necessary to prevent old and replacement capacity overlapping. Existing admissions waiting to submit receive a typed generation-unavailable outcome and release their unused reservation; they never submit to a quarantined generation.

## Submission protocol and invocation witness

The generation-owned gated reservation/witness envelope applies to BOTH ordinary and required helper submissions to the shared pool. `RequiredSQLTicket` is only an optional semantic observer atop this infrastructure reservation. Ordinary callables also cannot enter before their returned Future is bound: a post-queue/no-return ordinary submission aborts its gate and quarantines the generation, rather than releasing admission while an unseen callable/provider/SQL can execute. Successful ACTIVE ordinary await/cancel behavior otherwise remains unchanged, and their infrastructure observations confer no R1 category, SDK cause promotion or business authority. Every submission route is enumerated by the existing executor owner; an ungated route is a failed custody inventory, not an exception.

Allocate the ticket, reservation and `RequiredInvocationWitness` BEFORE admission. The witness has a lock/event, immutable ticket/generation identity, gate state WAITING/ARMED/ABORTED, and monotonic wrapper fields ENTERED, OBSERVED_ABORTED, CALLABLE_STARTED, CALLABLE_FINISHED, EXITED. Only the wrapped executor callable writes wrapper fields. Only the submission owner arms or aborts the gate. Never let the wrapper invoke the SQL callable unless ARMED.

After admission, under the generation submission lock, verify ACTIVE, mark reservation held, call `executor.submit(gated_callable)`, bind the returned actual Future to the retained ticket, install completion observation and release-once callbacks, then arm the gate. These operations are synchronous, with NO await or async/user callback window. The wrapper may ENTER before submit returns, but waits on the gate. Inline done callbacks must not deadlock registry locks. Binding/callback setup failure retains any returned Future, aborts an unarmed gate and drains the actual Future. Once armed, ordinary repeated cancellation cannot erase custody or undo SQL.

If submit raises before returning a Future, abort the gate under its witness lock, retain the original exception, mark SUBMISSION_UNKNOWN and notify the generation custodian. This is not NOT_SUBMITTED: live Python3.13 submits by queue.put before `_adjust_thread_count` and returning its Future, so an exception can occur after queueing. The generation is immediately quarantined under the same submission lock before another submission can pass ACTIVE. No SQL retry/provider replay follows.

The gated wrapper executes a minimal nonthrowing bookkeeping envelope:

1. Set ENTERED once; duplicate entry is impossible-state integrity failure.
2. Wait for gate decision. If ABORTED, set OBSERVED_ABORTED under the lock, leave CALLABLE_STARTED false and never access/invoke the SQL callable.
3. If ARMED, atomically set CALLABLE_STARTED then invoke the exact callable once; retain exact result/exception and set CALLABLE_FINISHED even on exception.
4. In final owned envelope, publish EXITED with the other fields and signal the witness. The signal is after all callable cleanup/results are retained. The wrapper does no SQL, callbacks, external code or user cleanup after publishing this signal, only returns/raises the already retained outcome to executor bookkeeping.

The valid aborted trace is ENTERED=true, OBSERVED_ABORTED=true, CALLABLE_STARTED=false, CALLABLE_FINISHED=false, EXITED=true, gate=ABORTED. This proves THIS invocation's SQL callable never ran. It proves wrapper completion at the defined invocation boundary; it does NOT assert the inaccessible executor Future.done or completion of executor internal bookkeeping. A valid armed trace cannot be a no-return recovery trace, because the submission owner only arms after binding the Future. ENTERED=false with any observed/start/finish/exit flag, EXITED without ENTERED, OBSERVED_ABORTED with CALLABLE_STARTED, CALLABLE_FINISHED without CALLABLE_STARTED, or ARMED without a retained Future are impossible states: retain an integrity observation, quarantine and use measured generation drain; never use an impossible witness to release custody.

## Release after sufficient witness, without leaking capacity

A known returned Future uses its real done callback and result, as today. A known pre-submit failure uses structurally proved unused-admission release. A no-return anomaly has this additional NARROW release proof: valid aborted wrapper EXITED proves the reserved invocation consumes no future SQL work. `reservation.release_once(proof=ABORTED_INVOCATION_EXIT)` releases its logical admission charge, and records the exact witness plus original submit error. This is a documented exception to real-Future callback release for only an inaccessible-Future aborted invocation; no wrapper Task or arbitrary finally event qualifies. Thread concurrency remains bounded by the existing executor's fixed workers. The anomalous generation stays quarantined, so this logical release cannot admit fresh work while the unobserved executor bookkeeping tails drain. There is no overlap of replacement generation capacity.

After that witness, the turn coordinator may move its ticket from SUBMISSION_UNKNOWN to OBSERVED_ABORTED_NOT_EXECUTED. It drains all OTHER submitted Futures/projections, then selects an ordinary recovery failure using the canonical receipts. It may run the existing sealed terminal failure via a verified ACTIVE replacement generation after old generation drain, or hand the durable job to existing exact fresh-owner recovery if its fence has lapsed. It never claims audit durable, creates zero-usage provider settlement, replays provider, repeats START or publishes a missing assistant. Local transition/CRL custody can release only after this required evidence and terminal/fresh-authority protocol, not merely at witness arrival.

Repeated anomalies with valid aborted witnesses release each reservation exactly once. The generation recovery below is still necessary before new shared work is admitted; no indefinite accumulation of16/32 logical admissions after proof is allowed.

## No entry / no sufficient witness: complete rare-anomaly lifecycle

The generation custodian owns every anomalous ticket strongly and begins a control-thread recovery exactly once. It closes shared submission admission for that generation, snapshots retained known Futures/reservations, and calls the exact old executor's `shutdown(wait=True, cancel_futures=False)` OFF the event loop. Do not cancel all queued known required audit/settlement work: they must finish once submitted. Already quarantined unknown wrappers have ABORTED gates and cannot execute SQL when eventually dequeued. Known cancellable work retains its own reviewed cancellation policy. Normal admitted-before-quarantine submissions have either completed registration under the lock or are refused before submit; none escape the snapshot/registry.

A successful return from shutdown(wait=True) is the measured generation-completion witness: the old executor's worker threads have joined and no queued invocation can later execute. It resolves even a no-return ticket whose wrapper never ENTERED. Combined with its never-ARMED, ABORTED gate, this proves its SQL never ran; release every unresolved reservation exactly once as GENERATION_DRAINED_ABORTED, preserve original submission/custody receipts, and drain known Future outcomes. Shutdown return does not invent missing results for known SQL: retained known Futures must still be read and their errors/projections observed. Only after this old generation completion can the custodian install a replacement using the existing max-workers/admission configuration, and reopen ACTIVE submission. No new parallel pool, same-process overlapping capacity, or cheap uncontrolled global shutdown is permitted. This is a rare shared-generation lifecycle action, not routine per-request cancellation.

If shutdown raises or fails to complete, the generation remains quarantined; never infer SQL completion from a timeout. The complete [selected hung-drain lifecycle contract](hung-drain-lifecycle-design-2026-10-06.md) supplies the controlling production mechanism, constructor/test ABI, private codec and supported-runtime limits. It explicitly adds application-lifecycle scope to the master; no unspecified external supervisor is assumed.

At startup capture the validated composer_async_drain_seconds once. The quarantine observation budget is exactly min(captured value,30.0) seconds. First quarantine fixes an immutable monotonic deadline, sets required_generation_unavailable and starts a strongly retained observer outside the hung executor/control-thread join. Immediate pre/post-cache readiness and shared/composer admission consult this separate generation latch. Production registers the typed ProcessRecovery callback before the first shared submission; standalone harnesses provide the explicit nominal fake, never a default kill callback.

If the exact R2 drain barrier is unresolved at that deadline, RequiredGenerationDrainExpired identifies the generation/deadline/outstanding owned tickets and invokes the callback once. ProcessRecovery synchronously sets permanent instance_draining, obtains BEGIN/GRACE_ACK within one second and arms its factory-prestarted independent Linux process-pidfd watchdog's immutable 30-second grace. Then it requests ordinary self-SIGTERM; helper hard termination is independent of the target's later GIL/ThreadPool teardown. Same-process sequential replacement is allowed only after complete R2 drain before process escalation. After escalation neither latch clears and no replacement can become ready in the old process. SIGKILL request is not actual exit proof; the linked contract requires kernel exit before a fresh local process slot starts/readies and preserves remote-DB commit reconciliation. Arbitrary untriggered GIL freezes and uninterruptible kernel sleep retain the declared limits. No helper respawn, CLI topology change, deployment or ACA self-SIGTERM timer inference is introduced.

Durable recovery markers are the existing running job row and exact session-operation fence/lease, plus any already valid terminal record; no new schema or generic failure-marker mutation is introduced. The process-local generation/ticket marker is retained and exposed via lifecycle diagnostics while alive. On restart, the existing DB-clock expiry/fresh-owner reaper reads authoritative DB state and validated terminal first, then performs only its existing sealed failed recovery if needed. SQL commit may have preceded process exit: a cancelled client/connection is not rollback proof, and fresh writer read/current-state reconciliation remains mandatory. No provider/START replay. Manual/synchronous requests have no durable job and receive connection loss during restart; fresh request admission still requires current fence authority and must not replay the vanished invocation's provider/effects.

App shutdown must not call ordinary lease release through an unresolved ticket. It either completes this drain and existing exact release/terminal protocol, or exits under supervisor custody with the durable lease allowed to expire naturally. Transition locks are not falsely released as completed while SQL can run; process exit destroys the local lock only after OS termination. There is intentionally no liveness promise for a permanently hung thread without process termination; the operational recovery is explicitly in scope rather than deferred.

## Exact terminal, renewal and lease-close phases

ACTIVE permits ordinary registered producers and required SQL. PRETERMINAL_DRAIN closes ordinary producer/SQL registration but explicitly permits declared finalizers: terminal initial/retry, independent writer read, required failure audit, and lease renewal/close. Renewal continues while required business SQL drains; the barrier waits for fixed registered producer/business tickets, not an endlessly growing sequence of future renewal ticks. Each actual renewal outcome remains registered with its predetermined tick key and is retained for final reduction.

TERMINAL_FINALIZATION drains the declared terminal/audit/readback finalizers and applies current valid-terminal-wins recovery. Then LEASE_CONTROL_DRAIN signals stop-renewal first, joins the actual latest/in-flight renewal Future and renewal task, and records its original receipts. No new renewal tick may launch after this signal. `prepare_lease_release` checks all business/terminal/renewal work and projections are resolved, permits exactly the still-unsubmitted last release finalizer, and refuses unresolved generation/SQL custody. It does not demand that an unregistered release already be completed.

LEASE_RELEASE registers the exact final source42/stage14/SQL_INITIAL release Future, submits through the same gated/joined bridge, and observes its actual physical outcome and required projection. Close bookkeeping has source41/stage14/PRODUCER. Logical turn/CRL/transition release and final public projection occur only after this last finalizer is observed. Release failure preserves its receipt and exact authority recovery requirements; an already hash-valid committed terminal still wins under the existing contract. This phase machine avoids both an infinite renewal barrier and a circular prerequisite for the final release. During quarantined/hung generation recovery, no release is submitted to the old pool; the preceding quarantine/drain/restart rules retain authority custody.
