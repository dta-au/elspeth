# Independent second model: cross-examination

**Chosen option: B′ (high confidence).** Give compose its own `composer_async_operations` table and authority; extract only the strict, schema-tagged request canonicalisation into a neutral helper. Use **one** client-minted ID for a send: the job's `operation_id` is the key of the existing immutable message-ingress binding. Cut the old wire name and acceptance branch over in the same epoch; do not accept two keys. Keep R2, R3, freeform-only scope, and 202 plus poll as ruled.

`Forwarded` was a courier result, not a design position. The argument here is independent of that result. The current checkout's receipt shape and methods were read directly: `src/elspeth/web/sessions/models.py:727-808`, `:825-873` and `src/elspeth/web/sessions/operation_receipts.py:39-53`, `:272-353`, `:441-527`.

## Reasons

- **The lifecycle boundary is a safety boundary.** A new receipt starts `in_progress` with a live receipt lease, and an expired `in_progress` row is explicitly taken over with a new token and attempt (`src/elspeth/web/sessions/operation_receipts.py:287-313`, `:316-353`). A compose job must be admitted queued before the session fence exists, may reclaim only a queued claim, and must never rerun a running provider turn (`docs/specs/2026-09-16-composer-async-operations-design.md:92-100`; `docs/plans/2026-09-20-composer-async-operations/contract.md:254-269`). Sharing the row would make the no-takeover guarantee depend on a kind branch in takeover, validation, settlement, and every future caller. The current receipt CHECK requires a receipt lease for every live row (`src/elspeth/web/sessions/models.py:794-808`).
- **The present readers and writer gate are receipt-specific.** The receipt reader rejects other kinds, validates only fork/revert locator bundles, and decodes a completed non-fork as a revert (`src/elspeth/web/sessions/operation_receipts.py:65-71`, `:93-148`, `:221-234`). Archive selects any `in_progress` receipt, then refuses it or raises Tier-1 on an unknown kind (`src/elspeth/web/coordination/repository.py:722-735`), whereas D7 says a compose job does not refuse archive (`docs/plans/2026-09-20-composer-async-operations/contract.md:77`). The existing exact writer pin and TablePolicy are scoped to the receipt tables (`tests/unit/architecture/test_session_db_mutation_authority.py:188-195`, `:12190-12215`). A new table preserves that proof and gets its own proof.
- **The shared part is smaller than either whole facility.** The request hash is a strict-DTO normalisation rule plus a schema tag; today it hardcodes the receipt tag, the field `operation_id`, and the closed fork/revert kind type (`src/elspeth/web/sessions/operation_receipts.py:36-53`; `src/elspeth/web/sessions/protocol.py:264-267`). Compose must store and verify the full public response: the stored state cannot reproduce transient `live_validation` (`src/elspeth/web/sessions/routes/_helpers.py:878-892`, `:918-920`) and receipt replay rebuilds a response from a locator before hash comparison (`src/elspeth/web/sessions/routes/operation_receipts.py:95-104`). A neutral hash helper is bounded reuse; a shared terminal-replay/state-machine core is not yet supported by these two consumers.

## Cross-examination of other positions

- **systems-thinker — B.** The structural no-takeover argument holds; the current takeover arm and live CHECK confirm it (`operation_receipts.py:316-353`; `models.py:794-801`, paths under `src/elspeth/web/sessions/`). The sharp objection is that plain B's instruction to reuse `operation_receipt_request_hash` is not executable as written: its kind is the two-value `OperationReceiptKind`, its field check literally requires `operation_id`, and its schema string is fixed (`src/elspeth/web/sessions/protocol.py:264`; `src/elspeth/web/sessions/operation_receipts.py:36-53`). Also, the running compose row **does** retain a queued-claim triple including `claim_expires_at`; R3 says its *liveness* is the SOL, not that it has no lease-shaped column (`contract.md:193-196`, `:267-269`; `T03.md:77-79`, all under `docs/plans/2026-09-20-composer-async-operations/`). The structural distinction remains real.
- **db-architect — B.** I accept the recommendation to consider a partial unique index on `(session_id)` for **both** queued and running, because D8 permits only one nonterminal job, while the planned unique index covers running alone (`contract.md:78`, `:197-203`). That would make the D8 invariant survive a second writer. It does not settle the identity/codec contract: the current send already supplies another minted key (`src/elspeth/web/sessions/schemas.py:143-155`; `src/elspeth/web/frontend/src/stores/sessionStore.ts:1495-1510`). I cannot adopt the suggested SQLite WAL or PostgreSQL archive measurements without reproducing their instruments; they are not needed for the table choice.
- **python-architect — C.** The no-reuse case for the authority is decisive: reserve has no unleased queue and settle requires a live receipt lease (`src/elspeth/web/sessions/operation_receipts.py:287-313`, `:499-512`). But C's byte-for-byte sibling codec leaves two definitions of the same strict normalisation. The proposed “optional” common helper is the material difference between C and B′. Its narrow parameterised form keeps separate schema tags and kind vocabularies while removing avoidable drift (`operation_receipts.py:36-53`; `contract.md:112-119`). The existing ingress key also makes an unchanged T02 impossible (`schemas.py:143-165`).
- **audit-integrity — B.** The concern about lost claim history is valid: the planned terminal write clears `claim_owner_instance_id`, and a later session operation can replace the single fence row (`docs/plans/2026-09-20-composer-async-operations/T06.md:316-321`; `src/elspeth/web/sessions/models.py:321-351`). That changes my plan recommendation: retain a forensic owner/settler fact or append a compose-owned event when the owner decides it is product audit evidence. It does **not** establish that compose needs a full copy of the receipt event chain. Receipt events assert an initial `claimed` event and tie terminal evidence to a locator-based receipt (`operation_receipts.py:170-200`); the compose table is a transport job with a different terminal body (`contract.md:174-196`). The event requirement needs an explicit custody decision, then its own table/gates if chosen.
- **sre — B.** Failure isolation and the archive example are well supported (`src/elspeth/web/coordination/repository.py:722-735`; `contract.md:77`). The weak point is treating B's operational simplicity as enough to ignore the send identity: `SendMessageRequest` requires `client_request_id`, the route checks it before writing, and the SPA reuses it on retry (`src/elspeth/web/sessions/schemas.py:143-155`; `src/elspeth/web/sessions/routes/messages.py:173-181`, `:236-246`; `src/elspeth/web/frontend/src/stores/sessionStore.ts:1495-1510`). A second ID would create two independent acceptance verdicts for one action. I did not verify the claimed poll-load or storage-growth measurements, so they do not drive this conclusion.
- **leverage, solution-architect, tech-critic — B′.** I agree with their one-identity correction. I reject only the literal claim that a B′ running row has no lease column: the planned running status retains the queued claim triple, including expiry (`contract.md:193-196`; `T03.md:77-79`). The important rule is that `claim_expires_at` cannot authorise a running takeover; SOL liveness alone decides it (`contract.md:267-269`). Leverage's proposed stronger T06 write predicate deserves a targeted negative control: D12 permits a terminal row before SOL close, while F-B2/C2's stated predicate only matches `status='running'` (`contract.md:46`, `:82`). If a job is bound to the exact fence triple, subsequent non-audit writes should require that job still be running and uncancelled. This is a plan safety refinement, not a change to R2/R3.
- **codex — Forwarded.** It contains no option A–D argument to rebut; its own text says it inspected no repository files. I assign it no evidentiary weight.

**What changed my mind:** the live `message_ingress_receipts` row is an immutable `(session_id, client_request_id) → user_message_id` binding (`src/elspeth/web/sessions/models.py:464-488`), and the route/SPA actively use that key (`src/elspeth/web/sessions/routes/messages.py:173-181`, `:236-246`; `src/elspeth/web/frontend/src/stores/sessionStore.ts:1495-1510`). That moves the answer from unqualified B to B′. It also means “one client ID” needs a concrete cutover, not a note in T14.

## Against itself

**Steelman for A/D:** receipts already have a reviewed Tier-1 validator, a terminal-immutable trigger, append-only events, terminal hash checking, and one exact writer inventory (`src/elspeth/web/sessions/operation_receipts.py:93-200`; `src/elspeth/web/sessions/models.py:1636-1697`; `tests/unit/architecture/test_session_db_mutation_authority.py:12190-12215`). A second facility incurs real schema and gate work and can drift. **Rebuttal:** those safeguards certify a lease that can be taken over and a replay reconstructed from locators. Compose's queued phase, non-replayed running turn, SOL-bound liveness, cancellation, and stored full DTO require different branches (`contract.md:174-203`, `:254-286`). Reusing the receipt table would also widen a kind-blind TablePolicy and change archive's current query (`test_session_db_mutation_authority.py:188-195`; `src/elspeth/web/coordination/repository.py:722-735`). Share the binding primitive and test vocabulary; add compose-specific evidence controls where an actual audit need is identified.

## Plan consequences

- **Before T02:** choose one wire name and one value for a send; I recommend `operation_id` on the new strict DTO and job, with the ingress receipt's physical key renamed in the epoch cut. Keep the immutable ingress row as the accepted user-row binding, write it in the same transaction as the user row, and make its conflict after job admission a Tier-1 invariant rather than a second 409 acceptance path. Remove the old route 409 and client recovery branch at cutover. Recompose keeps `expected_user_message_id` (`src/elspeth/web/sessions/schemas.py:143-165`; `src/elspeth/web/sessions/models.py:464-488`; `src/elspeth/web/sessions/service.py:1396-1423`; `:4508-4537`). Update ACA/replica acceptance tooling that currently sends or queries `client_request_id` (`src/elspeth/web/azure_container_apps_acceptance.py:315-325`; `src/elspeth/web/_acceptance_common/replica_probes.py:630-647`).
- **T02:** lift a neutral helper taking `schema`, `kind`, strict DTO, and identity-field name; have a receipt wrapper pass the existing receipt tag and a compose wrapper pass `composer-operation-request.v1`. Pin receipt hash bytes with a golden vector. Do not widen `OperationReceiptKind`; use `_SessionOperationRequest` for the strict DTOs, and change the existing `RecomposeRequest` rather than creating another (`src/elspeth/web/sessions/operation_receipts.py:36-53`; `src/elspeth/web/sessions/protocol.py:264`; `src/elspeth/web/sessions/schemas.py:72-88`, `:162-165`; `contract.md:112-119`, `:155-162`). Keep full response JSON/result hash validation in the compose codec.
- **T03:** retain the separate table, CHECKs, terminal trigger, own TablePolicy, digest inventory, and PostgreSQL reflection gate (`contract.md:174-203`). Consider enforcing D8 with a partial unique index over queued **and** running, then prove the duplicate-admission race on both dialects. Re-anchor stale guided insertion instructions on the current receipt table/events (`T03.md:689-700`; `src/elspeth/web/sessions/models.py:727-873`). Decide explicitly whether claim/settler identity is product audit evidence; if so, retain it or append compose-owned events before nulling the live claim token. The current session epoch is 71, so use the next free epoch at the final cut (`src/elspeth/web/sessions/models.py:57-59`; `src/elspeth/web/sessions/schema.py:40-45`; `contract.md:39`).
- **T04:** keep `ComposerAsyncOperationAuthority` independent. Claim/reclaim/release predicates must name `status='queued'`; no method may re-adopt a running row. The `running` reaper paths only settle under the R3 SOL proof (`contract.md:225-250`, `:267-269`). Add a negative control for a lapsed running claim that cannot become queued or run again. Admission deduplicates on the one job key, while worker ingress insertion binds that same key to the user row.
- **T05:** preserve the one-transaction claim-to-running plus SOL mint, then adopt; no receipt reserve or takeover call enters it (`contract.md:254-269`). Prove a queued job and fork/revert still arbitrate through the session fence rather than a receipt-table status query (`src/elspeth/web/sessions/service.py:1059-1075`).
- **T06:** preserve the composite terminal transaction and full DTO persistence (`contract.md:271-286`). Bind user row, immutable ingress receipt, and job `user_message_id` in one transaction or verify their equality before terminal CAS (`src/elspeth/web/sessions/service.py:1396-1423`; `src/elspeth/web/sessions/models.py:464-488`; `T03.md:77-85`). Add the exact-fence post-terminal negative write control raised above; keep audit-only cancellation writes as adopted (`contract.md:46`, `:82`).
- **T13/T14/T17:** perform the single-key route/client cutover and update the spec's deleted-guided-codec wording (`docs/specs/2026-09-16-composer-async-operations-design.md:102-113`) and stale contract DTO/epoch text (`contract.md:39`, `:155-162`).
