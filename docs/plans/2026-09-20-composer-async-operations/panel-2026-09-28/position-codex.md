# Independent second-model position: composer async job storage

**Recommendation: B, separate table with a domain-separated shared request codec. Confidence: high.** Keep `composer_async_operations` as the transport job authority. Extract only the strict DTO normalization and hash-envelope construction shared with `operation_receipt_request_hash`; retain two named public wrappers and two distinct schema tags. Do **not** call the existing receipt wrapper directly for compose jobs. This is a narrow refinement of B, because that wrapper hardcodes `session-operation-receipt-request.v1` (`src/elspeth/web/sessions/operation_receipts.py:36-53`) while the plan specifies `composer-operation-request.v1` (`docs/plans/2026-09-20-composer-async-operations/contract.md:104-119`). Existing receipt hashes must remain byte-identical under the refactor; the shared helper should take an explicit, closed schema discriminator, and golden-vector tests should prove both domains.

## Three decisive reasons

1. **The state machines have different custody and crash meanings.** A receipt is inserted already `in_progress` with a live token and attempt 1; an expired receipt may be taken over as attempt 2+ (`src/elspeth/web/sessions/operation_receipts.py:272-313`, `src/elspeth/web/sessions/operation_receipts.py:318-353`). Its table admits only `in_progress`, `completed`, and `failed`, with a single lease shape (`src/elspeth/web/sessions/models.py:727-747`, `src/elspeth/web/sessions/models.py:763-766`, `src/elspeth/web/sessions/models.py:794-808`). The compose contract instead needs an admitted, unstarted `queued` row, a reclaimable queued claim, and a `running` row that must never restart a provider call (`docs/specs/2026-09-16-composer-async-operations-design.md:92-100`, `docs/specs/2026-09-16-composer-async-operations-design.md:244-252`). The adopted plan binds that running row to the COMPOSE session fence in one start transaction and reaps only after that fence is lost (`docs/plans/2026-09-20-composer-async-operations/contract.md:58-65`, `docs/plans/2026-09-20-composer-async-operations/contract.md:254-269`). Widening the receipt table and reusing its reserve/renew/settle functions would require kind-specific takeover, lease, and terminal rules throughout functions that currently assume one receipt lifecycle (`src/elspeth/web/sessions/operation_receipts.py:356-399`, `src/elspeth/web/sessions/operation_receipts.py:441-527`). That is not meaningful lifecycle reuse.

2. **The stored result and audience are different.** Receipt success stores a result locator and response hash, then the route reconstructs and verifies a synchronous response (`src/elspeth/web/sessions/models.py:738-743`, `src/elspeth/web/sessions/operation_receipts.py:221-234`, `src/elspeth/web/sessions/routes/operation_receipts.py:95-105`). The public compose response includes a `proposals` list (`src/elspeth/web/sessions/schemas.py:234-244`); the design requires storing the exact validated public DTO so a later poll can return it, with request JSON cleared at settlement (`docs/specs/2026-09-16-composer-async-operations-design.md:74-90`, `docs/specs/2026-09-16-composer-async-operations-design.md:133-143`). The plan's queued/running/terminal bundles, actor binding, cancellation marker, deadline, full result JSON, schema and hash are coherent as one job-specific table (`docs/plans/2026-09-20-composer-async-operations/contract.md:174-203`). Putting these nullable fields on fork/revert receipts would make their existing closed status, result-locator, event, and terminal-hash validation conditional on kind (`src/elspeth/web/sessions/models.py:794-808`, `src/elspeth/web/sessions/models.py:825-871`, `src/elspeth/web/sessions/operation_receipts.py:93-148`, `src/elspeth/web/sessions/operation_receipts.py:151-200`). The receipt's append-only events and terminal immutability are real safeguards, not an argument that its row must own unrelated jobs (`src/elspeth/web/sessions/models.py:1636-1696`, `src/elspeth/web/sessions/models.py:1857-1885`).

3. **The write boundary is materially different while the hashing rule is genuinely reusable.** The fork/revert route helper acquires a session lease before reserving, waits on an active receipt, and can take over an expired one (`src/elspeth/web/sessions/routes/operation_receipts.py:193-223`, `src/elspeth/web/sessions/routes/operation_receipts.py:239-249`, `src/elspeth/web/sessions/routes/operation_receipts.py:281-323`). The async POST must return 202 after durable admission without waiting for that lease or provider (`docs/specs/2026-09-16-composer-async-operations-design.md:102-131`). Compose completion must publish assistant/audit rows and the stored response in one transaction under the bound COMPOSE fence, including cancel precedence (`docs/plans/2026-09-20-composer-async-operations/contract.md:42-50`, `docs/plans/2026-09-20-composer-async-operations/contract.md:271-290`). Existing receipt writes already have fork/revert-specific callers and fences in session, coordination, blob, and route code (`src/elspeth/web/sessions/service.py:1045-1119`, `src/elspeth/web/coordination/repository.py:4040-4058`, `src/elspeth/web/blobs/service.py:484-499`, `src/elspeth/web/sessions/routes/sessions.py:918-938`, `src/elspeth/web/sessions/routes/composer/state.py:760-784`). Sharing a small normalization primitive avoids a second implementation of strict/forbid validation, default/None materialization, operation-ID exclusion, and the session/kind binding (`src/elspeth/web/sessions/operation_receipts.py:39-53`), without coupling these writers.

## Strongest counterargument

**C is simpler at first implementation:** the receipt request hash is roughly one short function, so extracting a shared helper creates a dependency and refactor risk for live fork/revert bindings (`src/elspeth/web/sessions/operation_receipts.py:36-53`; the plan's proposed sibling is `docs/plans/2026-09-20-composer-async-operations/contract.md:104-119`). C also keeps the compose schema domain obviously separate. I still prefer B because two copied canonicalization implementations can silently diverge as request DTOs evolve. The shared helper should be limited to request normalization and envelope hashing; do not generalize result, lease, event, or terminal handling. If preserving the existing receipt hash cannot be demonstrated by a golden vector, choose C until that check is fixed, rather than changing durable receipt identity.
