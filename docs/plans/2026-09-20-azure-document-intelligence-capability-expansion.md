# Azure Document Intelligence capability expansion — implementation plan

> **For implementation:** Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans`, task by task. Use `superpowers:systematic-debugging` for any unexpected failure. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `azure_document_intelligence` accepts documents as payload-store bytes, publishes Azure's generated PDF and cropped figures as content-addressed blobs referenced from the row, and authenticates with an API key, managed identity, or a service principal — without weakening per-row audit, routing, or reproducibility.

**Architecture:** A transform is a closed interface: **row in, row out.** The Azure plugin adds no Landscape table, no audit-writer method and no schema change. (Task 7, a separate platform cleanup the operator folded into this plan, *removes* a RAG-only audit-writer method and is schema-breaking.) Three additions sit under one unchanged submit → poll → enrich path. (1) `AuditedHTTPClient` gains a bytes-request leg and a bytes-response leg that record a `{sha256, size_bytes, content_type}` descriptor instead of the body. (2) Generated bytes go to the run's `PayloadStore` — content-addressed, so a retry can never replace different bytes under one identity — and the plugin reshapes the result into flat, announced row fields (blob ref, MIME type, size; index-aligned lists for figures), never bytes or a path; this is the pattern `blob_fetch`, `web_scrape` and `pdf_rasterize` already use. Because the engine records only a *hash* of an ordinary transform's output row, the durable audit record of what was published is a manifest in the node state's existing `success_reason` metadata, not the row. (3) Authentication becomes a per-leg header provider so an Entra token can refresh mid-row. URL and base64 modes, their YAML, and their output fields are untouched.

**Tech stack:** Python 3.12, httpx, pydantic v2, `azure-identity>=1.25,<2` (already in the `azure` extra — no new dependency), pytest.

**Spec:** [docs/specs/2026-09-20-azure-document-intelligence-capability-expansion.md](../specs/2026-09-20-azure-document-intelligence-capability-expansion.md). Executors read both; this plan argues from the spec.

### D1 — row in, row out

**The ruling.** A transform plugin is a closed interface. It may call audited clients and the payload store through its context; it does not get tables, audit-writer methods, or export record types of its own. If a platform-level "published artifact" record is ever wanted, that is a platform feature every publisher would share — not something a plugin plan introduces.

**The precedent was already in the tree.** Three transforms publish payload-store bytes and answer with row fields alone: `blob_fetch.py:541-552` (`blob_ref`, `content_type`, `size_bytes`, `sha256`, status, final URL), `web_scrape.py:909`, and `pdf_rasterize.py:691-703` (`page_blob_ref`, `page_mime_type`, `page_size_bytes`, …). Earlier revisions of this plan read that as a gap to close; it is the house pattern.

**What the superseded design would have cost** — recorded so nobody re-proposes it: a new `transform_artifacts` table, a schema-epoch bump that invalidates **every** Landscape database including deployed PostgreSQL (`_sync_schema_identity`, `database.py:1345-1352`, checks the epoch on all backends), a 14th method on the ratcheted `PluginAuditWriterAdapter` (`RATCHET = 13`), three hand-written retention/grade enumerations (`purge.py:109`, `purge.py:325`, `reproducibility.py:177`), the snapshot export read model and record union, MCP, the TUI, and — for real discoverability — the web run-outputs stack in Python and TypeScript. Three independent reviews called that design reasonable *as a table*; none of them asked whether a plugin should have one.

**How each spec §2 requirement is met without a table.**

| Spec §2 asks for | Met by |
| --- | --- |
| a durable artifact identity | the SHA-256 content address. It is the identity `blob_rows`, `blob_fetch` and `aws_textract_inline_analysis` already use as `blob_ref`. |
| a retry neither duplicates nor silently replaces different bytes under one identity | content addressing: identical bytes store to the same address (no duplicate); different bytes **are** a different identity (no replacement). There is no mutable name to collide on, so the idempotency-key machinery of the old design has nothing to protect. |
| the row receives an owned reference (kind, MIME, length, digest, identity; figure id and order), never bytes or a temp path | flat announced fields, written only after `store()` returned: the PDF's blob ref / MIME / size; for figures, index-aligned lists of ids, blob refs and sizes plus one MIME string. Kind is *which field*; digest and identity are the blob ref; order is list order. |
| audit links each retrieval call and publication to the source row and operation | two durable records under one `state_id`: the audited `get_bytes` call's descriptor (the body's `sha256`), and a **publication manifest** in `success_reason["metadata"]["generated_artifacts"]`, written only after every `store()` returned, carrying the same digests plus the `operation_id`. |
| discoverable from the Landscape audit trail | the manifest is in `node_states.success_reason_json`, which token lineage returns with the node state and the public exporter already carries — the snapshot read model selects the whole `node_states` row and loads it through `NodeStateLoader` (`export_read_model.py:412-420`, `model_loaders.py:412`, DTO field at `contracts/export_records.py:355`); `get_calls` for the state shows the retrievals with matching digests. No new reader, record type or column. |
| a requested but unpublished artifact fails the row closed | unchanged — that is transform logic (Task 3). |

**The output row is not an audit record — the manifest is (second review, V2-1).** An earlier revision said the output row is "recorded through the engine's ordinary token payload". Measured, it is not: for an ordinary one-to-one transform `complete_node_state` stores `output_hash = stable_hash(output_data)` and nothing else (`core/landscape/execution/node_states.py:530-562`); `token_data_ref` is the expand/coalesce writers' payload (`contracts/audit.py:261`); lineage returns the source row, node states and calls, not each intermediate row (`lineage.py:340-350`); scheduler payloads are scrubbed at terminalization; and a downstream `field_mapper` can drop the generated fields before any sink sees them. So the row fields are the **data-plane** reference, for downstream nodes, and the durable evidence goes through the channel the platform already gives every transform: `success_reason`, stored as `success_reason_json` (`Text`, unbounded — `schema.py:1353`), validated only for a string `action`. This plan already put `operation_id` there.

```python
success_reason["metadata"]["generated_artifacts"] = {
    "pdf": {"sha256": str, "size_bytes": int, "mime_type": "application/pdf", "field": "<pdf_blob_ref_field>"} | None,
    "figures": [{"ordinal": int, "figure_id": str, "sha256": str, "size_bytes": int}, ...],   # analyzeResult order
    "figure_mime_type": "image/png",
    "figure_fields": {"ids": str, "blob_refs": str, "size_bytes": str, "mime_type": str} | None,  # configured names
    "figures_key_present": bool,
    "total_bytes": int,
}
```

About 150 bytes per figure: ~30 KB at the default `max_figures=200`, ~300 KB at the 2000 ceiling — in a `Text` column, written once per row. It is a plain JSON value in an existing column, so row-in/row-out holds: no table, no verb, no record type. The reviewer's alternative — "explicitly design a generic platform facility" — is exactly what a plugin plan must not do (D1); if the operator wants one, that is its own ticket.

**What is genuinely given up, stated rather than hidden:** no `artifact_id` separate from the digest; no indexed "list every generated artifact in run R" — it is a scan of `success_reason_json` for this plugin's node; figure order lives in the manifest list and the row's list, not in a column. None of these is in the spec's acceptance list.

### D7 — row-referenced blobs and retention (OPEN, out of scope)

`PurgeManager` is the only caller of `payload_store.delete` (`purge.py:433`), and it finds refs through a hand-written UNION over ten ref columns (`purge.py:139-176`). **None of them is a row field value.** So a blob referenced only from inside a row — a `pdf_rasterize` page, a `blob_fetch` body, and now a generated PDF or figure — is **invisible to retention**: it is in neither the expired nor the active set.

**That is two risks, not one (corrected after the second review).** An earlier revision said such blobs are "never purged" and drew two comforting conclusions from it. The accurate statement is that retention does not *govern* them:

- **Leak.** Bytes referenced only from rows are never eligible, so the payload store grows without bound for every publishing transform.
- **Dangling reference.** Eligibility is "expired direct refs minus active direct refs", and the store is content-addressed. If the **same bytes** are also an expired *direct* audit reference, they are eligible and get deleted — the row reference is not in the active set to protect them. The second review demonstrated this with a controlled `PurgeManager` test (nested-only active reference invisible; an expired direct reference to the same bytes made it eligible; an active direct reference protected it). It is a real exposure for a publisher like `blob_fetch` fetching JSON that also appears as a call payload. For *this* plugin it needs a validated PDF or PNG to be byte-identical to some canonical-JSON audit payload, which the signature checks make implausible — but "implausible" is the honest word, not "impossible".

The spec says "keep raw bytes in the configured artifact store under its retention policy", and today that policy does not reach these bytes in either direction. It is a pre-existing platform defect shared by four plugins; solving it inside one of them would be exactly the plugin-owned infrastructure D1 forbids. **Recommendation:** file a platform ticket that names **both** risks; the user manual (Task 5) says generated artifacts are not governed by the retention policy.

### D8 — startup readiness uses the facility the platform already has

The operator asked for "a generic readiness check across all plugins". **It already exists**, and the audit that prompted this found the one plugin that went around it.

- `BaseTransform.requires_runtime_preflight: bool = False` and `runtime_preflight(self, ctx: LifecycleContext) -> None` (`plugins/infrastructure/base.py:585-586`, `:1493-1500`). The orchestrator runs every declaring transform before the source loads a row (`engine/orchestrator/runtime_preflight.py:62-110`), inside `track_operation(operation_type="runtime_preflight", …)`, with the engine's retry manager, and a failure aborts the run. The probe's HTTP call is parented on that operation, so it is a real audited call; `operations` and their calls **are** exported (`export_read_model.py:274-283`).
- Today exactly one plugin declares it: the LLM transform (`llm/transform.py:1207`, implementation `:1753-1769`).
- `record_readiness_check` is a *second*, RAG-only path: built for RAG (commit `eff1a3b19`: "RAG transform records the CollectionReadinessResult…"), vector-store vocabulary in its signature (`collection`, `count`), written to `preflight_results`, which **nothing in `src/` reads** — not the export read model, MCP, web or TUI. RAG's probe itself is unaudited.

**Rejected — "rename its parameters and open it to every plugin".** An earlier turn of this planning proposed exactly that. It would have stood up a second generic readiness facility beside the first: two ways to say the same thing, one exported and one write-only. Both requested reviews (systems-thinking and solution-architecture) recommended removing `record_readiness_check`; the architecture review found the existing facility, and every claim above was re-measured before it was accepted.

**What the facility does not cover:** it iterates `config.transforms` only. Sources and sinks cannot use it (`chroma_sink` probes live at `on_start`, unaudited). Extending it to sources and sinks is a platform change — noted for the operator, not done here.

### D2 — why "new analysis"

Resuming needs the `Operation-Location` to survive process death; nothing persists it outside the call audit, and reading the audit trail back to drive behaviour would make audit a control input. A retry therefore submits again and gets a **new** `operation_id`.

**What a retry costs.** Every engine retry of a row submits again, so each of these can bill a second analysis: a network error on a **poll** GET (the first analysis may well complete unobserved); an **ambiguous submit** (the POST times out after Azure accepted it — we never saw the `Operation-Location`, so that analysis is orphaned and billed); and, new with this plan, a network error on an **artifact** GET after a fully successful analysis. The first two exist today. That is the honest price of not resuming; state all three in the user manual (Task 5). Blobs stored by a failed attempt stay in the payload store unreferenced (see D7). `success_reason["metadata"]["analysis_attempt"]` is not invented — the engine's existing attempt accounting is the budget.

### D3 — why `ManagedIdentityCredential`

Measured in the installed `azure-identity` 1.25.1 (`.venv/.../azure/identity/_credentials/`):

- `DefaultAzureCredential` is a `ChainedTokenCredential` whose **first** link is `EnvironmentCredential` (`default.py:260`), followed by workload identity, managed identity, the shared token cache, VS Code, Azure CLI, PowerShell, `azd`, and optionally an interactive browser or broker (`default.py:263-309`). A pipeline configured `auth_mode: managed_identity` on a host that happens to carry `AZURE_CLIENT_ID`/`AZURE_TENANT_ID`/`AZURE_CLIENT_SECRET` would silently authenticate as that **service principal**. The run would succeed, and `success_reason["metadata"]["auth_mode"]` would record `managed_identity` — an audit statement that is false. The later links also shell out to CLIs and read developer caches, which has no place in a pipeline worker.
- `ManagedIdentityCredential` is not a chain across identity *kinds*; it selects one managed-identity **transport** from the hosting environment (`managed_identity.py:82-137`): App Service / Container Apps (`IDENTITY_ENDPOINT`), Service Fabric, Azure Arc, Azure ML, Cloud Shell, **AKS workload identity** (`WORKLOAD_IDENTITY_VARS` → `WorkloadIdentityCredential`), else IMDS for VMs. That covers Azure Container Apps today and AKS for 0.8.1 with one explicit class, and `client_id` selects a user-assigned identity.
- Local development does not need a chain: use `api_key`, or `service_principal` with a dev app registration.

`azure_auth.py:212-220` uses `DefaultAzureCredential` for the storage plugins' managed-identity mode. Same defect, different plugin; **out of scope here** (the spec fences storage auth off) and worth its own ticket.

### D4 — auth-mode availability in the Web Composer

Measured: `web/catalog/service.py:490-502` flattens `discovery_secret_requirements` into `PluginSecretRequirement(field, candidates)` (`web/catalog/schemas.py:38-47`), and `web/plugin_policy/availability.py:44-53` requires **every** entry to be satisfied — before any pipeline config exists, so it cannot know which `auth_mode` an author will pick. All three obvious moves are wrong: keep the api-key requirement and a managed-identity deployment never sees the plugin; drop it and an unconfigured deployment advertises readiness; add `client_secret` unconditionally and both other modes break.

**Decision (operator, 2026-09-20):** the deployment declares it. A `WebSettings` profile for this plugin, following the existing `AWSTextractProfileSettings` precedent (`web/config.py:38`), names the auth modes the operator has provisioned (`azure_document_intelligence.auth_modes: [managed_identity]`). Requirements become per-mode; the plugin is available iff **at least one declared mode** has all its secrets in the inventory (managed identity has none, so declaring it is the operator's assertion that an identity is attached). The composer's knob schema offers only declared modes. An **undeclared** profile means today's behaviour exactly.
**Rejected alternative:** any-of groups inferred from the plugin alone. Cheaper, but makes the plugin "available" everywhere the moment it lists a secret-free mode.

**The declaration is enforced at admission, not only advertised (second review, V2-6).** Filtering what the planner is *shown* does not bind a node that is hand-authored, restored from an older session, or patched. And the Textract precedent does not transfer as-is: Textract is `OPERATOR_PROFILED` and alias-based, while this plugin is `USER_CONFIGURABLE`, for which `_profile_lowering_context` returns early when no `profile` option is present (`web/plugin_policy/validation.py:739-741`) — and adopting that path wholesale would import its **required** alias (`validation.py:470-478`), contradicting "undeclared means today's behaviour". So Task 4b adds a small admission check of its own in `validation.py`: when the deployment has declared modes, a node whose **effective** `auth_mode` is not among them is rejected with a policy finding that names the mode and the declared set, never a secret. Rejection is what Composer invariant 1 explicitly allows; nothing is authored server-side.
**Default (agreed by the operator 2026-09-20):** no silent lowering. The plugin's config default stays `auth_mode="api_key"`. If the declared set excludes `api_key`, the knob schema shown to the planner marks `auth_mode` **required** with no default, and an omitted `auth_mode` fails admission — it is *not* rewritten to the deployment's only mode. A rewrite would make the recorded config differ from what the author wrote, and would be a server-side edit of pipeline structure in all but name.

`availability.py` had uncommitted edits from another session in the shared checkout on 2026-09-20 — rebase onto that work; do not write over it. **YAML pipelines are unaffected by D4**, which is why Task 4 is split.

### D5 — how strong is "malformed"

A prefix-plus-trailer check accepts `%PDF-%%EOF`. PNG can be validated **structurally** with the standard library. PDF cannot: the only parser in the tree is `pypdfium2`, a native library deliberately imported only inside `pdf_rasterize`'s worker subprocess because PDFs are untrusted input — and Azure's PDF is Tier-3 too.
**Decision (operator, 2026-09-20):** narrow the guarantee explicitly. PDF admission = header `%PDF-1.`/`%PDF-2.`, a `startxref` whose integer offset lies inside the file and lands on `xref` or an `N N obj` header, and `%%EOF` in the final 1024 bytes. That catches truncation and gross corruption; it does **not** catch a corrupt middle. The user manual says so and points at `pdf_rasterize` (which does parse, in isolation) for anyone who needs proof the PDF renders.

### D6 — requested figures, no `figures` key (BLOCKER for Task 3)

> **Status 2026-09-20: unresolved. The operator cannot run the live probe now. Task 3 must not start until the evidence line below is filled in.** The fail-closed row in the table is the *designed default*, not a licence to proceed: choosing between "fail the row" and "succeed with `[]`" on a guess would either fail every figure-less document in production or quietly accept a malformed response, and the spec forbids both.
>
> **Evidence (to be filled in by the operator):** date · model · api-version · `figures` was absent / `null` / `[]` · who ran it.

| Case | Behaviour |
| --- | --- |
| figures **not** requested, key absent | unrequested optional facet: nothing happens (today's behaviour) |
| figures requested, `"figures": []` | explicit empty list → success, the three figure lists are `[]` |
| figures requested, key **absent** | **fail closed**: `malformed_response` / `requested_figures_absent` |

The probe: one live `prebuilt-layout` analysis of a page with no figures, `output=figures`. If Azure demonstrably omits the key, the third row flips to "success with `[]`" and `figures_key_present` stays in success metadata so audit can still tell the two apart.

### The "no row points at absent bytes" argument (spec, sequence step 1)

Per requested output, strictly in this order: `get_bytes` (audited) → validate → `payload_store.store(bytes)` → assert the returned address equals the locally computed SHA-256 → build the reference. The row is assembled only after every requested output has a reference. The publication manifest (D1) is written in the same `TransformResult.success`, so it too exists only once every blob does. Process death at any point leaves, at worst, stored blobs that no row references — never a reference without bytes. This is an argument about **publication order** only; what retention may later do to those bytes is D7's subject, and D7 does not promise they survive.

## Global constraints

- API version stays `2024-11-30`; no other version is admitted.
- `url` and `base64` modes, the default schema, and existing YAML keep working byte-for-byte. `api_key`-only YAML stays valid. No compatibility alias, no dual acceptance.
- **The Azure plugin (Tasks 1–6) makes no Landscape schema change and adds no `PluginAuditWriter` method, no export record type, and no plugin-owned persistence of any kind** (D1). Task 7 is the one schema-breaking task, and it only *removes* surface (D9).
- No direct `httpx` call in the plugin. Every Azure leg goes through `AuditedHTTPClient`.
- Request/response bytes are never recorded in a call payload, a log line, telemetry, an exception message, or a row. Audit records `sha256`, `size_bytes`, `content_type`, status, elapsed time, error classification.
- Generated-output MIME is exactly `application/pdf` (PDF) and `image/png` (figures).
- Entra scope is exactly `https://cognitiveservices.azure.com/.default`.
- Only declared extraction fields and artifact references enter the output row; all generated metadata goes in `success_reason["metadata"]`.
- Raw provider error messages and credential-bearing URLs never enter a routable error reason.
- Storage connection-string and SAS modes from `azure_auth.py` are not copied into this config.
- No `# noqa`, `# type: ignore`, `getattr` sprinkled for convenience, or `runtime_checkable` Protocol used as a control (ADR-032).

## Review focus

Inputs the spec implies but does not enumerate. Each line names the task whose tests pin it.

1. `extract.figures` (metadata facet) is set but `generated_outputs.figure_blob_refs_field` is not → **zero** figure GETs and no `output=` parameter. (Task 3, `test_figures_facet_alone_fetches_nothing`)
2. Azure answers `Content-Type: application/pdf; charset=binary` or `IMAGE/PNG` → accepted; parameters and case are ignored, the essence must match exactly. (Task 1, `test_media_type_essence`)

4. `429` with `Retry-After: 0` or `Retry-After: 86400` on a figure GET → no hot loop, no sleep past the retrieval deadline. (Task 2 helper change, exercised again in Task 3)
5. A figure download that **succeeds slowly** — no error, no 429 — must still expire the row at the retrieval deadline. (Tasks 1 + 3)

Both new legs return a bare `httpx.Response`, like `get`/`post`. (An earlier revision wrapped the response to hand back a call id for a table row; with no table there is nothing to link, and the wrapper is gone.)

`binary_document_is_complete` (per D5):

- **PNG — full structural walk, standard library only.** After the 8-byte signature, iterate chunks: 4-byte big-endian length, 4-byte type, data, 4-byte CRC; verify `zlib.crc32(type + data) == crc` for every chunk; the first chunk is `IHDR` with length 13; at least one `IDAT`; the last chunk is `IEND` with length 0; **no trailing bytes**; any length that runs past the buffer is a failure, not an exception. This does reject a corrupt middle.
- **PDF — the narrowed guarantee of D5.** Header matches `^%PDF-[12]\.\d`; `%%EOF` within the final 1024 bytes; the last `startxref` is followed by an integer offset `0 < n < len(data)` and `data[n:]` begins with `xref` or matches `^\d+ \d+ obj`. The docstring states plainly that this detects truncation and gross corruption, **not** a corrupt middle.
- JPEG is out of scope (no generated output is JPEG) and any other format raises `ValueError` (programming error, same convention as `binary_document_signature_matches`).

Transport design, from what `http.py` does today:

- `_request_with_optional_body_cap` knows only `json`/`params`. Add a `content: bytes | None` keyword passed to httpx as `content=`; when set, `json` is not sent. Add `max_body_bytes: int | None` that overrides `self._max_response_body_bytes` for that call — the 50 MB analyzeResult cap is not the per-artifact cap. With `client.stream` the status is known before the body: apply `max_body_bytes` to **2xx bodies only** and the client-level cap to non-2xx bodies, otherwise a small figure cap turns Azure's real 4xx JSON error into a misleading too-large error.
- `HTTPCallRequest` gains `body_descriptor: Mapping[str, Any] | None`. `to_dict()` emits it only when set. **Do not touch the existing rule** that POST always emits `json` (even `None`): hash stability of every recorded JSON POST depends on it, so a bytes POST records `json: None` **and** `body_descriptor`.
- `_parse_response_body` (`http.py:261-290`) base64-embeds any body that is not JSON or text — **including a missing content-type** — as `{"_binary": ...}`, and it is status-blind: a binary `502` from a proxy would copy bytes into the call payload **and** telemetry. So on the two new legs the recording rule is by **content, regardless of status**:
  - **a 2xx response to `get_bytes` → always a descriptor, whatever the content-type says** (second review, V2-5). `get_bytes` exists to fetch bytes the caller must not record; the server's label is Tier-3 and cannot be allowed to decide that. An ASCII PDF served as `text/plain` would otherwise be copied verbatim into audit and telemetry before Task 3 rejects its MIME. The rules below apply to `post_bytes` responses (Azure's 202 with an empty or JSON body) and to **non-2xx** `get_bytes` responses only.
  - JSON content-type, body ≤ 65 536 bytes → parsed and recorded (Azure's error envelope; this is what makes a 4xx diagnosable). Larger → descriptor.
  - `text/*` → first 10 000 characters (the bound the existing `_raw_text` path already uses) plus `_truncated: true` when cut.
  - anything else, **or no content-type** → `{"_binary_descriptor": {sha256, size_bytes, content_type}}`. Never `_binary`.

  Existing `get`/`post` callers are unchanged — `blob_fetch`, `web_scrape` and others depend on today's behaviour; do not alter `_parse_response_body` itself, add a sibling used only by the two new legs.
- **Total-transfer deadline — enforced below httpx's buffering** (second review, V2-2). httpx's `timeout` is an *inactivity* timeout: a server trickling one byte every few seconds never trips it. And checking a clock around the existing loop does not help: `_consume_capped_response` iterates `response.iter_bytes(chunk_size=min(cap + 1, 65536))` (`http.py:449-450`), and httpx **coalesces** raw reads until it has a full decoded chunk — the reviewer measured 65 536 one-byte raw reads before the first chunk was yielded, so a per-chunk check sees the clock once per 64 KiB, which a trickling peer can stretch indefinitely. `iter_bytes` is there so the cap is measured on the *decoded* size (decompression bombs). The two bytes legs remove that need instead of fighting it:
  - send `Accept-Encoding: identity`; a response carrying **any** `Content-Encoding` is an ERROR call (`_reason: "unexpected_content_encoding"`), never decoded. Raw bytes are then the body, so raw size *is* the bomb-relevant size.
  - a **sibling** consumer for these legs (leave `_consume_capped_response` and every `get`/`post` caller untouched) iterates `response.iter_raw()` with **no** `chunk_size`, so each transport read is yielded as it arrives; it enforces the byte cap and checks `deadline` before the first read and after **every** read, raising `HTTPResponseDeadlineExceededError` — recorded as an ERROR call with `_reason: "deadline_exceeded"`, `_captured_body: False`, and the observed byte count, mirroring the too-large path.
  - the request's read timeout is `min(timeout, deadline - now)` at the moment the request starts. httpx cannot re-clamp it per read, so the honest bound is **deadline plus at most one read timeout**, not the deadline exactly; say so in the docstring.
  - `get_bytes` takes `deadline: float | None` (a `time.monotonic()` instant); `None` means cap-only.
- The client is built with `follow_redirects=False`; the new legs do not opt in. A 3xx is returned as a non-2xx, recorded as an ERROR call, and the credential header goes nowhere else.

## Task 2 — Binary input (`source_mode: blob`), bounded payload reads, Retry-After

**Files:** modify `document_intelligence.py`, `contracts/payload_store.py`, `core/payload_store.py` + stand-ins. **Tests:** `tests/unit/core/test_payload_store.py`, `tests/unit/plugins/transforms/azure/test_document_intelligence.py`, `tests/unit/contracts/transform_contracts/test_azure_document_intelligence_contract.py`.

This is the `aws_textract_inline_analysis` pattern (`textract_inline_analysis.py:460-516`): the row carries a **payload-store SHA-256**, not bytes and not an arbitrary string. That satisfies "no implicit conversion from an arbitrary string or URL", and the reference *is* the digest, so provenance is exact by construction.

Config changes:

- `source_mode` pattern becomes `^(url|base64|blob)$`.
- `document_format: str | None` — required iff `source_mode == "blob"`, must be in `BINARY_DOCUMENT_FORMATS` (`jpeg|png|pdf`). Azure's stream endpoint also accepts TIFF/BMP/HEIF/HTML/OOXML, but the spec admits only types "where ELSPETH has a signature contract", and that vocabulary is closed at three.
- `max_document_bytes: int = 20_000_000`, `gt=0`, `le=500_000_000`. The ceiling is Azure's S0 "Max document size 500 MB" (service-limits page, fetched 2026-09-20; F0 is 4 MB — note it in the field description). The default is a **memory** bound: `connect_output` runs up to 30 rows in flight, each holding its document.
- `_validate_consistency`: `document_format` set with a non-blob mode → error; `blob` mode without it → error.

**Making the memory bound real.** `PayloadStore.retrieve` reads the whole file before anyone can check its length (`core/payload_store.py:135`, a bare `fd.read()`), so "retrieve, then compare `len`" allocates a 2 GB blob in order to reject it — times up to 30 rows. Add to the protocol:

```python
class PayloadTooLargeError(Exception):      # .content_hash, .size_bytes, .max_bytes
def retrieve_bounded(self, content_hash: str, *, max_bytes: int) -> bytes: ...
```

`FilesystemPayloadStore`: open through the same validated directory fd, `os.fstat(fd).st_size > max_bytes` → raise **before reading**; otherwise `fd.read(max_bytes + 1)` and raise if more than `max_bytes` came back; then the **same** integrity verification `retrieve` performs. The protocol docstring sets a high bar for new exception types ("one for corruption, one for absence"); this is the third honest state — *present and intact but refused* — say so in the docstring.
`PayloadStore` is `runtime_checkable`, so every stand-in gains the method in the **same commit** (measured implementers of `retrieve`): `core/payload_store.py`, `core/landscape/factory.py:219`, `plugins/transforms/pdf_rasterize.py:313`, the in-plugin probe stores in `blob_text_expand.py:330`, `blob_json_expand.py:538`, `blob_csv_expand.py:456`, `aws/textract_inline_analysis.py:678`, plus test fakes (`grep -rn "def retrieve(self" tests/`). `aws_textract_inline_analysis` has the same read-then-check shape (`:481-496`); moving it over is a one-line improvement but it is another plugin's behaviour — mention it to the operator, do not fold it in silently.

That is fine for this plugin — it needs no handle from the probe — but it means the probe proves the *leader's* credential, not each follower's managed identity. A follower with a broken identity fails per row, as today.

The spec says a reference carries kind, MIME type, byte length and digest, and that figures carry Azure's id. So the companions are **required together**, enforced in a `GeneratedOutputs` model validator: `pdf_blob_ref_field` set ⇒ `pdf_mime_type_field` and `pdf_size_bytes_field` set, and neither companion without it; `figure_blob_refs_field` set ⇒ `figure_ids_field`, `figure_size_bytes_field` and `figure_mime_type_field` set, and none of them without it. A half-declared output is a config error, not a silently thinner row.

**The plugin announces what it requires and what it guarantees (operator ruling 2026-09-20: "it must announce what fields it requires and guarantees though, for the composer").** Reshaping is free; doing it silently is not. The composer, the DAG validator and the executor's collision check all read the same three declarations, so every one of the seven fields goes through them:

- **Guarantees.** Every configured generated field name joins `all_output_field_names()` → `declared_output_fields` → `_build_output_schema_config` merges it into the output schema's `guaranteed_fields` (`infrastructure/base.py:1371-1406`). That is what lets a downstream node that *requires* `di_pdf_blob_ref` validate at compose time instead of failing per row. The guarantee is honest only because a declared field is **always written** on a success row (empty lists included) — `write_generated_fields` must never skip a configured field.
- **Types.** `_apply_declared_output_field_contracts` gives each declared field its contract type: `str` for the blob ref and MIME fields, `int` for `pdf_size_bytes_field`, `list` for the three figure fields. A downstream `declared_string_input_fields` check against `pdf_blob_ref_field` then passes statically, which is what makes the PDF hash chainable in the composer rather than only at runtime.
- **Requirements.** `source_field` stays the one required input (`declared_input_fields`) and stays in `declared_string_input_fields` — in `blob` mode it holds a hash string, so the existing string-type half of the contract is still exactly right and needs no new declaration.
- **Classification trap.** The base class treats any **top-level** config option whose name ends in `_field`/`_fields` as naming a column the transform *consumes*, unless it is listed in `output_naming_config_keys` (`base.py:98-102`, `:797`, `:1176-1185`) — fail-closed, so a mis-declared output becomes a phantom required input and the parity probe reds. The seven new names are nested under `generated_outputs`, exactly as the facet names are nested under `extract`, so they are not seen as top-level column options; **do not hoist any of them to the top level** without adding it to `output_naming_config_keys`. `_reject_input_options_naming_created_fields` already stops `source_field` from naming a field this transform creates; the new names are covered through `declared_output_fields`.
- **Composer surface.** The knob schema and `get_agent_assistance` (Task 5) state the same thing in words: which fields appear, their types, and that they are guaranteed on success.

`generated_outputs: GeneratedOutputs = Field(default_factory=GeneratedOutputs)`; its field names join `all_output_field_names()` (so the duplicate check and `declared_output_fields` cover them) and count toward "at least one output target". Add `artifact_retrieval_timeout_seconds: float = 300.0` and include it in `_effective_batch_wait_timeout_seconds`. `_validate_consistency`: `max_total_bytes >= max_artifact_bytes`. `on_start`: if either field is set and `ctx.payload_store is None`, raise.

**Part A — RAG uses the real facility.**

- `requires_runtime_preflight = True`. `on_start` keeps constructing the provider (the LLM transform's `runtime_preflight` relies on the same ordering: provider first, preflight second — `llm/transform.py:1755`), but **stops probing**: the `check_readiness()` call, both `_record_readiness_check` call sites (`rag/transform.py:261, 273`) and the helper (`:474-490`) are deleted.
- **Construction must stop doing remote I/O, or the failure boundary does not move (second review, V2-3).** Moving only `count()` is not enough: `ChromaSearchProvider.__init__` builds the `HttpClient`, calls `client.get_collection()` and validates the collection's distance metadata (`chroma.py:188-214`) — so a missing or unreachable collection still fails inside `on_start`, before the preflight operation or the retry manager exists. Split it:
  - `__init__` validates config and stores it. **No client, no network.** (`chromadb.Client()`/`PersistentClient` for the ephemeral and persistent modes are local and may stay, but keep all three modes on one path for simplicity: nothing is opened in `__init__`.)
  - `open(self, *, operation_id: str | None = None, state_id: str | None = None, token_id: str | None = None) -> None` builds the client, looks the collection up and validates metadata, **recording the lookup as an audited call** under whichever parent it was given (exactly one of `operation_id`/`state_id`). Idempotent; guarded by a lock. On any failure it closes and clears whatever it half-built (`self._client`, `self._collection` back to `None`) before raising, so a retry starts clean and `close()` after a failed `open()` is harmless — pin both.
  - **Leader:** `runtime_preflight` calls `open(operation_id=…)` then the count probe. **Followers are separate processes that run `on_start` but never `runtime_preflight`** (`cli.py:96-122`; `run_transform_runtime_preflights` is called from `leader_drain.py:167` and `resume.py:1403` only), so a follower has no opened handle. It gets one **lazily**: `search()` calls `open(state_id=…, token_id=…)` when the provider is not yet open, which makes the follower's connection an audited call under the first row it serves, and a failure there is a classified `RetrievalError` on that row. Do **not** open in the follower's `on_start`: that is the unaudited, unretried path this task exists to remove.
  - Azure Search's constructor: confirm it does no remote I/O (it builds an `httpx.Client` and, for managed identity, a credential object — neither connects). If it does, give it the same `open()`; if not, its `open()` is a no-op so the transform treats both providers alike.
- **Typed failure at the provider boundary (second review, V2-4).** `CollectionReadinessResult` carries `collection`, `reachable`, `count` and free-text `message` (`contracts/probes.py:15-31`), and both probes fold every failure into `reachable=False`: Chroma catches connection, SDK and malformed-count errors in one `except` (`chroma.py:537-546`); Azure Search does the same for SSRF denial, network errors and — via `raise_for_status()` — 401/403/429/503 alike (`azure_search.py:497-546`). The transform therefore **cannot** tell transient from permanent, and must not try to by reading `message` — recovering a category from free text is how distinctions get silently lost. The carrier already exists: `RetrievalError(message, *, retryable, status_code=None)` subclasses `PluginRetryableError` (`retrieval/base.py:14-27`), which `_runtime_preflight_is_retryable` already classifies (`runtime_preflight.py:37-42`). So `open()` and `check_readiness()` **raise** it for failures, classified where the facts are known, *after* the failed call has been recorded:

  | Failure | `retryable` |
  | --- | --- |
  | connection refused / reset / timeout; HTTP 429, 500, 502, 503, 504 | `True` |
  | HTTP 401 / 403 (credential or RBAC) | `False` |
  | collection / index does not exist (Chroma lookup failure that is not a transport error; Azure Search 404) | `False` |
  | distance-function / metadata mismatch; malformed count body | `False` |
  | SSRF validation refused the endpoint | `False` |

  `check_readiness()` keeps returning `CollectionReadinessResult` for the one outcome that is not a failure of the call — **reachable, with a count** (zero included). `CollectionReadinessResult` itself is unchanged: commencement gates share it (`plugins/infrastructure/probe_factory.py`). chromadb 1.5.5 raises a plain `ValueError` for an unreachable server (noted at `chroma.py:539`), so Chroma's transport-vs-absent split needs care: classify by exception type, treat `ValueError`/`httpx.HTTPError`/`ConnectionError`/`OSError` from the lookup as transport (retryable) and `chromadb.errors.NotFoundError` (confirm the class name in the installed version) as absent.
- **Audit-write failures are not retrieval failures.** Neither provider may catch `LandscapeRecordError` or anything else raised by `record_operation_call` / the audited client's recorder; they propagate untouched and abort the run. Write the `except` clauses narrowly enough that this is true by construction, and pin it.
- `runtime_preflight(self, ctx)`: `ctx.operation_id is None` → `FrameworkBugError`; `open(operation_id=…)`; `check_readiness(operation_id=…, coordination_token=ctx.require_coordination_token())`. A `RetrievalError` with `retryable=True` propagates **as is** (it already is a `PluginRetryableError`, so the retry manager applies); `retryable=False` is re-raised as `RuntimePreflightFailedError` from it. **Reachable but empty still fails the run**, non-retryably — that behaviour ("refuse to start against empty/missing collection") is kept exactly, only its channel changes.
- **The probes become audited.** Today neither is: Chroma calls a bare `self._collection.count()` (`chroma.py:524`) and Azure Search's docstring says it "Uses raw httpx (NOT AuditedHTTPClient) because this is a startup" check (`azure_search.py:472`). That reason does not hold — an audited client parents its calls on `operation_id` when one is given (`clients/base.py:147-153`). Azure Search: an `AuditedHTTPClient` built with `state_id=None, operation_id=…, coordination_token=…`; if the current probe pins the resolved IP, use `get_ssrf_safe` so that protection survives the move. Chroma: an SDK call, not HTTP — record it with `record_operation_call` the way the provider already records its search calls, with `{collection, reachable, count}` as the response payload. `RetrievalProvider.check_readiness` in `retrieval/base.py:71` gains the `operation_id`/`coordination_token` keywords; both implementers change in the same commit.
