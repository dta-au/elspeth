# Composer Provider Boundary Remediation Plan

**Goal:** Make gateway 502/503 failures produce safe user outcomes and terminal, settled Composer provider-call evidence, then audit the adjacent cancellation paths.

**Target:** `release/0.8.1`. Source diagnosis: [Composer provider failure boundary gap](../reviews/2026-09-27-composer-provider-boundary-gap.md). The historical staging attempts are evidence inputs; this plan does not edit deployed records or change gateway/AWS configuration.

**Architecture:** Classify SDK failures once at the Composer provider boundary into an owned outcome: audit status, safe public category, and conservative retry eligibility. Every admitted physical planner call records a terminal `ComposerLLMCall` before the quota wrapper settles it. The message and recompose routes share one provider-failure translation path so progress, audit draining, redaction, and HTTP behavior remain equal. Quota's missing-evidence check stays fail-closed.

**Stack:** Python 3.13, FastAPI, LiteLLM/OpenAI exceptions, SQLAlchemy Sessions DB, pytest. Worktree creation follows review approval. In the worktree set `PYTHONPATH=<worktree>/src:<worktree>/elspeth-lints/src` and verify imports before testing.

## Contract and decision table

Classification is valid only for an exception caught at a known LiteLLM dispatch or for an SDK exception that escapes `ComposerServiceImpl.compose`. It must not turn an arbitrary first-party `ValueError`, `AuditIntegrityError`, or `CancelledError` into a provider error. Do not inspect `str(exc)`, raw response body, provider URL, or a dynamic attribute to classify. Leave status and error text in the audit as class-only values. Preserve the gateway's stricter nonretryable meaning for its `BadGatewayError`; a generic `APIError` retains the existing bounded retry behavior.

| Concrete error at dispatch | Audit status | Planner outcome | Ordinary HTTP | Automatic retry |
| --- | --- | --- | --- | --- |
| `AuthenticationError` | `AUTH_ERROR` | `PROVIDER_ERROR` | 502, configuration guidance | No |
| `BadRequestError` or existing `_BadRequestLLMError` | `BAD_REQUEST_ERROR` | `PROVIDER_ERROR` | 502, request/configuration guidance | No |
| `BadGatewayError` | `API_ERROR` | `PROVIDER_ERROR` | 502, safe investigation/retry-later guidance | No |
| `ServiceUnavailableError` | `API_ERROR` | `PROVIDER_ERROR` if provider attempts exhaust; admission refusal if quota blocks the next attempt | 502 for ordinary route if attempts exhaust; safe accounting-unavailable 503 if retry admission is refused | Eligible only, within deadline and attempt cap and subject to fresh quota admission |
| Generic LiteLLM `APIError` | `API_ERROR` | `PROVIDER_ERROR` | Existing safe 502 | Existing bounded retry |
| Other `openai.OpenAIError` | `API_ERROR` | `PROVIDER_ERROR` | 502, class-only | No unless explicitly justified by a typed subclass |
| `openai.APITimeoutError` / LiteLLM `Timeout` | `TIMEOUT` | `TIMEOUT` | Existing timeout outcome | No new retry policy |
| `TimeoutError` at the call boundary | `TIMEOUT` | `TIMEOUT` | Existing timeout outcome | No new retry policy |
| `asyncio.CancelledError` | `CANCELLED` | propagate cancellation | Existing cancellation outcome | Never |
| Unknown non-SDK `Exception` after dispatch | `API_ERROR` audit with original class; original exception propagates | Original exception, not provider translation | Existing internal error | Never |

The gateway's closed `code`, `retryable`, and `request_id` are not currently available as an owned Composer error carrier after LiteLLM translation. Do not parse error prose to recover them. If that loss is confirmed at the live wire seam, document it as a separate gateway-correlation follow-up; the current repair must not expose upstream response bodies through `composer_expose_provider_errors`.

**Quota and retry contract:** `retryable` means the provider failure is eligible for another attempt; it never authorizes dispatch. Before each retry, `admit_provider_attempt` settles the preceding terminal record and asks quota authority for a new admission. A failed call with unknown token usage produces a settled ledger row with NULL counts. With identity or container token quotas, the next admission may correctly refuse with `TOKEN_ACCOUNTING_UNAVAILABLE`, including a fresh operation later that day. Preserve this refusal as the authoritative outcome: publish terminal failed progress with a distinct accounting-unavailable reason and return a sanitized HTTP 503 instructing the user to contact an administrator to review usage/accounting before retrying. Do not label it a provider outage, promise that immediate retry will work, invent a third call, fill unknown tokens with zero, or weaken quota. Existing other admission refusal reasons retain their established policy semantics. Quota-free calls can reach bounded provider retry exhaustion and the provider-failure response.

## Rollback and residual state

Code rollback is a branch revert before deployment or a normal application rollback afterward; no schema change is planned. A historical `quota_provider_attempts` row cannot be marked settled from a synthetic verdict: its original dispatch/usage evidence must be investigated separately. If the gateway's safe error code and request ID prove unrecoverable through LiteLLM, report that correlation limitation and propose a separately scoped wire-boundary change. This plan does not claim to resolve the AWS upstream 502/503 causes.
