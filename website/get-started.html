Get started

Run a small example.
Inspect the result.

Use a local source checkout and the tracked threshold-gate example to learn the CLI. The example needs no model-provider account. Composer setup is a separate path below.

Try the CLI.

01 / Install

Create an isolated Python environment

You need Python 3.12 or newer, Git and uv. These commands install from your checkout; they do not select an immutable release. 

git clone https://github.com/dta-au/elspeth.git
cd elspeth
uv venv
source .venv/bin/activate
uv pip install -e ".[dev]"
02 / Validate and run

Use the tracked example

From the repository root, validate the settings, then explicitly execute the pipeline. Output files and audit records are written below the example directory. 

elspeth validate --settings examples/threshold_gate/settings.yaml
elspeth run --settings examples/threshold_gate/settings.yaml --execute
03 / Inspect

Follow the output back to its input

Use run and row identifiers from your run. The first-pipeline guide explains the configuration and lineage inspection. 

elspeth explain --run <run_id> --row <row_id> --database examples/threshold_gate/runs/audit.db --no-tui

Set up the Web Composer.

Composer adds a web service, local authentication and a React frontend. For LLM authoring, configure the primary planner and independent advisor models with their required provider credentials. A local login alone does not enable the planner.

Install and build

In your activated checkout, use Node.js 24 and npm 11. Use the lockfile for the frontend dependency install; npm install is for intentional dependency updates. 

uv pip install -e ".[webui,dev]"
npm --prefix src/elspeth/web/frontend ci
npm --prefix src/elspeth/web/frontend run build

npm run build type-checks and builds the frontend.

Configure a local instance

In the same shell, generate local keys and set the required Composer limits. Keep keys out of shared files and source control. 

mkdir -p data/blobs data/outputs
export ELSPETH_WEB__SECRET_KEY="$(openssl rand -hex 32)"
export ELSPETH_WEB__SHAREABLE_LINK_SIGNING_KEY="$(openssl rand -base64 32)"
export ELSPETH_WEB__COMPOSER_MAX_COMPOSITION_TURNS=15
export ELSPETH_WEB__COMPOSER_MAX_DISCOVERY_TURNS=10
export ELSPETH_WEB__COMPOSER_TIMEOUT_SECONDS=180.0
export ELSPETH_WEB__COMPOSER_RATE_LIMIT_PER_MINUTE=60

Then configure both models using the provider configuration reference . Review which data each provider will receive.

Create an account and start the service

The user command prompts for a password. Avoid the --password option in interactive use so the password does not enter shell history. Follow the local development guide and identity guide for account and workload-role setup. 

elspeth composer users add demo --display-name "Demo User" --email demo@example.com
elspeth composer users add demo-admin --display-name "Local administrator"
elspeth composer users bootstrap-admin local demo-admin --note "First administrator for local evaluation"
elspeth web --host 127.0.0.1 --port 8451

Open 127.0.0.1:8451 on the machine running the service. Sign in once as demo to create its deployment identity, then sign out. Sign in as demo-admin and use People & access to grant demo the deployment-wide user role. Sign back in as demo to author pipelines. The administrator role alone does not permit pipeline work.

The bootstrap command is for a new local instance without an existing administrator. This setup binds to loopback for local development.

Important upgrade posture

Preserve existing stores; qualify a new compatible target.

Before 1.0, compatibility is considered within explicitly supported boundaries. Existing-store conversion and cutover require separate review.

From 0.8.0 to 0.8.10, this unreleased candidate requires Sessions epoch 79 and Landscape epoch 50. In 0.8.10, Sessions advance from 78 to 79; Landscape epoch 50 remains unchanged. Qualification uses explicitly new compatible stores. Epoch 79 retains versioned Composer continuation segments together with epoch 78's committed graph-review authority over immutable snapshots, quota custody and shared rate-limit policy binding; older readers ignore those completion blockers or cannot admit the new representation. Landscape epoch 50 records durable provider-attempt identity on run calls. Preserve epoch-75 stores, both distinct epoch-76 contracts, epoch-77 and epoch-78 Sessions stores and epoch-49 Landscape stores with compatible prior application access, and configure an explicitly new epoch-79 target and an explicitly new epoch-50 Landscape target. Drain and isolate old/new deployments; do not share session stores or Landscape stores or rely on automatic replica eviction. Unsupported session, Landscape and local-auth stores must remain preserved and refused before incompatible writes. Do not recreate, delete, restamp or migrate them. Exact schema admission is required even when an epoch matches. Quota API quantities are exact signed-64-bit decimal strings; API consumers must adapt response parsing. Proxy deployments must explicitly configure their trusted forwarding peers. Authentication families, bound tickets and graph recovery remain available alongside ordinary freeform composition, Run, Audit, and Graduation. Release tagging, image publication and deployment require separate verification.

From 0.8.0 to 0.8.6, this version requires Sessions epoch 76 and Landscape epoch 49. Qualification uses explicitly new compatible stores. Epoch 76 makes committed graph-review facts authoritative without rewriting immutable snapshots; older readers ignore those completion blockers. Preserve epoch-75 stores and compatible prior application access, and configure an explicitly new epoch-76 target. Drain and isolate old/new deployments; do not share session stores or rely on automatic replica eviction. Unsupported session, Landscape and local-auth stores must remain preserved and refused before incompatible writes. Do not recreate, delete, restamp or migrate them. Keep a Landscape database already at epoch 49 only when its complete schema matches current admission. Authentication families, bound tickets and graph recovery remain available alongside ordinary freeform composition, Run, Audit, and Graduation. Release tagging, image publication and deployment require separate verification.

From 0.8.0 to 0.8.2, the current formats are Sessions epoch 71 and Landscape epoch 49, reached by the 0.8.1 cutover. Upgrades from 0.8.1 keep both database epochs unchanged. 0.8.2 adds bounded validation and release-check hardening while retaining ordinary freeform composition, Run, Audit, and Graduation.

From 0.8.0 to 0.8.1, the Sessions and Landscape schemas change together: Sessions epoch 71 and Landscape epoch 49. This release adds durable Composer request receipts, stronger digest checks, advisor evidence, replay and verification records, and a first-run tutorial built through ordinary freeform composition while retaining Run, Audit, and Graduation. Follow the paired database-recreation runbook; do not relabel or open older stores with the new service.

The earlier upgrade from 0.7.1 to 0.8.0 also changed both database schemas and required coordinated recreation.

The preceding 0.8.3 source candidate used Sessions epoch 74 and Landscape epoch 49 for immutable graph parks and operation-bound checkpoints. Its historical schema facts do not authorize converting or resetting existing stores for the current candidate.

If upgrading from 0.8.0 or earlier, preserve the existing service and its evidence; qualify a separately provisioned new target before installing 0.8.10. Current store admission authorizes no existing-store conversion or reset. Preserve the separate auth.db. Follow the current deployment runbook for admission and operator prerequisites. Historical recreation instructions do not authorize changing existing stores for this fix.

Plan deployment separately.

The AWS deployment profile uses one AWS ECS Fargate web task with Aurora PostgreSQL, EFS, task-role access to S3 and Bedrock, Cognito/OIDC, and CloudWatch/X-Ray. Deployments use planned downtime and zero overlap.

Review the deployment platform reference for available topologies. Use the AWS ECS deployment runbook for the operating contract. Review access, provider policy, evidence retention and recovery requirements before using your own data.
