## P2: a parsed debt row is not yet proven consistent recovery debt

Map step 4 proposes the existing typed ledger parsers to preserve corruption faults before returning recovery-needed. Those parsers do not perform all existing non-writing consistency checks. `repository.py::_blob_replacement_plan` (2176) validates snapshot structure/hashes but never compares the actual live row to the phase-appropriate snapshot. That comparison occurs in `replacement.py::_recover_plan` (162): current metadata must equal `old_blob` before commit and `replacement_blob` in `purge_pending`. A structurally valid plan with mismatched or missing live metadata could therefore be mislabeled ordinary recovery debt by the proposed parser-only implementation.

Likewise, `BlobReplacementPlan`, `BlobDeletionPlan`, and `BlobAtomicDeletionObligation` validate mostly path shape/nonemptiness, not actual custody-qualified locations. Replacement's `_validated_paths` (70), deletion's `_validated_blob_deletion_paths` (2877), and `_atomic_blob_deletion_stage` (723) perform the missing exact path checks. The last helper is a non-writing path/absence validator despite its name; `_finalize_staged_blob_deletion` is the destructive operation and must never run in admission. A valid-looking neighboring/foreign staging, backup, or tombstone path must remain an integrity fault, not ordinary recovery-needed feedback. Qualified deletion's existing parser already checks live metadata versus the snapshot and absence in purge; atomic deletion already rejects live metadata. Those checks must be retained.

The brief correction requires extracting/reusing these non-writing checks before the recovery-needed disposition, preserving driver-supported interrupted substates and fault classes. It also makes explicit that observing both mutually exclusive ledgers cannot short-circuit on whichever valid row is read first, and that the final fenced recheck must bind the exact observed debt/metadata after any filesystem observation. No recovery action is authorized.

Required controls use genuine interrupted producers for each qualified phase and the all-NULL atomic obligation, with paired corrupt copies: phase-inconsistent replacement live metadata, absent replacement metadata, wrong qualified deletion snapshot/purge metadata, atomic live metadata, typed-but-foreign invocation paths, and impossible simultaneous ledgers. Verify exact fault categories and complete unchanged resource snapshots. Do not fabricate malformed owned objects merely to exercise a constructor; mutate persisted evidence only in isolated corruption controls after producing real debt.

## Other boundaries assessed

- Preview is a separate entry point and expressly forbids destructive dispatch, reconciliation, reservation, intent preparation, provenance edits, receipts, and cleanup. Existing actual handlers reconcile before acting, so calling them and rolling back cannot implement this preview. The resource snapshot plus tripwire and actual-acceptance positive controls are appropriate.
- Fenced DB phases bracket filesystem reads under BLOB_CUSTODY. `authority.mutate` supplies the current session/fence and Composer-operation checks; broad `read_blob` authority alone does not establish the required mutation kind. Final admission must use the narrow mutation-kind checks. Holding its transaction callback across a filesystem helper would violate the brief.
- Replacement's exact canonical byte checks and deletion's deliberate absent-file behavior remain distinct. Proposal readiness belongs in the adapter, allowing direct nonready deletion to retain its existing behavior. Deletion admission's conceptual method signature in the map must accept the observed present/size/hash evidence (or an exact owned equivalent), since a final metadata-only check cannot reuse `prepare_blob_deletion`'s evidence predicates. The appended correction makes this explicit.
- Current draft references and relational proposal/run/fork retention are complementary; no future proposal exclusion may be invented for COMPOSE preview. Acceptance still excludes only its exact pending matching proposal and reruns checks.
- The quota plan correctly retains output-reservation excess, session projection even for nonpositive growth, positive-growth identity/container admission, revoked/unavailable accounting distinctions, and the exact owner-first nonpositive-delta bypass. The real refusal recorder remains required. No reservation or durable quota promise may result from preview; existing prepare/commit checks remain authoritative.
- Same-text replacement remains an external effect because provenance and receipt semantics still apply. Graph equality is not a blob-admission no-op test. Creation remains immediate.
- The proposed SQLite matrix and PostgreSQL wait/expiry/custody/quota tests address different properties. PostgreSQL tests must demonstrate real contention with independent connections/barriers, not just parameterized sequential calls. The existing parent-owned serial selection remains necessary; no results are claimed by this preflight.

The brief is now usable for implementation without an unresolved policy/API decision. This approval is conditional on implementing and testing the explicit corrected debt/evidence boundary, not permission to label every syntactically parsed ledger recovery-needed.
