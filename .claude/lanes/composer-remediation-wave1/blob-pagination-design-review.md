## Required corrections

### 1. Make the wire scope and REST item projection explicit

The v2 example has no session ID, while Task 2 requires a canonical session echo and Task 4 requires the decoder to reject the wrong session. Add a canonical top-level `session_id` to both successful tool envelopes and the REST page envelope, including empty pages. Keep the tool item shapes distinct. The resulting common shell is:

```json
{"schema_version":2,"session_id":"<canonical-session-id>","blobs":[],"page":{"limit":50,"has_more":false,"next_cursor":null,"consistency":"live_keyset","projection":"session","order":"created_at_desc_id_asc_v1"}}
```

Use `projection="composer"` for the ready-only tool. Adapter admission must compare the admitted service scope with the request-owned session, tool projection, and normalized limit; a well-formed but mismatched envelope is a producer fault, not a successful empty result. The browser compares the envelope session and every REST item's session with the captured request session. Session echo supports detection; ownership still comes from authenticated server context.

Resolve the plan's wording conflict about descriptions: the tools already omit descriptions, but the existing REST `BlobMetadataResponse` includes `source_description`, timestamps, and provenance (`web/blobs/schemas.py:47–83`). Task 4 currently promises `BlobMetadata` items, not the narrow Composer shape. Recommended minimal choice: retain ordinary REST metadata items in the new REST page, keep the legacy collection unchanged, and qualify the no-description rule as the **Composer discovery projection** rule. The new REST decoder must use that actual closed REST schema. If the new page must omit descriptions as well, define a separate frontend inventory item type and enumerate its consumers instead of casting it to `BlobMetadata`. This is a visibility-contract choice to settle explicitly, not an excuse for a broad reader migration.

### 2. Keep an active inventory gap, not just page keys

The plan correctly requires rooted contiguous traversal. Its integration instructions must also specify how a global inventory gap enters and leaves the real planner's pending set. At this HEAD, `PlannerDiscoveryPolicy.initial` only initializes required catalogue-detail gaps; blob gaps arise from `_tool_information_keys`. `pending_information` receives those keys before dispatch (`pipeline_planner.py:4876–4878`), and the end-of-batch notice checks whether every pending key is supplied (`5138–5139`). Replacing the current global key with only `blob.index.page:...` would allow the first successful partial page to satisfy every pending key and emit the same premature notice.

Required state transition: once a valid inventory discovery is attempted, maintain a separate active gap for its normalized session/projection/limit/order/consistency scope. A successful page supplies a page observation; only the rooted terminal transition supplies the active exhaustion fact and resolves the associated inventory gap. An unrooted valid continuation may supply that page but leaves an inventory gap plus the restart hint. Missing context, credential refusal, invalid cursor, and operational failure must not resolve that gap through `available=False`. Invalid authored scalar/wire arguments roll back only attempt-local keys, preserving an already-open traversal gap. Do not require both inventories before every proposal; open only the inventory demand actually introduced by the request or relevant discovery attempt.

Also define **restart invalidation**. `PlannerInformationManifest.with_result` is additive (`292–307`), and the proposed exhaustion key has no traversal generation. After root → terminal, a new root returning `has_more=true` must reopen the active gap; a retained old exhaustion key must not make the new traversal complete. Keep old observations as historical evidence if useful, but compute active coverage from the current tracker generation. No persistent epoch or database mutation counter is needed.

Add precise acceptance cases to Task 3: first partial root with no predeclared blob gap; terminal then refresh into multiple pages; two authored root calls in a batch; valid terminal-only call; prior operational unavailability followed by a valid root; and invalid continuation during an existing chain. Assert both pending/manifest state and the actual model-facing notice. Compute `new_information` after admission/tracker transition, rather than from the pre-result keys at `5061`.

### 3. Define retry behavior and bound all tracker state

Retain the expected-token check and authored-result ordering. Define repeated consumed requests as page observations with no second advancement; a retry cannot rewind the active chain or mint exhaustion. A successful omitted-cursor request is an explicit new root. A failed omitted-cursor request does not silently destroy an existing chain, but it cannot certify freshness of that chain. Keep a small bounded record of accepted request/page identities if needed for those distinctions.

The stated memory bound must include scope entries and restarts, not merely accepted pages within one scope. Use the existing executable planner call/turn limits (including the hatch behavior) to derive an invocation bound, or enforce an equally small invocation-local cap with truthful incomplete termination. Do not evict unresolved state and later interpret its absence as completion. There is no need to retain every blob ID, persist traversal state, or add a general progress framework.

Page keys can include raw opaque cursors in the existing argument/evidence channel. They must not be inserted into `ComposerPlannerAttempt`'s value-free information-class enum: map them to appropriate closed classes. Existing `_PLANNER_INFORMATION_PREFIXES` and `_valid_information_key` need coordinated updates. A new enum is optional if the existing session/composer classes can represent the new page/exhaustion keys without ambiguity.

### 4. Specify the cursor byte format and credential-guard interaction

Domain-separated HMAC from the existing web `secret_key` is a reasonable small implementation of the assessment's forged/wrong-scope/expired-cursor requirements. Use the existing HKDF authority in `web/key_derivation.py` with a new info label. This is application runtime key derivation; it has no relationship to `ELSPETH_JUDGE_METADATA_HMAC_KEY`, allowlist signing, or operator lint clearance. Agents need no real secret value to implement or test it. Do not alter any existing derivation labels or share-link key custody.

Specify a non-JWT format. `contracts/credential_material.py:87–115` rejects JWT-shaped strings, and both tool arguments and the returned metadata pass credential guards. For example, a two-component canonical base64url payload plus lowercase hex HMAC is preferable to a three-component JWT. Test actual issued cursor bytes through both argument and response credential guards, normal provider wire decoding, redaction, and audit serialization. Do not globally exempt arbitrary strings under `cursor`, or bypass scanning filenames and other metadata. Authentication does not make an arbitrary caller-supplied cursor safe to disclose before validation.

Freeze the payload schema and strict integer/time rules in `BlobPagePosition`/codec-owned types. Carry traversal start/expiry and traversal nonce through every continuation without renewing them. Exact expected-token equality benefits from deterministic encoding for the same continuation payload. A fresh-root nonce is useful because independent roots can otherwise issue identical next tokens and blur invocation provenance; it needs no server registry. The cursor is opaque to consumers, **not encrypted** and not an authorization bearer: its payload must contain only allowed scope/order metadata, never filenames, paths, credentials, or signing material.

Session/projection/order binding and exact saved ordering tuple are correctness requirements. Binding page limit is a conservative policy consistent with the proposed tracker; variable page sizes could also be safe, but would require a different declared scope contract. Thirty minutes is an explicit usability/replay-lifetime choice, not a proof of freshness or a security necessity imposed by keyset SQL. Keep the recommended value unless existing product requirements contradict it; do not require new operator configuration or approval ceremony. Expiry and key rotation should yield restart guidance on tools and the UI. A later-page retry with an expired cursor cannot succeed, so the UI must offer Refresh rather than only repeating Load more.

## Supported design, with implementation constraints

**Compatibility.** The intentional tool v2 transition is coherent: `list_blobs.data` changes from list to object; `list_composer_blobs.data.blobs` remains but the outer object gains required version/scope/page fields. This is not universally additive for strict consumers. Update selected producers, actual callers, fixtures, reference/release notes, strict-provider omission handling, and redaction together. Keep successful producer admission v2-only. Preserve historical v1 records as evidence; add a legacy reader only at an actual parser consumer, with unknown completeness and no planner coverage. The browser currently reads legacy REST via `parseResponse<BlobMetadata[]>` (`frontend/src/api/client.ts:1573`) and the tool card is not a blob decoder. Keeping that legacy API while moving the panel to an explicit `/blobs/page` route avoids an unnecessary historical-message migration. No release number should be inferred from this review.

**Shared configured service.** The plan identifies the right dependency, but merely adding a constructor parameter is insufficient. `app.py:2155` constructs the authoritative service and already supplies it to Composer. `ComposerService.__init__` accepts it at `service.py:577` and currently passes it into preflight at `686`; the shown `ToolBatchCustody` construction and `PlannerCustodyConfig` construction do not carry it. Retain the configured object on the appropriate owned carrier and pass the same object through freeform `execute_tool`/`ToolContext` and `PlanningApplication` → planner custody → request `ToolContext`. Reinspect these exact paths after identity integration. A narrow page protocol is optional; reusing the existing BlobService protocol is adequate. No ad hoc `BlobServiceImpl` inside the listing handler, guessed storage root, fallback signer, or new authority. Missing service context is unavailable; a configured service lacking its required codec is a framework wiring fault. Neither becomes an empty successful list or inventory coverage.

**Query and timestamps.** Keep one ordered/filtering query builder for legacy and page APIs. `created_at DESC, id ASC` and the proposed mixed-direction predicate are correct, with filtering before `limit+1` and the last emitted row as pivot. Continue from the saved tuple after pivot deletion. The schema uses `DateTime(timezone=True)` and string IDs (`sessions/models.py:2309–2325`); service `_aware_utc` attaches UTC to SQLite-naive values but currently preserves an already-aware offset (`blobs/service.py:2241`). Define cursor serialization as exact UTC with six fractional digits, derived from the persisted value rather than the browser's timestamp or a float; preserve exact comparison on rebind. Assert adjacent microsecond boundaries as well as ties. Use canonical persisted IDs under the landed identity contract; do not reformat a dirty stored ID into a different SQL ordering value. PostgreSQL/SQLite ordering assertions must use the actual selected DB order; do not infer cross-database collation behavior solely from Python sorting.

**Live semantics.** The plan's insert/delete/readiness-transition rules are appropriate. Readiness filtering before the bound prevents unrelated statuses from consuming ready-only slots. Replacement commit changes metadata without changing ID/created_at (`coordination/repository.py:2599–2636`); output finalization changes status/hash/size. Reinspect the landed relevant writers before asserting immutable ordering keys. The legitimate guarantee is no cursor-movement duplicate of an already-emitted surviving row while those ordering keys remain immutable. New or newly-ready rows ahead of the cursor may be missed until refresh, and behind-cursor arrivals may extend traversal. A terminal page observes exhaustion only behind that position at that query time. Even a refreshed live traversal cannot prove unconditional current absence if mutations continue. Do not let the wording “refresh before absence” imply that one refresh creates snapshot guarantees. Stronger absence guarantees would be a genuinely different product requirement requiring a separately scoped design.

**Admission and integrity.** Keep strict request bounds, owned-row integrity failure, ready hash integrity, page count/duplicate/cursor invariants, and whole-emitted-page credential refusal. Validate service-fetched lookahead rows under the chosen owned-row policy, but never expose the extra row. A credential-bearing emitted row causes the page to fail; do not skip it and advance the cursor past it. Use a narrow cursor-invalid exception translated into ToolArgumentError/generic REST 422; do not wrap DB integrity errors, missing codec, or malformed first-party producer data as caller mistakes. REST owner/session checks precede cursor-dependent inventory access. Document whether the new REST page applies an additional output credential guard: legacy collection listing currently maps records straight through `_blob_response`; tool whole-page refusal is the established behavior, not evidence that legacy REST already performs the same check.

**Browser state.** Task 4 correctly builds on existing activation epoch and request-sequence fences (`stores/blobStore.ts`). Decoder admission precedes any publication. Root refresh, local upload/delete, identity invalidation, A→B→A switch, and reset must invalidate pending continuation success **and error** publications. Keep one outstanding continuation and preserve accepted loaded rows after a later-page failure while marking the inventory incomplete. Cross-page deduplication must not silently turn a protocol violation into completeness: reject an unexpected duplicate from an otherwise monotone immutable-key chain, or mark/restart incomplete. Duplicate requests can be ignored by their captured request identity. “Files (N loaded)” remains truthful; category grouping does not promise global SQL order. A locally added upload may be shown immediately, but is not evidence that the current traversal remains complete.

**MCP.** The source exclusion is real: `_COMPOSER_TOOL_NAMES` is built from `_DISCOVERY_TOOLS` and `_MUTATION_TOOLS` (`composer_mcp/server.py:119`); `_build_tool_defs` filters with it (`212–223`), and dispatch membership is checked at `393`. These blob lists are `BLOB_DISCOVERY`, a separate registry kind. Preserve this exclusion. Future runtime definition/dispatch checks with a known-positive tool are the correct proof; there is no blob MCP payload-parity target.

Task 5 should exercise actual SQL and admitted adapter/tracker paths under committed mutations; a pure tracker mock is not PostgreSQL proof. ## Scoped amended-plan rereview — 2026-11-09

**Verdict: design-ready after the already-required identity integration/reinspection.** The amended plan resolves the four earlier corrections. The parent has accepted ordinary REST visibility/output policy and the live/fixed-limit/30-minute application-HKDF/non-JWT choices; the earlier “outstanding decisions” paragraph is superseded on those points. This rereview found no new blocking contradiction in the private position seam or amended progression rules. It is not implementation verification.

The new `inspect_blob_page_positions_sync` seam is appropriately narrow. The same configured service authenticates request/next cursor schema and scope using the existing codec, verifies same-root provenance and forward order when both positions exist, and returns only owned ordering keys. It neither reads the DB nor grants read authority. Omitting a second wall-clock expiry check after successful listing correctly avoids invalidating an observation that crossed the expiry boundary during accounting. Actual listing admission must retain the live-expiry check. Terminal-root `(None,None)` and terminal-continuation `(request_after,None)` are sufficient: terminal status and selected item metadata supply the remaining fingerprint facts.

The described carrier matches the inspected source: `_AuditedDiscoveryResult.to_dict()` delegates to `admitted.to_dict()` (`pipeline_planner.py:1564–1573`), and `_result_to_audit_payload` invokes that method (`audit.py:1287–1307`). Inspecting positions inside the existing dispatch body before success finalization preserves fault audit classification; carrying the extra field through the nested result tuple preserves authored result ordering without widening public response types. Keep malformed claimed-success tokens as producer faults, and do not invoke the inspector on failed or rejected discovery.

Active gaps now enter pending state independently of page keys, current generations invalidate earlier active exhaustion, consumed retries do not advance twice, and failed roots preserve the existing chain without freshness gain. Nonce-independent fingerprints prevent new signatures, issuance times, or local generation numbers from manufacturing information. The accepted 256-entry aggregate cap is a reasonable bounded implementation choice alongside the unchanged lower execution budgets.

Two precise implementation follow-through points belong in the existing proof obligations, not a new design phase:

- Account for any retained historical generation-exhaustion keys or page receipts as well as tracker containers. Do not keep an ever-growing manifest-side history while replacing tracker state in place and claiming the 256-entry aggregate bound. Reserve capacity before publishing the corresponding progression/coverage change; overflow stays incomplete and follows the existing exhaustion/hatch path.
- Interpret the “no ordering/key material on wire” assertion as **no new separately serialized private DTO/position fields**. The accepted opaque, unencrypted cursor necessarily already encodes its authenticated ordering tuple. Compare actual wire/audit/event envelopes with the admitted v2 response; do not require that decoding an authorized cursor reveals no ordering tuple.

Scope of this rereview: amended plan, the baseline planner carrier/execution loop, and audit serializer seam only. No whole-audit restart, tests, scans, code edits, agents, commits, provider calls, or real key access. The only write was this append.
