## Approaches and recommendation

1. **Recommended: opt-in live keyset pages on existing surfaces.** `{}` tool calls and legacy REST calls retain their exact roots. New callers explicitly request pages. Share ordering/query authority with the service. Add bounded cursor and truthful per-page end evidence; planner aggregates a complete sequential traversal. Lowest lifecycle complexity, no database migration or token secret.
2. Always replace tool/REST roots with a new envelope. Simpler producer branching, but breaks bare-array clients and recorded-shape assumptions; unnecessary when explicit opt-in works.
3. Materialize server snapshots/revisioned memberships. Gives stable membership under arbitrary readiness changes but needs durable snapshot storage, retention/expiry, authorization and failure recovery. There is no current inventory snapshot authority. Audit does not require this guarantee.

The recommendation is an engineering choice consistent with existing fresh reads, rather than a product-policy ruling. No material product answer is required to implement it. If the parent wants an exact point-in-time inventory despite concurrent mutation, that is a different feature: choose approach 3 and design its custody before implementation. Do not describe approach 1 as such a snapshot.

## Proposed wire contract

Tool arguments: add optional nullable `page` with closed non-null value `{limit: integer 1..50, cursor: string|null}`. A present page object requires both fields; `cursor=null` starts at the newest row. Omitted `page` or explicit `page=null` is the legacy call. This keeps `{}` accepted, avoids inference from an omitted cursor, and uses existing provider optional-field projection. Advertise `{page:{limit:50,cursor:null}}` as the normal discovery recipe. For continuation copy the returned cursor exactly and keep the same limit. Do not retain the obsolete parameterless wire marker for newly advertised schemas; recorded old invocations remain recorded, not re-decoded against current schemas.

Paged tool data is exactly `{blobs:[...], page:{schema_version:1, consistency:"live", limit:N, cursor:<requested cursor or null>, next_cursor:<token or null>, has_more:boolean}}`. Item fields retain each tool's current distinct whitelist, including ordinary `id` versus ready `blob_id`. Legacy ordinary data stays `[...]`; legacy ready data stays `{blobs:[...]}`. `has_more` is the existence of an additional eligible row in this page's SQL observation, not a count or snapshot guarantee. `has_more == (next_cursor is not null)` is mandatory. A page with `has_more=true` contains exactly `limit` items; all pages contain at most `limit`; an empty page has null continuation. A terminal continuation page is not evidence that earlier pages were read.

REST keeps the same URL and legacy `limit`/`offset` response. Add `pagination=cursor` and optional `cursor`; with this explicit selector return the same page envelope, with ordinary REST `BlobMetadataResponse` entries. Retain `limit=1..500`, default 50; reject a supplied offset in cursor mode, or a cursor without cursor mode, with 422. Legacy callers retain array results and offset semantics; stable tie ordering applies to them too. The browser uses explicit cursor mode at limit 50. `Cache-Control: no-store` for cursor responses and cursor errors, as in operation history. Route ownership verification precedes parsing/using the cursor. No REST ready-only API is needed.

Strict request admission rejects booleans as limits, floats, coercible strings on tool input, wrong/null nested values, extra keys, overlength/non-ASCII/invalid cursor encoding. Query-string integer conversion remains FastAPI's existing REST boundary. Define one invalid-inventory-cursor domain error: tool maps it to a safe typed argument refusal through the current ToolArgumentError path; REST maps it to generic 422. Do not echo invalid token text or embedded foreign identities.

## Shared query and cursor

Put nominal page/cursor values alongside `BlobRecord` in `contracts/blobs.py`, because the existing L0 BlobServiceProtocol declares the new async method. Put the external cursor codec in small dependency-light `web/blobs/inventory.py` (proposed path); never import web types into contracts. Place `list_blob_inventory_page_sync(engine, *, session_id, scope, limit, cursor)` in the existing service module beside `_row_to_blob_record`. Both tool handlers and an async BlobService wrapper call that synchronous authority. Keep legacy `list_blobs` signature/offset support and factor its base session predicate/ordering with the page query rather than attempting to implement arbitrary offset by walking cursors. No new connection authority or owned-row loader in tools.

Scopes are exact `all` and `ready`. Every query uses the trusted session id independently of cursor content; ready uses `status == "ready"`. Order `created_at DESC, id DESC` with predicate `(created_at < after_time) OR (created_at = after_time AND id < after_id)`. Fetch at most `limit+1`, guard owned rows, emit the first limit, and derive next position from the last **emitted** row. Normalize timestamp representation using the existing aware-UTC rule and preserve microseconds across SQLite/PostgreSQL. An invalid owned timestamp/id/status/hash remains an integrity failure. Do not re-query the cursor row; deleting it must not destroy continuation.

Cursor v1 is bounded base64url-encoded canonical JSON, maximum 512 ASCII characters, exact fields `{v:1, session_id:<canonical UUID>, scope:<all|ready>, limit:<integer>, created_at:<UTC timestamp>, id:<canonical UUID>}`. It carries ordering metadata only. Validate exact keys/types, duplicate JSON keys, canonical UUID/time encoding and canonical re-encoding; reject unsupported versions, foreign sessions/scopes and changed limit uniformly. Canonicalization here is protocol format, not permission to broaden stored resource grammar. Decoding does not authorize a read. Following the existing operation-history pattern, no signature or cursor registry is needed: a fabricated position can only select a subset of an independently authorized session; planner completeness must never trust fabrication as proof of prior pages.

There is no TTL, snapshot version or revision binding. A valid old position remains a live position; deleting its anchor, replacing contents or changing readiness does not make it malformed. An unsupported cursor version is the stale-protocol case: refuse and instruct restarting from cursor null. A cursor for a deleted/unowned session fails the ordinary session authorization/existence path. Do not invent an expiry error or imply a snapshot was preserved.

## Consistency and concurrency

Each page is one fresh SQL observation. There is no transaction across tool calls/browser clicks. With unchanged eligibility and immutable `(created_at,id)`, keyset intervals do not overlap and all rows are reachable; equal timestamps are deterministic. Deletes before the next call remove rows without offset drift; a deleted anchor still works. Already delivered rows can later disappear or change metadata, and consumers must not treat them as current custody.

New rows above the position are intentionally not revisited; refresh from null discovers them. A concurrently inserted/backdated row below the position can appear later. Ready transitions above the position can be missed during that traversal; transitions below it can appear later; ready-to-nonready removes a candidate before a later page. The general all-status inventory does not newly include an existing row merely because readiness changed, but later metadata reads can differ. In ordinary unchanged operation a row's key does not move; if a future writer changes creation time, it must revise this contract or accept explicitly documented repeat/omission behavior.

All clients call later metadata/read/bind actions through existing readiness, hash and custody checks. A terminal page means “no further matching rows below this position when queried.” A complete chain means “the client traversed this live enumeration,” never “this is the exact set now” or “no such file exists at any time.” Update declaration, skill, repair and planner text accordingly. A missing target after live traversal can justify asking the user for a selection/upload with this observation limit; do not falsely assert absence based on an initial partial page.

The planner's inventory gap is therefore defined as “has traversed the available live inventory,” not an absence proof at one revision. No revision or staleness control is necessary for that defined fact. If later audit interpretation requires stronger absence evidence, neither a high-water creation timestamp nor an end-only revision check proves it: readiness can change behind the cursor, and a revision scheme must cover every create/delete/readiness/replacement writer and invalidate/restart the entire chain. That would be a separate change requiring a complete mutation-revision authority or snapshot membership policy. Do not quietly strengthen the claim while retaining this implementation.

## Planner evidence and budgets

Track page observation keys separately from `blob.index.session` / `blob.index.composer`. Page keys include admitted mode, canonical cursor and limit; scopes remain distinct. Put per-request nominal traversal state in a small helper (proposed `web/composer/blob_inventory_evidence.py`), owned by one planner invocation, not the process, DB or cache. A successful root initializes/replaces that scope's traversal and its expected next token. Only a successful page requested with the exact expected token from a previously **delivered/admitted** page advances it. Only a root-to-terminal chain supplies the whole-scope key. Empty root completes immediately. Duplicate, out-of-order, guessed, foreign-scope or standalone terminal calls may supply their own valid page observation but cannot advance/complete that chain. Do not speculate or parallelize dependent pages; independent scopes can be batched.

Before a fresh root attempt, remove old supplied whole-scope evidence and mark it unresolved. A failed/refused root or continuation never supplies completion; legacy success with fewer than 50 items can conservatively supply its observed window as complete, but length 50 cannot. New root traversal after earlier completion must not inherit old completeness. Keep whole-scope key pending while pages remain even if all individual page keys were supplied. Update `_valid_information_key`, pending-key bookkeeping, new-information classification, and the gaps-closed message together. The notice must qualify blob completion as a completed live traversal, not present an absolute inventory claim. A failed page may be retried under existing policies; repeat reads remain legal.

Canonical identity/encoding/assistance-selector work in group 2 stays separate from inventory continuation: after group 1, metadata/content/inspection keys use canonical ids; inspection also includes admitted encoding; assistance keys distinguish omitted/null general requests from the empty string according to actual admitted handler semantics. Do not use truthiness to collapse selectors. Failed/invalid observations cannot fabricate successful coverage.

Every page is one ordinary BLOB_DISCOVERY call with existing budget, provider context, invocation audit and progress handling. No hidden auto-fetch in a tool, no extra calls after budget exhaustion, no relaxed D7/reread policy, and no discovery cache opt-in. A budget that ends mid-traversal yields incomplete inventory evidence and the existing exhaustion/handoff behavior. Page metadata adds bounded overhead but does not silently enlarge provider/context budgets; use existing refusal/truncation behavior honestly and do not record completion if the admitted page was not delivered. Redaction cache-hit audit work remains a different group.

## Browser and recorded compatibility

Keep `api.listBlobs` legacy for callers needing its current signature; add `listBlobPage` for the explicit cursor mode. Add an exact page decoder (using the established operation-history decoder pattern), types and cross-field validation. Blob store loads one root, stores next cursor, and exposes `loadMoreBlobs`; BlobManager offers “Load more files” and “Refresh files.” Show “N files loaded” while continuation exists, and only an observed total after terminal traversal. No unbounded background fetch loop.

Carry activation epoch/request ownership through every page, refresh and mutation. A session change invalidates every old completion. Only one continuation for a traversal is in flight. A refreshed root supersedes old continuation responses. Upload/delete invalidate pending page publication and restart/reload the root or explicitly mark traversal for refresh; do not append a pre-mutation response that can resurrect deleted files. Merge by canonical id to avoid duplicate UI rows on retries, preserving authoritative server order. A continuation failure keeps displayed rows and the retryable position, clearly marks incomplete/error, and never publishes an exhausted state. A browser test must actually find the oldest of 51+ files through load-more and perform an existing action on it.

Do not rewrite stored invocations, old hashes, old ToolResult payloads or old provider dialect arguments. Strict response admission supports exactly the legacy and v1 paged variants; encoders reproduce each admitted variant's root. Historical legacy arrays and ready envelopes still render as recorded and do not acquire fictional cursors or completeness. A consumer that needs coverage may conservatively classify old 50-item records as bounded/unknown. Unknown/future page versions and malformed mixed roots fail closed, not fall back to legacy. Update redaction allowed page argument fields and content-free rationale; exercise audit/private evidence hashes against actual emitted envelopes. The page carries no content bytes, descriptions, storage paths or new provenance fields.
