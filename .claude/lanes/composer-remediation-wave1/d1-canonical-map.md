## Authority and ordering

Use `composer/pipeline_proposal.py::composition_content_hash(state)` (746). Its exact preimage is sources, nodes, edges, outputs, metadata, excluding version. `composer_authority_hash` preserves authored source-map and mapping-form row_union/coalesce branch order. This includes the actual serialized review, controls and source/blob provenance; do not compare public/redacted arguments, source text, version or ordinary Python mapping equality. Changed identity/provenance, required-control wiring, review reconciliation, or meaningful ordering must continue through existing changed-plan controls.

There are three publishers/acceptance routes: freeform tool_batch (separate worker), `planning_application.py::_stage_pipeline_plan` (607), and canonical acceptance via `sessions/routes/composer/pipeline_settlement.py::_settle_pipeline_proposal_under_compose_lock` (290). ## A. Canonical preparation: minimal seam

`composer/pipeline_commit.py::prepare_pipeline_proposal_commit(*, authority, current_state, current_state_id, policy_catalog, plugin_snapshot, config, recorder, actor, recovery_dispatch=None, recovery_executor_content_hash=None) -> PreparedPipelineCommit | RecoveredPipelineCommit` (428).

Current order is exact owned authority/context/session and pending check; plugin snapshot; exact absent/present base identity/content; thaw and exact proposal row argument authority hash; owned-state restoration and execution argument derivation; bounded prior validation/reviewed-source authority/context; candidate construction/acceptability; proposed-vs-candidate hash; recovery pair/hash check and recovered return; fresh audited execution; exact one invocation binding and candidate-vs-executor checks.

Insert a typed `PipelineCommitError(code="NO_CHANGE", dispatch=recovery_dispatch)` after the candidate is acceptable, no prepared inline blob remains, and owned proposed hash is equal to candidate. Preserve recovery pair validation and candidate-vs-recovery executor hash validation **before** no-change classification; then put equality before both recovered success return and fresh `begin_dispatch`. Thus:

1. Invalid/malformed authority and stale base retain their current fault/conflict semantics.
2. A valid matching successful recovery dispatch survives on the no-change error; a mismatched recovered executor still raises `PipelineCommitMismatchError` with that binding.
3. Fresh equal candidate creates no successful executor invocation solely to prove equality. It proceeds to the existing required rejection operation/event.
4. Changed candidate retains exactly the existing fresh dispatch or recovered result, later runtime preflight and settlement policy.

No new Prepared/Recovered result type is required. Current `PipelineCommitError` already carries optional invocation/dispatch and the route already knows how to persist/reject its closed failures. An owned disposition would also work but is unnecessary at this seam.

Use candidate equality only after actual server finalization represented by this canonical builder: no early return on raw arguments. For owned-state authority, preserve exact `proposed_content_hash == candidate_hash` proof; candidate normalization that changes the exact owned proposal remains an integrity error rather than a no-op.

### ToolArgumentError must be separate from integrity and invocation bindings

`build_set_pipeline_candidate` is a real Tier-3 schema boundary (`tools/sessions.py:652`) and raises `composer.protocol.ToolArgumentError`. It currently escapes preparation and enters settlement's generic exception arm, preserving pending status. `dispatch_with_audit` also re-raises ToolArgumentError after recording one ARG_ERROR invocation (`audit.py:1187`). Catch precisely this exception around candidate build and around audited execution and translate into a leak-safe `PipelineCommitError(code="ARGUMENT_ERROR")`; do not catch all ValueError/TypeError or convert owned-authority restoration errors.

Keep safe category/message diagnostics from the owned error (no raw args, exception repr, schema values or secret resolution). The minimum persisted reason can remain `validation_failed` with distinct structured public `proposal_argument_error` response/category. If a distinct terminal reason `argument_error` is chosen, add it to the same closed vocabularies and round-trip tests as `no_change`; it is additive, not a lifecycle/schema migration.

**Important existing constraint:** `PipelineDispatchAuditBinding` accepts SUCCESS only (145). `_persist_tool_invocations` returns a binding only for successful set_pipeline invocations (`routes/_helpers.py:2069`); an ARG_ERROR invocation has no successful dispatch content binding. Do not set `exc.invocation` to ARG_ERROR and take the route's `len(bindings)==1` success-binding check. Leave it buffered, persist it once through the existing recorder path, retain any independently validated recovery binding, and reject with dispatch absent for a fresh argument failure. Candidate-build argument failure has zero executor invocations. Executor argument failure has exactly one ARG_ERROR invocation and no fabricated SUCCESS/content hash.

The existing operation-authority test `test_executor_argument_error_persists_its_category_as_the_error_code` currently expects raw ToolArgumentError. Intentionally update the expected preparation error wrapper if translation is owned here; preserve its exact one invocation/status/category/payload assertions. Alternatively keep raw preparation propagation and add a **specific** route ToolArgumentError terminalization arm; this avoids changing that helper contract but must reuse the exact same required-custody cleanup logic rather than the generic pending arm. Prefer one normalized preparation failure path to avoid duplicate cancellation/persistence logic.

## C. Recovery integrity and audit cardinality

Retain `service.py::_pipeline_dispatch_recovery_on_connection` (8197) and `proposal_authority.py::_pipeline_dispatch_recovery_from_envelope` (423). They validate same-call audit kind/tool/status, canonical arguments/result hash bindings, reserved successful executor-content binding, semantic redacted authority, and reject duplicate successes. Failed attempts may precede one success and are not recoveries. Do not short-circuit these reads merely because proposed/current content looks equal.

| Path | Executor/audit disposition | Proposal terminal/state disposition |
| --- | --- | --- |
| Fresh acceptable equal candidate | zero executor dispatches / zero new successful execution audit | one rejection event `no_change`, pending -> rejected; zero composition rows |
| Equal candidate with matching saved success | same original persisted dispatch binding; no redispatch/no duplicate audit | one rejection bound to original success; zero composition rows |
| Candidate malformed ToolArgumentError | no executor dispatch; no fabricated success | one validation/argument rejection, safe structured refusal; zero composition rows |
| Executor ToolArgumentError after accepted changed candidate | one ARG_ERROR invocation persisted once; no successful binding | one validation/argument rejection; zero composition rows |
| Recovery tampered/duplicated/mismatched | current integrity/mismatch behavior, never equality bypass | no fabricated no-change evidence |
| Already committed retry | exact saved state/event replay; no execution/audit duplication | remains committed |
| Repeated accept of rejected | no executor, no new audit/event | rejected remains terminal; existing 409 |

Persisted private/public audit drafts can be multiple storage rows per one invocation; count semantic invocation occurrences and actual table rows separately. The ordinary rejection attempt is its terminal event/required-work evidence; do not add a synthetic SUCCESS dispatch to make its count resemble commit.
