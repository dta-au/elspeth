## Necessary clarifications

1. **Use the existing closed status authority.** `proposal_blob_refs.py:178` currently groups every value other than `ready` under ValueError. Replacing that branch wholesale with the expected domain exception would launder corrupt same-session status. `contracts/blobs.py:77–85` already owns `BlobStatus`/`BLOB_STATUSES`; `models.py:2441` mirrors its values in the database constraint. Missing and foreign rows are expected unavailable-resource outcomes. For an owned row, exact-string/closed-status validation must precede the `pending`/`error` refusal. Unknown or malformed owned status remains an integrity fault. Extractor ValueErrors at `proposal_blob_reference_ids` remain distinct and must not be caught as resource races. This clarifies the brief's stronger wording against section F's loose “non-ready” phrase.

2. **Cover both freeform creation APIs, including promotion.** `tool_batch.py:2208` creates canonical pipeline proposals; `:2235` creates ordinary tool proposals. An incremental tool whose required-control finalization changes the candidate is promoted to canonical authority at `:2138`. Tests must cover the real selected publisher, not assume all freeform work calls the ordinary API. On the expected exception, `_unapplied_admission(..., "refused", ...)` must reach `_do_dispatch` (`:3060`) and the existing canonical audit/outcome/feedback path, while skipping the complete success block beginning at `:2258`. That preserves original state/preflight, clears change fields through the existing admission normalization (`:224`), avoids redispatch, records one semantic invocation, and leaves proposal count and business-success accounting unchanged. Ordinary dispatch SUCCESS can describe a completed refused operation under existing semantics; it must not be mistaken for a successful mutation.

3. **Move the failed-creation cancellation barrier.** The reusable required-creation tests park at proposal INSERT (`test_pipeline_rejection_required.py:299`; `test_pipeline_rejection_callers.py:342`). The new expected exception arises earlier, inside reference validation, so an unchanged INSERT barrier would never fire and would test a timeout rather than cancellation of the failed operation. Pre-arrange the resource change after admission, then park the real validator/SQL callable before that failure. Preserve the INSERT barrier for the distinct successful-SQL/telemetry-fault case.

## Confirmed design obligations

**Transaction authority:** `mutation_capabilities.py:129` and `:217` validate references before proposal-created event and proposal INSERT. Canonical creation first validates exact base. `service.py:3314` retains session/process/write/COMPOSE transaction authority and principal/running-claim checks. The new domain outcome belongs at the queried missing/foreign/known-non-ready branches only. No unlocked availability precheck can replace these checks, and SQL, malformed argument/owned authority, stale-base, or fence failures must not become user refusals.

**Planner direct path:** `_stage_pipeline_plan` persists the completed cohort first (`planning_application.py:649`). Catching the new exception only around the creation await at `:723` permits a fixed backend unchanged `ComposerResult` without duplicating audit evidence, adding a provider attempt, manufacturing `PlannerDeclined`, exposing parser/resource details, or advertising the candidate's preflight as a verdict on the original state. `_await_pipeline_staging_write_with_deferred_cancellation` (`:124`) preserves an original external cancellation with child failure as its cause; the narrow catch must leave this outcome intact.

**Planner required path:** Reserve the existing SQL/projection pair and invoke finish-once, then call `project_creation_handoff` before classifying (`planning_application.py:779`). `pipeline_rejection_custody.py:60` verifies the exact registered SQL outcome; a genuine raised handoff completes unused projection and returns the actual error and cancellations. Expected refusal is permitted only for no row, exactly the domain error, and no creation cancellations. Groups, additional faults, corrupt/forged outcomes, and any cancellation retain existing propagation. No exception-leaf search or handoff fabrication is justified.

**Receipts and tickets:** `required_work.py:655` preserves the physical failure receipt. `assert_completed` (`:1468`) checks completion rather than absence of failures. A no-row outcome requires no proposal rejection child. The ordinary returned result does not trigger worker failure reduction; if later cancellation/fault occurs, `_settle_failure` and `_failure_for` (`composer_async_worker.py:1007`, `:1396`) recover original receipts. The brief correctly forbids clearing them or inventing a successful SQL outcome.

**Row returned plus telemetry fault:** `service.py:3370` records post-SQL faults in `PipelineCreationReturned`; `project_creation_handoff` preserves the real row and completes projection with those failures. This must continue to fault, preserving an existing proposal and any cancellation-driven rejection obligations. It cannot return “no proposal” merely because the public handoff is unsuccessful. The existing real caller test already exercises cancellation plus post-SQL telemetry failure and nonzero child scope; retain that control alongside the new no-row case.
