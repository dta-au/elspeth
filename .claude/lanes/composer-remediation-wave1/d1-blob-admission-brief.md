## Design-review correction: consistent debt before recovery-needed

This requirement refines map step 4; the map remains dated extraction evidence. See `d1-blob-admission-design-review.md`. A successfully constructed typed plan is insufficient proof of valid recovery debt. Before returning the recovery-needed disposition, reuse/extract the existing **non-writing** driver consistency checks below. Never invoke a recovery/advance/retire/abort function merely to obtain its checks, and do not expand or redesign recovery behavior.

- Read and classify both ledgers in deletion-then-replacement order before returning. Their simultaneous presence for one blob violates the existing mutually exclusive intent contract and remains an integrity fault, even when each row individually parses. Retain qualified deletion's existing exact live-snapshot check for intent/staged and absence check for purge; retain atomic deletion's all-NULL producer schema and no-live-metadata predicate.
- Replacement must additionally read the actual row under the same fenced transaction and compare its complete record to `plan.old_blob` for intent/swap_pending, or `plan.replacement_blob` for purge_pending. Extract/reuse the comparison currently in `BlobReplacementCoordinator._recover_plan`; do not call that method. Missing/rebound/mismatched live metadata is corrupt replacement evidence, not an ordinary missing-target or recovery-needed refusal. Do not require current authority to match the historical producer's expired lease: valid successor-recoverable debt is expected here.
- Validate exact artifact paths without touching foreign paths: reuse `BlobReplacementCoordinator._validated_paths`, `BlobServiceImpl._validated_blob_deletion_paths`, and the non-writing checks of `_atomic_blob_deletion_stage`. These bind actual custody and invocation-qualified paths; the carrier constructors alone only validate structural path properties. Keep atomic producer path rules distinct from qualified operation-token rules. `_finalize_staged_blob_deletion` remains forbidden.
- When debt classification observes filesystem evidence, extract only existing non-writing checks, using pinned directory fds/no-follow reads outside the Sessions transaction. Preserve the driver's valid interrupted alternatives and its existing integrity categories. For example, replacement before commit may have old canonical bytes **or** recoverable old backup bytes; purge may already have removed cleanup artifacts. Qualified deletion can have canonical or tombstone bytes before completion according to its existing phase logic, while absent-file evidence must not acquire bytes. Do not apply the fresh-replacement canonical-file prerequisite to interrupted debt. Return recovery-needed only after required consistency observations; never restore, rename, delete, stage, reconcile, or retire anything.
- After filesystem observations, use a fresh fenced DB phase to recheck the exact observed ledger evidence and phase-specific metadata as well as live authority. A changed observation must not publish a success or stale recovery-needed result. On the fresh no-debt path, final admission repeats the shared metadata, retention, and quota prerequisites as already specified.

The deletion facet's conceptual signature in the map must carry the observed `(present, size, hash)` evidence or an exact owned equivalent alongside the expected record/snapshot. Its final fenced prerequisite checker must apply the same evidence/metadata predicates as `prepare_blob_deletion`; an `expected` record alone cannot establish them. Keep absence `(False, None, None)` valid under the existing direct-driver contract.

Add genuine interrupted-producer controls for replacement intent/swap_pending/purge_pending, qualified deletion phases, and all-NULL atomic debt. Pair each applicable valid recovery-needed/no-write case with corruption controls over persisted evidence: complete replacement live-row mismatch or missing row; qualified deletion snapshot/live-row or purge-presence mismatch; atomic live metadata; nonblank/distinct but foreign or wrong-invocation stage/backup/tombstone paths; and simultaneous incompatible ledgers. Use intact typed snapshots where possible so controls reach the omitted consistency predicate rather than fail unrelated constructors. Verify exact original fault category, no foreign file access, unchanged ledger/metadata/bytes/artifacts, and no recovery call. Existing safe successor recovery remains the separate positive control. These controls supplement rather than replace the map's quota, fence, retention, no-write, and PostgreSQL contention matrix.
